# 排查决策树 + 验证闭环

## 「看不到变化」六层排查（按序）

1. **地址对吗**：18787=隧道→dev（线上版）／18788=本地测试（改动在这）。报地址前 curl 该地址 grep 新代码标记。
2. **dev 拉了吗**：push 后 5 分钟窗口；两端 `git log -1` 对齐。
3. **浏览器缓存**：Cmd+Shift+R；同时 curl 服务端核对——服务端有新标记而浏览器没有 = 缓存。
4. **重启窗口**：重启期间打开的页面持有旧 JS，重新加载再下结论。
5. **Pages legacy 覆盖**：workflow 成功但站点是旧的 = legacy 构建后到覆盖，重新 dispatch。
6. **磁盘真写了吗**：grep 磁盘文件。声称删除/修复必须附验证计数（曾有断言失败静默退出的假报告）。

## 截图验证闭环

- 工具：复用 `scripts/note_verify_shots.py --base <验证地址>`，通过真实 HTTP 页面截图和读取 computed style，不向源码写入探针。
- 等待：导航使用 `domcontentloaded`，随后断言目标文章标题、正文非空、主题生效、字体及图片完成加载、Mermaid 完成渲染。固定等待秒数不能证明页面已准备完成。
- 覆盖：375 / 768 / 1024 / 1440 四种宽度与双主题，代表文章含表格、代码、引用及列表。保存全页、表格开始与滚动末端截图；逐元素测量字号和对比度，逐列比较表头与表体边界。缺少元素或加载失败必须终止验证。
- 清单：改动前基线 → 改动后同角度 → 页面切换第二状态 → 深浅主题（涉颜色）→ console error 检查 → 服务端 curl 核对。
- 高亮类改动加做**双态语义验证**：位置框与推荐样式在两种页面状态下可区分。

## 意图对齐

- 用户陈述是目标状态。动手前写出一句你的理解；方向定不了就给出理解 + 选定方案直接实现，截图对齐。
- 不抛选择题（用户全权委托）；推广内容前确认内容被认可（推广即背书）。

## 自主巡检（用户明令）

每个改动落地后：自己全站截图巡检，主动发现布局/对齐/字号/截断/空洞问题并修掉。发现一个同类问题 → 全站扫一遍同类。**不等用户报 bug**——用户报一个 = 你漏了一片。

## 持续工作模式（用户明令）

- 长任务一口气做完：不暂停、不问「要不要继续」、不拆成多次确认。
- 用户离开也持续工作；一个会话解决一类问题。
- 超长会话注意 JS heap OOM（4GB/8GB 反复爆）：及时压缩上下文或重启会话，重活拆会话。

## 性能预算

- 外部 API 有配额（BestBlogs Pro 每日 500 次，429 会拒绝）。
- 抓取固定化：本地抓好落盘，定时更新（如每日 9 点），不做每次刷新实时拉取。
- 去掉无意义刷新按钮；展示固定化后的数据。
