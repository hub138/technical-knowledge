# 可观测性靠结构化事件，不靠日志文本

## 背景：出问题时只能 grep

线上 p99 从 200ms 涨到 2s，但平均延迟没变。

团队开始排查：`grep "slow" app.log`、`grep "timeout" app.log`……翻了半小时，只看到一堆零散的"某请求用了 1.8s"，**但归纳不出"慢的是谁、慢在哪一段"**。

日志是给人看的文本，它回答"发生了什么"（what），但很难回答"为什么"（why）。**因为文本没有结构，无法聚合、无法关联、无法切片。**

## 方案：把每次请求变成一条结构化事件

核心思路：**不要输出文本，输出带字段的事件。**

### 1. 宽事件（Wide Events）

一条事件包含这次请求的**所有**上下文，而不是分散在多条日志里：

```json
{
  "trace_id": "8f14e45f",
  "span_id": "a3f21b",
  "service": "order-api",
  "endpoint": "POST /orders",
  "user_id": "u_8821",
  "user_tier": "vip",
  "duration_ms": 1832,
  "db_duration_ms": 1780,
  "db_query_count": 12,
  "cache_hit": false,
  "downstream": {"inventory": 45, "payment": 7},
  "status": 200,
  "error": null
}
```

**为什么是"宽"**：出问题时你并不知道该查哪个字段。宽事件让你事后能自由切片："所有 vip 用户、缓存未命中、db 耗时超 1s 的请求"——这个查询在文本日志上做不了。

### 2. 三个支柱，各自回答不同问题

| 类型 | 回答 | 特点 |
| --- | --- | --- |
| 指标（Metrics） | **有多少**异常？ | 聚合、便宜、适合告警；但不知道具体哪次请求 |
| 日志（Logs） | 这次请求**发生了什么**？ | 详细；但难聚合、量大 |
| 追踪（Traces） | 请求**慢在哪一段**？ | 呈现调用链；需要埋点和上下文传播 |

**三者通过 trace_id 关联**：指标告警 → 找到慢的 trace_id → 看这条 trace 的完整日志。

### 3. 追踪：上下文必须跨进程传播

这是追踪能工作的前提：

```go
// 出口：把 trace 上下文注入请求头
ctx = trace.Inject(ctx, req.Header)

// 入口：从请求头提取
ctx = trace.Extract(ctx, req.Header)
```

标准是 **W3C Trace Context**（`traceparent` 头）。**所有跨进程调用都要传播**：HTTP、gRPC、消息队列、异步任务。

漏掉任何一跳，调用链就断在那里——而断裂的位置往往正是问题所在。

### 4. 埋点：埋在哪

不要埋得到处都是。优先埋四个位置：

- **入口**：每个请求/任务的开始和结束（含耗时、状态）
- **出口**：每次外部调用（DB、缓存、HTTP、MQ）
- **关键分支**：业务逻辑里的重要判断（是否命中缓存、走了哪个分支）
- **错误**：所有异常，带完整上下文

**不要埋**：循环体内的每一步、纯函数内部。这些靠 trace 的 span 树就能还原。

## 效果与代价

**收益**

- **从"猜"变成"查"**：前面那个 p99 问题，用宽事件一个查询就能得出"慢请求全部 cache_hit=false 且 db_query_count > 10"——**根因是 N+1 查询**
- **告警可定位**：告警带上 trace 链接，值班人点进去直接看到完整调用链
- **能回答未知问题**：结构化字段支持的事后切片，是文本日志做不到的

**代价**

- **成本显著上升**：宽事件 + trace 的存储量可能是纯日志的数倍。**必须采样**
- **埋点有侵入性**：需要在代码里加 instrumentation，且要保证上下文传播不出错
- **需要纪律**：字段命名不统一（`user_id` vs `userId` vs `uid`）会让聚合失效

## 从什么地方做

**第一步：先统一 trace 上下文传播**

在加任何埋点之前，确保 trace_id 能跨所有进程传播。**这是地基**，后面所有东西都依赖它。

**第二步：定义字段命名规范**

写下来，加进 code review 检查：`user_id`（不是 userId）、`duration_ms`（单位进名字）、`status`（不是 code）。**不统一的字段等于没有字段。**

**第三步：设置采样策略**

| 策略 | 适用 |
| --- | --- |
| 头部采样（固定比例） | 简单，但会漏掉罕见错误 |
| 尾部采样（按结果） | **推荐**：保留所有错误 + 慢请求 + 按比例的正常请求 |
| 动态采样 | 高流量时降采样，低流量时全采 |

尾部采样的价值：**错误和慢请求永远被保留**，正常请求采样。这正是排查时需要的。

**第四步：把 trace_id 放进所有日志**

哪怕不用追踪系统，也让日志能按 trace_id 串起来。一行配置的事，排查效率差很多。

**第五步：从告警倒推需要的字段**

拿最近的 3 次线上问题，问："如果当时有哪个字段，就能 5 分钟定位？"把这些字段加进事件。

## 常见错误

**错误 1：只加日志，不加字段**

`log.Info("cache miss for user " + uid)` —— 这个 uid 在文本里，无法聚合。应该是 `log.Info("cache_miss", "user_id", uid)`。

**错误 2：trace 上下文传播有断点**

消息队列消费时不从消息头提取 trace 上下文 → 异步链路全部断开。**每个异步边界都要检查。**

**错误 3：采样把错误也采掉了**

头部固定采样 1%，那 99% 的错误都看不到。**错误和慢请求必须全采。**

**错误 4：指标维度爆炸**

给指标的每个 user_id 打标签 → 基数爆炸，监控系统直接挂。**指标标签要低基数**（tier、region、status），高基数的放事件里。

**错误 5：以为日志量越大越好**

日志量涨 10 倍，成本和信噪比都恶化。**先想清楚"要回答什么问题"再决定记什么。**
