# 容量规划先测瓶颈，不要先加机器

## 背景：加了 4 倍机器，QPS 只涨了 20%

一个服务扛不住流量，从 4 台加到 16 台。

**QPS 从 2000 只涨到 2400。** 而数据库 CPU 打到了 95%。

原因：瓶颈从来不在应用层的 CPU，在**数据库连接池**——每台机器配 20 个连接，16 台就是 320 个连接，数据库扛不住，大量请求在等连接。

**加机器反而让数据库更糟。** 这就是"没找到瓶颈就扩容"的典型结果：花了 4 倍成本，几乎没收益，还引入了新问题。

## 方案：先找瓶颈，再决定加什么

### 第一步：用 USE 方法定位瓶颈

对每一层资源问三个问题（ Brendan Gregg 的 USE 方法）：

| 指标 | 含义 | 工具 |
| --- | --- | --- |
| **U**tilization 使用率 | 资源忙的时间占比 | `top`、`iostat` |
| **S**aturation 饱和度 | 排队的长度 | `vmstat` 的 run queue、连接池等待 |
| **E**rrors 错误 | 错误次数 | 日志、监控 |

**饱和比使用率更早暴露问题**：CPU 70% 但 run queue 很长 = 已经在排队了。

**按层检查**：

```
CPU        → 使用率、load
内存       → 使用量、swap、OOM
磁盘       → IOPS、util%、await
网络       → 带宽、重传、连接数
数据库     → 连接数、慢查询、锁等待
连接池     → 活跃数、等待数  ← 最常被忽略
线程池     → 活跃数、队列长度
```

### 第二步：压测找拐点

不要问"能扛多少 QPS"，要问"**在哪里开始劣化**"。

```
逐步加压：100 → 500 → 1000 → 2000 → 4000
每档记录：QPS、p50/p95/p99 延迟、错误率、资源使用率
```

画出来通常是这样：

```
延迟
 │            ╭──── 陡增（拐点：约 2500 QPS）
 │        ╭───╯
 │   ╭───╯
 │──╯
 └──────────────────── QPS
```

**拐点才是容量，不是"还没挂"的那个点。** 超过拐点后延迟指数增长，这时系统虽然"活着"，但用户体验已经不可接受。

### 第三步：理解 Little's Law

```
并发数 = 吞吐 × 响应时间
L = λ × W
```

这个公式极其实用：

- 目标 QPS 5000、p99 延迟 100ms → **需要 500 并发能力**
- 如果线程池只有 200 → **永远达不到 5000 QPS**，无论加多少 CPU

**它直接告诉你该调什么参数**：

| 想提升 | 做法 |
| --- | --- |
| 提高 QPS | 增加并发能力 或 降低延迟 |
| 降低延迟 | 优化慢的部分（通常是 IO） |
| 减少资源占用 | 降低延迟（并发数随之下降） |

### 第四步：分组件定容量，不要只看整体

```
用户请求 → 应用（4 核 × 8 台）
             ↓
          缓存（Redis 单实例）
             ↓
          数据库（主 + 从）
```

每个组件独立测算：

| 组件 | 单机容量 | 当前负载 | 余量 |
| --- | --- | --- | --- |
| 应用 | 800 QPS | 2000（8 台） | 充足 |
| Redis | 50000 QPS | 12000 | 充足 |
| 数据库 | 3000 QPS | **2800** | **几乎满了** ← 瓶颈 |

**整体 QPS 不等于每个组件的 QPS。** 一个用户请求可能触发 5 次数据库查询。

### 第五步：留余量，并设降级预案

```
规划容量 = 预期峰值 × 1.5
```

**为什么要留**：

- 流量预测本来就不准
- 单机故障时要能扛住（N+1 冗余）
- 突发流量

**降级预案**：超过容量时先降什么？

| 优先级 | 超容量时 |
| --- | --- |
| 核心交易 | 保留 |
| 推荐、个性化 | 关闭（走默认） |
| 报表、导出 | 拒绝 |
| 异步任务 | 延后 |

## 效果与代价

**收益**

- **成本花在刀刃上**：加对了组件，QPS 线性提升
- **知道系统的真实上限**：能回答"还能撑多久"
- **有降级预案**：超容量时有序降级，而不是整体崩溃

**代价**

- **压测有成本**：需要环境、数据、时间
- **压测环境和生产有差异**：数据分布、网络、依赖都不一样。**压测结果要打折看**
- **容量会变**：代码优化/劣化、数据增长都会改变瓶颈位置

## 从什么地方做

**第一步：先建立监控，看当前各组件的饱和度**

没有监控就没法定位。**优先补齐连接池、线程池、数据库这些容易漏的指标。**

**第二步：画一条请求链路，标出每个组件**

从入口到数据库，每一跳都列出来。**每一跳都可能是瓶颈。**

**第三步：压测找拐点**

用阶梯加压，找到延迟开始陡增的那个点。**那就是当前容量。**

**第四步：用 Little's Law 反推需要的并发数**

算一下当前配置能支持多少并发，**是否匹配目标 QPS**。常见的发现是：线程池/连接池配小了。

**第五步：先优化，再扩容**

加机器前先问：有没有慢查询？有没有不必要的串行？**优化通常比扩容便宜得多。**

## 常见错误

**错误 1：不看瓶颈直接扩容**

前面那个案例。**加机器前必须知道瓶颈在哪。**

**错误 2：只看平均延迟**

平均值掩盖长尾。**p99 才是用户体验的真实反映**，也是最先劣化的。

**错误 3：压测用假数据**

均匀分布的数据 vs 真实的热点分布，结果可能差数倍。**用生产数据的脱敏副本。**

**错误 4：忽略连接池/线程池**

CPU 和内存都很闲，但连接池打满 → 所有请求排队。**这是最常见的"隐形瓶颈"。**

**错误 5：压到系统崩溃才算容量**

"能扛 8000 QPS"——但那时 p99 已经是 10 秒。**用拐点，不用崩溃点。**

**错误 6：没有降级预案**

超容量时所有功能一起劣化。**提前定义降级顺序。**
