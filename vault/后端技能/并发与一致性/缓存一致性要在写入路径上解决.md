# 缓存一致性要在写入路径上解决

## 背景：用户改了昵称，刷新还是旧的

一个用户改了昵称，接口返回成功，但页面刷新后还是旧名字。过一会儿又变成新的。

排查发现是典型的**先删缓存再写库**：

```go
func UpdateName(id, name string) {
    cache.Delete(key(id))       // 1. 删缓存
    db.Update(id, name)         // 2. 写数据库
}
```

并发时序：

```
请求 A：删缓存 → (还没写库)
请求 B：读缓存未命中 → 读库（旧值）→ 写回缓存（旧值）
请求 A：写库（新值）
结果：数据库是新值，缓存是旧值 → 长期不一致
```

**问题不在"删除顺序"，在于缓存的写入路径没有被并发保护。**

## 方案：把一致性设计放在写路径上

三种方案，按一致性强度递增：

### 方案 1：先写库，再删缓存（Cache-Aside 改良）

```go
func UpdateName(id, name string) {
    db.Update(id, name)         // 1. 先写库
    cache.Delete(key(id))       // 2. 再删缓存
}
```

**为什么是"删"而不是"更新"**：删除是幂等的，更新不是。两个并发更新如果顺序颠倒，缓存里会留下旧值（写回顺序和数据库不一致）。删除则不会——删两次和删一次结果一样。

**残留风险**：如果删缓存失败（网络抖动），缓存里就是脏数据，直到 TTL 过期。所以要**配合 TTL 兜底**。

### 方案 2：延迟双删

```go
func UpdateName(id, name string) {
    cache.Delete(key(id))
    db.Update(id, name)
    time.AfterFunc(500*time.Millisecond, func() {
        cache.Delete(key(id))   // 再删一次，清掉并发读写回的旧值
    })
}
```

延迟时间要**大于一次读请求的最长耗时**（读库 + 写缓存）。代价是多一次删除，且延迟窗口内仍可能读到旧值。

### 方案 3：把删除变成消息（最可靠）

用 binlog 订阅或事务内 outbox：

```
事务内：写库 + 写 outbox 表
事务提交后：消费者读 outbox → 删缓存
```

**这是唯一能保证"库更新了缓存一定被清"的方案**，因为 outbox 和业务写入在同一个事务里。代价是需要引入消息队列和消费者。

### 对比

| 方案 | 一致性 | 实现成本 | 残留窗口 |
| --- | --- | --- | --- |
| 先删缓存再写库 | 差 | 最低 | 长期（可能） |
| 先写库再删缓存 | 中 | 低 | TTL 内 |
| 延迟双删 | 中+ | 中 | 延迟窗口内 |
| 事务 outbox | 强 | 高 | 无 |

## 效果与代价

**收益**

- `先写库再删缓存` + TTL 已经能解决绝大多数场景，**这是默认选择**
- 配合 TTL 后，即使删缓存失败，脏数据也有时间上限，不会永久不一致

**代价**

- **TTL 越短越一致，但命中率越低**：这是无法绕过的权衡。"强一致"和"高命中率"不能同时最大化
- **延迟双删有延迟窗口**：窗口内读到的仍是旧值，只是窗口更短
- **outbox 方案复杂度陡增**：需要消息可靠性、消费幂等、顺序保证

## 从什么地方做

**第一步：先确认真的需要缓存**

缓存带来的复杂度（一致性、穿透、雪崩、热 key）远超它的实现代码量。**如果 QPS 不到数据库上限的 50%，先别加缓存。**

**第二步：选定一致性目标，写下来**

问业务方：读到 5 秒前的旧数据可以接受吗？

- 可以 → `先写库再删缓存` + TTL 5 秒
- 不可以 → 走 outbox 方案
- **不用默认"要强一致"**，那是最贵的选项

**第三步：给所有缓存键设 TTL**

无论用哪个方案，TTL 都是最后一道保险。**永不放过期 = 永久脏数据的风险。**

**第四步：处理三个经典问题**

| 问题 | 现象 | 对策 |
| --- | --- | --- |
| 缓存穿透 | 查不存在的数据，每次都打到库 | 缓存空值（短 TTL）或布隆过滤器 |
| 缓存击穿 | 热点 key 过期瞬间，大量请求打到库 | 单飞（singleflight）合并同 key 请求 |
| 缓存雪崩 | 大批 key 同时过期 | TTL 加随机抖动 |

**第五步：监控命中率和一致性**

- 命中率低于预期 → 检查 key 设计或 TTL
- 定期抽样对比缓存和数据库 → 发现不一致

## 常见错误

**错误 1：更新缓存而不是删除**

```go
cache.Set(key, newValue)   // 错
```

两个并发更新时，写回缓存的顺序可能和数据库相反，导致长期脏数据。**删除更安全。**

**错误 2：把缓存和数据库放进同一个事务**

数据库事务无法回滚 Redis。**缓存操作必须在事务外，用最终一致的方式处理。**

**错误 3：只给热点数据设 TTL**

冷数据不设 TTL，一旦被改就永久不一致。

**错误 4：忽略"缓存更新失败"**

`cache.Delete` 返回错误被忽略了。必须**记录 + 告警 + 有兜底**（TTL 或重试队列）。
