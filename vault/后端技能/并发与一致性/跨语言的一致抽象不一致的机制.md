# 跨语言的一致抽象，不一致的机制

## 背景：把 Go 的并发模式直接搬到 Python

一个用 Go 写过的服务要移植到 Python。开发者照搬了 goroutine 的写法：

```python
# 照搬 goroutine 的思路
for item in items:
    threading.Thread(target=process, args=(item,)).start()   # 起了 5000 个线程
```

结果：内存暴涨、上下文切换吃掉 CPU、性能比串��还慢。

**问题不是代码写错了，是机制不同**：

- Go 的 goroutine 是**用户态调度**，初始栈 2KB，可以起百万个
- Python 的 `threading.Thread` 是**操作系统线程**，栈 8MB，且有 GIL

**看起来都是"并发"，底层机制完全不同。** 照搬写法必然踩坑。

## 方案：记住抽象，查清机制

### 同一抽象，三种实现

**"并发执行多个任务"这个抽象**，在各语言里：

| 语言 | 机制 | 调度 | 并行 | 单位开销 |
| --- | --- | --- | --- | --- |
| Go | goroutine | 用户态 M:N | 是（GOMAXPROCS） | ~2KB 栈 |
| Rust + tokio | async task | 用户态，协作式 | 是（多线程 runtime） | 极小 |
| Python asyncio | coroutine | 事件循环，协作式 | **否**（单线程 + GIL） | 极小 |
| Python threading | OS thread | 抢占式 | **受限**（GIL，IO 时可并行） | 8MB 栈 |
| Java（21+） | 虚拟线程 | 用户态 | 是 | ~几 KB |
| Node.js | 事件循环 | 协作式 | 否（单线程） | 极小 |

**关键差别**：

1. **能不能用多核** —— Python asyncio 和 Node 单线程跑不满多核
2. **阻塞的代价** —— 事件循环里一个同步阻塞调用会卡住**所有**任务
3. **取消的语义** —— Go 用 `context`、Rust 用 `Drop`、Python 用 `CancelledError`

### 三个最容易踩的跨语言陷阱

**陷阱 1：async 传染性**

```python
async def a(): ...
def b():
    a()          # 错：返回 coroutine 但不执行
```

在 Rust 里 `.await` 是显式的，忘记会编译报错。
在 Python 里忘记 `await` **不报错**，只是静默不执行——**这是最难查的 bug 之一**。

**陷阱 2：阻塞调用**

```javascript
// Node：整个进程卡住
const data = fs.readFileSync('big.txt');
```

```python
# asyncio：整个事件循环卡住
data = open('big.txt').read()
```

**在协程/事件循环模型里，任何同步阻塞调用都是全局性的。** 各语言的对应做法：

- Go：阻塞 API 通常没问题（goroutine 会被调度走），但要确认
- Python asyncio：用 `aiofiles`、或 `run_in_executor`
- Node：用 `fs.promises` / `fs.readFile`

**陷阱 3：取消与超时**

| 语言 | 机制 |
| --- | --- |
| Go | `context.Context`，显式传递，`ctx.Done()` |
| Rust | `Drop` + `select!`，或 `tokio::time::timeout` |
| Python | `asyncio.wait_for` / `CancelledError` |
| Java | `Future.cancel` / `interrupt` |

**Go 的 context 必须显式传递给每一层**，漏传一层超时就失效。这是 Go 里最常见的资源泄漏来源。

### 并发安全的机制差异

| 语言 | 共享状态保护 |
| --- | --- |
| Go | 编译期无保护，靠 `sync.Mutex` / channel；**有 race detector** |
| Rust | **编译期保证**（所有权 + Send/Sync） |
| Python | GIL 让简单操作"看起来"安全，但复合操作仍需要锁 |
| Java | `synchronized` / `java.util.concurrent` |

**Python 的 GIL 是最危险的**：`x += 1` 不是原子的，但很多开发者以为"有 GIL 就安全"。

### 各语言的错误处理哲学

| 语言 | 风格 |
| --- | --- |
| Go | `if err != nil` 显式返回，**错误是值** |
| Rust | `Result<T, E>` + `?`，**编译期强制处理** |
| Python/Java | 异常，可选择性捕获 |
| Erlang/Elixir | "let it crash"，靠监督者重启 |

**跨语言移植时的坑**：把 Go 的 `if err != nil` 风格写成 Python 的 try/except 捕获所有异常——会吞掉本该暴露的问题。

## 效果与代价

**收益**

- **移植时不会照搬错**：知道同一个抽象在不同语言下的实际约束
- **能选对并发模型**：而不是默认用最熟悉的那个
- **调试有方向**：性能问题先怀疑机制差异

**代价**

- **需要了解每个语言的运行时**：不是只学语法就够
- **心智负担**：写 Go 和写 Python asyncio 时要切换思维
- **团队跨语言协作困难**：同一段逻辑在不同语言下的正确写法不同

## 从什么地方做

**第一步：移植代码前，先查目标语言的并发模型**

问三个问题：能并行吗？阻塞的代价是什么？怎么取消？

**第二步：不要照搬线程/协程数量**

Go 可以起 10 万 goroutine，Python 起 1000 个线程就已经很重。**按目标语言的机制重新设计。**

**第三步：找出所有同步阻塞调用**

在协程/事件循环模型里，**每一个同步 IO 都是潜在的性能杀手**。逐个替换。

**第四步：确认取消路径**

超时能真正传递到最底层吗？**在目标语言里写个测试验证**，不要假设。

**第五步：用目标语言的惯用法，不要翻译语法**

| 不要 | 要 |
| --- | --- |
| 在 Python 里写 Go 风格的显式错误返回 | 用异常，但要具体 |
| 在 Go 里用异常式的 panic/recover 做流程控制 | 用 `error` 返回 |
| 在 Rust 里到处 `.clone()` 绕开借用检查 | 重新设计所有权 |

## 常见错误

**错误 1：把 goroutine 的数量级搬到线程**

10000 个 OS 线程 = 80GB 栈空间（理论值，实际会 OOM）。

**错误 2：在事件循环里用同步 IO**

一个 `requests.get()` 卡住整个 Node/asyncio 服务。**必须用异步客户端。**

**错误 3：漏传 context**（Go 特有）

```go
func handler(w, r) {
    doWork()                        // 没传 ctx
}
func doWork() {
    db.Query(...)                   // 客户端断开后这个查询还在跑
}
```

**错误 4：以为 GIL 让 Python 线程安全**

`counter += 1`、`list.append()`（这个安全）和 `dict[k] += 1`（不安全）表现不同。**复合操作仍需锁。**

**错误 5：跨语言复制错误处理风格**

把 Rust 的 `?` 翻译成 Go 的 `panic`，或把 Go 的显式错误翻译成 Java 的 checked exception 泛滥。

**错误 6：忽略运行时的调优参数**

`GOMAXPROCS`、tokio 的 worker 线程数、Node 的 `UV_THREADPOOL_SIZE`——**默认值不一定适合你的负载**。
