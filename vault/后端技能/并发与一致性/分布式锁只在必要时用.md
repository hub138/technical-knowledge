# 分布式锁只在必要时用，且必须配 Fencing Token

## 背景：那个锁不住人的锁

一个定时任务用 Redis 分布式锁保证只有一个实例执行：

```python
if redis.set("job:lock", "1", nx=True, ex=30):   # 拿锁，30 秒过期
    do_work()                                      # 实际跑了 45 秒
    redis.delete("job:lock")
```

问题出在 `do_work()` 跑了 45 秒 > 30 秒的锁过期时间：

```
t=0   实例 A 拿锁，开始工作
t=30  锁过期（A 还在工作）
t=30  实例 B 拿到锁，开始工作
t=45  A 完成，delete 锁（删的是 B 的锁！）
t=50  C 拿到锁，开始工作
        → A、B、C 同时在跑
```

**这个锁没有保证任何东西**，反而给了"已加锁"的错觉。

## 方案：先问"真的需要锁吗"

### 第一步：绝大多数"需要锁"的场景其实不需要

| 场景 | 更好的方案 |
| --- | --- |
| 防止重复执行定时任务 | **数据库唯一约束**（插入成功才执行） |
| 防止并发扣库存 | **数据库行锁 + `UPDATE ... WHERE stock >= n`** |
| 防止重复创建 | **幂等键 + 唯一索引** |
| 保护共享资源 | **单线程 actor 模型**（消除共享状态） |
| 串行处理某类任务 | **按 key 分区到固定消费者** |

**锁是最难用对的方案。** 能用约束或幂等解决的，不要用锁。

### 第二步：确实需要时，锁必须配 Fencing Token

Fencing Token 是一个**单调递增的版本号**。资源侧记录见过的最大 token，拒绝更小的：

```
t=0   实例 A 拿锁，得到 token=33
t=30  锁过期
t=30  实例 B 拿锁，得到 token=34
t=45  A 完成，带着 token=33 去写资源
        → 资源侧记录的是 34，33 < 34，拒绝！
t=45  B 带着 token=34 写入，成功
```

**关键点**：Fencing 的校验必须在**被保护的资源侧**，不能在锁服务侧。

```python
# 资源侧（比如数据库）
def write(record, fencing_token):
    if fencing_token <= record.last_token:
        raise StaleTokenError()          # 过期的持有者，拒绝
    record.last_token = fencing_token
    record.data = new_data
```

### 第三步：锁的续期要正确处理

如果任务确实需要长时间，用看门狗续期：

```python
def acquire_with_renewal(key, ttl=30):
    token = redis.incr("lock:counter")     # 单调递增，作为 fencing token
    if not redis.set(key, token, nx=True, ex=ttl):
        return None
    # 后台线程定期续期
    stop = threading.Event()
    def renew():
        while not stop.wait(ttl / 3):       # 每 1/3 TTL 续一次
            # 只有锁还是自己的才续期（Lua 保证原子）
            redis.eval(SCRIPT_RENEW, [key], [token, ttl])
    threading.Thread(target=renew, daemon=True).start()
    return Lease(token=token, stop=stop)
```

**续期失败的后果要明确**：续不上就是丢了锁，任务必须能安全中止。

### 第四步：租约（Lease）优于锁

租约 = 有期限的锁 + 明确的持有者身份。

```
Lease {
    owner: "instance-a",
    token: 33,
    expires_at: "2026-09-15T10:00:30Z"
}
```

**好处**：
- 持有者会主动检查"我还没过期吗"
- 过期后持有者知道自己可能被替换

**关键约束：持有者必须在租约到期前完成工作，或明确放弃。** 不能"我也不知道自己还有没有锁"。

## 效果与代价

**收益**

- **不会出现两个持有者同时写**：Fencing 在资源侧强制
- **过期不再导致双重执行**：双重执行会被资源侧拒绝
- **可诊断**：token 和 owner 记录在案，能追溯谁在什么时候持有

**代价**

- **需要在资源侧维护 last_token**：所有被保护的写操作都要改
- **Redis 单点**：Redis 挂了锁就不可用。**Redlock 有争议**（Kleppmann vs antirez），生产环境更推荐 etcd/ZooKeeper
- **复杂度高**：正确实现分布式锁涉及续期、网络分区、时钟偏移等问题
- **性能开销**：每次操作多一次锁服务往返

## 从什么地方做

**第一步：列出所有用了分布式锁的地方**

搜 `setnx`、`SET NX`、`Lock`、`Redlock`。**每一个都问：真的需要吗？**

**第二步：能换成约束的立刻换**

`INSERT ... ON CONFLICT DO NOTHING` 比锁简单得多，且绝对可靠。

**第三步：给剩下的锁加 Fencing Token**

用 Redis 的 `INCR` 或数据库序列生成单调递增的 token。**不要用时间戳**（时钟会回退）。

**第四步：在资源侧校验 token**

这是关键一步，也是最容易被漏掉的。**如果只有锁服务有 token 校验，等于没做。**

**第五步：监控锁等待和续期失败**

- 锁等待时间（上升说明有竞争或死锁）
- 续期失败次数（说明任务跑太久）
- 锁被抢占次数（说明有 bug）

## 常见错误

**错误 1：锁过期时间小于任务耗时**

前面那个案例。**要么加大 TTL + 续期，要么拆小任务。**

**错误 2：没校验持有者就释放锁**

`redis.delete(key)` 会删掉别人的锁。**必须用 Lua 脚本原子地检查 owner 再删。**

**错误 3：用时间戳做 fencing token**

两台机器的时钟不同步 → token 顺序错乱。**必须用单调计数器。**

**错误 4：只锁不加 TTL**

进程崩溃 → 锁永久不释放 → 死锁。**锁必须有 TTL。**

**错误 5：把锁当成事务**

"加了锁就安全了"——锁只保证互斥，不保证原子性。**跨资源的操作仍然需要事务或补偿。**

**错误 6：用 Redis Redlock 做正确性保证**

Redlock 在时钟偏移和网络分区下不保证安全。**需要正确性时用 etcd/ZooKeeper（基于共识）。**
