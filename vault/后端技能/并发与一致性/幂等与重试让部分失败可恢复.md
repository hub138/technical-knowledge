# 幂等与重试让部分失败可恢复

## 背景：扣了两次款的那次超时

客户端调用支付接口，等了 30 秒超时。它不知道服务端到底扣款成功没有，于是重试。

服务端其实**第一次就成功了**，只是响应在网络里丢了。结果用户被扣了两次钱。

这不是极端案例——**只要网络存在，就无法区分"请求没到达"和"响应没回来"**。这是分布式系统的基本事实，不是 bug。

## 方案：让重复执行等价于执行一次

**幂等的定义**：同一个操作执行一次和执行 N 次，对系统状态的最终影响相同。

实现幂等需要三样东西：

### 1. 幂等键（Idempotency Key）

客户端在**第一次请求**时生成一个唯一 key（UUID），之后重试都带同一个 key：

```
POST /payments
Idempotency-Key: 8f14e45f-...
```

服务端处理流程：

```text
收到请求
  → 查这个 key 有没有处理记录
     有 → 直接返回上次的保存结果（不重复执行）
     没有 → 在事务内：执行业务 + 写入 (key → 结果)
```

关键点：**"执行业务"和"记录结果"必须在同一个事务里**。否则会出现"业务做了但没记录"，下次重试又会做一遍。

### 2. 幂等键的存储与过期

| 存储 | 适用 | 注意 |
| --- | --- | --- |
| 数据库唯一索引 | 强一致要求，已有事务 | 用唯一约束防并发重复插入 |
| Redis `SET NX` | 高吞吐，允许最终一致 | 要处理 Redis 和业务库的不一致 |
| 业务表上的唯一键 | 天然幂等的场景（如唯一订单号） | 最省事，优先用这个 |

**并发处理**：两个相同 key 的请求同时到达，都没查到记录。解法是让数据库唯一索引兜底——第二个插入会失败，此时再查一次返回结果。

**过期**：key 不能永久保留。通常按业务周期设（比如 24 小时或 7 天），过期后同样的 key 会被当作新请求。这也意味着**幂等是有时间窗口保证的**。

### 3. 重试策略：什么时候该重试

不是所有失败都该重试：

| 失败类型 | 重试？ | 理由 |
| --- | --- | --- |
| 超时 / 连接重置 | 是 | 可能根本没执行 |
| 503 / 429 | 是（退避） | 对方暂时不可用或限流 |
| 500 | 视情况 | 可能是未知状态，需先确认 |
| 400 / 422 | **否** | 请求本身有问题，重试也没用 |
| 401 / 403 | 否 | 权限问题 |
| 明确的业务失败（余额不足） | 否 | 已经执行过了 |

**退避 + 抖动**：

```text
delay = min(cap, base * 2^attempt) * random(0.5, 1.0)
```

不加抖动的后果是**重试风暴**：一批请求同时超时、同时重试、再次同时超时。抖动把重试时间打散。

**重试预算**：给重试设上限（比如总请求量的 10%）。如果重试占比过高，说明系统已经过载，继续重试只会雪上加霜——这时应该**快速失败 + 熔断**。

## 效果与代价

**收益**

- 网络抖动导致的失败可以自愈，不需要人工介入
- 客户端可以安全地"不确定就重试"，简化错误处理
- 配合超时和熔断，构成完整的故障恢复链路

**代价**

- **需要额外存储**：幂等键表会持续增大，要设计清理或过期
- **业务逻辑要配合**：不是所有操作都天然幂等。"余额 +100" 不幂等，"余额设为 500" 幂等。有些业务必须转换成"设定目标值"才能幂等
- **掩盖问题**：重试可能把真正的性能问题藏起来。一定要监控重试率——它上升通常是系统出问题的**信号**，而不是解决方案
- **延迟放大**：重试会让 p99 变差。一个 3 次重试的请求，最坏情况是正常耗时的 3 倍多

## 从什么地方做

**第一步：给所有写操作设计幂等键**

优先找业务天然的唯一标识（订单号、流水号），用它做数据库唯一索引——这是最便宜的幂等。

**第二步：区分"安全重试"和"危险重试"**

画一张表，列出你系统里所有对外的写调用，标注：这个调用是幂等的吗？重试会不会造成重复扣款/重复发货？

**第三步：读操作天然幂等，不用管**

`GET` 不会改变状态。真正要处理的是 `POST`、`PUT`（PUT 语义上幂等，但要确认实现符合）、`DELETE`。

**第四步：为"不确定"设计查询接口**

提供一个 `GET /payments/{idempotency_key}` 让客户端能主动查结果。这比盲重试更可控。

**第五步：监控重试率**

至少三个指标：

- 重试请求占比（超过 10% 要告警）
- 因幂等键命中而直接返回的次数（说明客户端在重试）
- 重试后仍然失败的比例（说明重试没救回来，需要熔断）

## 常见错误

**错误 1：在重试里换幂等键**

客户端每次重试都生成新 UUID——那幂等形同虚设。**幂等键必须在第一次请求时就固定，重试复用同一个。**

**错误 2：先查后写，没有唯一约束兜底**

```go
if !exists(key) { doBusiness() }
```

并发下两个请求都会通过检查。必须用数据库唯一索引或分布式锁兜底。

**错误 3：把响应体丢了**

幂等命中时应该返回**上次保存的完整响应**，而不是简单的"成功"。客户端需要拿到第一次的业务结果（比如支付流水号）。

**错误 4：重试链条叠加**

A 重试 B，B 重试 C，C 重试 D。每层 3 次，最坏 27 次。**重试应该只在系统的边界做一次**，内部调用快速失败。
