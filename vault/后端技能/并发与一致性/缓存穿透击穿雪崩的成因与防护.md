# 缓存穿透击穿雪崩的成因与防护

## 背景：一次热点事件，数据库被打挂

一个电商大促，某爆款商品详情页 QPS 峰值 8 万，缓存挡住了 99%。

事故过程：

```
23:59  商品开始抢购，缓存命中率 99%
00:00  缓存 key 到期（这批 key 是上架时批量写入的，TTL 相同）
00:00  8 万 QPS 全部 miss，直接打到数据库
00:00  数据库连接池打满，其他所有接口全部超时
00:03  数据库崩溃，整个站点不可用
```

事后复盘发现这不是单一问题，而是三个问题叠加：

| 现象 | 这次事故里的表现 |
| --- | --- |
| **击穿**：单个热点 key 过期 | 爆款商品的 key 到期，8 万请求同时回源 |
| **雪崩**：大量 key 同时过期 | 整批 key 的 TTL 相同，同时失效 |
| **穿透**：查询不存在的数据 | 攻击者用不存在的商品 ID 刷接口 |

**这三个问题都需要防护，且解法不同。** 只做其中一个，另外两个仍会出事。

## 从 0 开始：先理解缓存的读取路径

```
请求 → 查缓存
         ├─ 命中 → 返回（数据库零压力）
         └─ 未命中 → 查数据库 → 写回缓存 → 返回
                        ↑
                    这一步是风险来源
```

**缓存的价值在于"挡住回源"。** 一旦大量请求同时未命中，数据库就要承受全部流量——而数据库的容量通常只有缓存的 1/100。

所以要防的就是：**任何情况下，都不能让大量请求同时回源。**

## 方案一：穿透 —— 查询根本不存在的数据

### 成因

```
攻击者用随机 ID 刷：GET /product/999999999
  → 缓存没有（因为数据库里也没有）
  → 查数据库：也没有
  → 不写缓存（因为没数据）
  → 下一次同样的 ID 还是穿透
```

**每次请求都打到数据库。** 用 10 万个不存在的 ID 刷，就是 10 万次数据库查询。

### 三种解法

**解法 1：缓存空值（最简单，优先用）**

```go
val, err := cache.Get(key)
if err == ErrNotFound {
    // 数据库也没查到，缓存一个空标记
    cache.Set(key, NullMarker{}, ttl=60*time.Second)
    return nil, ErrProductNotFound
}
```

**要点**：
- **TTL 要短**（30-120 秒）。太长会占内存，且真数据写入后要等 TTL 才可见
- 用**专门的空标记**，不是 `null`——要能区分"不存在"和"值为空"
- 数据写入时**主动删除空标记**，避免短期不一致

**解法 2：布隆过滤器（ID 量大时）**

```
请求 → 布隆过滤器判断 ID 是否存在
         ├─ 不存在 → 直接返回，不查库
         └─ 可能存在 → 走正常缓存流程
```

| | 优点 | 缺点 |
| --- | --- | --- |
| 缓存空值 | 实现简单 | 占内存（每个不存在的 key 都存一份） |
| 布隆过滤器 | 内存极省（10 亿 ID 约 1.2GB，误判率 1%） | 有误判（不存在的可能判成存在）；不支持删除 |

**选择建议**：key 空间可枚举且量不大 → 缓存空值。ID 海量（比如爬虫刷各种 ID）→ 布隆过滤器。**两者可以一起用。**

**解法 3：参数校验（最便宜，别漏）**

```go
if id <= 0 || id > MAX_ID {
    return ErrInvalidID     // 连缓存都不查
}
```

**负 ID、超大 ID、格式非法的请求直接挡掉。** 这一步零成本，能拦住相当比例的恶意流量。

## 方案二：击穿 —— 单个热点 key 过期

### 成因

```
一个 key 有 8 万 QPS
  → key 过期
  → 8 万个请求同时发现 miss
  → 8 万个请求同时查数据库
```

**注意：不是 8 万次不同查询，是同一个查询做了 8 万遍。** 这是极大的浪费。

### 三种解法

**解法 1：单飞（Singleflight）—— 最推荐**

合并同一个 key 的并发回源请求，**只让第一个去查数据库，其余等待结果**。

```go
var g singleflight.Group

func GetProduct(id string) (*Product, error) {
    v, err, _ := g.Do("product:"+id, func() (interface{}, error) {
        return db.QueryProduct(id)     // 同一时刻只有一个在执行
    })
    return v.(*Product), err
}
```

**效果**：8 万并发 → 1 次数据库查询。**这是击穿的最优解。**

Go 有 `golang.org/x/sync/singleflight`，其他语言也有类似实现（或直接自己用 `map + mutex` 实现）。

**注意**：singleflight 是**单进程内**的合并。多实例部署时，每个实例仍会各自查一次——但 8 台机器查 8 次，比 8 万次好得多。

**解法 2：逻辑过期（热点 key 永不过期）**

```
缓存里存：{value: ..., expire_at: 1730000000}
  → 物理 TTL 设为永不过期（或很长）
  → 读的时候检查 expire_at，逻辑上过期了就触发异步刷新
  → 刷新期间返回旧值（不会阻塞）
```

```go
type CacheItem struct {
    Value    []byte
    ExpireAt int64      // 业务过期时间
}

func Get(key string) ([]byte, error) {
    item := cache.Get(key)
    if item == nil { return nil, ErrNotFound }

    if time.Now().Unix() > item.ExpireAt {
        // 逻辑过期：异步刷新，本次仍返回旧值
        go refreshAsync(key)
    }
    return item.Value, nil
}
```

**适用场景**：极热点数据（首页推荐、爆款商品、配置）。代价是可能短暂返回旧值。

**解法 3：互斥锁重建（不推荐）**

```go
lock := acquireLock(key)
if lock {
    v := db.Query()
    cache.Set(key, v)
    releaseLock(key)
} else {
    time.Sleep(50ms)
    return Get(key)      // 重试
}
```

**为什么不推荐**：等待期间请求被阻塞，超时会引发重试风暴；且分布式锁本身有复杂度。**用 singleflight 或逻辑过期。**

## 方案三：雪崩 —— 大批 key 同时失效

### 成因

```
上架时批量写入 10 万个商品缓存，TTL 全是 3600 秒
  → 1 小时后，10 万个 key 同时过期
  → 全部回源
```

**根因：TTL 相同。** 这是最容易预防也最常犯的错误。

### 三种解法

**解法 1：TTL 加随机抖动（必须做）**

```go
base := 3600 * time.Second
jitter := time.Duration(rand.Int63n(600)) * time.Second   // ±10 分钟
cache.Set(key, val, base+jitter)
```

**这一行代码能挡住大部分雪崩。** 写在缓存工具类里，不要每次手动加。

**经验值**：抖动幅度 = 基础 TTL 的 10-20%。

**解法 2：多级缓存**

```
L1：本地缓存（进程内存，1-5 分钟）
L2：分布式缓存（Redis，1 小时）
L3：数据库
```

L1 的过期时间各不相同（因为各进程启动时间不同），天然错开。**即使 L2 全挂，L1 还能挡一阵。**

代价：L1 和 L2 之间有一致性问题（更新时要清两级，且进程间不同步）。**只缓存变更不频繁的数据。**

**解法 3：缓存预热 + 永不过期**

大促前提前把热点数据加载到缓存，**并且不设 TTL**（用逻辑过期或主动更新）。

```
大促前 10 分钟：
  1. 从历史数据预测热点商品
  2. 批量加载到缓存，TTL 设为永不过期
  3. 数据变更时主动更新缓存
  4. 大促结束后清理
```

## 三个问题一起防：完整方案

```go
type SafeCache struct {
    cache    Cache
    db       DB
    group    singleflight.Group
    bloom    *BloomFilter      // 可选
}

func (c *SafeCache) Get(key string, id int64) ([]byte, error) {
    // 1. 参数校验防穿透（最便宜）
    if !validID(id) {
        return nil, ErrInvalidID
    }

    // 2. 布隆过滤器防穿透（可选，海量 ID 场景）
    if c.bloom != nil && !c.bloom.MayContain(id) {
        return nil, ErrNotFound
    }

    // 3. 查缓存
    if v, ok := c.cache.Get(key); ok {
        if isNullMarker(v) { return nil, ErrNotFound }
        return v, nil
    }

    // 4. singleflight 防击穿：同一 key 只回源一次
    v, err, _ := c.group.Do(key, func() (interface{}, error) {
        data, err := c.db.Query(id)
        if err != nil { return nil, err }

        if data == nil {
            // 5. 缓存空值防穿透
            c.cache.Set(key, NullMarker{}, 60*time.Second)
            return nil, ErrNotFound
        }
        // 6. TTL 加抖动防雪崩
        c.cache.Set(key, data, baseTTL()+jitter())
        return data, nil
    })
    return v.([]byte), err
}
```

## 效果与代价

| 防护 | 收益 | 代价 |
| --- | --- | --- |
| 参数校验 | 零成本拦掉非法请求 | 无 |
| 缓存空值 | 挡住重复穿透 | 占内存；短期不一致 |
| 布隆过滤器 | 内存极省 | 误判；不能删除 |
| Singleflight | 8 万并发→1 次回源 | 单进程内有效；需要库支持 |
| 逻辑过期 | 热点永不过期 | 可能返回旧值 |
| TTL 抖动 | 一行代码防雪崩 | 无 |
| 多级缓存 | 双保险 | 一致性复杂 |

## 从什么地方做

**第一步：先加 TTL 抖动（5 分钟就能做完）**

搜代码里所有 `Set(key, val, ttl)` 的调用。**统一改成 `ttl + jitter`。** 这是投入产出比最高的一步。

**第二步：加参数校验**

所有按 ID 查询的接口，检查 ID 合法性。**零成本。**

**第三步：引入 singleflight**

对回源逻辑包一层。**这一步能防住绝大部分击穿。**

**第四步：决定是否要缓存空值**

看日志里有没有大量"查询不存在"的请求。**有就加。**

**第五步：热点 key 单独处理**

识别出 Top 100 热点 key（用 Redis 的 `OBJECT FREQ` 或自己统计），对它们用逻辑过期。

**第六步：压测验证**

模拟：热点 key 过期瞬间的高并发、批量 key 同时过期、大量不存在的 ID。

## 常见错误

**错误 1：所有 key 用相同 TTL**

最常见的雪崩原因。**必须加抖动。**

**错误 2：缓存空值用长 TTL**

设成 1 小时 → 真数据写入后 1 小时才可见。**用 30-120 秒。**

**错误 3：只防穿透不防击穿**

布隆过滤器挡住了不存在的 ID，但热点 key 过期时照样打挂数据库。**三个问题要分别防。**

**错误 4：用分布式锁重建缓存**

请求被阻塞 → 超时 → 客户端重试 → 更糟。**用 singleflight。**

**错误 5：忽略"缓存挂了"的情况**

所有防护都建立在缓存可用的前提下。**Redis 整体不可用时，要么降级（限流 + 快速失败），要么直接返回兜底数据——绝不能让全部流量打到数据库。**

**错误 6：缓存空值没有清理路径**

真数据写入后，空标记还在 → 用户看到"不存在"。**写入时主动删空标记。**
