# 消息投递语义决定你要处理多少次重复

## 背景：那笔被扣了两次的款

一个订单支付成功后发消息通知发货。消费者处理时：

```
1. 收到消息
2. 扣库存、创建发货单
3. 提交 offset（告诉 MQ 这条处理完了）
4. 进程崩溃 ← 在第 3 步之前
```

重启后 MQ 重新投递这条消息 → **扣了两次库存，创建了两个发货单**。

反过来，如果先提交 offset 再处理：

```
1. 收到消息
2. 提交 offset
3. 扣库存
4. 进程崩溃 ← 在第 3 步之前
```

重启后 MQ 不会再投递 → **这笔订单永远不发货**。

**这就是投递语义的核心难题：你无法让"处理业务"和"提交 offset"原子。**

## 方案：理解三种语义，选对的那一种

### 三种语义

| 语义 | 含义 | 实现 | 代价 |
| --- | --- | --- | --- |
| **最多一次** | 可能丢，绝不重复 | 先提交 offset，再处理 | 丢消息 |
| **至少一次** | 可能重复，绝不丢 | 先处理，再提交 offset | 要幂等 |
| **恰好一次** | 不丢不重 | 事务或幂等 + 去重 | 最复杂 |

### 恰好一次的两种实现

**方式 1：事务（Kafka 事务）**

```
1. 处理业务（写数据库）
2. 写消息到另一个 topic
3. 提交 Kafka 事务
```

**限制**：只能保证 Kafka 内部的原子性。如果业务是写外部数据库，**Kafka 事务管不到**——仍然需要下面这种方式。

**方式 2：幂等 + 去重（生产环境的实际做法）**

```
消费者收到消息
  → 查去重表：这个 message_id 处理过吗？
      处理过 → 直接确认，跳过
      没处理 → 在事务内：处理业务 + 记录 message_id
```

**关键：处理业务和记录 message_id 必须在同一个事务里。**

```sql
BEGIN;
  UPDATE inventory SET qty = qty - 1 WHERE product_id = ?;
  INSERT INTO processed_messages (message_id) VALUES (?);  -- 唯一索引
COMMIT;
```

如果消息重复，第二条 INSERT 会因唯一约束失败 → 整个事务回滚 → 业务不会重复执行。

### 幂等设计：比去重表更根本

去重表解决"同一条消息重复投递"。但还有另一种重复：**业务逻辑上的重复**（用户手抖点了两次下单）。

**幂等键应该在生产者侧生成**，而不是用 MQ 的 message_id：

```
下单请求 → 生成 idempotency_key = hash(user_id + product_id + 时间窗口)
         → 放进消息体
```

消费者用业务幂等键去重。**这样即使消息走了不同链路、被重新投递，也能识别。**

### 顺序保证

| 需求 | 做法 | 代价 |
| --- | --- | --- |
| 全局有序 | 单分区 | 无法并行，吞吐极低 |
| **同一 key 有序**（常用） | 按 key 分区（如订单 ID） | 同一 key 串行，不同 key 并行 |
| 无需有序 | 任意分区 | 最大吞吐 |

**Kafka 只保证分区内有序。** 要保证"同一订单的创建、付款、取消按顺序处理"，必须让它们进同一个分区——用订单 ID 作为分区键。

**注意**：如果消费者失败重试，可能打乱顺序（后面的消息先处理完）。**用 `max.in.flight.requests.per.connection = 1` 或幂等生产者避免。**

### 死信队列：失败消息不能无限重试

```
主 topic → 消费失败 → 重试 3 次 → 仍失败 → 进入 DLQ
                                              ↓
                                       人工/自动排查
```

**没有 DLQ 的后果**：一条永远失败的消息会阻塞整个分区（Kafka）或反复重投（RabbitMQ）。

## 效果与代价

**收益**

- **不丢消息**：至少一次 + 幂等，兼顾可靠和正确
- **可重试**：失败的消息能安全地重新处理
- **顺序可控**：按 key 分区保证业务需要的顺序

**代价**

- **消费者必须幂等**：这是额外的设计工作，且容易遗漏
- **去重表会增长**：需要定期清理（按时间窗口，比如保留 7 天）
- **事务开销**：处理业务 + 记录去重在同一个事务里，增加锁持有时间
- **顺序和并行冲突**：保证顺序就要牺牲并行度

## 从什么地方做

**第一步：明确每个 topic 的语义要求**

问：这个 topic 的消息，丢了会怎样？重复了会怎样？

- 通知类：丢了严重，重复可接受 → **至少一次 + 幂等**
- 指标/日志：丢了可接受 → **最多一次**
- 资金类：都不能接受 → **至少一次 + 幂等 + 对账**

**第二步：生产者侧生成业务幂等键放进消息**

不要依赖 MQ 的 message_id（重试时可能变）。

**第三步：消费者实现幂等**

用唯一约束（不是"先查再插"，那有并发窗口）：

```sql
INSERT INTO processed_messages (message_id) VALUES (?)
ON CONFLICT DO NOTHING;   -- 返回 0 行表示已处理
```

**第四步：配死信队列和重试上限**

重试 3 次后进 DLQ。**监控 DLQ 大小**——它上涨说明有系统性问题。

**第五步：加对账**

对于资金、库存这类，**定期跑对账任务**（比对消息数和实际处理数）。这是最后一道保险。

## 常见错误

**错误 1：先提交 offset 再处理**

崩溃就丢消息，且悄无声息。**至少一次的场景必须"先处理再提交"。**

**错误 2：用"先查再插"做去重**

```sql
SELECT ... WHERE message_id = ?;  -- 没查到
-- 并发下另一个消费者也查到"没查到"
INSERT ...;                        -- 两个都插入
```

**必须用唯一约束兜底。**

**错误 3：消费者不幂等就靠"恰好一次"**

以为 Kafka 事务能保证业务不重复——**它管不到你的数据库**。业务幂等必须自己实现。

**错误 4：没有 DLQ**

一条毒丸消息阻塞整个分区。**必须配 DLQ。**

**错误 5：忽略分区键导致顺序问题**

订单创建和取消进了不同分区 → 取消先被处理 → 状态错乱。**需要顺序的用同一个 key。**

**错误 6：去重表不清**

保留两年的去重表比业务表还大。**按业务窗口清理（通常 7-30 天足够）。**
