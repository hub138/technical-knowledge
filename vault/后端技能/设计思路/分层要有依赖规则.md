# 分层要有依赖规则，不只是目录结构

## 背景：有 5 个目录，但等于没分层

一个项目结构很"标准"：

```
src/
  controllers/
  services/
  repositories/
  models/
  utils/
```

半年后发现：

- `models/order.go` 里 import 了 `gorm.io/gorm`（ORM 注解）
- `services/order.go` 直接 import 了 `net/http` 调第三方
- `controllers/` 里写了业务校验逻辑（因为"顺手"）
- `utils/` 被所有层依赖，里面既有日期格式化又有数据库连接

**目录分了，依赖没分。** 结果和"一个 main.go 写全部"没有本质区别——只是文件变多了。

**分层不是把文件放进不同文件夹，是规定依赖只能单向流动。**

## 方案：显式规定依赖规则，并用测试锁住

### 规则 1：依赖只能向内

```
外层 ──依赖──→ 内层
内层 ──✗────── 外层
```

```
接口层（HTTP/gRPC/CLI）
   ↓ 可依赖
应用层（用例编排）
   ↓ 可依赖
领域层（业务规则）        ← 不依赖任何外层
   ↑ 实现
基础设施层（DB/MQ/外部 API）
```

**领域层在最中心，不 import 任何外部框架。**

### 规则 2：每层的职责边界要明确

| 层 | 该做什么 | 不该做什么 |
| --- | --- | --- |
| 接口层 | 协议转换、参数解析、错误映射 | 业务逻辑、直接调数据库 |
| 应用层 | 用例编排、事务边界、调用领域对象 | 业务规则本身、SQL |
| 领域层 | 业务规则、不变量、领域计算 | 数据库、HTTP、框架注解 |
| 基础设施层 | 实现领域层定义的接口 | 业务判断 |

**判断某段代码属于哪层**：问"改这个规则时，业务方要参与吗？" 要 → 领域层。

### 规则 3：用架构测试强制

规则写在文档里没人遵守。**用测试强制：**

```python
def test_domain_has_no_infrastructure_deps():
    """领域层只允许 import 标准库和自身。"""
    allowed = {"fmt", "time", "errors", "strings", "sort"}
    for f in Path("src/domain").rglob("*.go"):
        for imp in parse_imports(f):
            assert imp in allowed or imp.startswith("myapp/domain"), \
                f"{f} 依赖了 {imp}"
```

```python
def test_controllers_do_not_use_repositories_directly():
    """接口层不能跳过应用层直接访问仓储。"""
    for f in Path("src/controllers").rglob("*.go"):
        imports = parse_imports(f)
        assert not any("repository" in i for i in imports), \
            f"{f} 直接依赖了仓储，应通过应用层"
```

**这两条测试比任何架构文档都管用**——它让违规变成 CI 失败，而不是 code review 时的争论。

### 规则 4：跨层传递用 DTO，不要传领域对象

```
控制器 收到 CreateOrderRequest（DTO）
   ↓ 转换
应用层 调用 domain.NewOrder(...)（领域对象）
   ↓ 返回
控制器 把领域对象转成 OrderResponse（DTO）
```

**为什么**：直接把领域对象序列化给前端，会导致领域模型被外部需求牵着走（加字段、改类型）。

## 效果与代价

**收益**

- **改动影响可预测**：换数据库只改基础设施层，业务代码零改动
- **可测试**：领域层不依赖外部，可以纯单元测试
- **新人上手快**：知道代码该放哪，不用猜
- **防止腐化**：架构测试阻止"顺手加个查询"这类侵蚀

**代价**

- **更多样板代码**：DTO ↔ 领域对象的转换代码量不小
- **小项目过度设计**：1000 行的服务分 4 层是浪费。**分层收益随规模增长**
- **初次设计要花时间**：要定义清楚每层职责
- **性能开销**：多层转换有轻微开销（通常可忽略）

## 从什么地方做

**第一步：先检查现有依赖，找出违规**

写个脚本统计每个目录 import 了哪些其他目录。**画出来会看到惊喜。**

**第二步：从"领域层不能依赖框架"开始**

这是最核心的一条，也是收益最大的。把 ORM 注解、HTTP 类型从领域模型上摘掉。

**第三步：加第一条架构测试**

先只加"领域层不依赖基础设施"这一条。**跑起来会有一堆失败**——按失败清单逐个修。

**第四步：定义 DTO，隔离外部契约**

接口层的请求/响应对象和领域对象分开。**这一步会让"加个字段给前端"不再影响领域。**

**第五步：在 code review 检查清单里加分层的项**

自动化能测的用测试，测不了的（比如"这个方法逻辑太多"）靠 review。

## 常见错误

**错误 1：分层只体现在目录名**

`controllers/` 里直接写 SQL —— 目录分层毫无意义。**必须配依赖规则和测试。**

**错误 2：领域层依赖 ORM**

领域模型上有 `gorm:"column:xxx"` 注解 → 换 ORM 或换数据库时领域层要改。**领域模型应该是纯的。**

**错误 3：application 层写业务规则**

"VIP 用户打九折"写在 service 里 → 换一个调用方就绕过。**规则要在领域对象里。**

**错误 4：所有东西都放 utils**

`utils/` 变成无所不包的垃圾场，被所有层依赖。**按职责拆分，或直接放进对应的层。**

**错误 5：分层过细**

7 层架构，一个请求穿过 7 个类才能到逻辑。**4 层通常够，小项目 2-3 层。**

**错误 6：忽略"基础设施层实现接口"的方向**

基础设施层 import 领域层是**合法的方向**（为了实现接口），但要确保它是"实现"而不是"被调用"。**用依赖注入装配，不要在领域层里 new 具体实现。**
