# 索引为访问路径服务，不是为列服务

## 背景：加了索引，查询还是 3 秒

一个 8000 万行的订单表，慢查询是：

```sql
SELECT * FROM orders
WHERE user_id = ? AND status = 'paid'
ORDER BY created_at DESC LIMIT 20;
```

DBA 给三个列各加了单列索引：`user_id`、`status`、`created_at`。

**查询还是 3 秒。** 因为优化器只能用一个索引：

- 用 `user_id` 索引 → 找到该用户 12 万行 → **回表 12 万次**过滤 status → 排序 → 慢
- 用 `status` 索引 → 找到 3000 万行 → 更慢
- 用 `created_at` 索引 → 全表扫描式回表

**给每个列加索引是最常见的误解。** 索引不是"给列加速"，是"为一条具体的访问路径服务"。

## 方案：按查询设计索引，不是按表设计

### 1. 复合索引的列顺序：等值 → 范围 → 排序

对上面那个查询，正确的索引是：

```sql
CREATE INDEX idx_orders_user_status_created
ON orders (user_id, status, created_at DESC);
```

顺序规则（从左到右）：

| 位置 | 放什么 | 原因 |
| --- | --- | --- |
| 第 1 位 | **等值条件**（`=`） | 精确定位，缩小范围最快 |
| 中间 | **范围条件**（`>`、`<`、`BETWEEN`） | 范围之后的列无法再用于精确定位 |
| 最后 | **排序/分组列** | 索引有序，可直接避免排序 |

**为什么顺序关键**：索引是有序的 `(user_id, status, created_at)`。

- 已知 `user_id + status` → 在这个组合下 `created_at` 是**有序的** → 排序和分页直接扫描即可，不用 `filesort`
- 如果顺序是 `(status, user_id, created_at)` → 同一 `status` 下 `user_id` 是乱序的 → 还要排序

### 2. 覆盖索引避免回表

如果查询只需要几个列，把它们放进索引里：

```sql
-- 查询：SELECT id, amount, created_at FROM orders WHERE user_id=? AND status=?
CREATE INDEX idx_cover ON orders (user_id, status, created_at DESC, id, amount);
```

**索引里就有全部需要的列 → 不用回表读主键行。** 这叫覆盖索引（covering index），`EXPLAIN` 里显示 `Using index`。

**代价**：索引变大，写变慢。**只对高频慢查询做。**

### 3. 用 EXPLAIN 验证，不要猜

```sql
EXPLAIN ANALYZE SELECT ...;
```

重点看：

| 指标 | 健康 | 问题信号 |
| --- | --- | --- |
| `type` | `ref`/`range`/`const` | `ALL`（全表扫描） |
| `rows` | 接近实际返回行数 | 远大于返回行数（过滤低效） |
| `Extra` | `Using index` | `Using filesort`、`Using temporary` |
| `key_len` | 用满索引长度 | 只用了前缀（说明后面的列没用上） |

**`rows` 是最重要的指标**：如果扫描 12 万行只返回 20 行，说明索引没覆盖到过滤条件。

### 4. 写放大：每个索引都有成本

```
一个 INSERT/UPDATE/DELETE 要维护所有索引
```

| 索引数 | 写性能影响 |
| --- | --- |
| 0-3 个 | 可接受 |
| 5-8 个 | 明显下降 |
| 10+ 个 | 写入可能成为瓶颈 |

**所以要定期清理没人用的索引：**

```sql
-- PostgreSQL：查看从未被使用的索引
SELECT indexrelname, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0;
```

### 5. 几种特殊索引

| 类型 | 适用 | 例子 |
| --- | --- | --- |
| 部分索引 | 只索引关心的行 | `WHERE status = 'paid'`（90% 是归档订单时极有效） |
| 表达式索引 | 对计算结果查询 | `CREATE INDEX ON t (lower(email))` |
| GIN | 数组、JSONB、全文 | `WHERE tags @> ARRAY['urgent']` |
| GiST | 地理、范围 | 附近的人、时间区间重叠 |

**部分索引是被低估的工具**：如果 95% 的查询只关心未删除的行，索引带 `WHERE deleted_at IS NULL` 能让索引小 20 倍。

## 效果与代价

**收益**

- **数量级的性能提升**：3 秒 → 20 毫秒 是常见的
- **减少 IO 和锁竞争**：扫描行数从 12 万降到 20
- **排序消除**：索引有序，不用临时表

**代价**

- **写变慢**：每个索引都要维护
- **存储空间**：索引可能和表一样大
- **需要持续维护**：查询模式变了，索引要跟着改
- **优化器不总是选对的**：统计信息过时会导致选错索引 → 定期 `ANALYZE`

## 从什么地方做

**第一步：找出慢查询**

开启慢查询日志（比如 `long_query_time = 1`），跑一周。**用真实数据，不要凭感觉。**

**第二步：对 TOP 5 慢查询逐个 EXPLAIN**

看 `rows` 和 `Extra`。**目标：扫描行数 ≈ 返回行数。**

**第三步：按"等值 → 范围 → 排序"建复合索引**

不要加单列索引。**一条设计好的复合索引胜过三个单列索引。**

**第四步：验证后再上线**

`EXPLAIN ANALYZE` 对比前后的实际耗时。**没验证就加索引等于赌。**

**第五步：定期清理未使用索引**

每季度跑一次 `idx_scan = 0` 的查询。**没人用的索引是纯负担。**

## 常见错误

**错误 1：给每个 WHERE 列都建单列索引**

前面那个案例。**优化器通常只用一个索引**，多个单列索引往往是浪费。

**错误 2：索引列顺序随意**

`(status, user_id)` 和 `(user_id, status)` 性能可能差 100 倍。**等值列放前面。**

**错误 3：忽略排序字段**

`ORDER BY created_at` 没有索引 → 每次查询都要排序。**排序字段放进索引最后。**

**错误 4：索引建了但查询写法用不上**

```sql
WHERE DATE(created_at) = '2026-09-15'   -- 函数包了列，索引失效
WHERE created_at >= '2026-09-15' AND created_at < '2026-09-16'   -- 正确
```

**错误 5：不看写放大的成本**

给一张高频写入的表加了 12 个索引 → 写入从 5ms 涨到 50ms。**索引要为高频查询服务，不是为所有查询服务。**

**错误 6：以为加了索引就一定会用**

优化器基于统计信息决策。**数据分布倾斜时（比如 90% 都是同一个 status），它可能选择全表扫描——而且这个选择可能是对的。**
