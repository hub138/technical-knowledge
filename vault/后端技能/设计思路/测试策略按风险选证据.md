# 测试策略按风险选证据，不追求覆盖率

## 背景：85% 覆盖率，上线还是炸了

一个服务测试覆盖率 85%，CI 全绿。上线后第二天出现资金对不上。

复盘发现测试长这样：

```go
func TestTransfer(t *testing.T) {
    mockRepo.EXPECT().Save(gomock.Any()).Return(nil)
    mockNotifier.EXPECT().Notify(gomock.Any()).Return(nil)
    err := svc.Transfer(ctx, req)
    assert.NoError(t, err)   // 只验证了"没报错"
}
```

**这个测试验证的是 mock 的行为，不是业务。** 覆盖率很高，因为所有行都跑到了——但没有任何一行验证"钱有没有转对"。

**覆盖率衡量的是"代码被执行了多少"，不是"正确性被验证了多少"。**

## 方案：按风险分配测试投入

### 测试金字塔，但按风险调整形状

```
    ╱╲        E2E（少）：关键用户路径
   ╱──╲       集成（中）：跨组件契约、数据库
  ╱────╲      单元（多）：业务规则、不变量、边界
```

**关键：不是所有代码都值得同等测试。**

| 代码类型 | 风险 | 测试强度 |
| --- | --- | --- |
| 资金计算、计费 | **极高** | 穷举边界 + 属性测试 + 对账 |
| 业务规则、状态机 | 高 | 单元测试全覆盖分支 |
| 数据校验、权限 | 高 | 单元测试 + 集成测试 |
| 外部集成（DB/MQ/API） | 中 | 集成测试，用真实组件 |
| CRUD、DTO 转换 | 低 | 少量即可，或靠类型系统 |
| 配置、脚手架 | 极低 | 不写测试 |

**把时间花在高风险区。** 一个计费函数的测试，价值高于 10 个 CRUD 的测试。

### 按"能发现什么 bug"选测试类型

**单元测试**：验证规则和边界

```go
func TestTransfer_InsufficientBalance(t *testing.T) {
    from := Account{Balance: Money{100}}
    err := from.TransferTo(Account{}, Money{200})
    assert.ErrorIs(t, err, ErrInsufficientBalance)
    assert.Equal(t, Money{100}, from.Balance)   // 失败后余额不变
}
```

**关键：断言不变量，不只是"没报错"。**

**集成测试**：验证真实组件协作

用真实的数据库（testcontainers），不用 mock。

**为什么**：mock 掉的 SQL 不会发现语法错误、约束冲突、事务问题。**这些恰恰是集成测试该抓的。**

**属性测试**：验证普遍性质

对"钱"这类逻辑特别有效：

```go
// 属性：转账前后总额不变
func TestTransferPreservesTotal(t *testing.T) {
    f := func(a, b Money, amount Money) bool {
        if !a.CanAfford(amount) { return true }
        from, to := Account{Balance: a}, Account{Balance: b}
        from.TransferTo(&to, amount)
        return from.Balance.Add(to.Balance).Equals(a.Add(b))
    }
    quick.Check(f, nil)
}
```

**自动生成几百个输入，验证性质永远成立。** 比手写 10 个用例更能发现边界问题。

**契约测试**：验证服务间约定

消费者驱动契约（Pact）：

```
消费者定义期望 → 生产者验证自己满足
```

比 E2E 快，比 mock 可靠（mock 可能和服务实际行为不一致）。

### 怎么写才算"有证据"

| 弱断言 | 强断言 |
| --- | --- |
| `assert.NoError(err)` | `assert.Equal(expectedBalance, actual)` |
| `assert.NotNil(result)` | `assert.Equal(3, len(items))` + 逐个检查内容 |
| 只测 happy path | 测边界、异常、并发 |
| mock 所有依赖 | 关键依赖用真实实现 |

**判断标准：如果这个测试失败了，说明什么？** 答"说明 mock 配置变了"→ 测试没价值。

### 不要为覆盖率写测试

反模式：

```go
func TestGetUser_NotFound(t *testing.T) {
    // 只为了覆盖 if err != nil 这一行
}
```

**覆盖率的正确用法**：

- 用来**发现未测试的代码**（哪些分支从来没跑过）
- 不用来**考核**（会催生无意义测试）

## 效果与代价

**收益**

- **bug 在上线前被抓**：测试针对真实风险，而不是刷数字
- **重构有信心**：高风险区有测试保护
- **测试维护成本可控**：不为低价值代码写测试

**代价**

- **需要判断风险**：这依赖对业务的理解，不是机械流程
- **集成测试慢**：真实数据库比 mock 慢 10-100 倍
- **属性测试需要设计性质**：想清楚"什么性质必须成立"比写用例难

## 从什么地方做

**第一步：列出系统的高风险区**

问："哪块代码出 bug 会造成资金损失/数据损坏/安全问题？" **这些必须先有测试。**

**第二步：检查现有测试的断言强度**

搜 `assert.NoError` 占比。**如果 80% 的测试只断言没报错，测试基本无效。**

**第三步：给高风险区补边界测试**

边界清单：0、负数、最大值、空、null、超长、并发、重复。

**第四步：把关键集成测试的 mock 换成真实组件**

至少数据库用真实的。**mock 掉的 SQL 是最常见的假成功。**

**第五步：用覆盖率找盲区，不看数字**

看"哪些分支没被覆盖"，判断这些分支是否高风险。**不要为了提高数字写测试。**

## 常见错误

**错误 1：追求 100% 覆盖率**

会催生大量无意义测试，且拖慢 CI。**80% 且有意义的测试 > 95% 的注水测试。**

**错误 2：mock 一切**

所有依赖都 mock → 测试通过但集成失败。**关键依赖用真实实现。**

**错误 3：只断言"没报错"**

覆盖了代码，没验证正确性。**断言具体的值和状态变化。**

**错误 4：测试之间有依赖**

测试 A 修改了数据库，测试 B 依赖 A 的结果 → 单独跑就失败。**每个测试要独立、可重复。**

**错误 5：不测并发**

单线程测试全绿，并发下数据竞争。**高风险区要有并发测试 + race detector。**

**错误 6：E2E 测试过多**

几百个 E2E 用例，跑一次 40 分钟，且经常因为环境问题假失败。**E2E 只覆盖最关键路径。**
