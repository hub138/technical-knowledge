# 部分失败决定分布式系统的设计

## 背景：那个"整体健康"却持续报错的服务

监控面板全绿：CPU 30%、内存 40%、错误率 0.1%。

但用户投诉找不到商品。排查发现：**商品服务正常，库存服务正常，但两者之间的网络链路有 5% 的丢包**——每个服务的健康检查都通过，组合起来却有 5% 的请求失败。

这是分布式系统的核心特征：**没有"整体成功或整体失败"，只有"一部分成功了，一部分没有"。** 单机程序里一个函数调用要么返回要么抛异常；跨网络后，出现了第三种状态——**不知道成功没有**。

监控看单点健康度，看不到这种状态。系统设计必须假设它会持续发生。

## 方案：为"不确定"设计，而不是为"成功/失败"设计

### 1. 三态思维取代两态

```
单机：  成功 | 失败
分布式：成功 | 失败 | 未知（超时）
```

**"未知"是最需要处理的**，因为：

- 请求可能没到（安全重试）
- 请求到了但响应丢了（重试会重复执行）
- 请求到了、执行了、响应还在路上（重试会重复执行）

处理未知的方式：**幂等键 + 主动查询**（见 [[后端技能/并发与一致性/幂等与重试让部分失败可恢复]]）。

### 2. 每个跨进程调用都要有：超时 + 重试 + 熔断

```go
client := &http.Client{
    Timeout: 2 * time.Second,   // 1. 必须有超时
}

resp, err := retry.Do(func() error {
    return callWithIdempotencyKey()  // 2. 幂等才能安全重试
}, retry.Attempts(3), retry.Backoff(...))
```

加**熔断**：连续失败 N 次后，直接拒绝请求一段时间，不再打下游。

| 机制 | 作用 | 不加的后果 |
| --- | --- | --- |
| 超时 | 限制单次等待 | 线程/连接被永久占用 |
| 重试 | 处理瞬时故障 | 抖动变成用户可见的失败 |
| 退避+抖动 | 避免重试风暴 | 一批请求同步重试，打垮下游 |
| 熔断 | 快速失败止损 | 雪崩：下游慢导致上游全部堆积 |
| 舱壁 | 隔离故障域 | 一个下游拖垮所有功能 |

**五个必须一起上**。只加超时，抖动会变成失败；只加重试，会打垮下游。

### 3. 状态必须能重建，不能只存在内存

部分失败的必然结果：**某个节点的内存状态丢了**。

所以关键状态要：

- **持久化到数据库**（带事务）
- **或可从事件重建**（事件溯源）
- **或可从副本恢复**（Raft/Paxos 复制）

**只存在单节点内存里的状态，在分布式系统里等于不存在。**

### 4. 用最终一致代替分布式事务

跨服务的强一致（2PC）代价极高且脆弱。实际做法：

**Saga 模式**：把长事务拆成一串本地事务，每步配一个补偿操作。

```
下单流程：
  1. 创建订单          (补偿：取消订单)
  2. 扣减库存          (补偿：回滚库存)
  3. 扣减余额          (补偿：退款)
  4. 通知发货          (补偿：取消发货)
```

任一步失败，反向执行已完成步骤的补偿。

**Outbox 模式**：保证"数据库变更"和"发消息"原子。

```
事务内：写业务表 + 写 outbox 表
事务提交后：后台任务读 outbox → 发消息 → 标记已发
```

这解决了"业务写成功但消息没发出去"的经典问题。

## 效果与代价

**收益**

- **故障不再级联**：熔断和舱壁把局部问题限制在局部
- **抖动可自愈**：超时 + 重试处理掉大部分瞬时故障
- **状态可靠**：持久化后节点重启不丢数据

**代价**

- **延迟增加**：重试会让 p99 显著变差（最坏是正常耗时的 N 倍）
- **复杂度上升**：每个调用都要考虑超时/重试/熔断，代码量翻倍
- **补偿逻辑难写**：Saga 的补偿操作要处理"补偿本身失败"的情况
- **最终一致的窗口**：用户可能短暂看到不一致的数据

## 从什么地方做

**第一步：找出所有跨进程调用，检查超时**

没有超时的调用是**定时炸弹**。先全部加上超时，这是投入产出最高的一步。

**第二步：区分"可重试"和"不可重试"**

列出所有下游调用，标注：这个操作幂等吗？不幂等的必须先改成幂等，再加自动重试。

**第三步：给每个下游配熔断**

用现成的库（resilience4j、go-breaker、Sentinel）。参数从保守开始：失败率 50%、窗口 10 秒、熔断 30 秒。

**第四步：把关键状态迁出内存**

检查：节点重启后，哪些状态会丢？逐项决定持久化方案。

**第五步：跨服务流程改成 Saga 或 Outbox**

不要用 2PC。从最关键的业务流程开始（通常是下单/支付），拆成补偿链。

## 常见错误

**错误 1：重试没有上限和退避**

一个请求重试 10 次，每次立即重试 → 下游被打垮。**必须：次数上限 + 指数退避 + 抖动。**

**错误 2：重试链叠加**

A→B→C→D，每层重试 3 次，最坏 27 次调用。**重试只在系统边界做一次。**

**错误 3：熔断后不恢复探测**

熔断器一直开着，下游恢复了也不知道。**必须有半开状态做试探。**

**错误 4：用超时时间做业务逻辑**

"如果 5 秒没返回就认为失败"——但对方可能第 6 秒成功了。**超时只用于保护资源，判定成功要靠查询。**

**错误 5：忽略"补偿失败"**

Saga 的补偿操作也可能失败（网络问题、对方服务挂了）。**补偿必须可重试，且有死信队列兜底人工处理。**
