# 限流与背压决定系统会不会被自己打垮

## 背景：一次重试引发的雪崩

一个服务常规 QPS 2000。某天依赖的 Redis 抖动了 800ms，然后：

```
1. 请求变慢，客户端超时重试
2. QPS 从 2000 涨到 6000（3 倍重试）
3. 服务端线程池打满，排队
4. 更多请求超时，更多重试 → QPS 涨到 15000
5. 服务彻底不可用，Redis 早已恢复但服务回不来
```

**Redis 恢复了，服务却没恢复。** 因为流量已经被重试放大到远超容量，系统进入了"死亡螺旋"。

这是**没有背压**的典型后果：系统无法告诉上游"我处理不了了"，只能硬扛，然后被压垮。

## 方案：在四个位置限流

### 1. 入口限流（Rate Limiting）

限制单位时间的请求数。三种常用算法：

| 算法 | 实现 | 特点 |
| --- | --- | --- |
| 固定窗口 | 每分钟重置计数 | 简单；窗口边界可能放过 2 倍流量 |
| 滑动窗口 | 按时间片加权 | 平滑；内存占用略高 |
| 令牌桶 | 按速率生成令牌 | **推荐**：允许突发，控制平均速率 |
| 漏桶 | 恒定速率出水 | 严格平滑；突发会被排队 |

**按什么维度限**：

```
全局      → 保护整个服务
按用户/IP → 防止单个用户刷接口（最常用）
按接口    → 保护重接口不影响轻接口
按租户    → 多租户系统必须做，防止互相影响
```

### 2. 并发限制（比 Rate Limiting 更关键）

**限 QPS 不如限并发。** 因为真正耗尽资源的是"同时在处理的请求数"，而不是"每秒来了多少"。

```go
sem := make(chan struct{}, 100)  // 最多 100 个并发

func handle(r Request) error {
    select {
    case sem <- struct{}{}:
        defer func() { <-sem }()
        return process(r)
    default:
        return ErrOverloaded  // 快速失败
    }
}
```

**为什么并发限制更有效**：如果下游变慢，请求持有时间变长，同样的 QPS 下并发数会暴涨。限 QPS 挡不住这个，限并发可以。

### 3. 队列长度限制（背压）

队列让突发流量被缓冲，但**队列必须有上限**：

```go
queue := make(chan Task, 1000)   // 有界队列

select {
case queue <- task:
default:
    return ErrQueueFull   // 队列满了就拒绝，不无限堆积
}
```

**无界队列是定时炸弹**：内存无限增长直到 OOM。有界队列 + 快速失败，让上游知道"满了"，这才是背压。

### 4. 自适应限流（最实用）

不看 QPS，看**系统自己的健康信号**：

- **延迟**：p99 超过阈值就开始丢流量
- **CPU/内存**：超过 80% 开始丢
- **队列等待时间**：排队超过 200ms 就拒绝

典型实现是 **CoDel 或 Google 的 SRE 自适应限流**：根据最近的延迟变化动态调整允许量。

**好处**：不需要预先知道系统容量。容量变了（扩容、代码变慢）自动适应。

### 5. 负载丢弃（Load Shedding）

实在扛不住时，**有选择地丢弃**：

| 优先级 | 处理 |
| --- | --- |
| 健康检查、核心交易 | 永远保留容量 |
| 普通读请求 | 过载时丢弃 |
| 批处理、报表、异步任务 | **最先丢弃** |

**关键：给重要流量预留配额。** 比如 80% 容量给核心接口，20% 给其他。

## 效果与代价

**收益**

- **避免死亡螺旋**：过载时快速失败而不是排队，系统能自愈
- **延迟可预测**：被拒绝的请求立刻返回，而不是等 30 秒超时
- **故障隔离**：一个接口被打爆不影响其他接口

**代价**

- **会拒绝合法请求**：限流必然有误杀。**参数调优是持续的活**
- **丢弃请求可能损失业务**：被拒的下单请求就是丢单。**要在业务上可接受的范围内限流**
- **分布式限流很难**：单机限流简单，但总量是 N 台机器之和。**需要 Redis 或专门的限流服务，引入新的依赖和延迟**

## 从什么地方做

**第一步：先加并发限制和超时**

这两个投入最小、效果最大。**每个对外的调用都要有超时，每个服务都要有最大并发数。**

**第二步：给最容易被刷的接口加用户级限流**

登录、短信、搜索、下单——这些是优先目标。用令牌桶，按用户 ID。

**第三步：把无界队列改成有界队列**

搜代码里的 `make(chan X)`（无缓冲）或无限增长的 slice。全部改成有界。

**第四步：加自适应保护**

监控 p99 延迟和队列等待时间，超过阈值时开始拒绝。**这比静态 QPS 阈值更能适应真实情况。**

**第五步：压测验证**

用 3 倍预期流量压测，确认：

- 系统不会崩，只是拒绝多余请求
- 被拒绝的请求返回明确错误（429/503），不是超时
- 流量降下来后能自动恢复

## 常见错误

**错误 1：只限 QPS 不限并发**

下游变慢时，同样的 QPS 下并发暴涨，资源照样耗尽。**并发限制才是保护资源的。**

**错误 2：无限队列**

`queue = append(queue, task)` 无上限——内存 OOM。**队列必须有界 + 满时快速失败。**

**错误 3：限流参数写死不调优**

上线时设 1000 QPS，一年后业务涨了 10 倍还是 1000。**定期 review，或直接用自适应限流。**

**错误 4：所有接口用同一个限流器**

一个重接口把配额用光，轻接口也被拒。**按接口或按重要性分组限流。**

**错误 5：拒绝时返回 500**

应该返回 **429（Too Many Requests）** 或 **503（Service Unavailable）**，并带上 `Retry-After`。返回 500 会让客户端以为是 bug，可能不重试或告警。

**错误 6：客户端不遵守退避**

服务端返回了 429，客户端立刻重试——限流白做。**客户端必须实现退避 + 抖动。**
