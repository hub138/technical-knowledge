# 技术方案要先写清约束和取舍

## 背景：评审会上吵了一小时，发现讨论的不是同一件事

一个方案评审：有人主张用 Kafka，有人坚持 RabbitMQ。争论了 40 分钟，各自举出对方方案的缺点。

最后有人问了一句："我们这个场景，峰值多少消息、能容忍多少延迟？"

答案是：**每秒 200 条，延迟 1 秒以内可接受。**

这个量级下，两者都绰绰有余——**争论的选项根本不是决定因素**。真正的约束（团队只有 3 个人、没人运维过 Kafka）反而没人提。

问题在于：**方案里没有写约束。** 没有约束，"哪个更好"就没有答案。

## 方案：方案文档必须有五个部分

### 1. 背景与问题

用具体症状开头，不要用抽象描述。

- 差："当前系统性能不足，需要优化。"
- 好："订单查询接口 p99 = 1.8s，超过 SLO 的 500ms。过去一周告警 23 次，日均影响 400 个用户。"

**为什么重要**：后面所有决策都要回到这个问题。问题描述含糊，方案就没法验证有没有解决。

### 2. 约束（最容易被跳过，但最关键）

约束分四类，必须量化：

| 类型 | 例子 |
| --- | --- |
| 规模 | 峰值 QPS 5000，日增数据 200GB |
| 延迟/SLO | p99 < 500ms，可用性 99.9% |
| 资源 | 3 人团队，预算 2000 元/月，无专职运维 |
| 兼容 | 不能停机迁移，需支持旧客户端 6 个月 |

**"我们团队没有 Kafka 运维经验"是合法且重要的约束。** 不写下来，方案就会选一个团队驾驭不了的东西。

### 3. 方案（含被否决的选项）

不要只写最终选择。写清楚**考虑过哪些、为什么不选**：

```markdown
### 选项 A：Kafka
- 优点：吞吐高、生态成熟
- 否决原因：需要专职运维，团队无经验；当前量级用不上
- 若规模涨到 5 万 QPS 可重新评估

### 选项 B：RabbitMQ
- 优点：运维简单，团队有经验
- 否决原因：当前消息量下功能过剩，且引入了新的组件

### 选定：Postgres LISTEN/NOTIFY + outbox
- 理由：当前 200 QPS 量级足够；复用已有数据库，零新增组件
- 已知限制：超过 5000 QPS 时需要迁移
```

**"为什么没选 X"是文档里最有价值的部分**——半年后有人问"为什么不用 Kafka"，答案就在这。

### 4. 取舍与代价

明确写出这个方案**放弃了什么**：

```markdown
选择 LISTEN/NOTIFY 的代价：
- 吞吐上限约 5000 QPS（Kafka 可到百万）
- 消息不持久化，消费者离线期间的事件会丢
- 无法跨数据库实例

这些在当前的 200 QPS 和"可容忍丢事件"的前提下可接受。
```

**没有代价的方案是不存在的。** 写不出代价，说明还没想清楚。

### 5. 验证方式

怎么知道方案生效了：

- **上线前**：压测目标（p99 < 500ms @ 5000 QPS）
- **上线后**：监控指标（错误率、延迟、积压）
- **回滚条件**：什么情况下回滚，怎么回

## 效果与代价

**收益**

- **评审聚焦**：有了量化的约束，争论从"哪个技术好"变成"哪个满足约束"
- **决策可追溯**：半年后能理解当时的取舍，而不是"不知道为什么这么设计"
- **减少返工**：写约束的过程本身就会暴露被忽略的前提

**代价**

- **写文档要时间**：一个完整方案 2-4 小时
- **约束可能写错**：基于错误约束做的决策，文档写得多清楚也没用。**约束需要和业务方确认**
- **小改动不需要**：改一个接口不用写方案。**判断标准：这个决策的影响超过 1 个月吗？**

## 从什么地方做

**第一步：先写"约束"和"问题"，再想方案**

顺序很重要。先想方案的话，会不自觉地选择熟悉的工具，然后倒推理由。**先量化约束，让约束来筛选项。**

**第二步：把约束发给相关方确认**

特别是规模和 SLO。"我们预期峰值多少"这个问题，不同人的答案经常差一个数量级。

**第三步：至少写两个被否决的选项**

只写一个方案，看起来像"通知"而不是"方案"。**列出的选项越多，说明考虑得越充分。**

**第四步：明确写出成本和运维负担**

很多方案的隐性成本是运维。**"需要 7×24 值守"这种代价必须写出来**，否则审批的人不知道自己在批准什么。

**第五步：定回滚条件**

上线前就想好：什么情况下回滚？回滚需要多久？**没有回滚方案的方案不能上线。**

## 常见错误

**错误 1：方案里只有"选什么"，没有"为什么"**

"我们决定用 Redis 做缓存"——为什么不用本地缓存？为什么不用数据库自带的？没写就等于没决策。

**错误 2：约束写得含糊**

"需要高性能"不是约束。"p99 < 100ms" 才是。含糊的约束无法验证，也无法筛选方案。

**错误 3：隐藏代价**

只写优点，不写"需要额外维护一个集群"。审批的人会以为没成本。**代价必须显式。**

**错误 4：没有"什么情况下重新评估"**

技术选型有前提条件。写清楚"如果 QPS 涨到 X，需要重新评估"，让后人知道边界在哪。

**错误 5：把方案文档写成教程**

大段粘贴 Kafka 的架构介绍——评审的人不需要。**只写和决策相关的部分。**
