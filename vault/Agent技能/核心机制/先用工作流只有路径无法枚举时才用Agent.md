# 先用工作流，只有路径无法预先枚举时才用 Agent

## 背景：能写死在代码里的流程，却交给了模型

一个"客户邮件自动分类处理"系统用 Agent 实现：

```
1. 读邮件
2. 模型判断：这是投诉/咨询/退款？
3. 模型决定：调用哪个工具？
4. 模型执行
```

实测准确率 87%，每封邮件平均 4.2 次模型调用，**成本 0.03 美元/封**。

后来改成工作流：

```
1. 读邮件
2. 一次模型调用：分类（输出枚举，结构化）
3. switch(分类):
     投诉 → 走投诉流程（代码）
     咨询 → 走咨询流程（代码）
     退款 → 走退款流程（代码）
```

准确率 **96%**，每封 1 次模型调用，成本 **0.006 美元/封**——**准确率更高，成本只有 1/5**。

**差别在于：分类之后该做什么，是确定的。既然确定，就该用代码写死，不该让模型在运行时决定。**

## 方案：按"路径能否枚举"来选

### 判断标准

问一个问题：**这个任务的下一步有几种可能？能列出来吗？**

| 情况 | 做法 |
| --- | --- |
| 能枚举（≤10 种） | **工作流**：代码写死分支，模型只做单点判断 |
| 不能枚举 | **Agent**：让模型在运行时决定 |
| 大部分能枚举，少数例外 | **混合**：工作流主干 + 兜底交给 Agent |

### 工作流：把确定性留在代码里

典型结构：

```
输入 → [模型调用1：分类] → 路由 → [模型调用2：提取] → 业务代码 → 输出
```

模型只在需要语义判断的点出现，**流程控制全在代码里**。

**什么时候用模型调用**：

- 分类（输出是枚举）
- 信息提取（输出是结构化字段）
- 生成文本（摘要、回复草稿）
- 语义匹配

**什么时候用代码**：

- 路由和分支
- 校验和约束
- 外部系统调用
- 状态管理

### Agent：只在真的需要时

真正的 Agent 场景长这样：

```
修一个 bug：
  第 1 步看什么？取决于代码结构
  第 2 步看什么？取决于第 1 步发现什么
  ...
  第 N 步？现在才知道
```

**下一步依赖上一步的结果，且可能路径无法预先列出** —— 这才是 Agent 的适用区。

### 混合模式：最常见也最实用

```
                    ┌─ 已知类型 → 代码流程
输入 → 模型分类 ────┤
                    └─ 其他/未知 → 交给 Agent 处理
```

比如客服工单：80% 是已知的 5 类，走代码流程；剩下 20% 交给 Agent。

**这样既拿到了工作流的确定性，又保留了处理长尾的能力。**

## 效果与代价

**收益**

- **准确率更高**：模型只做它擅长的事（单点判断），不让它做它不擅长的事（流程控制）
- **成本大幅下降**：调用次数从 N 次降到 1-2 次
- **延迟更低、可预测**：没有不确定步数的循环
- **可测试**：每个分支都能单独测，Agent 的循环很难测

**代价**

- **需要预先分析流程**：要把"有哪些情况"想清楚，这本身是工作量
- **长尾覆盖不足**：枚举不全的情况会走到兜底，体验可能不好
- **流程变了要改代码**：业务需求变化时，工作流的维护成本比改提示词高

## 从什么地方做

**第一步：先手工跑 20 个真实案例，记录实际路径**

不要凭空设计。找 20 个真实输入，人工处理一遍，**记录每一步做了什么**。

**第二步：看这些路径能不能归类**

如果 20 个案例里有 16 个走的是 3 条固定路径 → 工作流 + 兜底。
如果 20 个案例路径各不相同 → 真的需要 Agent。

**第三步：把模型的输出约束成枚举或结构**

分类任务用 enum，提取任务用 JSON schema。**不要让模型输出自由文本再解析。**

**第四步：代码里做路由，模型只做判断**

```python
category = llm.classify(email, output=Enum["投诉","咨询","退款","其他"])
if category == "其他":
    return agent.handle(email)     # 长尾交给 Agent
return workflows[category].run(email)
```

**第五步：监控"兜底率"**

如果兜底率超过 30%，说明枚举不全，该把高频的长尾也纳入工作流。

## 常见错误

**错误 1：不管什么都用 Agent**

"我们要做 AI 产品，当然要用 Agent"。**Agent 是手段不是目的。** 能写死就用代码，代码是确定性的、免费的、可测的。

**错误 2：用 Agent 做格式转换**

"把这段文本转成 JSON"——这是确定性的，用代码或结构化输出就够了，不需要 20 步的循环。

**错误 3：工作流里每一步都调模型**

提取 5 个字段调 5 次模型。**一次调用输出 5 个字段的 JSON** 就行。

**错误 4：分类输出自由文本**

模型输出"这像是一个投诉"，然后代码 `if "投诉" in text`——脆弱。**用枚举约束输出。**

**错误 5：没有兜底**

工作流枚举了 5 类，第 6 类来了直接失败。**必须有 default 分支：要么交给 Agent，要么转人工。**
