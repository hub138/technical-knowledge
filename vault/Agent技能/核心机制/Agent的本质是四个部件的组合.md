# Agent 的本质是模型、工具、状态与控制流的组合

## 背景：把 Agent 想成"会自己想"的东西，会做错所有设计

一个团队把"AI 助手"接进系统，让它自主完成"排查线上问题并修复"。上线后发现：

- 它有时会重复执行已经做过的步骤，浪费大量 token
- 长任务跑到一半崩了，重启后**从头再来**，之前的工作全丢
- 它报告"已修复并验证"，但没人能确认这句话有没有对应真实执行

这些都不是模型能力问题，是**把 Agent 当成了一个整体**，而不是四个可以分别设计的部分。

## 方案：拆成四个部件

```
┌─────────────────────────────────────────┐
│  控制流 Control Flow                     │  ← 谁决定下一步
│  (循环 / 状态机 / 图 / 人在环路)           │
├─────────────────────────────────────────┤
│  状态 State                              │  ← 记住什么
│  (消息历史 / 工作记忆 / 持久化的任务状态)   │
├─────────────────────────────────────────┤
│  工具 Tools                              │  ← 能做什么
│  (读文件 / 执行命令 / 检索 / 调 API)       │
├─────────────────────────────────────────┤
│  模型 Model                              │  ← 负责判断
│  (理解上下文、选择工具、解释结果)          │
└─────────────────────────────────────────┘
```

**模型只是其中一个部件**。它的作用是"在给定上下文下判断下一步该做什么"——**它不负责记住、不负责执行、不负责决定整体流程**。

这个拆法的实际价值：上面那三个问题分别对应状态、控制流、执行证据的缺失，**没有一个是靠"换个更强的模型"能解决的**。

### 1. 模型：只做语义判断

模型擅长的是**开放语义判断**：

- 这个报错说明什么？是代码问题、依赖问题还是权限问题？
- 接下来该看哪个文件？
- 这批证据最支持哪个假设？

模型不擅长、也不该负责：记住 20 步之前发生了什么（靠状态）、保证命令真的执行了（靠执行器）、判断重试到第几次该放弃（靠控制流）。

### 2. 工具：能力的边界就是 Agent 的边界

工具定义决定了 Agent 能做什么。关键设计：

- **工具描述就是提示词**：模型通过 description 决定用不用。写得含糊，模型就不会用或乱用
- **参数要 schema 化**：让模型输出结构化参数，而不是自由文本命令
- **返回值要可读且可截断**：几万行的日志直接塞回上下文会爆窗口，要返回引用 + 摘要

### 3. 状态：什么该记、记多久

三种状态，混淆会造成大问题：

| 类型 | 内容 | 存哪 |
| --- | --- | --- |
| 会话消息 | 完整的对话历史（含工具调用和结果） | 内存/数据库，按 session |
| 工作记忆 | 当前任务的关键事实（已确认的、已排除的） | 结构化存储，可压缩 |
| 长期记忆 | 跨任务的用户偏好、项目知识 | 向量库/知识库，按需检索 |

**不要把执行事实只存在消息历史里**——消息会被压缩、截断、丢失。真实执行记录（命令、退出码、产物）必须独立持久化。

### 4. 控制流：谁决定下一步

从简单到复杂：

```text
单步：      提问 → 模型回答（无工具）
ReAct 循环：思考 → 选工具 → 观察 → 再思考 → ... → 结束
计划-执行： 先生成完整计划 → 逐步执行 → 按结果调整
状态机/图： 显式建模节点和迁移条件，支持回退和人工介入
并行/多体： 多个 Agent 分工，共享状态或互相通信
```

**默认的 ReAct 循环没有终止保证**：可能陷入"反复尝试同一件事"的死循环。所以必须有：

- 步数上限
- token/成本预算
- 重复动作检测
- 人工接管点

## 效果与代价

**收益**

- **问题可定位**：Agent 表现不好时，能判断是模型判断错、工具描述不清、状态丢了还是控制流没兜住
- **可逐步改进**：换更强的模型、加更好的工具描述、改控制流，可以独立进行
- **可靠性能工程化**：状态持久化和控制流约束，是"能跑 demo"和"能上生产"的分界线

**代价**

- **工程量比想象中大**：模型 API 调用可能只占代码的 20%，剩下 80% 是状态管理、错误处理、重试、预算控制
- **复杂度上升**：四个部件都要设计，比直接调 API 复杂得多
- **调试要分层**：要能分别看到"模型当时看到了什么""工具返回了什么""状态是什么"

## 从什么地方做

**第一步：先用最简单的控制流**

不要一上来做多智能体。先用 ReAct 循环跑通，观察它实际在哪里失败。大多数"需要复杂架构"的判断，来自于没有先跑起来看。

**第二步：把工具描述当成产品文案来写**

工具的 `description` 是直接给模型看的。写清楚：什么时候该用、什么时候不该用、返回什么。这是**投入产出比最高**的优化点。

**第三步：尽早加步数和预算上限**

在 demo 阶段就加。否则长任务会烧掉大量 token 才失败。

**第四步：把状态持久化做在前面**

不要等"以后再说"。任务中断后能否恢复，决定了这个 Agent 能否用在真实工作里。

**第五步：记录完整轨迹**

每一步的：输入上下文、模型输出、工具调用、工具返回、耗时、token。没有轨迹就无法诊断问题，也无法做评测。

## 常见错误

**错误 1：把所有东西塞进提示词**

把整个代码库、所有文档、全部历史都塞进上下文。**结果不是变聪明，是变笨**——注意力被稀释，成本还暴涨。正确做法是检索 + 按需注入。

**错误 2：让模型自己维护"已完成"状态**

模型说"我已经修改了 3 个文件"——这句话可能错。完成情况必须由系统根据工具调用记录判定。

**错误 3：没有幂等就重试**

Agent 重试一步操作，结果重复创建了资源、重复发送了通知。**重试必须配合幂等键。**

**错误 4：把控制流完全交给模型**

让模型自己决定"要不要继续"，等于没有终止保证。循环终止条件应该是代码里的硬约束。
