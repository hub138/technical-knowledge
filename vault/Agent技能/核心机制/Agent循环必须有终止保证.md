# Agent 循环必须有终止保证

## 背景：那个跑了 4 小时、烧了 80 美元的 Agent

一个自动修 bug 的 Agent 接到任务："修复 CI 里失败的测试"。

它的执行轨迹：

```
第 1 次：运行测试 → 失败，报错是缺依赖
第 2 次：装依赖 → 还是有错
第 3 次：改 build 文件 → 装依赖失败
第 4 次：回滚 build 文件，装依赖 → 又失败
第 5 次：改 build 文件 ...        ← 开始循环
...
第 147 次：还在改同一个文件
```

4 小时后被人工发现时，已经烧掉 80 美元，改了 40 多次代码，**而根本原因是 CI 环境的网络无法访问那个依赖源**——一个它永远解决不了的问题。

**ReAct 循环没有内在的终止保证。** 模型总是在"下一步还能做什么"，于是它会一直做下去。终止条件必须由**代码**提供，不能交给模型判断。

## 方案：四层终止约束

### 第 1 层：硬上限

最简单也最必须：

```go
const (
    MaxSteps    = 50
    MaxTokens   = 200_000
    MaxCost     = 2.00   // 美元
    MaxDuration = 10 * time.Minute
)
```

任何一个超限就停止，**并明确报告是哪一条触发**（这决定了后续怎么调参）。

### 第 2 层：重复检测

比硬上限更早发现问题。三种检测：

**完全相同动作**：连续两次调用同一个工具、同样的参数。

```go
if lastAction == currentAction {
    repeats++
    if repeats >= 2 { return ErrLoopDetected }
}
```

**语义相同**：参数略有不同但意图相同（`pattern="TODO"` 然后 `pattern="todo"`）。用规范化后的参数比较，或让模型自己判断"这和上次是不是在做同一件事"。

**状态无进展**：连续 N 步，系统的关键状态没变化（文件没改、测试结果没变、错误信息没变）。**这是最强的信号**——它说明 Agent 在原地打转。

### 第 3 层：进展检测

定义一个"任务进展"的判据，每步检查：

| 任务类型 | 进展信号 |
| --- | --- |
| 修 bug | 报错信息变了 / 失败测试数减少 |
| 写代码 | 文件被修改 / 测试通过数增加 |
| 调研 | 新信息被加入状态 |

**连续 K 步没有进展就停止**。比"重复动作"更宽松，能抓住"换着花样做无效尝试"的情况。

### 第 4 层：不可解检测

有些问题 Agent 永远解决不了（环境缺依赖、权限不足、外部服务挂了）。特征是：**重复出现同一个外部阻塞，且重试无法改变它**。

处理方式：识别出这类错误后**立即停止并升级**，而不是继续重试。

```go
var unrecoverable = []string{
    "connection refused",
    "permission denied",
    "no such host",
    "disk quota exceeded",
}
```

## 效果与代价

**收益**

- 成本可控：最坏情况有明确上限，不会无限烧钱
- 快速失败：原地打转的任务在 5 分钟内被发现，而不是 4 小时
- 可诊断：报告"因检测到 3 次无进展而停止"比"跑了很久被人工杀掉"有用得多

**代价**

- **可能过早停止**：复杂任务可能真的需要 60 步，硬上限设成 50 就切断了。需要按任务类型调参
- **重复检测可能误判**：合法的重试（比如等资源就绪）看起来像重复。**要在检测里区分"重试"和"打转"**——关键是状态有没有实质变化
- **增加实现复杂度**：状态规范化、进展判据都要针对具体任务设计

## 从什么地方做

**第一步：先加硬上限，立刻**

不需要任何设计，10 行代码。**这一步能挡住 80% 的失控场景。** 从 50 步 / 10 分钟开始。

**第二步：记录每一步的动作指纹**

```json
{ "step": 7, "tool": "edit_file", "args_hash": "a3f2...", "state_hash": "8b1c..." }
```

`args_hash` 用于检测重复动作，`state_hash` 用于检测无进展。

**第三步：定义你任务的状态指纹**

- 修 bug：`hash(失败测试列表 + 报错摘要)`
- 写代码：`hash(已修改文件 + 测试结果)`
- 调研：`hash(已收集信息的 key 列表)`

**第四步：分级处理超限**

- **无进展但没到硬上限** → 换个策略（比如强制它先写分析再动手），或者升级给人工
- **重复同一动作** → 直接停，报告卡在哪
- **命中不可解错误** → 立即停，报告需要什么外部条件

**第五步：把停止原因写进报告**

`"停止原因：连续 3 步修改 BUILD 文件但依赖安装始终失败。建议：检查 CI 环境的网络出站规则。"` —— 人拿到这个就能接手。

## 常见错误

**错误 1：只靠模型自己判断该停**

提示词里写"如果无法解决就停止"——模型在陷入循环时**恰恰是判断力最差的时候**，它那时认为自己"正在解决"。终止必须由代码保证。

**错误 2：上限设得过大**

`MaxSteps = 1000` 等于没有上限。这个数字应该根据"正常任务需要多少步"来定，通常是 P95 的 2-3 倍。

**错误 3：检测到时直接抛异常**

抛异常会让中间状态丢失，无法诊断。**应该优雅停止，保留完整轨迹**，然后报告。

**错误 4：把"重试一次"和"陷入循环"混为一谈**

网络抖动重试是合理的。区分方法：**重试后状态是否改变**。改变了就是有效重试，没改变就是打转。
