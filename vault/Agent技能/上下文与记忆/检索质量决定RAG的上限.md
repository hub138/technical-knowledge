# 检索质量决定 RAG 的上限

## 背景：答案对了，但引用的是错的文档

一个内部知识问答 Agent，回答准确率看起来有 80%。但抽查发现：

- 很多回答"碰巧正确"（模型用自身知识答对了），**但引用的文档根本不包含答案**
- 一旦遇到模型不知道的内部信息（比如公司特定流程），准确率掉到 **35%**

**检索召回不到正确文档时，再强的模型也答不对。** 而外部知识问答恰恰是模型自身知识最少、最需要检索的场景。

RAG 的瓶颈从来不是生成，是检索。**优化提示词和换模型，都不如提升召回率有效。**

## 方案：先测召回，再谈生成

### 第一步：单独评估检索，不要只看最终答案

建一个评测集：**100 个问题 + 每个问题对应的正确文档**。

```yaml
- question: "报销流程需要几个人审批？"
  relevant_docs: ["docs/finance/报销制度.md"]
- question: "如何申请生产环境权限？"
  relevant_docs: ["docs/ops/权限申请.md", "docs/ops/生产变更.md"]
```

然后测：

| 指标 | 含义 | 目标 |
| --- | --- | --- |
| Recall@5 | 前 5 条里含有正确文档的比例 | **>85%**（最关键） |
| MRR | 正确文档的平均排名位置 | >0.7 |
| Precision@5 | 前 5 条里相关文档的比例 | >40% |

**Recall 是上限**：如果 Recall@5 只有 60%，那最终准确率不可能超过 60%，无论怎么调提示词。

### 第二步：按问题类型选检索方式

| 查询类型 | 例子 | 最好用的检索 |
| --- | --- | --- |
| 精确词/ID/报错 | `"ORA-01555"`、`getUserById` | **关键词（BM25）** |
| 概念/描述 | "怎么处理并发冲突" | **向量** |
| 混合 | "订单服务的重试策略" | **混合 + 融合** |

**单用向量检索是最常见的错误。** 向量擅长语义，不擅长精确匹配；而代码、ID、报错几乎都是精确匹配。

### 第三步：分块策略比模型选择影响更大

分块错了，什么都检索不到。

| 策略 | 适用 | 问题 |
| --- | --- | --- |
| 固定长度（512 token） | 通用文档 | 会切断语义单元 |
| **按结构分块** | Markdown/代码（按标题、函数） | **推荐**：保留完整语义 |
| 语义分块 | 无结构长文本 | 需要额外模型调用 |
| 小块 + 上下文扩展 | 需要精确匹配又要上下文 | 实现稍复杂 |

**按文档结构分块**（Markdown 按 `##`、代码按函数/类）通常比固定长度好得多——因为语义单元是完整的。

**关键技巧：给每个块加上下文前缀。**

```
原块："重试次数默认 3 次"
加前缀后："[订单服务 > 配置参考 > 重试] 重试次数默认 3 次"
```

这个前缀让块在脱离原文时仍然可检索。**实测能显著降低召回失败率。**

### 第四步：用重排提升精度

两阶段：

```
1. 粗召回（快、全）：向量 + 关键词，取 50-100 条
2. 精排（慢、准）：cross-encoder 重排，取 Top 5
```

重排把 Recall@5 提升 10-20 个百分点是常见的。

代价：多一次模型调用，延迟增加 100-300ms。**只在单路召回确实不够时才加。**

### 第五步：让模型学会说"不知道"

检索到的文档里没有答案时，模型倾向于**编一个**。

明确在提示词里约束：

```
只使用提供的文档回答。
如果文档中没有答案，直接说"文档中没有找到相关信息"，并说明检索了哪些内容。
不要根据常识推测。
```

**"不知道"比编造有价值得多**——在知识问答场景下尤其如此。

## 效果与代价

**收益**

- **准确率提升可测量**：Recall@5 从 60% 提到 90%，最终准确率会跟着涨
- **优化有方向**：知道是召回问题还是生成问题，不用瞎调提示词
- **成本可控**：检索优化通常比换大模型便宜

**代价**

- **需要建评测集**：100 条问题 + 标注，这是实打实的工作量，且需要领域知识
- **分块和索引需要调优**：不同文档类型最优策略不同
- **混合检索增加复杂度**：两路召回 + 融合逻辑 + 可能的重排模型
- **文档质量是硬约束**：文档本身写得差、过时、自相矛盾，检索再好也白搭

## 从什么地方做

**第一步：先建 30 条评测集**

不用 100 条，30 条真实问题就够看出问题。**这是所有优化的前提。**

**第二步：测 Recall，看是召回问题还是生成问题**

如果正确答案的文档在召回里 → 是生成问题，调提示词。
如果不在 → 是召回问题，**调提示词没用**。

**第三步：检查分块**

打印几个被检索到的块，看是否语义完整。**被截断的块是最常见的召回失败原因。**

**第四步：加关键词检索**

如果现在只有向量检索，加 BM25 做混合。**这一步通常见效最快。**

**第五步：给块加上下文前缀**

用文档标题路径作为前缀。改动小、效果好。

## 常见错误

**错误 1：只优化提示词，不测召回**

调了两天提示词，准确率没变——因为正确答案是召回不到的。**先测 Recall。**

**错误 2：只用向量检索**

搜 `ERROR_CODE_5042` 用向量，返回一堆语义相近但完全无关的文档。**精确匹配必须用关键词。**

**错误 3：分块切断了语义**

一个函数的定义被切成两半，两半都检索不到完整信息。**按结构分块。**

**错误 4：不处理"检索不到"的情况**

强行让模型回答，结果编造。**必须允许说不知道。**

**错误 5：忽略文档本身的质量**

文档过时、重复、矛盾。**清洗文档比优化检索更有效**，只是不那么"技术"。

**错误 6：把整个知识库都向量化**

几千篇文档全量索引，检索噪声大。**按领域分组，检索时限定范围。**
