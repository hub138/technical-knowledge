# 记忆要分层，不能让模型自己总结

## 背景：跑了 3 小时的任务，重启后从零开始

一个长任务 Agent 执行到第 60 步时进程崩了。重启后：

- 它**不知道已经改过哪些文件**，于是重复修改
- 它**不记得已经排除的方案**，于是又试了一遍
- 之前 55 步的工作全部作废

更糟的是另一类问题：它**记得错误的东西**。

它在第 20 步说"我已经修复了依赖问题"，但实际没有。这个错误结论进入了"记忆"，之后 40 步都在这个错误前提上推进。

**两个问题的根源相同：把"模型说的话"当成了记忆。**

## 方案：三种记忆，来源和可信度都不同

### 1. 会话消息 —— 原始记录，最可信

完整的对话历史，包括工具调用和返回。

- **来源**：系统记录
- **可信度**：高（是实际发生的）
- **问题**：会膨胀，必须压缩

压缩的正确做法：**保留结构，丢弃细节。**

```
保留：完成了什么、排除了什么、当前目标、关键约束
丢弃：具体的搜索过程、失败的尝试细节（除非失败原因重要）
```

**压缩必须由代码做，不能只让模型总结。** 模型总结会丢关键信息，也可能加入没有的内容。

### 2. 工作记忆 —— 结构化状态，用于恢复

这是长任务能恢复的关键。独立于对话历史，结构化存储：

```json
{
  "task_id": "t_8821",
  "goal": "修复 CI 中失败的集成测试",
  "completed": [
    {"step": "定位失败测试", "evidence": "artifact://logs/1", "at_step": 12},
    {"step": "确认是依赖版本冲突", "evidence": "artifact://logs/3", "at_step": 34}
  ],
  "excluded": [
    {"hypothesis": "网络问题", "reason": "本地能重现", "at_step": 20}
  ],
  "modified_files": ["pom.xml", "src/test/IT.java"],
  "constraints": ["不能改测试断言", "不能升级主版本"],
  "current_hypothesis": "需要显式指定 transitive 依赖版本"
}
```

**关键：每条"完成"都要有 evidence 引用。** 没有证据的"完成"标记为"待验证"，不能作为后续推理的前提。

### 3. 长期记忆 —— 跨任务，需要检索而非全量注入

| 类型 | 例子 | 存哪 | 怎么用 |
| --- | --- | --- | --- |
| 用户偏好 | 注释用中文、喜欢 pnpm | 配置 | 每次注入 |
| 项目约定 | 构建命令、目录结构 | 仓库里的 `AGENTS.md` | **按需读取** |
| 经验教训 | 上次踩的坑 | 向量库 | 语义检索 |

**项目约定放在仓库里**（`CLAUDE.md` / `AGENTS.md`）比放在外部记忆系统可靠得多：能被版本控制、被 review、被团队共享。

## 效果与代价

**收益**

- **可恢复**：进程崩溃后从工作记忆恢复，不用重跑
- **不重复**：明确记录"已排除的方案"，避免反复尝试
- **可追溯**：每条结论指向证据，能判断可信度

**代价**

- **需要设计 schema**：工作记忆的结构要针对任务类型设计，不是通用的
- **写入时机难定**：什么时候更新工作记忆？每步都写开销大，写少了会丢信息
- **长期记忆会过期**：项目结构变了，记忆里的信息就错了。**必须有失效机制**

## 从什么地方做

**第一步：先把工作记忆做出来**

这是投入产出最高的。定义你的任务需要记住什么：

- 修 bug：已定位的原因、已排除的假设、改过的文件
- 写代码：已实现的接口、待实现的、测试状态
- 调研：已收集的信息、待查的、结论

**第二步：每个"完成"必须绑证据**

```go
type Fact struct {
    Claim    string
    Evidence []string   // artifact 引用或 tool_call_id
    Verified bool       // 证据是否被独立确认
}
```

**没有 evidence 的 Fact 不能作为推理前提。** 这一条能拦住大部分"基于错误前提推进"的问题。

**第三步：在关键节点写盘，不是每步**

- 完成一个子目标时
- 做出重要排除时
- 即将执行不可逆操作前

**不要每步都写**——开销大且噪声多。

**第四步：恢复时注入工作记忆，不注入全部历史**

重启后，prompt 结构：

```
[系统提示]
[任务目标]
[工作记忆：已完成 / 已排除 / 约束]
[最近 N 轮对话]
[当前状态]
```

**早期的对话历史不注入**，因为关键信息已经在工作记忆里了。

**第五步：给长期记忆加失效机制**

- 每条记忆带 `updated_at`
- 定期（或每次使用时）验证是否仍然成立
- 项目结构类记忆绑定 commit/revision，版本变了就重新读取

## 常见错误

**错误 1：让模型自己总结历史**

模型总结会丢信息、可能加入没有的内容。**代码负责压缩结构，模型只负责生成摘要文本。**

**错误 2：把"模型说完成了"记成"完成了"**

必须有工具调用的证据。**模型的自述是 claim，不是 fact。**

**错误 3：工作记忆和对话历史不一致**

恢复时注入了工作记忆，但对话历史里还有旧的结论。**两者必须有一个是权威的**——让工作记忆权威，对话历史只作参考。

**错误 4：长期记忆只增不减**

用了一年的记忆里有一半过时了，检索出来反而误导。**必须有 TTL 或定期清理。**

**错误 5：把敏感信息写进记忆**

用户数据、凭据、内部地址。**记忆存储也要做脱敏和权限控制。**
