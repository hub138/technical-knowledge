# 上下文工程决定模型能看到什么

## 背景：把整个仓库塞进去，它反而变笨了

一个代码 Agent 的上下文里塞了：系统提示、20 个工具定义、完整的 50 个相关文件、全部历史对话。结果：

- 响应变慢，成本暴涨（每次调用 10 万 token）
- 它开始**忽略中间部分的内容**——放在上下文中段的指令经常被漏掉
- 明明给过关键信息，它还是会问"这个项目的构建命令是什么"

这是 **context rot（上下文退化）**：上下文不是越大越好。注意力是有限资源，塞得越多，每条信息分到的注意力越少。**这和"给一个人 500 页资料让他找一句话"是同一个问题。**

## 方案：把上下文当成稀缺资源来管理

核心原则：**每一条进入上下文的内容，都要能回答"模型现在做决定需要它吗？"**

### 1. 分层：什么必须常驻，什么按需取

| 层级 | 内容 | 策略 |
| --- | --- | --- |
| 常驻 | 系统提示、当前任务目标、关键约束 | 始终在，但要精简到必需 |
| 按需检索 | 代码文件、文档、历史记录 | 用检索（grep/向量/符号索引）取，不用就别放 |
| 引用 | 大文件、完整日志、长报告 | 只放引用 + 摘要，需要时再展开 |
| 压缩 | 早期的对话轮次 | 用摘要替换原文 |

### 2. 检索：用什么把相关内容取出来

| 方式 | 适用 | 弱点 |
| --- | --- | --- |
| 关键词 / 正则（grep） | 知道确切符号、报错信息、ID | 同义词、语义概念搜不到 |
| 向量相似度 | 概念性、描述性查询 | 精确匹配差；需要分块和 embedding |
| 符号索引（AST / LSP） | 代码：定义、引用、类型 | 只适用于结构化代码 |
| 结构化查询 | 有明确元数据（时间、作者、状态） | 需要先有结构化数据 |

**代码场景优先用符号索引 + grep，而不是向量库。** 代码有精确结构，用语义搜索反而模糊。这是我反复看到有效和无效的差别所在。

**混合检索**：多路召回（关键词 + 向量）后融合（RRF）或重排（cross-encoder），比单路召回明显更全。代价是延迟和复杂度——**只在单路召回确实不够时才上**。

### 3. 压缩：历史对话怎么办

长任务的对话历史会迅速膨胀。三种处理：

- **滑动窗口**：只保留最近 N 轮。简单，但会丢掉早期的关键决策
- **摘要压缩**：把早期对话压缩成一段结构化摘要（已完成/已排除/当前目标）。**推荐**，因为保留了决策
- **结构化状态外置**：把关键信息（已改的文件、已确认的事实）提取到结构化字段，对话历史只留最近的

**不要用"模型自己总结"当唯一真相**——摘要可能丢信息或产生幻觉。关键事实必须有结构化存储。

### 4. 记忆：跨任务记住什么

| 类型 | 例子 | 存哪 | 怎么取 |
| --- | --- | --- | --- |
| 用户偏好 | 喜欢用 pnpm、注释用中文 | 配置文件 / 数据库 | 每次注入 |
| 项目知识 | 构建命令、目录约定 | 项目文档 / `AGENTS.md` | 按需检索 |
| 任务经验 | 上次踩过的坑 | 向量库 | 语义检索 |

**项目约定的最佳实践是放在仓库里的 `CLAUDE.md` / `AGENTS.md`**——它能被版本控制、被团队共享、被 review，比存在某个 SaaS 的记忆里可靠得多。

## 效果与代价

**收益**

- **成本可降一个量级**：精准检索后，单次调用从 10 万 token 降到 5 千是常见的
- **准确率提升**：相关信息密度高，模型更容易抓住重点
- **能做长任务**：配合压缩和状态外置，任务长度不再受上下文窗口硬限制

**代价**

- **检索本身会出错**：召回不全或召回噪声，都会导致模型看不到关键信息或看到干扰信息。**检索质量是新的瓶颈**
- **工程复杂度**：需要索引、检索、重排、压缩一整套管线
- **难调试**：模型"没看到"和"看到了但没用"是两种完全不同的问题，要靠完整日志才能区分

## 从什么地方做

**第一步：先测量当前上下文里都有什么**

把一次典型调用的完整 prompt 打出来，按 token 占比排序。通常会发现：某个大文件占了 40%，而它其实没被用到。

**第二步：给每类内容设预算**

比如：系统提示 ≤ 2千，工具定义 ≤ 4千，检索结果 ≤ 8千，历史 ≤ 4千。**超了就触发压缩或裁剪。**

**第三步：优先删，再考虑检索**

很多时候不需要"更聪明的检索"，只需要**不把无关的东西塞进去**。先做减法。

**第四步：为代码场景上符号索引**

如果 Agent 处理代码，`grep` + AST 索引（如 tree-sitter）比向量库的投入产出高得多。

**第五步：记录"模型看到了什么"**

每次调用都存下完整的 prompt（或它的 hash + 结构摘要）。这是诊断"为什么它没注意到"的唯一依据。

## 常见错误

**错误 1：无脑塞更多上下文**

认为"信息越全越好"。实际上每加一段无关内容，都在稀释相关内容的权重。**先做减法。**

**错误 2：把关键指令放在长上下文的中间**

模型对开头和结尾的注意力最强，中间最弱。**关键约束放在开头，并考虑在结尾重复一次。**

**错误 3：用向量检索做精确匹配**

搜 `getUserById` 用向量检索会返回一堆"看起来相关"的函数。**精确符号用 grep/索引，语义概念才用向量。**

**错误 4：压缩后不验证**

压缩掉了关键决策，Agent 开始重复做已经做过的事。**压缩时保留：已完成、已排除、当前目标、约束**，这些不能丢。

**错误 5：把记忆当成真相**

长期记忆里的内容可能是过时的、错误的。**记忆里的信息用于"提示"，不用于"判定"。**
