# 评测集要能自动判分，否则跑不起来

## 背景：那套没人跑的评测集

团队花了两周建了 100 条评测用例。第一次跑完了，人工判分花了 3 天。

第二次改了提示词想再跑一次 —— **没人愿意再判 3 天**。

三个月后，这套评测集再也没跑过。提示词改了十几次，**全靠"我试了几个例子感觉还行"**。

**不能自动判分的评测集，等于没有评测集。** 人工判分只在第一次有动力，之后就废弃了。

## 方案：判分必须自动化

### 判分的四个层次（优先用上面的）

| 层次 | 方法 | 可靠性 | 成本 |
| --- | --- | --- | --- |
| **1. 可执行断言** | 跑测试、比文件、查数据库 | **最高** | 低 |
| **2. 结构化字段检查** | 校验 JSON 字段、枚举值 | 高 | 低 |
| **3. 规则匹配** | 正则、关键词、长度 | 中 | 低 |
| **4. 模型评分（rubric）** | 另一个模型按标准打分 | 中 | 中 |
| **5. 人工判分** | 人看 | 高 | **极高** |

**目标：80% 的用例用层次 1-2 自动判分，剩下的用层次 4。层次 5 只用于抽检。**

### 层次 1：可执行断言（优先设计成这样）

**代码任务** —— 用测试框架判：

```yaml
task: fix_failing_test
setup:
  repo: internal/api
  commit: a3f21bc
judge:
  - run: pytest tests/test_order.py::test_discount
    expect: {exit_code: 0}
  - run: pytest tests/          # 整个测试套件不能破坏
    expect: {exit_code: 0}
  - run: git diff --name-only
    assert: "tests/" not in output    # 不能改测试
```

**这是最可靠的判分方式** —— 测试通过就是通过了，没有解释空间。

**数据任务** —— 查数据库验证：

```yaml
task: create_order
judge:
  - query: SELECT status FROM orders WHERE id = ?
    expect: "paid"
  - query: SELECT COUNT(*) FROM inventory_log
    expect_delta: 1
```

**文件任务** —— 比文件内容：

```yaml
task: extract_to_json
judge:
  - file: output.json
    assert_valid_json: true
    has_fields: ["name", "email"]
    field_values: {name: "张三"}
```

### 层次 2：结构化字段检查

对输出是结构化的任务，直接校验字段：

```python
def judge(result):
    data = json.loads(result)
    checks = {
        "category": data["category"] in VALID_CATEGORIES,
        "confidence": 0 <= data["confidence"] <= 1,
        "has_evidence": len(data.get("evidence", [])) > 0,
        "no_hallucination": all(e in SOURCE_DOCS for e in data["evidence"]),
    }
    return all(checks.values()), checks
```

**好处**：能给出"哪一项没过"，定位问题比一个总分有用得多。

### 层次 4：模型评分（要有 rubric 和锚点）

无法用断言的任务（比如"回答是否有帮助"），用模型评分。

**关键：必须有明确的 rubric（评分标准）**：

```python
RUBRIC = """
评估这个回答，按 1-5 打分：

5 分：直接回答了问题，引用了具体来源，没有编造
4 分：回答了问题，有来源，但不够完整
3 分：回答了问题，但没有来源
2 分：部分相关，或包含明显错误
1 分：完全错误，或编造了信息

特别注意：如果回答中出现了文档里没有的信息，最高只能给 2 分。
"""
```

**三个要点**：

1. **rubric 要具体**，不要"评估质量"这种空话
2. **给出每个分值的具体标准**（锚点）
3. **特别说明要扣分的情形**（幻觉、遗漏）

**模型评分的局限**：

- 评分结果有波动（同样的回答可能得 3 分也可能 4 分）
- 评分模型本身可能判断错误
- **不能替代可执行断言**

**建议**：模型评分用于"辅助信号"，不作为唯一的通过标准。

### 评测集的组织

```yaml
# evals/code_review.yaml
- id: cr_001
  input:
    diff: "diffs/cr_001.patch"
  judge:
    - type: rubric                    # 主观部分用 rubric
      prompt: "评估这个审查是否发现了真实的空指针风险"
      min_score: 4
    - type: assert                    # 客观部分用断言
      check: "output mentions the null check on line 42"
  tags: [security, null-safety]
  source: "2026-08 线上事故复盘"       # 为什么有这条
```

**每条用例记录来源**。"为什么有这条用例"决定了它值不值得保留。

### 让评测跑得起来：工程要求

| 要求 | 原因 |
| --- | --- |
| **快** | 100 条要在 10 分钟内跑完，否则没人愿意等 |
| **可重复** | 同样的输入要得到同样的结果（temperature=0，固定随机种子） |
| **隔离** | 每条用例环境独立，不能互相污染（用容器/temp dir） |
| **可并行** | 用例之间无依赖，能并发跑 |
| **结果可读** | 输出"哪条挂了、为什么挂"，不是只有一个通过率 |

**"快"是最关键的工程要求。** 超过 30 分钟就没人跑了。

## 效果与代价

**收益**

- **能持续跑**：改一次提示词就能验证，不用等人工
- **能发现回归**：之前修好的 case 不会再坏
- **能对比方案**：A/B 两个提示词用同一套评测对比
- **能定位问题**：知道是哪类任务挂了

**代价**

- **建自动判分本身是工作量**：写代码任务相对容易（有测试），判断类任务难
- **判分标准可能不准**：自动判分"通过"但实际质量差 → **要抽检**
- **评测集会过拟合**：为了刷分优化 → **留 holdout 集**
- **维护成本**：代码/文档变了，用例要跟着更新

## 从什么地方做

**第一步：先选能自动判分的任务类型**

从代码任务、数据提取任务开始——**它们天然有可执行判据**。

**第二步：写 20 条，确保能一键跑完**

```
$ agent eval run --suite code_review
Running 20 evals... [====] 100%
PASS 17/20
FAILED: cr_003 (rubric score 3 < 4), cr_007 (missing field), cr_015 (test failed)
```

**目标：一条命令出结果。**

**第三步：接进 CI**

改提示词/工具/模型时自动跑。**通过率下降就阻止合并。**

**第四步：每次线上问题加一条用例**

这是最有价值的部分：**问题不会复发。**

**第五步：留 20% 作为 holdout**

调优时只看 80%，最后用 20% 验证没有过拟合。

**第六步：定期人工抽检成功的用例**

自动判分通过 ≠ 真的好。**抽检能发现"改了测试让它通过"这类作弊。**

## 常见错误

**错误 1：评测集不能自动跑**

前面那个案例。**不能一键跑的评测集会被废弃。**

**错误 2：只用模型评分**

没有断言，全靠另一个模型打分 → 评分本身不可靠，且成本高。**优先可执行断言。**

**错误 3：rubric 太模糊**

"评估回答质量" —— 评分模型只能瞎猜。**给具体标准和锚点。**

**错误 4：用例之间不隔离**

用例 A 改了文件，用例 B 受影响 → 结果不稳定。**每条用例独立环境。**

**错误 5：不看失败详情**

只知道通过率 85%，不知道哪 15% 挂了、为什么。**输出必须能定位。**

**错误 6：没有 holdout**

所有用例都用来调优 → 分数虚高，实际没提升。**留 20%。**
