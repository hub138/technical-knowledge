# Agent 的可观测性要记录决策而不只是调用

## 背景：日志里什么都有，却查不出为什么

一个 Agent 的错误排查，日志长这样：

```
[10:00:01] POST /v1/messages 200 (1820ms, 12400 tokens)
[10:00:03] tool_call: read_file({"path": "src/a.go"})
[10:00:03] tool_result: 200 (45 lines)
[10:00:05] POST /v1/messages 200 (2100ms, 15800 tokens)
[10:00:07] tool_call: read_file({"path": "src/b.go"})
...
[10:02:10] POST /v1/messages 200 (1900ms, 28000 tokens)
[10:02:10] tool_call: edit_file(...)
[10:02:15] task_status: failed
```

**HTTP 层面的信息很全，但查不出问题**：

- 它为什么读 `a.go` 然后读 `b.go`？是在找什么？
- 第 8 轮为什么突然改了文件？基于什么判断？
- 任务为什么失败？它自己认为卡在哪？

**这些"为什么"都不在日志里。** 而 Agent 的失败原因 90% 是决策问题，不是调用问题。

## 方案：记录"决策"这一层

### 每次模型调用要记录的不只是 token 数

```json
{
  "step": 8,
  "span": "model_call",
  "trace_id": "8f14e45f",
  "model": "claude-sonnet-4",
  "latency_ms": 1820,
  "tokens": {"input": 12400, "output": 380, "cached": 8200},
  "cost_usd": 0.042,

  "context_summary": {
    "history_turns": 14,
    "tools_available": 5,
    "retrieved_docs": ["src/a.go", "src/b.go"]
  },

  "decision": {
    "reasoning": "需要在 b.go 里确认接口定义，因为 a.go 里只看到了调用方",
    "chosen_action": "read_file",
    "action_args": {"path": "src/b.go"},
    "alternatives_considered": ["grep 搜索符号", "读整个目录"]
  }
}
```

**`decision` 这一段是传统日志里缺失的核心信息。**

### 记录什么，怎么记

| 层次 | 内容 | 用途 |
| --- | --- | --- |
| **调用层** | HTTP、延迟、token、成本 | 性能、成本分析 |
| **动作层** | 工具名、参数、返回摘要、耗时 | 执行路径还原 |
| **决策层** | 为什么选这个动作、考虑过什么 | **诊断 Agent 行为** |
| **任务层** | 目标、当前进度、剩余步骤 | 判断有无进展 |
| **状态层** | 工作记忆的快照 | 恢复、重放 |

**决策层怎么拿到**：

1. 让模型在工具调用前输出简短理由（用 `thinking` 或结构化字段）
2. 记录模型输出的完整内容（不只是工具调用）
3. 如果是工作流，记录路由决策的依据

**注意成本**：记录完整上下文会让日志量暴涨。**策略：完整内容存对象存储，日志里存结构化摘要 + 引用。**

### 三层关联

```
trace_id  ─┬─→ 决策链（为什么）
           ├─→ 工具调用（做了什么）
           └─→ HTTP 指标（多快多贵）
```

**排查时的顺序**：

1. 看指标：哪一步慢/贵？
2. 看决策：那一步为什么这么选？
3. 看动作：实际执行结果是什么？

### 可重放：最有价值的调试能力

如果记录了完整的输入（上下文 + 模型参数），可以在本地重放：

```bash
agent replay --step 8 --override "model=claude-opus-4"
```

用途：

- **验证假设**："换个模型这步会不会做对？"
- **回归测试**：改了提示词，用历史轨迹重跑，看决策是否改善
- **复现问题**：不用等线上再出现

**这要求记录完整的输入**，而不只是摘要。

### 必须监控的指标

| 指标 | 异常含义 |
| --- | --- |
| 每任务平均步数 | 上升 → 效率下降或任务变复杂 |
| 工具调用失败率 | 上升 → 工具问题或描述不清 |
| 无效步占比（无进展） | 上升 → 陷入循环 |
| 成本 P95 / 最大值 | 长尾失控 |
| 每步 token 增长曲线 | 陡增 → 上下文泄漏 |
| 终止原因分布 | 超步数占比高 → 任务太复杂或循环检测不够 |

## 效果与代价

**收益**

- **能回答"为什么"**：不只是"它做了什么"，而是"它为什么这么做"
- **可重放验证**：改提示词后能用历史轨迹验证
- **量化改进**：指标让优化有依据
- **成本可归因**：知道钱花在哪一步

**代价**

- **日志量大幅增加**：完整上下文可能是请求本身的 10 倍。**必须分级存储 + 采样**
- **需要模型配合**：让模型输出理由会增加 token 成本（虽然很少）
- **隐私风险**：完整上下文可能含敏感数据。**必须脱敏和访问控制**
- **重放环境难搭建**：工具是真实世界的（文件系统、数据库），重放需要快照或 mock

## 从什么地方做

**第一步：先把 trace_id 串起来**

所有模型调用、工具调用、外部请求都带同一个 `trace_id`。**这是地基。**

**第二步：加决策层记录**

最简单的做法：要求模型在每次工具调用前输出一句理由（放进 `thinking` 或专门的字段）。

**第三步：定义关键指标并上监控**

从"每任务步数"和"终止原因分布"开始——**这两个最容易暴露结构性问题**。

**第四步：实现分级存储**

```
热存储（7天）：结构化摘要 + 指标
温存储（30天）：完整轨迹（压缩）
冷存储：完整上下文（按需取）
```

**第五步：做最小可用的重放**

先支持"用同一个输入重跑"，不需要完整的工具 mock。**只是重跑模型调用就能验证很多假设。**

## 常见错误

**错误 1：只记录 HTTP 层**

前面那个案例：什么都记了，就是没记"为什么"。**决策层才是 Agent 特有的。**

**错误 2：记录完整上下文但不采样**

存储成本爆炸，且 99% 的日志没人看。**错误和慢请求全存，成功请求采样。**

**错误 3：没有 trace 传播**

异步任务、消息队列消费时断了 trace → 调用链不完整。**每个异步边界都要显式传递。**

**错误 4：指标只看平均值**

Agent 的步数和成本分布是长尾的。**必须看 P95/P99 和最大值。**

**错误 5：忽略"终止原因"**

只记录"失败了"，不记录"因为什么停下来"。**终止原因分布是最有价值的诊断信号**——超步数占比高说明循环检测不够，环境阻塞占比高说明工具或环境有问题。

**错误 6：不做脱敏就存完整上下文**

用户数据、凭据进了日志系统。**记录前必须过一遍脱敏。**
