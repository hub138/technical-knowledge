# 工具契约决定 Agent 能做什么

## 背景：模型不是不会用工具，是看不懂你的工具

一个代码 Agent 有三个工具：`read_file`、`search`、`run_command`。实测发现它几乎不用 `search`，而是反复 `read_file` 整个目录的文件——慢、费 token、还常常读错文件。

排查后发现问题在描述：

```json
{
  "name": "search",
  "description": "搜索代码",
  "parameters": { "query": "string" }
}
```

**"搜索代码"这四个字对模型来说信息量是零。** 它不知道搜的是什么、什么时候该用、返回什么格式。相比之下 `read_file` 的描述写得很具体（"读取指定路径的文件内容，返回文本"），模型当然选它。

**工具描述不是注释，是给模型的提示词。** 这是投入产出比最高的优化点——改几句话，Agent 行为可能整个变好。

## 方案：把工具当成一份契约

一份好的工具契约包含四部分：

### 1. 名称：动词开头，表达动作

- 好：`search_code`、`read_file`、`create_pull_request`
- 差：`search`、`file`、`pr`

名称本身携带语义，模型会读。

### 2. 描述：说清"何时用、何时不用、返回什么"

这是最关键的部分。模板：

```
<一句话：做什么>

何时使用：<具体场景，2-3 条>
何时不用：<容易误用的场景>
返回：<返回什么，格式/量级>
```

实例：

```
在代码库中按关键词或正则搜索文件内容。

何时使用：
- 需要定位某个符号/字符串出现在哪些文件时
- 知道要找什么但不知道在哪，范围大、不适合逐个 read 时

何时不用：
- 已经知道确切路径时，直接用 read_file
- 要搜的是语义概念而非字面匹配时，用 grep_by_concept

返回：最多 50 条匹配，每条含 file:line 和匹配行上下文。
结果过多时会截断，应缩小 query 范围。
```

**"何时不用"比"何时用"更重要**——它消除了模型在相似工具间的选择困难。

### 3. 参数：schema 化，加约束和示例

```json
{
  "type": "object",
  "properties": {
    "pattern": {
      "type": "string",
      "description": "要搜索的正则表达式"
    },
    "path": {
      "type": "string",
      "description": "搜索根目录，相对仓库根。留空表示全仓库"
    },
    "max_results": {
      "type": "integer",
      "description": "最多返回多少条，默认 50",
      "default": 50,
      "maximum": 200
    }
  },
  "required": ["pattern"]
}
```

几个要点：

- **用 enum 限定取值范围**，比让模型自由生成可靠得多
- **给 default**，减少模型需要决定的事
- **描述里写格式要求**（比如"相对路径，不要以 / 开头"）

### 4. 返回值：可读、可截断、带引用

工具返回直接进入上下文，所以：

- **限制体积**：日志、搜索结果一律截断，返回 `前 N 条 + 总数 + 怎么拿到更多`
- **结构化**：返回 JSON 而不是自由文本，模型解析更稳
- **给引用**：大内容返回 `artifact://...` 引用而不是全文
- **错误信息要可行动**：`"文件不存在"` 不如 `"文件不存在：/src/a.go。可用路径：/src/a_test.go, /src/ab.go"`——**错误里带上"下一步可以做什幺"**，模型就能自己恢复

## 效果与代价

**收益**

- **选对工具的准确率显著提升**：描述清楚后，模型在相似工具间的选择错误大幅下降
- **参数错误减少**：schema 约束 + 示例让格式错误几乎消失
- **自我恢复能力**：错误信息里带可执行的下一步，模型能自己纠错，减少一轮往返

**代价**

- **每个工具都要认真写描述**：20 个工具 = 20 段要打磨的文案。这部分工作无法省
- **上下文占用**：详细描述会增加 prompt 体积。工具很多时（>20 个），描述本身可能占几千 token
- **工具太多反而变笨**：超过 15-20 个工具，模型选择准确率会下降。这时需要**工具分组/动态加载**

## 从什么地方做

**第一步：先写 3 个核心工具，把描述打磨到极致**

不要一次给 20 个工具。先 3 个，反复测试模型在什么情况下会用错，然后改描述。这 3 个打磨好的工具，比 20 个半吊子的有用。

**第二步：为每个工具写"反例测试"**

构造 10 个 query，其中 5 个**不该**用这个工具。看模型会不会误用。这是验证描述是否清晰唯一可靠的方法。

**第三步：错误信息里带上恢复路径**

把所有工具的错误分支过一遍，把 `"failed"`、`"not found"` 这类改成带上下文的、可行动的提示。

**第四步：给返回值设上限**

检查每个工具：最坏情况下返回多大？会不会超过上下文的一半？加 `max_results` 参数和截断逻辑。

**第五步：工具数量超过 15 个时分组**

按场景分组，只把当前任务相关的工具注入上下文。全量注入会让模型选择困难。

## 常见错误

**错误 1：描述里写实现细节**

"调用内部 search_service 的 v2 接口"——模型不需要知道这个。它只关心"这个工具能帮我解决什么问题"。

**错误 2：参数名过于简略**

`{"q": "string"}` —— 模型能猜出 `q` 是 query，但不稳定。用 `search_pattern` 这种自解释的名字。

**错误 3：一个工具干太多事**

`manage_file(action: create|read|update|delete, ...)` —— 把四个操作塞进一个工具，模型经常传错 action。**拆成四个独立工具**，名称即语义。

**错误 4：忽略工具的幂等性**

`create_issue` 被重试两次 = 创建两个 issue。**写工具必须有幂等设计**（接受 client 提供的 idempotency key，或用唯一约束兜底）。

**错误 5：返回一大段原始日志**

`run_tests` 返回 3 万行日志，直接撑爆上下文。应该：返回退出码 + 失败摘要 + 完整日志的引用。
