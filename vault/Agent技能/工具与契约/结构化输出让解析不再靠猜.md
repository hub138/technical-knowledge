# 结构化输出让解析不再靠猜

## 背景：正则解析模型输出的那段代码

一个提取任务，提示词写："请以 JSON 格式输出，包含 name、age、city 三个字段。"

模型返回了：

```
好的，以下是提取结果：
```json
{"name": "张三", "age": 28, "city": "北京"}
```
希望对你有帮助！
```

于是代码里有了这段：

```python
m = re.search(r'```json\s*(.*?)\s*```', text, re.S)
if not m:
    m = re.search(r'\{.*\}', text, re.S)   # 再试试裸 JSON
if not m:
    return None                             # 放弃了
data = json.loads(m.group(1))               # 可能 json 解析失败
```

**这段代码的存在本身说明设计错了。** 用正则去猜模型的输出格式，是在为不确定性打补丁——而现代模型 API 已经提供了消除这个不确定性的机制。

## 方案：让结构由 schema 保证，不由提示词请求

### 1. 用原生 JSON / schema 模式

大多数模型 API 支持约束模式：

```python
resp = client.messages.create(
    model="...",
    messages=[...],
    # 输出被约束为合法 JSON，且符合 schema
    response_format={
        "type": "json_schema",
        "json_schema": {
            "name": "person",
            "schema": {
                "type": "object",
                "properties": {
                    "name": {"type": "string"},
                    "age": {"type": "integer"},
                    "city": {"type": "string"},
                    "confidence": {"type": "number"}
                },
                "required": ["name", "city"]
            }
        }
    }
)
```

**效果**：输出保证是合法 JSON 且符合 schema，不需要正则、不需要重试解析。

### 2. 用枚举约束取值范围

分类任务不要让模型自由输出：

```json
{
  "category": {
    "type": "string",
    "enum": ["complaint", "inquiry", "refund", "other"]
  }
}
```

**这消除了"模型输出了第 5 个类别"的问题**——它只能从这四个里选。

### 3. 工具调用本身就是结构化输出

如果已经有工具调用机制，可以直接用：

```json
{
  "name": "extract_person",
  "description": "从文本中提取人物信息",
  "input_schema": { /* 同上 */ }
}
```

模型"调用"这个工具，参数就是结构化提取结果。**好处是不用额外的 schema 模式，复用已有的工具契约。**

### 4. 约束解码的边界

要知道结构化输出**能保证什么、不能保证什么**：

| 能保证 | 不能保证 |
| --- | --- |
| 语法合法（是合法 JSON） | 内容正确（字段值可能错） |
| 符合 schema（类型、枚举、必填） | 语义合理（age 可能是 999） |
| 字段名正确 | 字段值来自原文（可能编造） |

**结构化输出解决的是"解析"问题，不是"正确性"问题。** 拿到结构化数据后仍然要校验业务规则。

### 5. 拿到之后还要校验

```python
data = json.loads(resp.content)          # 语法一定合法
if not (0 < data["age"] < 150):          # 但仍然要校验语义
    raise ValidationError()
if data["city"] not in KNOWN_CITIES:     # 业务规则
    data["city"] = None
```

## 效果与代价

**收益**

- **解析代码消失**：不再需要正则、重试、容错分支
- **下游类型安全**：可以直接反序列化成语言里的结构体
- **错误率下降**：消除了"输出格式不对"这一类失败
- **可测试**：schema 是契约，可以写契约测试

**代价**

- **部分模型/模式不支持**：需要确认所用的 API 和模式支持约束解码
- **schema 复杂时可能降低质量**：非常复杂的嵌套 schema 有时会让模型输出质量下降。**schema 要尽量扁平**
- **仍然要校验语义**：结构化不等于正确
- **可能限制创造性任务**：写诗、头脑风暴这类任务不该用结构化输出

## 从什么地方做

**第一步：找出所有"解析模型输出"的代码**

搜 `re.search`、`json.loads`、字符串切割。**每一处都意味着一次可以消除的不确定性。**

**第二步：把提取和分类任务改成 schema 约束**

优先改这两类，它们最需要结构：信息提取、分类路由。

**第三步：schema 从简单开始，按需加字段**

不要一次定义 30 个字段。**先 5 个核心字段**，不够再加。字段越多，模型越容易出错。

**第四步：给每个字段写 description**

schema 里的 description 是给模型看的，和工具描述一样重要：

```json
{"age": {"type": "integer", "description": "人物年龄，从文本推断。无法推断时填 null"}}
```

**第五步：保留必要的降级路径**

如果 API 不支持约束解码，或者约束失败：

1. 重试一次（temperature 设为 0）
2. 用工具调用机制代替
3. 最后才用正则 + 明确的错误信息

## 常见错误

**错误 1：在提示词里"请求"格式而不是约束它**

"请只输出 JSON，不要其他内容" —— 这是请求，会被违反。**用 API 的约束能力。**

**错误 2：schema 嵌套过深**

三层以上的嵌套对象和数组，模型容易出错。**扁平化：用 `user_name` 而不是 `user.name`。**

**错误 3：以为结构化输出 = 内容正确**

`{"age": 999}` 完全符合 schema。**业务校验不能省。**

**错误 4：对创造性任务用结构化输出**

让模型"写一段有创意的文案"却用 schema 限制成三个字段——**那不如直接用模板。**

**错误 5：schema 变了没有版本管理**

下游依赖字段名。改名会导致解析失败。**schema 演进要加版本或用兼容策略（新增可选字段，不删旧字段）。**
