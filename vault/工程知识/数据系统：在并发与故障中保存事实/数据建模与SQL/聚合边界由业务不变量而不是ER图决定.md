# 聚合边界由业务不变量而不是 ER 图决定

它解决的是数据库表能分别保存成功，但业务规则在并发更新后被破坏的问题。**聚合把必须原子保持的不变量圈进一个写入边界，并只允许外部通过聚合根修改**；**收益是规则有唯一入口，代价是聚合过大会增加冲突和加载成本**。**边界不由 ER 图、外键或对象引用数量决定，而由「哪些事实必须同时成立」决定**。

## 要解决的问题是什么：跟着数据库表设计为什么会变成一团泥

照着 ER 图建了对象：`Order`、`OrderItem`、`User`、`Address`、`Payment`、`Shipment`，互相都有引用。

改完边界后业务代码变成下面的样子：

```go
// 下单时要保证：总金额 = 各项之和，且库存够
order := repo.Find(id)
for _, item := range order.Items {
    item.Price = calcPrice(item)     // 改单项
}
order.Amount = sum(order.Items)      // 再改总额
repo.Save(order)
repo.SaveItems(order.Items)          // 分别保存
```

问题在并发下暴露：两个请求同时改订单项，**总额和明细对不上**。

根本原因：**"总额必须等于明细之和"这个不变量，跨越了 Order 和 OrderItem 两个对象，没有任何东西强制它们一起更新。**

## 方案怎么实现，机制是什么：把不变量圈进一个边界

### 聚合到底是什么

**照着 ER 图建了对象再照着外键互连，结果就是开头那类互相都有引用的实体网**：**几十个 `Entity` 两两牵线，改一个牵动全图**。ZOOZ（一个 ZooKeeper 相关的缩写） 工程博客把这种没有边界的实体网叫「big ball of mud（一团泥）」：

![DDD 反例：几十个实体互相关联没有边界，形成一团泥式实体网](/static/figures/zooz-ddd-entity-tangle.png)

*图源：ZOOZ 工程博客《Designing DDD aggregates》（https://engineering.zooz.com/@allousas/designing-ddd-aggregates-db633f1caf88，Medium 托管）。图中每个矩形都是一个实体，箭头是对象引用，没有任何分组边界。*

先把形状说成一件事：**聚合像一间必须同时锁门才能离开的房间**——**屋里所有值钱的东西（一组对象）要么一起锁在屋里（一次事务内一起更新），要么都别动；不能锁了门却把保险柜留在走廊（不变量跨边界）**。**房间的隔墙怎么砌，不看原来房子里走廊与房间的旧格局（ER 图的外键），看"哪些东西必须时刻待在一起才不出事"（业务不变量）**。这个比喻到"一起锁门"为止——现实里房间还有大小与开门频率的权衡：房间太大，人人挤一个门（冲突变多、加载变慢），这是设计规则一节的内容。

**聚合是一组必须一起保持一致的对象**。**它的边界由业务不变量决定，而不是由数据库表的外键决定**——**后者画出来的是存储结构，前者才是「改一个必须同时改另一个」的真实约束**。

**聚合 = 一组必须保持一致的对象，有一个根（Aggregate Root），外部只能通过根访问。**

划定边界的唯一依据：**不变量（invariant）**——那些"必须永远成立"的业务规则。

![DDD 聚合的形状：每个虚线椭圆是一个聚合，内部由聚合根、实体、值对象组成，外部只能引用聚合根](/static/figures/zooz-ddd-aggregate-structure.png)

*图源：同上（ZOOZ 工程博客《Designing DDD aggregates》）。*

```mermaid

    a["不变量：订单总额 = 所有订单项金额之和"]
    b["Order 与 OrderItem 必须在同一个聚合里"]

    d["外部只能通过 Order 改订单项，由 Order 保证总额正确"]
    a -->|"必要约束"| b --> c --> d
```

### 边界怎么划：设计规则

**规则 1：聚合内强一致，聚合间最终一致**

这是最重要的一条。跨聚合的一致性用事件/消息实现，**不要试图用事务保证**。

同样的几张表，按不变量划和按 ER 图划会得到完全不同的边界：

```mermaid
flowchart TB
    subgraph byer["按 ER 图划分：跟着外键走"]
        direction TB
        E1["订单表"] --> E2["订单项表"]
        E2 --> E3["库存表"]
        E3 --> E4["积分表"]
        E4 --> E5["物流表"]
        E5 --> E1
    end
    subgraph byinv["按不变量划分：只圈必须同时成立的"]
        direction TB
        I1["订单聚合<br/>订单与订单项金额一致"] -->|"领域事件"| I2["库存聚合<br/>锁定与扣减一致"]
        I1 -->|"领域事件"| I3["积分聚合<br/>增减与余额一致"]
    end
    byer --> byinv
```

左边那张图里**所有表被外键串成一个环，任何一个对象的修改都可能牵动整张网，事务边界随之膨胀到覆盖全部五张表**。右边**把"必须立刻成立"的规则各自圈起来，跨边界的用事件在稍后达成一致**——**积分晚几秒到账不是业务错误，订单总额错一分钱才是**。

一致性边界的判断依据参考中文资料：[《实现领域驱动设计》聚合（博客园）](https://www.cnblogs.com/afei-24/p/18052677)、[关于 DDD（Domain-Driven Design，领域驱动设计：以业务领域模型为核心的软件设计方法） 中聚合设计的一些思考（CSDN）](https://blog.csdn.net/NTJzc3o3i/article/details/163219743)、[业务视角下的微服务架构设计实例（论 ER 图建模对服务划分的危害）](https://huaweicloud.csdn.net/6712302b0636ea24a0c16447.html)。

```
Order 聚合（强一致）：订单 + 订单项 + 金额
Inventory 聚合（强一致）：库存 + 锁定量

订单扣库存 → 跨聚合 → 用事件最终一致
```

上面这套聚合、聚合根、值对象、领域事件的分工在战术 DDD 的整体图景里各有位置——应用服务编排用例、领域服务承接跨聚合逻辑、聚合根守住事务边界、领域事件负责跨聚合传播：

![战术 DDD 模式总览：应用服务编排领域服务，领域服务操作聚合（根实体、实体、值对象），聚合变更后发布领域事件](/static/figures/ms-ddd-tactical-patterns.png)

*图源：Microsoft Learn 中文文档《使用战术 DDD 设计微服务》，CC BY 4.0，https://learn.microsoft.com/zh-cn/azure/architecture/microservices/model/tactical-domain-driven-design。本篇的聚合边界规则落在最右侧 Aggregate 一格——聚合根就是那道事务边界的唯一入口。*

**规则 2：聚合要小**

**聚合越大，并发冲突越多（因为整个聚合被锁）**。

| 做法 | 后果 |
| --- | --- |
| 聚合太大（User 包含所有订单） | 改用户信息锁住整个用户的所有订单 |
| 聚合太小（每个字段一个聚合） | 不变量无法保证 |

**判断标准：能小就小，只要不变量还在边界内。**

**规则 3：聚合之间通过 ID 引用，不通过对象引用**

```go
// 差：直接持有对象
type Order struct {
    User *User      // 加载订单会连带加载用户
}

// 好：只存 ID
type Order struct {
    UserID UserID   // 需要用户信息时单独查
}
```

**为什么**：**对象引用会让聚合边界失效（改一个聚合能摸到另一个），且加载成本高**。

**规则 4：一个事务只修改一个聚合**

**如果必须改两个聚合，就用领域事件**，写法是：

```
事务 1：修改 Order（发布 OrderPlaced 事件）
事务 2（异步）：修改 Inventory（消费事件）
```

### 聚合根怎么保证不变量：实现

```go
type Order struct {
    id     OrderID
    items  []OrderItem   // 私有，外部无法直接改
    amount Money
}

// 唯一的修改入口，保证不变量
func (o *Order) AddItem(product ProductID, qty int, price Money) error {
    if o.status != StatusPending {
        return ErrOrderNotModifiable
    }
    o.items = append(o.items, OrderItem{product, qty, price})
    o.amount = o.recalculate()   // 总额在这里重算，不可能不一致
    return nil
}

func (o *Order) recalculate() Money {
    var total Money
    for _, it := range o.items {
        total = total.Add(it.Price.Mul(it.Qty))
    }
    return total
}
```

**关键：`items` 私有 + 唯一入口 + 不变量在入口处保证。** **外部无法构造出"总额和明细不一致"的订单**。

## 划对了能拿到哪些好处、要付哪些代价

**收益**

- **不变量由类型保证**：编译期（代码编译成可执行文件时发生的阶段）/构造期就不可能造出非法状态
- **并发冲突减少**：小聚合 = 小锁粒度（锁保护的范围大小、直接影响并发度）
- **边界清晰**：哪些是强一致（聚合内），哪些是最终一致（跨聚合），一目了然

**代价**

- **需要识别不变量**：这要和领域专家反复确认，不是看代码能得出的
- **跨聚合查询变麻烦**：不能 `order.Items` 直接拿了，要单独查询。**通常需要读模型（CQRS）配合**
- **边界划分错误的代价高**：边界划错后重构成本大——因为聚合是领域的核心结构
- **团队需要共同理解**：聚合概念需要团队达成共识，否则会退回 ER 图思维

## 动手从哪一步开始

**第一步：列出所有不变量**

**问业务方："什么条件必须永远成立？"**

- **订单总额 = 明细之和**
- **库存不能为负**
- **已发货的订单不能取消**
- **账户余额不能小于 0**

**每一条不变量都对应一个聚合边界。**

**第二步：按不变量分组，而不是按表分组**

**把必须一起保持一致的对象圈在一起**。**ER 图上的外键不代表聚合边界。**

**第三步：检查聚合是不是太大**

如果一个聚合有 10 个以上的实体，问：**它们真的都需要强一致吗？** **很多时候"用户地址"不需要和"订单"强一致**。

**第四步：用 ID 替换对象引用**

**逐个把跨聚合的对象引用改成 ID**。**这一步会让一些隐式依赖暴露出来**——那些"以为能用其实不该用"的引用。

**第五步：给聚合根写不变量测试**

```go
func TestOrderAmountAlwaysMatchesItems(t *testing.T) {
    o := NewOrder()
    o.AddItem(p1, 2, money(10))
    o.AddItem(p2, 1, money(15))
    assert.Equal(t, money(35), o.Amount)   // 不变量
}
```

## 哪些划法一看就错：常见错误

**错误 1：照着数据库表建对象**

**ER 图是存储结构，不是领域模型**。**外键关系不等于聚合关系。**

**错误 2：聚合过大**

**把整个"用户"做成一个巨大聚合，包含订单、地址、支付、偏好**。**结果：任何用户相关操作都锁住整个用户。**

**错误 3：在应用层保证不变量**

**不变量的检查写在 service 里 → 换一个 service 调用就绕过**。**不变量必须在聚合根内部保证。**

**错误 4：跨聚合用事务**

为了"保证一致"用分布式事务锁两个聚合。**应该接受最终一致，用事件。**

**错误 5：聚合之间双向引用**

`Order.User` 和 `User.Orders` 互相持有 → 循环依赖，加载成本爆炸。**单向引用 + ID。**

五条错误分成了三组，每组对应一种把边界画错的方式，见下表：

```mermaid
flowchart TB
    E1["照着数据库表建对象"] --> G1["错在来源<br/>拿存储结构当领域模型"]
    G1 --> E2["聚合过大"]
    E2 --> G2["错在粒度<br/>圈进了不必同生共死的部分"]
    G2 --> E3["在应用层保证不变量"]
    E3 --> G3["错在位置<br/>不变量写在了能绕过的层"]
    G3 --> X["修正 外键关系不等于聚合关系"]
```

**第一条与第三条最常见，且常被一起犯：照着表建对象，顺手把不变量检查写在 service 里**。**前者混淆了存储结构与领域模型，后者让不变量待在一个换次调用就能绕过的层**。第二条与第五条说的是边界与引用——**聚合过大让任何操作都锁住整个用户，双向引用则把加载成本推到爆炸**，两条都指向同一个修正方向：**边界只圈进不变量要求同生共死的部分，跨聚合只保留单向引用加 ID**。
