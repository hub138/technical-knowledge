# 复制滞后的一致性补救：读己之写与会话保证

## 要解决的问题

异步复制（见 [[工程知识/数据系统：在并发与故障中保存事实/可靠性与运维/复制的三种模式：主从、多主与无主的失败形态.md]]）的代价在读写分离场景显形：**用户刚写完的数据，立刻读却读不到**。写进主库，读路由到从库，从库重放还差几百毫秒——用户改了头像刷新页面还是旧的、下单后订单列表里没有这笔单。数据没丢（最终会同步），但用户视角是“写丢了”。这不是故障，是异步复制的正常行为被暴露在用户路径上。本文写这组问题的会话级补救：读己之写、单调读、前缀读三档保证，以及实现它们的工程手段。

## 机制

**三档会话保证**。读己之写（read-your-writes）：同一会话的写对后续读可见。单调读（monotonic reads）：同一会话不会读到越来越旧的值（两次读被打到延迟不同的从库，第二次比第一次旧——时间倒流的体验）。前缀读（read-your-writes-follows-prefix，因果一致性的读侧）：同一会话观察到写入的顺序与写入因果一致（先发消息后删帖，读者看到删帖却还看到消息）。三档是递进的弱保证：读己之写 ⊂ 单调读 ⊂ 因果一致，都弱于线性一致（全局读写总序）。

**实现手段按侵入度排**。
- 会话粘性（sticky session）：同一用户的读写都路由到同一从库。实现最简单，但负载不均（热点用户堆积），从库宕机时粘性重置（旧读窗口重现）。
- 写后读主（read-your-writes from primary）：写后 X 秒内（或该会话未同步的位点确认前）的读强制路由主库。实现要求：会话要带时间/位点标记，路由层要懂复制位点。MySQL 5.7+ 的 WAIT_FOR_EXECUTED_GTID_SET、PostgreSQL 的同步回放等待，把“从库追上位点”做成可查询的谓词。
- 会话令牌（session token / causality token）：客户端记住上次写的版本号/时间戳，读时带令牌，服务端保证读到不旧于令牌的版本（不够新就等待或重定向）。DynamoDB 的 session token、Couchbase 的 CAS 令牌是产品化实现。这是最强的会话保证，实现也最重。
- 单调读的专门解法：读也走 quorum（R 调大，见复制的三种模式（上文链接）的无主段）或会话粘从库；前缀读的解法：版本向量或把有因果的写固定到同一分区。

**CAP 视角的定位**。会话保证是 CAP 谱系的中间点：线性一致（CP 侧）全局总序太贵（跨地域 RTT），最终一致（AP 侧）用户路径旧读太伤体验。会话保证把一致性范围从“全局”缩到“单用户”，代价从“所有读都慢”缩到“该用户的读偶尔慢”——多数业务（改资料、下单、发消息）只需要这个范围，这是工程上性价比最高的一致性档位。

## 背景与代价

思想背景：会话保证的术语体系来自 Bayou（1994，Xerox PARC 的移动离线数据库研究）与 TACT（2000，会话保证的形式化）——研究离线协作时发现“全局一致不可得，但用户对自己写的可见性是刚需”。产品化分两波：数据库侧（MySQL GTID 等待、PostgreSQL 逻辑复制位点）与中间件侧（读写分离中间件的会话路由规则）。DynamoDB 的 session token（2012+）把它带进托管服务主流。

最精巧的一笔是**“保证范围从全局缩到会话”的降维**。线性一致的代价是全局协调（每读都可能等跨地域确认），会话保证把这个集合从“所有用户 × 所有数据”缩到“单用户自己的写”，协调只在“该用户的读”与“该用户的写位点”之间发生——一个位点比较的谓词就够。这是把 CAP 的不可绕过转化为“你要多大范围的一致性”的可选菜单。代价要摆明：会话保证救不了跨用户因果（A 发帖 B 评论，B 评论时读不到 A 刚发的帖——两个会话之间无保证，跨会话要业务层显式传递因果或上线性一致）；令牌机制把状态从服务端移到客户端（令牌丢失=保证失效，客户端实现正确性成为新依赖）；粘性方案与故障切换天然冲突（切换瞬间粘性失效，旧读窗口重现），SLA 要把切换瞬间的保证降级写清楚。

## 边界

- **“读己之写”经常被误当线性一致卖**。产品文档说“read-after-write consistency”（DynamoDB 的强一致读、S3 的 read-after-write PUT），指的是单对象单写后的可见性，不等于跨对象跨操作的总序。跨对象读己之写（改头像+改昵称后刷新，两者都要新）需要更强的因果或事务保证，选型时要拿场景去对文档原文，不能望文生义。
- **写后读主的窗口估算要留余量**。X 秒的窗口按复制延迟 P99+缓冲设；复制延迟在写尖峰（大事务、DDL、从库重放堆积）时突增，固定小窗口在尖峰时失效。位点谓词（GTID 等待）比时间窗口可靠，能等就等位点。
- **单调读被忽视但伤害体验**。用户第二次刷新看到比第一次更旧的头像，比读不到自己的写更诡异（时间倒流感）。读写分离中间件若把同用户请求随机路由，单调读违反是常态。会话粘从库或读 quorum 是标配修复，监控指标要含“同会话读版本回退”计数。
- **会话保证与多设备登录冲突**。同一账号手机+网页双端，写发生在手机（会话 A）、读发生在网页（会话 B），会话间无保证。跨设备同步是业务层问题（推送、版本号 UI 提示），不要指望数据库会话保证覆盖它。

## 验证

- **读旧复现实验**：压测主库写（制造 500ms+ 复制延迟），写后立即读从库，预期：部分读返回旧值；同一会话加粘性路由（或 GTID 等待）重跑，预期：读旧率归零。两种配置的读旧率对比就是补救手段的直接证据。
- **单调读违反复现**：读随机路由两个延迟不同的从库（一个滞后 1s），轮询读同一行，预期：能观察到值版本回退（v2→v1）；会话粘单从库后重跑，预期：回退消失。
- **位点谓词实测**（MySQL）：写主库后 WAIT_FOR_EXECUTED_GTID_SET 在从库等位点，测量等待时间分布，预期：P50 在毫秒级、P99 随写压力上升——位点等待把“盲等 X 秒”变成“等到即走”，等待分布数据是窗口参数的依据。
