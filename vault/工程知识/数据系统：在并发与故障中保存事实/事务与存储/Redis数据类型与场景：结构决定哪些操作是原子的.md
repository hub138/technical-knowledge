# Redis数据类型与场景：结构决定哪些操作是原子的

**Redis 不是「一个很快的 KV 存储」，是九种数据结构的集合；选对结构，业务逻辑里的锁、去重、排行榜、消息队列就变成一条原子命令，选错结构就在应用层用事务与重试重新发明它们。** 读完你能回答：每种类型对应哪类场景、哪些操作天然原子、Stream 与 List 做队列的差别在哪、内存与淘汰怎么配套。

## 要解决的问题

把 Redis 当字符串 KV 用，计数器要 `GET` + `SET` 两步，中间会被并发插入——应用层就得加锁。用对 `INCR`，一步原子完成，锁根本不需要出现。**数据结构的选择直接决定并发控制发生在哪一层：命令内建原子性，还是应用层自建。** 这是类型选型的第一判据，其余（内存、语义、运维）都排它后面。

## 九种类型与各自的地盘

| 类型 | 底层结构 | 原子能力 | 典型场景 |
| --- | --- | --- | --- |
| String | SDS 动态字符串 | `INCR`/`SETNX`/`GETSET` | 计数器、分布式锁、缓存条目 |
| Hash | ziplist / hashtable | `HINCRBY`、单字段读写 | 对象属性、购物车 |
| List | quicklist（双端链表） | `LPUSH`+`BRPOP` 阻塞消费 | 简单任务队列、最新列表 |
| Set | intset / hashtable | `SADD` 去重、`SINTER` 交并差 | 标签、共同关注、抽奖去重 |
| Sorted Set | skiplist+hash | 按分数有序、`ZRANGE` 原子排名 | 排行榜、延迟队列、滑动窗口限流 |
| Stream | radix tree + listpack | 消费组、ACK、`XRANGE` 回放 | 事件流、可靠队列 |
| Bitmap | String 位操作 | `SETBIT`/`BITCOUNT` | 签到、在线状态、布隆过滤器底座 |
| HyperLogLog | 概率寄存器 | `PFADD`/`PFCOUNT` | 亿级去重计数（误差 0.81%） |
| GEO | Sorted Set 编码 | `GEOSEARCH` 半径查询 | 附近的人、门店距离 |

选型判据按顺序过三问：**操作需要原子性吗（选内建原子的类型）；需要有序或排名吗（Sorted Set）；需要回放与确认吗（Stream）。** 三问之后还落在 KV 上的，才用 String。

### 三个高频场景的结构决定

**计数与限流**：`INCR` + `EXPIRE` 两步有过期竞态（计数成功与设置过期之间崩溃，键永不过期），`SET key 0 EX 60 NX` 或 Lua 把两步合成一次原子执行。**滑窗限流用 Sorted Set：member 存请求标识、score 存时间戳，`ZREMRANGEBYSCORE` 清窗口外、`ZCARD` 计数、`ZADD` 记录，三条命令包进 Lua 或 pipeline。**

**队列**：List 的 `LPUSH`+`BRPOP` 最简单，但**消息取出即责任转移，消费者崩溃消息就丢**；Stream 的消费组（consumer group）记录每个消费者的读取位置，`XACK` 确认前消息保留，崩溃后 `XAUTOCLAIM` 交接——**「消息丢了能不能找回」是 List 与 Stream 的分界判据**。

**排行榜与延迟队列**：**Sorted Set 一个结构两个用途，score 是排序键。**延迟队列把执行时间戳存 score，消费端 `ZRANGEBYSCORE key -inf now LIMIT 10` 取到期任务——**排序由结构维护，应用层不需要任何排序代码。**

## 案例：类型语义错配的三次真实事故

Redis 的缺陷分析案例全与「类型/语义错配」相关。[[工程知识/缺陷分析：从个案到体系/正确性/案例九：数字越过了边界——Redis 里三次截断导致的崩溃]] 是数值边界：**把超范围整数塞进按紧凑编码优化的结构，三次截断层层放大成崩溃——紧凑编码（ziplist/listpack）对小数据优化内存，对越界值的容错有限，写入前校验数值范围属于结构选型的配套纪律。**[[工程知识/缺陷分析：从个案到体系/正确性/案例十：类型说谎时——静默删数据的 TTL 与算错的比较]] 是 TTL 语义：**类型系统在关键路径上给了隐式转换，比较永远不成立，数据静默删除——键的过期语义与业务过期语义要显式对齐。**[[工程知识/缺陷分析：从个案到体系/安全/案例二十六：公告栏没查门禁——Redis 的 ACL 键名泄露与解析崩溃]] 是权限面：**Redis 6 的 ACL（access control list，按用户与键模式授权）没启用时，能连上就能读写全部键——结构能力越强，账号边界越要显式划。**

**三案共性：Redis 把默认值设计得「开箱即用」（紧凑编码、隐式转换、全键可访问），工程纪律是把每个默认值显式核对一遍再上生产。**

## 怎么测

- **原子性验证：并发脚本同时 `INCR` 一万次，终值必须等于一万；同场景改用 GET+SET 复现竞态，确认理解差异。**
- **淘汰与内存：`MEMORY USAGE` 抽查大键；压测时观察 `maxmemory` 触发后的淘汰策略行为（`noeviction` 拒写、`allkeys-lru` 驱逐），写路径对驱逐要显式容错。**
- **队列交接演练：消费者中途 kill，确认 Stream 消费组的 `XAUTOCLAIM` 把未 ACK 消息交给新消费者；List 方案同场景确认消息丢失范围符合预期。**
- **持久化核对：RDB 快照间隔与 AFS/appendfs 配置下的崩溃恢复丢失窗口，用实际重启演练测出来而不是查文档背出来。**

## 哪些认识一看就错

- **「Redis 是缓存，丢了无所谓」——Sorted Set 里的排行榜、Stream 里的待办、String 里的分布式锁都是状态不是缓存；丢不丢看持久化配置，不看产品定位。**
- **「分布式锁用 SETNX 就行」——锁要带过期与持有者标识（防误删），续期要 watchdog；单命令只是起点，RedLock 的争议也在锁语义不在性能。**
- **「大 key 删一下没事」——百万 member 的 Set/List 同步删除阻塞主线程，`UNLINK` 异步回收才是正确姿势；大 key 的发现要靠 `--bigkeys` 扫描常态化。**
- **「事务用 MULTI/EXEC 就安全」——EXEC 只保证命令连续执行，不提供回滚；中途失败前面的照样生效，需要条件原子的场景用 Lua。**

## 效果从哪来、要付什么代价

**选对结构后，并发控制内建于命令，应用代码变薄、竞态面消失，内存由结构的紧凑编码自动优化（小集合 ziplist/listpack 自动降级）。**代价是**语义学习与运维面扩大：九种类型各有自己的编码切换阈值**、淘汰行为与持久化语义，**大 key、热 key、集群模式下的 hash tag 约束都要进监控与评审清单。结构选型是一次性决策，语义错配的修复成本随数据量线性增长——选错后迁移的成本远高于选型时多花的那一小时。**
