# 数据质量规则挂在管道上：每条规则有等级与动作，不只有报警

> **要点**：数据质量规则的执行点在管道环节内（不是终端抽查），每条规则声明等级（阻断、降级、告警）与对应动作（停管道、标坏区间、通知）——等级与动作的矩阵在管道设计期定好，坏数据在链路内被拦住，消费者按数据状态字段决定是否可用。

## 要解决的问题

数据质量检查的常见做法是"终端报表对数"：数据到了终端才被发现错——**发现点离出错点隔了整条链路**，回溯定位（哪一环引入的错）要逐环考古；更常见的形态是规则"有而无效"：检查跑了、报警发了、没人处理（报警疲劳），坏数据继续流向下游。本库数据治理域"血缘图谱的价值"讲过影响面的追溯；本篇讲执行面：**规则的挂载点、等级-动作矩阵、坏数据的消费者可见性**——质量规则从"事后审计工具"变成"管道内的执行机制"。

## 机制：挂载点与等级-动作矩阵

**挂载点按链路环节选**：源数据进入同步管道的入口（schema 校验、空值率、主键唯一性——拦源头错误）、加工环节的出口（行数波动、聚合守恒、业务规则——拦加工错误）、终端可见前（抽样比对、跨源勾稽——最后一道门）。**每个环节挂它"职责内"的规则**：入口规则报出的错归上游，出口规则报出的错归本环节——挂载点同时是责任分界点。

**等级-动作矩阵三档**：**阻断**（规则违反即停管道——关键约束如主键唯一、金额非负，坏数据向下流一行的代价都高于停管道）；**降级**（管道继续、输出标记坏区间——统计波动类问题，数据有业务价值但可信度降级）；**告警**（只通知不干预——轻微偏差，人工判断）。**每一类规则在建时就定好档位**，"全部告警"的规则集等于没有规则（报警疲劳让真问题淹没）；"全部阻断"则脆弱（上游抖动把管道停成常态）。上游 BookKeeper 的一个复现缺陷（pendingDeletedLedgers 清理错误导致元数据残留）给同类启示：**清理路径的错误被静默吞掉，残留逐日累积**——管道的质量规则同样最怕"跑了但结果没人看"，等级与动作绑定后才算"跑过"。

**消费者可见性**：降级与阻断产生的"坏区间"信息要写到数据的状态字段（分区元数据、质量标签），**消费者按状态决定使用方式**（跳过坏分区、加权使用、照常使用）——坏数据的存在本身是信息，藏起来它就在下游以"对不上"的形式重新出现。

## 看完能判断：规则设计与运营

**规则从故障反推**：每次数据事故的根因（上游改 schema、时区错乱、重复推送、补数覆盖）都应沉淀为一条防再发的规则挂到对应环节——**规则集是事故史的具象化**，从零开始的"通用规则清单"没有这个沉淀过程，覆盖不住本链路的真实风险。

**阈值按统计基线定**：行数波动 ±5% 还是 ±20% 该报——阈值按历史基线的分布定（均值 ± N 倍标准差），拍脑袋的阈值要么吵（太敏感）要么聋（太钝）。**基线随业务季节性调整**（大促日行数暴涨是正常，按固定阈值误报）。

**规则的维护成本要算**：每条规则要跟上 schema 变更、业务规则变更——**规则失效（该报不报）比没有规则更危险**（给消费者虚假的安全感），规则的变更管理与管道代码同级（评审、测试、版本化）。

## 边界

三条边界防止防线走形。

**质量规则不是测试的替代**：管道代码的单测、集成测在开发期拦截逻辑错误；质量规则在生产期拦截数据与环境的意外——**两道门各管一段**，用质量规则兜代码 bug 是把生产当测试环境。

**阻断的恢复动作要预设**：阻断停管道后，修复动作（回滚上游、跳过坏批次、人工放行）与恢复负责人在规则建时定——**阻断 without 预案 = 管道停摆等救援**。

**跨源勾稽的成本与价值**：多源比对（源库行数 vs 管道产出行数）是最可靠的规则也最贵——**按数据重要性分配勾稽强度**，核心金额数据全量勾稽，日志类数据抽样即可。

## 验证

可复现的验证路径：

1. 拦截验证：构造 schema 变更与重复数据注入，预期入口规则按等级阻断或降级，坏数据不越过挂载点；
2. 状态可见验证：降级场景下消费端读到的分区元数据带坏区间标记，消费者按标记走降级逻辑；
3. 基线验证：用三个月历史数据回放规则，预期误报率与漏报率在可接受范围（阈值调整有依据）；
4. 断言锚点：**每条规则有等级与动作、挂载点覆盖链路三段、坏区间状态字段被消费者使用、规则集与事故史对得上**——四件齐备，数据质量从终端对数变成链路内的执行机制。

```text
拦截断言 = 坏数据不越过挂载点
状态断言 = 坏区间对消费者可见
回放断言 = 阈值误报漏报有基线
```

质量规则的价值在执行不在声明：挂载点定责任、等级定动作、状态字段定消费者的知情权——三个机制配齐，坏数据在链路内被处理，而不是在终端被抱怨。
