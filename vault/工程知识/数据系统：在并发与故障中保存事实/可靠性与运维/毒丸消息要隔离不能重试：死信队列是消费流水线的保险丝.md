# 毒丸消息要隔离不能重试：死信队列是消费流水线的保险丝

> **一句话总结**：毒丸消息（永远处理失败的消息）在重试循环里把分区卡住——防线是"有限重试 + 死信隔离"：重试预算耗尽立即进死信队列，分区继续流动，坏消息单独排查修复后重放；重试策略（次数、间隔、范围）与死信的监控、重放流程是这套机制的三件套。

## 要解决的问题

一条消息让消费者永远失败（格式非法、引用了不存在的数据、触发消费者 bug）：消费 → 失败 → 重试 → 再失败——**重试循环不仅消化不了这条消息，还占住处理预算**：同一分区的其他消息排在后面，延迟逐秒攀升，极端时整条流水线卡住。本库缺陷分析域的幂等键篇讲过重试的安全前提；本篇讲重试的失败终点：**毒丸的识别、重试预算的设计、死信的监控与重放**——死信队列的定位是保险丝：过载（坏消息）时断开局部、保护整体。

## 机制：重试预算与死信隔离

**重试预算的设计**：次数上限（一般 3-5 次，按"瞬时故障的恢复时间"定：网络抖动重试一两次能过，格式错误重试一百次也是失败）+ 间隔策略（立即重试对瞬时故障有效，退避对下游过载有效）+ **重试与主流的分离**（重试消息进重试主题/队列，不占主流的处理位置——老练的实现用延迟队列按退避时间重新投递）。**预算的设计判据**：瞬时故障的重试成功率与毒丸的重试成功率分开看——前者高（值得重试），后者为零（不值得）——重试预算覆盖前者、终止后者。

**死信的进入条件**：重试预算耗尽；或**可判定为永久失败的错误直接跳过重试**（反序列化失败、schema 不匹配——这类错误重试没有意义，直接死信，**错误分类决定是否消耗重试预算**）。

**死信队列的要素**：隔离存储（独立主题，不占主流分区）+ **上下文完整**（原消息、错误信息、失败时间、重试次数——重放时要知道为什么死）+ 监控告警（死信出现即告警，**死信是缺陷信号**：每条死信背后是一个数据质量或代码缺陷）。

**重放流程**：死信的修复与重放是标准操作——修根因（数据修复或代码修复）→ 验证（对死信样本在测试环境重放）→ 批量重放（带限速，重放也是写入流量）→ 核对（重放后的下游对账）。**重放工具化**：手写脚本重放易错（漏上下文、重复写入），平台化的重放命令带幂等保障。

## 看完能判断：毒丸的预防与分类

**消费端的两道预防**：输入校验前置（消费的第一步做 schema/合法性校验，非法消息直接死信——**校验失败不消耗重试预算**）；处理隔离（单条消息的处理异常不拖垮消费者进程——catch 单条、记死信、继续下一条，消费者进程级崩溃才是事故）。

**错误的三分类**：瞬时错误（网络、下游超时——重试有效）、永久错误（格式、数据缺失——死信）、资源错误（下游过载——退避重试 + 限流）——**错误分类写进消费框架**，分类错误的代价是把毒丸当瞬时错误重试一百次。

**毒丸的扩散防护**：一条毒丸卡住一个分区是局部的；**批量拉取模式下毒丸卡住整批**（一批 500 条里有 1 条毒丸，整批失败重试）——批量模式下失败粒度要下探到单条（部分成功语义），否则批内毒丸的杀伤面 ×500。

## 边界

三条边界防止防线走形。

**死信不是垃圾桶**：死信队列只收"确实处理不了"的消息——**把它当"暂时不想处理"的丢弃处（负载高时随手丢死信）会让数据静默丢失**，死信的进出都要有监控与账。

**重试预算与幂等绑定**：重试的前提是操作幂等（本库幂等键篇）——**非幂等的消费加重试 = 重复处理**，先幂等后重试是顺序约束。

**死信的重放也有毒丸风险**：修复不彻底的重放让消息再次进死信——**重放带次数标记**，二次死亡的消息升级处理（人工介入），不让重放变成新的重试循环。

## 验证

可复现的验证路径：

1. 毒丸复现：向分区注入格式非法消息 + 正常消息混合流，预期无死信机制时分区延迟持续攀升，有死信机制时毒丸 3 次重试后隔离、主流延迟平稳；
2. 分类验证：瞬时故障注入（下游短暂超时），预期重试成功不计死信；永久错误注入，预期跳过重试直接死信；
3. 重放验证：死信修复后重放，预期下游收到且无重复（幂等生效）、重放限速生效；
4. 断言锚点：**死信告警在管、错误三分类在消费框架实现、重放命令工具化且带幂等、批量消费的单条失败粒度有测试覆盖**——四件齐备，毒丸从"卡住整条流水线"变成"一条告警加一次重放"。

```text
隔离断言 = 预算耗尽即隔离主流不停
分类断言 = 永久错误不耗重试预算
重放断言 = 幂等限速且可核对
```

消费流水线的韧性不在"永不失败"在"失败不停"：有限重试消化瞬时故障，死信隔离终止永久失败，重放流程兜底恢复——保险丝装好，一条坏消息烧不掉整条流水线。
