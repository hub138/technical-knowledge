# 复制的三种模式：主从、多主与无主的失败形态

## 要解决的问题

```mermaid
flowchart TD
    M["主从 单点写"] --> F1["主库故障要切换"]
    MM["多主 多点写"] --> F2["写冲突要合并"]
    N["无主 多数派"] --> F3["要读修复"]
```

三种模式分别把代价转移到了不同环节，对照见下图：



复制要解决的问题，是**单机失效不能带走数据的可用性**。**RAID——把多块盘组合成逻辑盘提升可靠性——解决机器内的磁盘失效（见 [[工程知识/数据系统：在并发与故障中保存事实/可靠性与运维/RAID等级与数据可靠性：镜像与纠删的数学.md]]），复制解决跨机器的机器失效**。核心矛盾：**多副本带来可用性，但同一数据的多个副本在网络上分处各地，写入怎么同步、冲突怎么解决、故障时怎么切换**——**每种复制拓扑都在这三个问题上给出不同答案，也各自暴露不同的失败形态**。本文写三种基本拓扑（主从、多主、无主）的机制与失败形态，**这是理解高可用数据库与分布式一致性的骨架**。

## 它是怎么做到的

**三种复制模式的差异，本质上是「谁有权写入」与「冲突何时解决」的差异**。资源隔离的思路在这里同样适用：把不同用途的连接池（预先建好连接反复取用、省去反复握手建连的开销）分开，一个耗尽不至于连带拖垮另一个。



**主从复制（主节点把变更同步给从节点的机制）：单点写，同步或异步**。**一个主节点接受全部写，把变更日志——binlog（MySQL 的变更日志）、WAL（Write-Ahead Log，先写日志再改数据，崩溃后靠日志恢复）、oplog（MongoDB 的操作日志）——发给从节点重放**。读可分散到从节点（读写分离）。同步/异步的取舍：**同步复制（主等从确认）保证故障切换不丢数据但延迟受最慢从节点拖累**；**异步复制（主不等）快但主崩溃时未同步的写入丢失**。主从（一个节点负责写入、其余节点同步副本的复制模式）的失败形态：**异步丢写**（**主宕机时从库落后，切换后已确认的写消失，对用户是数据丢失**）；**脑裂（集群分裂成两半各自为政的故障）**——**网络分区时旧主还在接受写，新主已选出，两主并存，必须配 fencing 强制旧主下台**，见 [[工程知识/后端系统：在并发、失败与变化中维持服务/分布式可靠性/租约必须配合FencingToken阻止过期持有者.md]]；**复制延迟（从库同步速度落后于主库、读到旧数据的时间差）读旧**——**读己之写在从库读不到**，见 [[工程知识/数据系统：在并发与故障中保存事实/事务与存储/复制滞后的一致性补救：读己之写与会话保证.md]]，本篇同步写的姊妹篇。

主从拓扑的通用形态见下图：**写入只进主库（Primary），变更经复制流（replication flow）单向流往全部副本（Replica），客户端读可打任意副本**——「谁有权写入」的答案决定了后面所有失败形态：

![存储复制拓扑：客户端写主库，复制流单向流向多个副本，读可分散](/static/figures/storage-replication.svg)

*主从复制的写入与传播方向（图源：Wikimedia Commons，Michel Bakni 绘，CC BY-SA 4.0）*

主从复制运转起来的完整流程，Redis（内存键值数据库，常当缓存与排行榜用） 的全量同步（首次把完整数据复制给从库）画得最细：从库发 `psync ? -1` 请求同步，主库回 `FULLRESYNC {runID} {offset}` 后执行 bgsave（fork 子进程后台生成内存快照） 生成 RDB（Redis 的全量快照持久化文件）发送，从库清空内存加载 RDB，**主库再把 RDB 生成期间积攒的写命令经 replication buffer 补发**——三个阶段把「变更日志发给从节点重放」这句话展开成可核对的报文序列：

![magebyte 中文时序图：Redis 主从全量复制三阶段——第一阶段从库发送 psync ? -1、主库响应 FULLRESYNC {runID}{offset} 协商同步；第二阶段主库 bgsave 生成 RDB 并发送、从库清空内存加载数据；第三阶段主库将 replication buffer 中积攒的新指令发送给从库执行](/static/figures/magebyte-redis-full-sync-three-phases.png)

*图源：博客园《Redis 高可用篇：你管这叫主从架构数据同步原理？》（作者 magebyte，转载注明出处），https://www.cnblogs.com/uniqueDong/p/15348169.html。*

断线重连后为什么能补发而不是重来，靠的是主节点上的环形积压缓冲区：master_repl_offset 与 slave_repl_offset 两个指针在环上追逐，**断连期间主库指针继续前移，重连后两个偏移量的差值若还落在环内就只补发差量（增量同步）**；**从库落后太多、差值越过环长，旧数据已被覆盖，只能退回全量同步**——「异步丢写」的失败形态，机制底座就是这个环的容量：

![magebyte 中文图：repl_backlog_buffer 环形缓冲区在主从断开重连前后的变化——左侧主从两个偏移量指针重合，右侧断连期间 master_repl_offset 前移、slave_repl_offset 停在原位，差值在环内可增量补发，越过环长则退回全量同步](/static/figures/magebyte-redis-repl-backlog-ring-buffer.png)

*图源：同上，博客园 magebyte。*

异步丢写的时间轴把"已确认"与"已持久"的缺口摆开，缺口位置见下图：

```mermaid
flowchart TB
    c["客户端写 w1<br/>主库应答 已确认"] --> m["主库落日志<br/>异步推送从库"]
    m --> x["| w1 尚未传到 |<br/>主库宕机"]
    x --> s["从库提升为新主<br/>位点停在 w1 之前"]
    s --> f["用户重连<br/>w1 消失"]
    c -.->|"同步复制同一时点<br/>等从库确认后才应答"| y["主宕时 w1<br/>至少存于一份从库"]
```

异步复制丢写的形成过程：**确认发生在传输之前，宕机切在传输中途，缺口就是这两拍之间的写入**。**同步复制把应答挪到从库确认之后，同一宕机时点 w1 已存于从库**——**两种模式的差异浓缩在应答时机这一拍上**。

**多主复制：多写点，冲突是常态**。**多个节点同时接受写，变更互相传播**。**优点是写可用性高（分区两侧都能写）、异地写延迟低**。失败形态集中在**写冲突**：**两个主同时改同一行，日志互传时冲突暴露**。解法光谱：最后写入胜LWW（Last-Write-Wins，最后写入覆盖：按时间戳取最新的冲突消解）——用时间戳，但时钟不可靠，见 [[工程知识/后端系统：在并发、失败与变化中维持服务/分布式可靠性/电源与时钟：UTC与单调钟的工程含义]]；CRDT（冲突解决内建在数据结构里，自动合并）；自定义合并函数。**LWW 靠时间戳比大小，机器时钟漂移就让「最后」变成「时钟快的那个」，静默丢写**。

**无主复制：客户端直写多数派**。**没有主节点，客户端（或协调者）把写发给 N 个副本中的任意若干个，读也直接读多个副本，版本号/时间戳/向量时钟（各节点维护计数器向量、用来比较事件的因果先后）裁决谁新**。Dynamo 系（DynamoDB、Cassandra）的法定读写（quorum）：**写 W 个副本、读 R 个副本，W+R > N 则读写集合必有交集，读必然覆盖到最新值**。quorum 的失败形态：**一致性调优的暗坑**（W=1 快但两个写并发时无仲裁，冲突丢写；W=N 慢但强）；**sloppy quorum**（**网络分区时写入临时节点保可用，恢复后回流，可用性换一致性，CAP 的直接体现**）；**读修复与 hinted handoff**（**读时发现旧副本顺手修、临时节点事后回流**）——**自愈机制让「最终一致」在正常时看起来像强一致，但分区期间的静默丢写风险真实存在**。

## 这些场景各自要付什么代价

**主从是最古老的形态（1980s 的磁盘镜像与早期数据库热备），它假设「写是稀缺的、读是海量的」（互联网读多写少负载），单点写+读扩展是性价比最高的解**。**多主兴起于离线协作场景（日历同步、CouchDB、Notion 类应用），承认「分区与离线是常态」，把冲突解决搬到数据结构层**。**无主来自 Dynamo 论文（2007，Amazon，可用性优先的购物车场景），核心判断是「多数派读写可以不要主」**，**把选主（多节点中选出一个负责决策的主节点的过程）与切换的开销省掉，代价是把这个开销转移给了开发者（一致性语义变弱，要自己处理旧读与冲突）**。

quorum 的 **W+R>N 交集论证**是这套机制的数学底座。**一行集合论保证读覆盖到写：写集合与读集合在 N 个副本上的交集非空，交集里的副本必然持有最新值**。

这个数学上极简的保证，**让无主系统在任意时刻可调（W+R=N 强，W+R<N 快但可能旧读）——把一致性做成参数，是 Dynamo 系留给行业的主要贡献**。代价：三种拓扑是按**业务对丢写与旧读的容忍度**排序的阶梯。

**主从+同步复制是丢写零容忍的默认选择**；**多主与无主用一致性换可用性/延迟，适合可以旧读但不能丢数据丢失感知的场景（购物车丢了用户重来，聊天记录丢了不可接受）**。**选型时先问业务语义：这笔写丢了会怎样？**

**这条读旧了会怎样？答案决定拓扑**。

```mermaid
graph TD
    N5["N = 5 个副本"] --- W3["写 W = 3 份"] --- R2["读 R = 3 份"]
    W3 -.->|"写集合 ∪"| I["交集至少 1 个副本"]
    R2 -.->|"读集合 ∩"| I
    I -->|"交集副本持有最新版本"| G["读必不旧于已完成写"]
    T["W+R ≤ N 的反例<br/>W=1 R=1：写落 1 号读打 2 号"] -.->|"读到旧值"| B["交集为空 保证失效"]
```

交集论证画出来就一行：**N 个副本里写 3 份、读 3 份，两个集合在 5 个副本上至少交 1 个，交集副本必然带着最新版本号**。**W 与 R 是可调的旋钮——往强调（W=N, R=1），往快调（W=1, R=N），唯独 W+R>N 这条线不能破，破了交集为空**（图下的反例：写落 1 号、读打 2 号，读到旧值）。把一致性做成参数，是这套数学对工程最大的便利；**参数由业务语义挑，不是默认值说了算**。

## 这套说法在哪儿会失效

- **同步复制的「不丢」以延迟为价**。**同步等确认（semi-sync 等 N 个）让主库写延迟受网络 RTT（Round-Trip Time，一个数据包从发出到收到应答的往返时间）放大（同机房 1ms，跨地域 30ms+），跨地域同步复制在数学上受光速约束**。**异地多活必然异步或多主，「跨地域不丢+强一致」是物理上做不到的组合**，见 CAP 详见超时（上文链接）。
- **故障切换不是瞬时事件是窗口**。**主宕到新主可写之间的秒到分钟窗口，写全部失败或排队**；**切换期间「哪台是主」的判定靠共识（consensus：Raft/Paxos），现代数据库把选主内建（etcd 系、MongoDB replica set），老式人工切换的高危操作已进化**。**但窗口存在本身没变——RTO（恢复时间目标）是 SLA（服务等级协议，对外承诺的可用性与响应目标）的一部分**。
- **复制不等于备份**。**复制防机器失效不防误删（DROP TABLE 删整表在从库同样重放）、不防逻辑损坏（bug 写坏数据，从库忠实复制坏数据）**。**备份是时间维度的独立防线**，见 [[工程知识/数据系统：在并发与故障中保存事实/可靠性与运维/备份的价值由恢复演练来验证.md]]。
- **从库不只是热备，还是读扩展与数据出口**。**读写分离（写入走主库、查询走从库的架构）分摊读负载**；**从库做分析查询、CDC（Change Data Capture，变更数据捕获：把数据库的增量改动当成事件流发出去） 源[[工程知识/数据系统：在并发与故障中保存事实/数据管道与流处理/CDC把数据库变化传播为可重放事实.md]]，把重查询从主库卸载**。**从库延迟（复制延迟）是读写分离的天花板，延迟大的从库读到的旧数据需要会话保证（姊妹篇）**。

## 这一例要怎么验证

- **同步与异步的行为差异实测**：PostgreSQL（开源关系型数据库）同步复制（synchronous_standby_names）与异步配置下插入延迟对比，预期：**同步复制延迟增加 1 个 RTT 量级**；主库突然断电（或 pg_ctl stop -m immediate）后重启，**预期：异步从库存在滞后窗口（某些已确认事务在新主不存在），同步复制无丢失**。**这是两种模式的代价最直接证据**。
- **复制延迟观测**：pg_stat_replication 的 write/lag 字段，压测主库写、从库读，**预期：延迟随写压力上升，从库重放有单调趋势**；**从库滞后造成的「写后立即读」读旧实验（会话保证的实况）**。
- **quorum 交集验证**（如有环境）：Cassandra/DynamoDB 调 W/R 参数（W=1,R=1 vs W=N,R=N），并发写读，**预期：弱 quorum 下读到旧值概率上升；W+R>N 配置下读不旧于已完成写**。**参数与行为的对应是交集数学的实证**。
