# 分区再平衡的三种策略：固定取模与一致性哈希

## 要解决的问题

分区（sharding）把数据水平切到多台机器，每个分片只存一部分。切完之后机器数会变：扩容（加机器）、缩容（减机器）、机器坏了（替换）。每次机器数变化，数据到机器的映射要重新计算，**已有数据要搬家**。再平衡策略要解决的核心问题：机器数变化时，数据移动量多大、哪些键的归属变化、移动期间服务怎么持续。三种策略是:固定取模（最朴素）、哈希空间分桶（range 分区的对偶）、一致性哈希（Dynamo 系标配）。存量文章一致性哈希把再平衡的数据移动量压到平均槽位（见 [[工程知识/数据系统：在并发与故障中保存事实/事务与存储/一致性哈希把再平衡的数据移动量压到平均槽位.md]]）写哈希环的机制，本文写三种策略的谱系与再平衡过程的工程问题。

## 机制

**固定取模：机器数的囚徒**。key % N（N 为机器数）：计算最简，但 N 变化（N→N+1）时几乎全部键重新映射——数学上，N+1/N 的键换归属。加一台机器，全库数据搬家，缓存集体失效（缓存场景=雪崩）。除了机器数固定的小场景，这个策略在扩缩容自由的云环境基本不可用。它的存在价值是反例：说明“映射对 N 的敏感度”是再平衡策略的核心指标。

**哈希空间分桶**。先把哈希空间切成固定数量的槽（slot，如 Redis 的 16384），槽再分配给机器。机器数变化时只调整槽的归属，槽内数据随槽走。移动量从“全库”降到“该机器该挪的槽”。槽的数量固定（提前切好），机器数变化不影响槽边界——这是与固定取模的本质区别。槽分配策略可以人工（Redis cluster 的人工迁移）、可以自动（按机器容量加权）。代价：槽数量要预估（切太少以后加机器分不匀，切太多管理开销大），槽迁移期间的双写与路由切换要协调。

**一致性哈希：机器就是哈希环上的点**。机器也哈希到环上，key 顺时针找最近的机器。机器加入/离开只影响环上相邻区段——移动量从“该挪的槽”降到“相邻区段的数据”。虚拟节点（vnode）修复均匀性：一台机器占环上多个点（数百个），区段归属的平均化由大数定律保证。再平衡时该机器的全部 vnode 一家家搬，对每台旧机器都是小口啃噬而非一次大搬家。

**再平衡过程的工程问题**（三种策略共同）。数据搬迁期间的路由：搬迁中的键到底问谁（旧主还是新主）？常用协议：搬迁进行中，写双发或写旧主+异步迁移；读旧主直到切换确认。搬迁速度与前台负载的平衡：全速搬迁压垮磁盘与网络，太慢则扩容迟迟不能分压。搬迁的原子切换点：一个键的归属从旧主到新主的瞬间，写入必须严格单点（否则脑裂），见租约与 fencing（见 [[工程知识/后端系统：在并发、失败与变化中维持服务/分布式可靠性/租约必须配合FencingToken阻止过期持有者.md]]）。

## 场景与代价

思想背景：固定取模是分布式哈希表（DHT）研究的起点，也是它自己的否定：Chord 论文（2001，MIT）与 Karger 的一致性哈希（1997）都在解决“节点加入离开的动荡”。一致性哈希的工程化是 Dynamo（2007）与 Cassandra，虚拟节点的引入（Dynamo 论文里叫 token）修复均匀性。哈希空间分桶的代表作是 Redis Cluster 的 16384 槽。

最精巧的一笔是**虚拟节点把“机器亲和”变成“ vnode 亲和”**。物理机对应环上一个点时，相邻区段的归属与机器负载强绑定（一台机器失效，它的全部负载只能由顺时针邻居扛）； vnode 化后，一台机器的负载散布在环上数百处，它的失效负载由几乎全部机器分摊，恢复也并行。这一笔还顺手解决了异构集群的容量加权（容量大的机器多占 vnode）。代价要摆明：一致性哈希的“最小移动”是渐近性质，不是每次保证——vnode 迁移的并行度、热点键的集中（哈希不匀或业务热点）、槽/环的元数据路由层的一致性（路由表过期期间读写打到错机器），这些都要工程化处理，详见存量一致性哈希篇（上文链接）的深水区。三分支选型：机器数极稳定用固定取模（内网小集群）；机器数常变、数据量大用一致性哈希（在线服务标配）；需要范围扫描与业务语义分片（按用户、按时间）用范围分区分+哈希空间分桶混合（LSM 的 range 分片、Bigtable 系）。

## 边界

- **哈希分区的代价是范围查询能力**。hash(key) 把相邻键打散到全集群，range scan（按时间区间取数、按前缀扫列）变成全分片 scatter-gather。范围分区保留顺序性但热点风险（头部分片热）。OLTP 点查用哈希、OLAP 扫描用范围，见列存与向量化执行（见 [[工程知识/数据系统：在并发与故障中保存事实/查询与索引/B+Tree索引为访问路径服务.md]]）的布局对偶视角。
- **热点是哈希分区治不了、又必须治的**。 celeb 键（明星用户的主页读写集中）、单调递增键（时间戳键全部落最右分片）是哈希与范围分区各自的坑。缓解：热点键加盐（key 前缀加随机数再哈希，读时 scatter）、分片内再排队（热点分片降级单写）。彻底解要业务层（热点键单独缓存层）。
- **再平衡期间的性能凹陷是常态**。搬迁 IO 与前台争带宽，P99 延迟在搬迁窗口劣化。运维排程（低峰搬迁、限速）是标配；监控要含搬迁进度与前台延迟的联动曲线，见脏页回写（见 [[工程知识/性能工程：从用户等待到资源瓶颈/操作系统与运行时/脏页回写在性能与崩溃丢失窗口间权衡.md]]）的回写调优同源思想。
- **路由层的一致性常被低估**。客户端缓存的分片表过期（搬迁后仍打旧主），旧主的响应是“moved”（重定向）或错误。缓存刷新的及时性与重定向协议的完备性，决定扩缩容期间的用户可见错误率。分片表的分发本身是一个元数据一致性问题（ ZooKeeper/etcd 系），见复制的三种模式（上文链接）的选主段。

## 验证

- **固定取模的动荡复现**：模拟 N=4→N=5 的 key 归属变化，1 万个均匀 key 统计换主比例，预期：约 80% 换主（N/(N+1)）；一致性哈希同实验，预期：约 25% 换主（1/(N+1)）。两个数字的对比是策略差异的最小证明，纯计算实验 10 分钟可做。
- **vnode 均匀性实验**：环上 4 机器 × 1 vnode vs 4 机器 × 256 vnode，均匀投 10 万 key，统计每机器占比的方差，预期：vnode 化后方差缩小一个数量级。虚拟节点数量与均匀性的收益曲线拐点。
- **再平衡负载观测**（如有环境）：Redis Cluster 扩容（cluster add-node + reshard）期间监控 QPS 与延迟，预期：搬迁分片的前台延迟劣化、搬迁结束后恢复。限速搬迁 vs 全速搬迁的对比数据是运维排程依据。
