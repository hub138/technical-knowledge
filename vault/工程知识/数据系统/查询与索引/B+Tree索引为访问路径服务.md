# B+Tree 索引为访问路径服务

索引不是“越多越快”，而是为特定过滤、连接、排序和覆盖路径保存有序导航结构；它用写放大、空间和维护时间换取读取时少扫描一些页。一个索引是否有效，只能在真实数据分布和查询计划下判断。

## 最小索引实验

固定数据量和缓存状态，比较无索引、单列、联合和覆盖索引的实际扫描行数、回表次数、写入成本与 p95；再改变选择性、排序和分页深度。若估算行数与实际行数偏离，先检查统计信息和数据分布，不要仅凭 `EXPLAIN` 的一行 `key` 宣布优化成功。

## B+Tree 和回表

InnoDB 是索引组织表：主键索引（聚簇索引）的叶子节点保存整行，二级索引叶子节点保存索引列和主键值。二级索引命中后再查主键索引称为回表；只查询二级索引已有列则是覆盖索引，可减少随机 I/O。

```text
二级索引 -> 主键值 -> 主键索引 -> 整行
覆盖索引 -> 二级索引叶子节点直接返回
```

主键应尽量短、稳定、单调追加。随机、宽大的业务主键会放大所有二级索引的空间和页分裂成本；是否使用业务字段做主键要结合唯一性、长度、写入顺序和迁移风险判断。

## 联合索引设计

- 遵循最左前缀：`(a,b,c)` 可支持 `a`、`a,b`、`a,b,c` 的连续前缀，不能把 `b` 单独当作同等路径。
- 字段顺序先看查询模式和选择性，再看排序、分组、覆盖和复用能力；不要只按“区分度从高到低”机械排列。
- 让索引尽可能覆盖过滤、连接和排序，减少回表；同时控制索引数量，避免写放大、空间和维护成本。
- 对低选择性字段（如状态）不要孤立建索引，除非与其他条件组成有效联合索引。

## 字符串索引

前缀索引 `INDEX(email(8))` 节省空间，但可能扫描更多候选行，且不能提供完整覆盖索引。用实际数据测量不同前缀长度的 `COUNT(DISTINCT LEFT(col,n))`，并用线上查询验证。

只需要等值查找、又无法承受长字符串索引时，可考虑：

- 增加规范化后的 hash/CRC 列并建立索引，命中后再用原值校验；需要处理 hash 冲突。
- 倒序存储解决后缀等值查询，但不支持范围查询，并增加读写转换成本。

## 普通索引、唯一索引和 change buffer

查询性能差异通常很小；唯一索引需要更早检查冲突。目标页不在 Buffer Pool 时，普通二级索引的变更可以先写入 change buffer，减少随机读，后台或访问该页时 merge。写多读少收益较好，写后立即读会很快触发 merge，可能抵消收益。

因此索引类型首先由业务约束决定：确实需要唯一性才用唯一索引；不能为了 change buffer 牺牲数据约束。对写多读少的历史/日志类表，再评估 change buffer 参数和磁盘类型。

## 优化器为什么会选错

优化器根据基数、采样统计、直方图（版本支持时）、回表成本和排序成本估算扫描行数。数据分布变化、相关列统计失真、参数化查询和索引过多都可能让估算偏离实际。

处理顺序：

1. 对照实际执行计划和数据分布，确认不是缓存、锁或 I/O 问题。
2. `ANALYZE TABLE` 更新统计信息，必要时补充直方图。
3. 改写谓词或排序表达式，使目标索引的成本更清楚；检查隐式转换和函数。
4. 只有在验证稳定且有回归保护时才使用索引提示；长期方案通常是调整索引或数据模型。

## 排序、JOIN 和分页

- `ORDER BY` 若不能沿索引顺序输出，会出现 `Using filesort`；检查联合索引的过滤列、排序列和方向。
- 大偏移分页会扫描并丢弃前面的行；优先使用基于稳定键的 seek/keyset pagination。
- JOIN 不是原罪。保证连接列类型一致、有合适索引、驱动表过滤充分，并用执行计划确认嵌套循环的实际代价。
- 多表大批量连接可评估 Multi-Range Read、Batched Key Access 或先缩小中间结果；不要仅靠拆 SQL 规避问题。

## 查询改写底线

```sql
-- 可能失去索引范围能力
WHERE YEAR(created_at) = 2026

-- 将范围改写为可搜索谓词
WHERE created_at >= '2026-01-01'
  AND created_at <  '2027-01-01'
```

同时检查字符串与数字的隐式类型转换、`LIKE '%x'`、无界 `ORDER BY`、`SELECT *` 和未限制的 `IN` 列表。任何改写都要以等价性测试和真实数据基准为准。
