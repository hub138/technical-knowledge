# 事务隔离决定并发读写能观察到什么

## 核心拆解

| 维度 | 回答 |
| --- | --- |
| 要解决的问题 | 多个事务同时读写时，系统必须定义每次读取能看到哪些版本、哪些冲突需要等待，以及提交后数据何时可见。 |
| 本质 | ReadView、undo 版本链和锁共同定义“可见性”和“互斥”；隔离级别是在一致性、并发和阻塞之间选择观察规则。 |
| 做法 | 按业务不变量选择 RC/RR 等隔离级别，区分快照读与当前读，缩短事务，统一锁顺序，并为不确定提交设计幂等重试。 |
| 效果与代价 | 快照读减少读写阻塞，锁保护冲突更新；代价是长事务、undo、死锁、锁等待和更高隔离级别的并发损失。 |
| 边界 | 事务只覆盖数据库内的原子边界，不能把网络、模型或消息自动纳入同一事务；复制延迟也不由隔离级别解决。 |
| 验证 | 用并发读写、范围锁、死锁、长事务、提交超时和副本延迟场景，核对可见版本、业务不变量、等待时间和恢复行为。 |

## 隔离级别和可见性

InnoDB 常用 `READ COMMITTED`（RC）和 `REPEATABLE READ`（RR）。

| 读法 | 含义 | 是否加行锁 |
| --- | --- | --- |
| 一致性读/快照读 | 从 ReadView 和 undo 版本链得到可见版本 | 普通 `SELECT` 不加行锁 |
| 当前读 | 读取最新已提交/自己的版本并参与锁规则 | `UPDATE`、`DELETE`、`FOR UPDATE`、`FOR SHARE` |

RR 通常在事务第一次快照读时建立并复用 ReadView；显式 `START TRANSACTION WITH CONSISTENT SNAPSHOT` 可立即建立快照。RC 通常在每条语句前建立新视图。`BEGIN` 本身不一定触发 InnoDB 快照，真正的时间点取决于第一次相关读操作。

每行带有事务版本信息，旧版本通过 undo 链接。ReadView 根据活跃事务 ID、低水位和高水位判断版本是否可见；因此快照读可以不阻塞写，但长事务会阻碍 purge 并放大 undo 和空间占用。

## 锁的层次

- **全局锁**：如 `FLUSH TABLES WITH READ LOCK`，主要用于全库一致性备份；优先评估 `single-transaction` 等不阻塞业务的方案。
- **表锁**：显式 `LOCK TABLES`，MyISAM 等非事务引擎更常见。
- **MDL**：访问表自动获得 MDL 读锁，DDL 需要 MDL 写锁。长事务或频繁访问会让加字段、加索引排队；DDL 要设置等待上限并提前清理长事务。
- **行锁/间隙锁/Next-Key Lock**：InnoDB 在索引记录和间隙上控制当前读。RR 下范围当前读可能锁住间隙以避免幻读；实际锁范围取决于索引、谓词和执行计划。

## 两阶段锁和死锁

行锁按需获取，但通常到事务提交/回滚才释放，称为两阶段锁协议。一个事务需要锁多行时，尽量把最可能冲突的锁放后面，并让所有代码按相同顺序访问资源。

死锁检测只在等待加锁时触发；热点行高并发可能让死锁检测本身消耗大量 CPU。处理顺序：

1. 缩短事务、减少锁范围和锁持有时间。
2. 统一访问顺序，拆分热点行或按业务键分片，必要时在服务端排队控制并发。
3. 应用捕获死锁错误并以幂等方式重试。
4. 只有确定业务不会形成死锁且有外部并发控制时，才评估关闭 `innodb_deadlock_detect`；不能用调参掩盖锁设计问题。

## 设计边界

- 事务要短且有明确边界；网络调用、模型调用、人工等待不能放在数据库事务内。
- 所有重试都要有幂等键，尤其是提交超时后无法判断“服务端是否已提交”的情况。
- 需要强一致读取时使用主库或当前读；读写分离必须把复制延迟纳入业务语义，而不是只做流量分配。
- 插入、自增和唯一性检查也会参与锁竞争；批量写入要控制批次大小和索引数量。

## 现场检查

```sql
SHOW PROCESSLIST;
SELECT * FROM information_schema.innodb_trx;
SELECT * FROM performance_schema.data_lock_waits;
```

再结合 `SHOW ENGINE INNODB STATUS`、慢日志和应用 trace 对齐阻塞者、被阻塞者、事务开始时间、SQL 指纹和业务请求。
