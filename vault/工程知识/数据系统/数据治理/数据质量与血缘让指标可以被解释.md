# 数据质量与血缘让指标可以被解释

## 核心拆解

| 维度 | 回答 |
| --- | --- |
| 要解决的问题 | 指标异常或模型效果下降时，如果不知道数据来自哪里、经过哪些变换、是否新鲜，就无法判断是业务变化还是数据故障。 |
| 本质 | 质量契约定义数据是否满足用途，血缘把来源、变换、版本和消费者连成可追溯图。 |
| 做法 | 为关键数据集登记 schema、主键、范围、分布、延迟、删除语义、敏感级别和所有者，并让失败状态传播到下游。 |
| 效果与代价 | 指标可解释、影响范围可计算、坏数据能被隔离；代价是采集元数据、维护契约和处理误报的成本。 |
| 边界 | 完整性检查不等于业务准确性；血缘能说明传播路径，不能单独证明因果或模型回答正确。 |
| 验证 | 持续注入 schema 漂移、迟到、重复、权限撤销和样本污染，抽样回到来源并检查质量报告、版本和下游阻断。 |

数据质量不是“表里没有 NULL”，而是数据在特定使用场景下满足及时性、完整性、唯一性、准确性、一致性、合法性和可追溯性。血缘把来源、变换、版本和消费者连接起来，才能解释指标变化和影响范围。

## 质量契约

每个关键数据集定义 schema、主键/唯一性、范围、分布、时间延迟、删除语义、敏感级别、所有者和失败动作。契约失败时要阻止下游发布、隔离坏分区或标记不可信，不能只发告警后继续喂模型。

## AI 场景

训练集、评测集、embedding、RAG 索引和在线特征都需要血缘。一个答案变差时，应能追到源文档、解析器、切分、embedding、索引、模型和 prompt；没有这条链路，任何“模型回归”结论都可能是数据变化。

质量检查应服务于用途：用于财务结算的数据需要完整、可审计和可重放，用于探索性推荐的数据可能允许迟到但必须标注新鲜度。把所有数据集套同一阈值会制造告警噪声，也会掩盖真正影响决策的字段。

## 验证

持续检查 schema、唯一性、分布漂移、迟到、重复、权限、删除传播和样本污染；随机抽样回到原始来源。给每次数据发布生成质量报告、版本和影响下游列表，并将失败状态传播到消费方。

最小实验：故意引入一列类型变化、重复主键、迟到分区和一条已撤权文档，跟踪质量门禁、血缘图、下游指标和 RAG 索引。检查坏数据是否被隔离、影响范围是否可定位，以及恢复后报告是否保留原始版本。
