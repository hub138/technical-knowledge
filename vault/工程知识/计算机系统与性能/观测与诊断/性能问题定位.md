# 性能问题定位方法

性能定位不是寻找一个“最慢函数”，而是把用户影响、资源等待、调用路径和可复现实验串成证据链。任何修复都要证明目标 SLO 改善且没有把成本、错误或尾延迟转移到另一层。

同一条请求的慢点可能出现在排队、锁、I/O、网络或业务计算；先按时间线定位等待段，再用 profile 或最小实验确认因果，才能避免对错误层次优化。

## 先区分四类现象

1. **延迟问题**：平均延迟、尾延迟、锁等待、IO 等待或下游等待上升。
2. **吞吐问题**：并发上升后 QPS 不再增加，或队列持续积压。
3. **正确性问题**：结果错误、数据丢失、重复执行、主备不一致。
4. **稳定性问题**：崩溃、内存泄漏、死锁、连接耗尽、资源耗尽。

同一个症状可能由不同层次造成。例如“SQL 慢”可能是计划改变、锁等待、IO 抖动、连接池排队或网络传输，而不一定是 SQL 文本本身。

## 根因证据链

```text
用户请求
  -> 服务日志/Trace（发生了什么）
  -> 数据库指标/慢日志（在哪里等待）
  -> 系统指标/Profile（资源是否紧张）
  -> 源码与配置（为什么走这条路径）
  -> 最小实验（改变后是否消失）
```

## 最小实验原则

- 固定版本、配置、数据规模和负载，只改变一个关键变量。
- 先做只读观测，再做低风险实验；生产写入、重启和参数变更需要审批。
- 记录基线、样本数、置信区间和失败样本，不用一次成功替代统计结论。
- 任何修复都要有反例：高并发、空值、大数据、异常中断、重复请求和降级路径。

## 数据库问题检查表

- [ ] 执行计划和实际行数是否一致？
- [ ] 是否存在长事务、锁等待、死锁或复制延迟？
- [ ] Buffer Pool、磁盘、网络和连接池是否达到边界？
- [ ] 重试和超时是否可能造成重复执行？
- [ ] 日志是否足够恢复完整时间线？
- [ ] 修复是否在原始用例和相邻用例上都验证？

## 三个容易漏掉的维度

| 维度 | 要追问什么 | 需要的证据 |
| --- | --- | --- |
| 积累 | 问题是否随连接、对象、缓存、队列或运行时长累积？ | 时间序列、heap/profile、对象/队列计数和稳定负载 |
| 时序 | 是否只在特定并发交错、切换、超时或重试顺序下发生？ | 带时钟的 trace、线程/锁事件、请求 ID 和故障注入 |
| 可观测缺口 | “没有错误”是否只是没有记录？ | 日志覆盖、指标基数、采样策略和 unknown 状态 |

排障不是只看 SQL 文本或最终错误。先判断是随时间累积、由特定事件顺序触发，还是关键观测缺失，再选择 heap、profile、trace、日志或最小并发实验。

### 一个值得保留的案例方法

[[知识库管理/归档/来源/实践证据/TDSQL小表热点案例.md]] 的长期价值在证据链，而不是“给表添加字段/索引”这个项目结论：

```text
CPU profile 发现调度/锁热点
  -> 源码把热点收敛到 buffer page 获取
  -> uprobe 记录真实 page 标识
  -> 数据库元数据识别 page 类型
  -> 失败实验解释为什么原方案无效
  -> 新方案用相同负载重新压测
```

这说明 profile 用于缩小范围，trace/probe 用于观察具体对象，元数据用于解释语义，受控实验用于验证因果。案例中的数据、函数和优化结果只适用于当时版本与负载，不能直接推广到其他数据库或业务表。
