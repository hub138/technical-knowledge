# 系统指标与观测方法

指标用于发现“什么时候、哪个资源域发生异常”，trace 用于串起请求路径，profile 用于解释时间或资源花在哪里，日志用于保留离散事件和上下文。任何一种都不能单独完成根因证明。

例如 p99 上升但 CPU 不变，可能是锁、网络、磁盘、GC 或队列等待；只有把 RED 的用户影响与 USE 的资源饱和、trace 的等待段和 profile 的调用路径对齐，才能缩小根因范围。观测系统本身也要暴露采样缺失和 unknown，而不是把空值当成零。

## 四类证据

| 证据 | 最擅长回答 | 不能单独回答 |
| --- | --- | --- |
| Metrics | 趋势、容量、SLO、告警 | 单个请求为何失败 |
| Traces | 一次请求在哪一段等待 | 函数内部 CPU/分配细节 |
| Profiles | CPU/off-CPU/内存在哪个调用路径 | 业务输入和跨服务因果 |
| Logs/Events | 特定状态变化和错误上下文 | 全量趋势与统计分布 |

## USE 与 RED

- **USE（资源视角）**：Utilization、Saturation、Errors；依次检查 CPU、内存、磁盘、网络、连接池、线程池和队列。
- **RED（服务视角）**：Rate、Errors、Duration；从用户请求出发，再下钻到资源。

资源利用率不是瓶颈的充分条件。CPU 100% 可能仍达到 SLO；现代并行 SSD 的 `%util` 也不代表性能极限。必须同时看排队、吞吐和尾延迟。

## 常用 Linux 入口

```text
总体: uptime, vmstat, pidstat
CPU: mpstat, perf, /proc/stat
内存: free, vmstat, /proc/meminfo, PSI
存储: iostat -x, pidstat -d, fio（验证）
网络: ss, ip -s link, ethtool, nstat, tcpdump
历史: sar（确认采样配置和口径）
```

`sar` 适合查看 sysstat 已采集的历史切片，但它无法补回未采集的 trace/profile，也会因采样间隔遗漏短尖峰。命令示例必须和 sysstat 版本、单位、采样间隔、时区、设备映射一起记录。

## 调查顺序

1. 固定问题窗口、时区、版本、请求类型和基线。
2. 用 RED 判断用户影响，用 USE 找资源域；检查队列而非只看利用率。
3. 用 trace 对齐上下游和重试；用 profile/eBPF 深挖 CPU、锁、I/O 或分配。
4. 提出可被最小实验区分的假设，一次只改变一个变量。
5. 验证业务 SLO、资源代价和错误是否共同改善，并保留回滚阈值。

## 数据质量

- counter 先求 rate，并处理进程重启/回绕；gauge 不应被随意累计。
- histogram bucket 设计应覆盖 SLO，平均延迟不能代表尾部。
- 标签维度控制基数；用户 ID、URL 全路径和异常文本不能直接作为 metric label。
- 主机/容器/进程/请求使用稳定 resource attributes 关联。
- 采集缺失与数值为零是不同状态；报告显式显示 unknown。
