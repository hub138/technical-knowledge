# 端到端网络延迟来自排队、协议、传输与处理

网络性能是端到端路径的结果：应用排队、连接建立、协议处理、链路 RTT、拥塞、丢包、服务端调度和客户端消费都会贡献延迟。

浏览器或 SDK 测到的 800 ms 不能直接归因于网络：其中可能包含连接池排队、TLS、服务端队列、下游调用、重试和客户端读取。只有把一条请求的时间线拆开，才知道该优化链路、协议还是服务实现。

## 从请求到响应

~~~text
应用排队 -> DNS/连接池 -> TCP/TLS -> HTTP/gRPC
         -> 服务端队列/线程 -> 下游调用 -> 响应传输/客户端读取
~~~

- TCP 提供有序可靠字节流，但重传、拥塞窗口和队头阻塞会增加尾延迟。
- UDP 只提供数据报传输；可靠性、顺序、拥塞和重试必须由上层协议负责。
- HTTP/2 多路复用减少连接数量，但共享连接上的队头阻塞和流量竞争仍需观察；HTTP/3/QUIC 的收益依赖客户端、网络和服务端支持。
- 带宽是容量，吞吐是实际完成量，RTT 是往返时间，丢包和重传会放大延迟；四者不能互相替代。

## 定位方法

1. 用 trace 和 access log 对齐 DNS、连接、TLS、服务端处理、下游等待和响应发送时间。
2. 用 ss、ip、ping、mtr、tcpdump/Wireshark 观察连接状态、RTT、重传、窗口和丢包；抓包注意隐私和权限。
3. 用 iperf3 或业务级压测建立容量基线，分离网络链路瓶颈与应用/数据库瓶颈。
4. 检查连接池、keep-alive、超时、重试、并发上限、代理、负载均衡、MTU 和内核队列。
5. 在单变量改变后比较 p50/p95/p99、吞吐、重传、CPU、软中断和错误率。

最小网络实验：固定响应大小和服务端处理时间，分别复用连接、重建连接、注入 1% 丢包、增加 RTT 和限制客户端读取速率；记录 DNS/TCP/TLS、排队、服务端处理、首字节和完整响应时间。若只有完整响应变慢，优先检查传输/消费；若首字节已变慢，检查服务端或入口队列。

## 调优边界

- 先确认瓶颈层，再调 TCP、内核或代理参数；参数优化不能修复错误的重试和超时策略。
- 重试必须有上限、退避、幂等和总预算；否则网络抖动会放大成雪崩。
- 大响应采用分页、压缩或流式协议；限制单请求大小并支持客户端取消。
- 负载均衡只改变流量路径，不自动提供一致性、幂等、故障恢复或应用级健康检查。
