# 成本要对账才能被治理：记账粒度、预算归属与超支信号

模型按 token（模型计费与计数的最小单位，中文里大致几个字到十几个字对应一个 token）计费，而治理要回答"这笔钱该谁付、花在哪个功能上、为什么超了"，**中间隔着一层记账：粒度太粗算不出归属，太细又采集不动**。读完这篇你能给自己的 AI 服务**设计一套记账粒度、把预算分到真实的责任主体上，并在超支发生前而不是账单寄到后拿到信号**。

成本控制要从上下文和重试两头下手 [[工程知识/AI 系统工程：从模型能力到生产能力/质量与运营/成本控制要从上下文和重试两头下手.md]] 讲的是把开销压下来的动作，本篇讲的是**让这些动作有数据可依的记账底座——没有对账，优化是不是真省了钱都无法验证**。

## 要解决的问题：为什么按请求记的账对不上按 token 计的费

一次用户请求进来，业务方想的是"这个功能花了多少钱"，账单上出现的是"某个模型 key 消耗了多少输入与输出 token"。**两个口径对不上，治理就落空：没人知道某条业务线用了三成预算还是七成，超支了也定位不到是哪次上线、哪个租户造成的**。

成因在计量与消费之间隔着三次聚合错位：

1. **按请求聚合丢掉 token 构成**。**同样的"一次请求"，检索问答与长文生成的 token 数可以差几十倍，请求次数相同的两天账单可以差数倍**。
2. **按模型 key 聚合丢掉业务归属**。**多个功能共用同一个调用凭证时，账单只能告诉你 key 花了多少，不能告诉你哪个功能花的**。
3. **按天聚合丢掉事件归因**。**日账单只能给出总额，回答不了"周三那次成本跳变是哪次发布带来的"**。

## 它是怎么做到的：三层记账粒度各答一个问题

可以把它想成公司的报销制度：出差坐了几趟车是计量（token 用量），每个部门报了多少是归集（预算归属），月度超支要写说明是问责（超支信号）。报销制度管不了差旅花销本身，但没有它，花销就变成一笔谁也说不清的糊涂账——这个比喻到"三件事要分开做"为止，真实系统里三层共用同一份明细数据，不存在三套账。

记账的三层粒度与它们的对应物：

| 层 | 记什么 | 回答什么 | 载体 |
| --- | --- | --- | --- |
| 明细层 | 每次调用的输入/输出 token、缓存读写、模型、时间 | 这笔钱怎么构成的 | 调用层日志或 trace 属性 |
| 归集层 | 按功能/租户/任务类型聚合的周期费用 | 预算花在谁身上 | 明细按维度聚合的账本 |
| 信号层 | 预算余量、消耗速率、异常跳变 | 谁该在什么时候被叫醒 | 告警规则与看板 |

明细层的字段有现成的行业标准可依：OpenTelemetry 的 GenAI 语义约定规定了 `usage.input_tokens`、`usage.output_tokens` 等属性，任何符合约定的后端都能聚合这棵记录树 [[工程知识/AI 系统工程：从模型能力到生产能力/质量与运营/可观测性必须能重建一次决策.md]]——重建决策需要的字段（模型版本、检索证据、工具参数）与对账需要的字段（token 用量、缓存命中）落在同一份 span 树上，一次采集服务两个目的。

**归集层的关键决策是预算挂在什么主体上**。**挂错主体，超支告警就会叫醒错误的人**：

- **挂在调用凭证（API key）上**：**实现最简单，但一个 key 服务多个功能时无法区分责任**。
- **挂在业务功能上**：**需要调用层显式写入功能标识，这笔小开销换来的是归因能力**。
- **挂在租户上**：**多租户服务必需，配额是租户隔离的一部分**。

定价换算的中间量（单价、缓存折扣、批处理分摊）由成本模型给出 [[工程知识/AI 系统工程：从模型能力到生产能力/推理服务与平台/推理服务的单位请求成本从token定价推出来.md]]，本篇不重复推导，只要求一点：**归集层用的换算系数与定价推导用的是同一套，两处各算一套必出分歧**。

## 效果从哪儿来，要付什么代价？

对账机制带来的直接能力有三项。**其一是超支可归因：预算按功能拆开后，账单偏差超过阈值时能定位到具体功能与时间段，处置动作（回滚发布、收紧配额、修缓存配置）有了明确对象**。**其二是优化可验证：缓存命中率（请求直接从缓存拿到结果的比例）、重试率这些优化杠杆的效果，只有从对账数据里才能读出来——"省了钱"从体感变成数字**。**其三是预算可以提前谈：有历史账本，容量与预算讨论就从"拍数字"变成"按曲线外推"**。

代价与失效边界同样清楚。**记账本身是观测，观测有成本** [[工程知识/性能工程：从用户等待到资源瓶颈/观测与诊断/指标、日志、Trace与剖析各答一问，合起来才构成证据.md]]：**明细层记录每次调用的 token 与费用，存储与查询开销随调用量线性增长**，高频低值调用（如心跳式的小请求）是否记全量明细要做取舍。**换算系数会失真：定价调整、缓存策略变化、模型替换都会让历史系数过期，账本要带生效时间戳，跨系数周期的对账要分段算**。**内部转移定价（把平台成本分摊给业务方）是治理决策，分摊规则本身引起的争议不属于工程对账能解决的范畴**。

## 超支信号：要在账单寄到前拿到通知

**预算的价值在超支发生前的信号，不在事后的账单确认**。三档信号按响应动作分级：

![成本对账链：明细层按维度聚合进归集层，再分出速率、水位、跳变三档信号，各自绑定定位、降级、回查三类响应动作](/static/figures/cost-recon-signals.svg)

图：信号层的三档告警各自对应不同的响应动作，**触发条件写进告警规则而不是靠人看账单**。

三档信号的判据：

1. **速率信号**：当前消耗速率外推到周期末超出预算时触发。**它比水位（队列或资源的当前占用程度）信号早，因为它不等问题过半**。
2. **水位信号**：消耗达到预算的固定比例（如 80%）时触发。**动作要预先绑定——降级（压力过大时关闭次要功能，保住主流程）到便宜模型、收紧限流**（限制单位时间内的请求量、超出部分拒绝或排队），动作本身在 LLM 网关（架在调用方与模型服务之间的一层代理，集中管鉴权、预算、限流与降级）里现成 [[工程知识/AI 系统工程：从模型能力到生产能力/推理服务与平台/LLM网关把模型调用变成可治理的流量：鉴权、预算、限流与降级.md]]。
3. **跳变信号**：日消耗环比跳升超过阈值（如 50%）时触发，**最常见的成因是一次发布引入了重复调用、缓存失效（缓存里的数据过期或不一致、需要回源加载）或循环重试** [[工程知识/AI 系统工程：从模型能力到生产能力/Agent与工作流/结构化输出与约束解码：schema约束形状，事实另需验证.md]] 里记录的重试风暴就是跳变的典型来源。

告警的分级与降噪遵循通用的告警纪律 [[工程知识/性能工程：从用户等待到资源瓶颈/观测与诊断/报警治理的降噪三件事：分级收敛与值班可持续.md]]：**成本告警挂在水位与跳变上，速率信号进看板，不把每次偏差都做成告警——告警疲劳会让真正的超支被淹没**。

## 怎么自己动手验证

1. **对账闭环**：从明细日志聚合（把分散在多台机器的日志集中到一处检索）出周期成本，与供应商账单对比。**偏差超过 20% 说明某个中间量错了（常见的是缓存命中率与重试率假设），先补观测再谈治理** [[工程知识/AI 系统工程：从模型能力到生产能力/推理服务与平台/推理服务的单位请求成本从token定价推出来.md]] 的对账清单。
2. **归因演练**：挑一次已知原因的成本跳变，从归集层数据出发，**验证能在两层定位内找到对应功能与时间段**。**定位不到就是归集粒度不够**。
3. **信号时效**：人为注入一次用量放大（对测试租户加倍配额），**验证速率与水位信号在预算耗尽前触发**。**等账单才看到的超支等于没有预算**。

## 案例回流：账目错算与泄漏的两个实录

记账数字的错法见 [[工程知识/缺陷分析：从个案到体系/正确性/案例三十三：估算不等于算术——按大小推条目的错算]]：**按字节大小推条目数做成本归集，条目大小分布偏离假设时推算全错，账面与账单对不上**。它对应本篇「对账闭环」一节——**聚合链路里任何一个推算环节都是潜在误差源，偏差超过阈值要先逐环核对，再谈治理**。资源泄漏型的超支见 [[工程知识/缺陷分析：从个案到体系/资源与容量/案例六：容量与泄漏——连接泄漏和 SST 堆积]]：**连接不释放让成本沿时间爬升，水位与速率信号（本篇超支信号一节）是唯一能在账单寄到前抓住它的观测**。两案共同判据：**成本数字必须能分解到可归因的消耗单元，分解不下去的账等于没账**。
