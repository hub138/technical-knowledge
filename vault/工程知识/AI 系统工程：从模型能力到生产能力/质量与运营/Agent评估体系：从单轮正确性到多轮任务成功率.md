# Agent评估体系：从单轮正确性到多轮任务成功率

要解决的问题是：传统模型评测用单轮问答的准确率（预测或判断正确的比例）就够了，但 Agent 的评测需要覆盖多轮交互、工具调用轨迹、任务完成度等多个维度，**只用"答对了没有"衡量不了 Agent 的工程质量**。读完这篇你能为自己的 Agent 设计一套分层的评测体系，知道每个维度用什么指标、离线与在线评测如何配合。

## 本质：Agent 评测从"回答对不对"扩展到"任务完成得好不好"

传统 LLM 评测的核心问题是"模型输出是否正确"，评测维度单一——准确率、BLEU（按 n 元词组重叠度给译文打分的指标）、ROUGE（按召回的 n 元词组给摘要打分的指标）等指标**都在衡量输出与参考答案的匹配度**。

Agent 评测的额外维度来自它的三个特性：

- **多轮交互**：Agent 不是一次回答就结束的，它需要多轮对话、工具调用、状态维护才能完成一个任务。**单轮正确不代表整体任务成功**。
- **工具调用轨迹**：Agent 的中间步骤（调了什么工具、传了什么参数、怎么处理工具返回）**比最终答案更能反映质量**。**答案对了但路径绕了三倍，不算好 Agent**。
- **非确定性输出**：受模型采样（从模型输出的概率分布中抽取一个结果，温度、top-p 等参数控制抽取的随机程度）参数影响，同一输入可能产生不同的工具调用序列。**评测需要统计分布而非单点结果**。

**Agent 评测的本质是把"回答正确"扩展为"任务成功"，评测维度从一维变成多维**。

## 评测维度框架

Agent 评测需要覆盖四个维度，**从基础到高级排列**，四个维度之后接**离线与在线的评测闭环**：

### 维度一：单步正确性

衡量 Agent 在单次交互中的输出质量，与传统 LLM 评测重叠**但要求更高**：

- **工具选择正确率**：给定上下文，Agent 是否选择了正确的工具。例如用户问天气，Agent 调用了天气查询工具而非搜索工具。
- **参数填充准确率**：工具参数是否填写正确。例如查询天气时城市参数传对了没有。
- **输出格式合规率**：结构化输出是否满足 schema 约束。JSON 格式错误、字段缺失都算不合规。
- **安全合规率**：输出是否包含不当内容、是否泄露敏感信息。

指标计算方式：`正确次数 / 总调用次数`，统计窗口建议至少 100 次调用。

### 维度二：任务完成度

衡量 Agent 是否完成了用户交给它的任务，这是 Agent 评测的核心维度：

- **任务成功率（Task Success Rate, TSR）**：Agent 是否在允许的步骤内完成了任务。成功标准由人工定义（如"订单已提交"、"问题已解答"）。
- **步骤效率**：完成任务用了多少步。基准步数由专家定义，Agent 的步数相对于基准步数的比值。
- **无帮助步骤率**：Agent 执行了与任务无关的工具调用或对话轮次的比例。**无帮助步骤越多，Agent 的规划能力越差**。
- **过早放弃率**：Agent 在任务未完成时主动放弃（返回"我无法处理"）的比例。放弃本身不是问题，但**放弃时应该给出明确的失败原因**。

任务完成度的评测需要**人工标注的"黄金轨迹"作为参考标准**，或者用"答案是否达到预期结果"作为自动判据。

### 维度三：鲁棒性

- **输入扰动容忍度**：用户输入有拼写错误、歧义、信息缺失时，Agent 是否还能完成任务。
- **工具故障恢复率**：工具调用返回错误或超时后，Agent 是否能正确重试或选择替代方案。
- **上下文窗口（模型一次能读入的最大文本长度）管理**：长对话中 Agent 是否会丢失关键信息，是否能在上下文接近上限时做摘要或截断。
- **对抗输入防御**：用户试图让 Agent 执行越权（访问了权限范围之外的资源）操作时，Agent 是否能拒绝。

鲁棒性评测需要**构造异常测试集**，包括拼写错误、缺失信息、工具故障模拟、对抗提示等。

### 维度四：可观测性

- **决策可解释性**：Agent 的关键决策（为什么选这个工具、为什么放弃任务）是否有明确的日志输出。
- **状态可重建性**：给定日志，能否重建 Agent 在任意时刻的内部状态（已收集的信息、已执行的操作）。
- **失败可归因性**：任务失败时，能否明确归因到"工具调用失败""模型理解错误""上下文丢失"等具体原因。

可观测性（通过系统的外部输出——日志、指标、调用轨迹——推断其内部状态的能力）指标是**定性而非定量的**，通过代码审查和故障演练来评估。

## 离线评测与在线评测的配合

**离线评测和在线评测回答不同的问题，两者需要配合使用**。

### 离线评测

离线评测在受控环境中进行，使用预定义的测试集，围绕四个方面展开：

- **优势**：可重复、可对比、成本低
- **适用场景**：模型选型、提示词（发给模型的输入指令与背景信息）调优、工具定义优化
- **测试集构成**：黄金轨迹（人工标注的正确答案和步骤）+ 异常场景（故障模拟、边界输入）
- **指标**：TSR、步骤效率、工具选择正确率

离线评测有三个常见陷阱：**测试集污染**（评测用例被模型训练数据包含，分数虚高，需定期更新测试集）、**单一难度**（所有用例难度相近，区分不出能力边界，测试集要按难度分层）、**静态评估**（离线高分不等于在线表现好，用户使用模式测不到）。

### 在线评测

在线评测在生产环境中进行，使用真实用户流量，围绕四个要点展开：

- **优势**：反映真实使用情况、能发现离线评测覆盖不到的边缘场景
- **适用场景**：上线前验证、灰度（先放开给一小部分用户验证、再逐步加量的发布方式）发布、持续监控
- **数据来源**：用户反馈（点赞/点踩）、人工抽检、自动规则（如"用户是否完成了预期操作"）
- **指标**：用户满意度、任务完成率、平均交互轮数、人工介入率

在线评测有三个常见陷阱：**反馈稀疏**（大多数用户不会主动反馈，要主动采样抽检）、**归因困难**（用户不满意可能来自 Agent 回答，也可能来自产品本身）、**长周期**（有些任务要多天才能完成，评测要等任务结束才有结论）。

### 配合策略

两者按四步接力：

1. **离线筛选**：用离线评测从多个候选方案中选出最优的 1-2 个
2. **在线验证**：将选中的方案灰度上线，用在线评测验证实际效果
3. **持续监控**：上线后持续监控在线指标，指标异常时回退到离线评测排查原因
4. **测试集回流**：在线评测中发现的失败案例回流到离线测试集，补齐覆盖盲区

## 效果与代价

搭起这套评测体系的收益：
- **回归防护**：每次模型升级、提示词修改、工具定义变更后都能快速评估影响
- **问题定位**：评测维度拆解后，可以定位 Agent 的薄弱环节（工具选择差还是参数填充差）
- **迭代加速**：离线评测让调优周期从"等用户反馈"缩短到"跑一遍测试集"

这套收益要付的代价：
- **评测基础设施**：需要评测框架、测试集管理、结果对比看板
- **指标设计难度**：TSR 的"任务成功"定义需要业务方参与，**不同任务的成功标准不同**

## 边界与失效

Agent 评测体系不是万能的，以下场景需要额外处理：

- **开放式任务**：任务没有明确的成功标准（如"跟我聊天"），TSR 无法定义。改用用户满意度等主观指标。
- **多 Agent 协作**：多个 Agent 协作完成一个任务时，需要区分是哪个 Agent 的决策导致了失败。
- **长周期任务**：任务需要数小时或数天完成，离线评测无法模拟。在线评测需要任务级追踪。
- **评测成本**：每次评测都调用模型 API，大规模评测的成本可能很高。需要按优先级分层评测。

这套体系自身的失效模式：
- **测试集过拟合（模型把训练数据的噪声也记住、在新数据上表现变差的现象）**：Agent 记住了测试集的答案，**离线分数高但在线表现差**。需要定期更新测试集。
- **评测偏差**：人工标注的黄金轨迹**反映了标注者的偏好，不代表所有用户的偏好**。

## 验证方法

部署评测体系后，验证以下预期是否成立：

- **离线与在线一致性**：离线评测排名与在线评测排名一致（Top 方案在离线和在线的表现排序相同）
- **指标区分度**：不同质量的 Agent 在评测指标上有显著差异（好 Agent TSR 85%，差 Agent TSR 60%）
- **回归检测能力**：故意引入一个已知缺陷，评测体系能检测到指标下降
- **测试集覆盖率**：测试集覆盖了所有已知的失败模式，新增失败模式能快速补充到测试集
