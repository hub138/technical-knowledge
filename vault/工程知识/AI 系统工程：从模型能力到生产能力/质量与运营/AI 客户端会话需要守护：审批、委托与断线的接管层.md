# AI 客户端会话需要守护：审批、委托与断线的接管层

AI 客户端（CodeBuddy、Claude Code、Codex 这类常驻命令行）把一次任务跑成长时间的自主循环，期间会反复弹出审批卡、选项题、文件读写请求。**这些交互默认要人坐在窗口前点确认**。人离开、网络抖动（性能指标不稳定的起伏）、窗口断开之后，交互层就没了应答者——**工具调用无限等待，用户只看到一个「卡住」的会话，却不知道卡在哪**。读完你能在自己机器上给 AI 客户端配一个守护进程，让无人会话不再卡住、断线能续跑。

解决它的办法是给 AI 客户端配一个**常驻守护的接管层**：一个独立进程，代替人在会话窗口里应答审批、代答选项题、执行文件读写，并在会话断线或卡死时自愈。这个守护是 Agent 与操作系统之间的运维层，**与 Agent 本身分开**——相当于给 AI 客户端请了一个永不离岗的值班员。这个比方到「替人守着」为止——值班员靠判断决定叫不叫醒老板，接管层靠的是白名单、审批规则与超时参数，规则怎么定要看正文。

## 要解决的问题

一个无人值守跑着的 AI 会话，有四类地方会无声卡死：

| 卡点 | 表现 | 根因 |
| --- | --- | --- |
| 权限审批 | 弹出一张「是否允许执行 Bash」的卡，没人点 → 永久等待 | 审批会当场卡住流程、必须立刻拿到结果（这叫同步阻塞），而答案只能来自交互窗口里的人 |
| 选项题 | AskUserQuestion 弹出「猫还是狗」，没人选 → 永久等待 | 同上，且模型在等答案才能继续 |
| 文件读写 | 读文件、写文件的请求发出去，对端不应答 → 永久挂起 | 读写本身委托给另一个连接执行，投递失败却静默丢弃 |
| 会话断线 / 卡死 | 网络断了、模型那边没结果了，会话僵在那 | 没有超时兜底，也没有自动重连续跑 |

共同点是：**这些卡点都发生在「需要有人应答」的环节，而人不在**。传统做法是把整个会话绑在一个 tmux（终端复用器，一个终端开多会话）/screen（让终端会话在后台持续存活、不随窗口关闭而结束的工具）里指望它不断，但会话自己不会应答自己的审批——**它需要一个外部的、独立的应答者**。

## 守护怎么做到替人在窗口里应答？

打个比方：会话守护像请一位值班经理——AI 要动重要东西时经理来问你要不要批（审批），你不在时按你事先写的授权书代办（委托），你掉线了他替你把活接着干完并记好账（断线接管）。这个比喻到"要有人替你守着"为止：授权书怎么存、断线后怎么恢复、审批记录怎么留痕，要看正文。

守护是一个与 AI 客户端进程分离的常驻进程，接管客户端的交互通道来工作：

```mermaid
flowchart TB
    u["用户终端 / IDE<br/>正常时人在这里点确认"] --> s["AI 客户端会话：模型自主循环<br/>触发审批 / 选项题 / 文件读写"]
    s --> g["常驻守护（独立进程）<br/>中断到达时接管"]
    g --> g1["审批策略：自动签 / 拒绝"]
    g1 --> g2["选项题策略：按策略代答"]
    g2 --> g3["文件读写：代执行并应答"]
    g3 --> g4["断线自愈：三级恢复"]
    g4 --> g5["无结果即重启的自救策略"]
```

关键设计是**守护与会话是两个进程**。**会话挂了守护还在；守护重启不影响已经在跑的会话状态**。守护通过客户端提供的「替身窗口」（客户端留出的旁路接口，允许外部进程以旁观者身份接管交互线）机制接入——**它不 fork（复制出子进程的系统调用） 会话，而是作为一个旁听者接管交互线，有求必应**。

人工电话总机给"值守的应答者"提供了实物：交换机（在局域网内按地址转发数据帧的设备）前的接线员不参与任何一通电话的内容，但每个呼叫请求（转接、占线、回叫）到总台时都必须立刻有人应答处理——应答者与通话双方是分离的，接线的动作按台面上的规程走（哪个口转哪个分机），不靠临场判断。人离席时通话可以继续，**转接请求无人应答才出问题**；守护进程之于 AI 会话，正是那个守在交换机前的座位。

云架构里的同构形态是异步请求回执：客户端调 API 后不等结果，API 把活排进队列、立刻回一个状态端点；后台算完把结果写进存储，客户端查状态端点拿到资源位置再取结果——「应答者」与「干活的」分离成两个角色，中间隔着队列与存储，谁掉线另一边都不丢：

![异步请求回执模式：客户端调 API，API 入队消息并返回状态端点；后台函数接收消息、处理并把结果写入存储；客户端查状态端点、取存储中的结果](/static/figures/ms-async-request-reply-functions.png)

### 审批、代答、委托、自愈，四类应答各管什么？

**审批自动批准**——守护拿到审批卡，按策略决定签或拒。**策略是显式配置的（哪些操作自动放行、哪些必须拦），不是让模型判断**。这与 [[工程知识/AI 系统工程：从模型能力到生产能力/安全与治理/沙箱限制能力，策略限制行为]] 一致：**边界由策略定，不由推理定**。

**选项题代答**——AskUserQuestion 到达时，守护按预设策略选一个选项（例如「第一选项」或「最保守选项」）。策略默认关闭，**开启后仍需真实弹卡验证过一次才算配置生效**。

**文件读写委托代执行**——这是最隐蔽的一类。客户端的读文件、写文件走的是委托路径：请求**委托**给一个对端连接执行（fs/read_text_file、fs/write_text_file），**本地不做**。守护作为那个对端应答，读写才秒回。如果守护不在，请求发给一个已经失效的连接，就永久挂起。这条委托链路也是**为什么永久挂起时「读写全挂、命令执行不挂」**——命令是后台本地跑的，不走窗口；读写走窗口。

两条通道在对端失效时的结局不同，用一张图对照：

```mermaid
graph TD
    H["会话发起一次操作"] -->|"fs/read_text_file<br/>走窗口委托链"| W["对端连接已失效<br/>请求静默丢弃"]
    W --> W1["读写永久挂起<br/>会话卡死"]
    H -->|"Bash 命令<br/>后台本地执行"| C["不依赖窗口通道"]
    C --> C1["照常返回结果<br/>会话继续"]
```

断线与卡死的自愈靠两层兜底：

- 断线自愈：连接断了按三级恢复提示词（发给模型的输入指令与背景信息）**逐级尝试重连续跑，而不是直接放弃会话**。
- 挂起自救：给每次工具调用一个「无结果时限」（例如 15 分钟无任何输出），超时就 kill 掉这次调用并 resume（从保存的进度继续）续跑——像给每次操作定一个最长等待时间，到点没动静就当这次作废重来，类似外卖下单超时自动取消。这个比方到「到点没动静就作废」为止——外卖取消退的是钱，工具调用取消还要回收已产生的副作用（操作对外部状态产生的额外影响），cancel 路径见正文。这对应 [[工程知识/后端系统：在并发、失败与变化中维持服务/分布式可靠性/超时的层次设计：连接、读写与整链路的预算分配]]——**每一层调用都要有自己的时限**。

## 怎么让守护脱离人的登录、变成开机就跑的系统服务？

登录会话结束时会带走其中运行的进程，守护若依附它就活不下去，所以**守护必须脱离人的登录会话独立存活**，用 systemd（Linux 的系统服务管理器）托管 + 开机自启：

```ini
[Service]
Type=simple
ExecStart=/path/to/guard
Restart=always
RestartSec=5
StandardOutput=journal
```

这套配置的每个字段都是 systemd.service 手册里的显式承诺：`Restart=` 的四个取值里 `always` 表示「无论干净退出、被信号终止还是超时都重新拉起」，`RestartSec=5` 把重启间隔定成 5 秒——进程的存活由 Supervisor（进程守护工具，崩溃自动拉起） 负责，与任何登录会话无关：

![systemd.service 手册 Restart= 段：no/on-success/on-failure/always 四个取值的语义，及 Restart=always + RestartSec=5 的示例 unit 文件](/static/figures/systemd-restart-always-doc.png)

*图源：freedesktop.org systemd.service(5) 手册页 Restart= 与示例段（整理排版截图），https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html，文档引用。*

**这三个要素缺一不可**：不托管就随会话结束被带走，不脱离登录会话就随人登出消失，不写进 journal（systemd 的日志）出了事查不到记录。细节见 [[工程知识/后端系统：在并发、失败与变化中维持服务/任务与并发/后台任务的守护链：进程托管与会话脱离是可靠性的底线配置]]：进程托管（systemd 拉起与重启）、会话脱离（不依附任何登录 shell）、日志归属（进 journald 而非某个终端）。再叠加**单实例锁（保证同时只跑一个守护进程）防止两个守护互抢指针**，pid 自注册（把当前进程号写入文件，供互相发现与防止重复启动）。

非 systemd 环境用等价的 setup 脚本兜底，同样要做 pid 自注册和单实例防护。

## 效果从哪儿来，要付什么代价

**隔离要落在资源上才算数**。把连接、线程池（预先建好一组线程反复取用、避免频繁创建销毁）按用途分成独立的池（池是预先建好、可反复复用的资源集合），**分池后一个用途耗尽不会连累其他用途**——这与守护进程独立于会话是同一个道理。

「一盏灯管一件事，灭一盏不黑全宅」的实物原型是宅院里的红灯笼：门口的、廊下的、库房门前的各挂各的杆，各点各的烛——库房那盏灭了，门口与廊下照常亮：

![成串的红灯笼：各挂各的杆、各点各的烛，一盏灭不连累别的](/static/figures/red-lanterns.jpg)

*图源：Wikimedia Commons，作者 Dcubillas，CC BY-SA 3.0，https://commons.wikimedia.org/wiki/File:Red_Lanterns_for_Chinese_New_Year_KK.jpg。*

审批通道、委托通道、通知通道就是门口、廊下、库房的三盏灯：各自的连接池（预先建好连接反复取用、省去反复握手建连的开销）与超时各自配额，**审批通道被占满时委托与通知照常走**——**灯杆分开（池隔离）是前提**，共用电线（共享线程池）时一盏短路全宅跳闸。


**收益**

- 无人值守的长任务不再因为一张审批卡或一道选项题而永久卡死。
- 断线和卡死有兜底，会话能自愈续跑，不需要人半夜去点鼠标。
- 文件读写经守护代执行，秒回，不再永久挂起。

**代价与边界**

- **自动批准是有风险的让步**：把审批权交给守护，**等于把安全边界从「人逐次确认」放宽为「策略一次性约定」**。因此策略必须显式、可关、可审计，且敏感操作仍应留在人工环路——呼应 [[工程知识/AI 系统工程：从模型能力到生产能力/质量与运营/人在环路要设在不可逆的决策点]]。
- **选项题代答可能选错**：按策略选第一选项不等于选对，**只在「哪个都行」的场景安全**；有实质分叉的选项仍应人工。
- **守护本身要可观测**：守护卡不卡、答没答，都要进日志（journalctl 一查便知），否则值班员自己失联了没人知道。

## 从什么地方做

1. **先定位卡点**：跑几天，把所有「会话不动了」的时刻分类——是审批、选项题、读写还是断线。看真实分布，通常集中在一两类。
2. **先接审批自动批准**：最高频、最确定，策略也最简单（放行白名单 + 拦黑名单）。
3. **再接文件读写委托**：这一类不显眼但一旦永久挂起最难查，守护作为对端应答即可根治。
4. **然后上选项题代答与自愈**：这两类依赖真实触发验证，代码就绪后等自然出现一次弹卡/断线，确认整条链路应答成功。
5. **最后做常驻化**：systemd 托管 + 开机自启 + 单实例锁，让它彻底脱离人的会话。

## 怎么自己动手验证

1. 无人值守演练：发起一个会长时间跑的会话，人离开窗口，确认审批卡、选项题与文件读写请求被守护进程应答，会话继续推进。
2. 断线自愈：中途切断网络或关闭窗口，确认守护进程探测到会话失联后重新接管，任务从中断处续跑而不是从头开始。
3. 放行边界：核对守护代答的每一条审批都在授权范围内，超出范围的操作被拒绝并留下记录。
