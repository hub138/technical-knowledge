# 解码与采样参数：概率分布到生成文本的控制面

同一个模型、同一个提示，temperature 从 0 调到 1.2，输出从稳定复读到天马行空再到不可控胡编——采样参数是把模型内部的概率分布翻译成实际文本的控制面，但多数团队是照抄默认值，没把它当作需要针对性验证的工程配置。要解决的问题：理解每个参数改变的是什么分布性质，按任务类型选参数组合，并用可复现实验验证参数选择，而不是凭感觉调。

本质是确定性映射与随机采样的光谱。模型每步输出的是词表上的概率分布；解码策略决定怎么从这个分布选出下一个 token。贪心（argmax）是完全确定性的，纯采样是完全随机的，中间的一切参数都是在调"多确定 vs 多多样"这个旋钮。

概率分布到文本这一步在搜索树上长什么样，一张图看贪心路径的选取：

![HuggingFace 官方博客图：贪心搜索的树结构——从「The」出发，每一步只在分支中选概率最高的节点（nice 0.5、woman 0.4、and 0.4 …），红色高亮的那条路径被选为输出，其余分支同时被丢弃](/static/figures/greedy-search.png)

来源：同上博客。红色路径之外的黑色分支就是贪心丢掉的候选——「低温复读」的机制在这幅图上可以指认：每一步都走最粗的那一支，长序列上容易反复回到同一个高概率节点；而采样的价值就是偶尔走细分支，把多样性买回来。

## 机制：参数与分布形状

| 参数 | 作用机制 | 调大的效果 | 调小的效果 |
| --- | --- | --- | --- |
| temperature | logits 除以 T 再 softmax，压平或锐化分布 | 分布更平，低概率词有机会，输出多样但易错 | 分布尖锐，接近贪心，稳定但重复 |
| top-p（nucleus） | 只在累积概率 p 内的词中采样 | 候选池大，多样性升 | 候选池小，接近贪心 |
| top-k | 只在概率前 k 个词中采样 | 同上 | 同上 |
| repetition penalty | 已出现 token 的 logit 减惩罚 | 减少复读，但过度惩罚专有名词 | 保留重复能力 |
| min-p | 以最高概率的固定比例过滤候选 | 近年替代 top-p 的方案，对分布形状更鲁棒 | — |

参数间是叠加关系：temperature 先改变分布形状，top-p/top-k 再截断候选池，penalty 再修正。组合的语义不是单参数语义的简单相加，改一个要看整体。

「分布更平」与「分布尖锐」在词表上各自长什么样，一张图看温度对同一分布的作用：

![HuggingFace 官方博客图：温度对概率分布的作用——同一句「The」之后的分布，左侧温度低时 the 后的候选被锐化成 nice 0.75、dog 0.23、car 0.02，右侧温度高时分布被压平为 woman 0.6、guy 0.2、house 0.2，低概率词被抬进候选](/static/figures/sampling-search-with-temp.png)

来源：HuggingFace 官方博客「How to generate text: using different decoding methods for language generation with Transformers」。两排立柱的高度差就是温度旋钮的读数：左排的 0.75/0.23/0.02 是尖锐分布，右排的 0.6/0.2/0.2 是压平后的分布——「低概率词有机会」在图上就是原本近乎为零的第三根立柱被抬了起来，事实类任务要的就是左排的形状。

![HuggingFace 官方博客图：top-k 采样的候选池截断——左侧 P(w|"The") 的完整分布上，前 k 个词的累积概率 0.68 被花括号框出；右侧 P(w|"The","car") 上同样的前 k 个词累积到 0.99](/static/figures/top-k-sampling.png)

来源：同上博客。top-k 与 top-p 的差别在同一幅对照里：固定词数 k（左图框住 0.68）与固定累积概率 p（右图框住 0.99）截出的候选池宽度不同。「top-k 太小砍掉正确候选」的失效就发生在 k 值把累积概率截在 0.68 这一侧的时候，而 top-p 的自适应宽度正是为这个形状问题设计的。

按任务选参数的起点：代码生成、结构化输出、事实问答用低温加截断（T≤0.3，top-p≤0.9），因为正确答案分布本来就尖锐；创意写作、brainstorm 用高温（T 0.7-1.0）让分布展开；客服对话类取两者之间、靠近低温，多样性留给意图层面。

## 失效形态

| 失效 | 机制 | 信号 |
| --- | --- | --- |
| 高温幻觉放大 | 低概率的错误词被采到，错误沿自回归链传播 | 事实类任务错误率随温度陡升 |
| 低温复读 | 贪心解码陷入循环，短重复模式 | 输出重复短语或无限循环 |
| 截断过狠 | top-k 太小砍掉正确候选 | 换个说法的正确答案出不来 |
| 惩罚误伤 | repetition penalty 惩罚了必须重复的专有名词 | 代码/名单里实体被改写 |
| 参数间冲突 | 高温 + 小 top-k：分布被压平又被砍，行为不可预期 | 参数敏感性测试不稳定 |

## 可运行示例与案例回流：采样参数的实录

```python
# 同一模型，三组采样参数，三种产出性格（通用示例）

# 组 1：贪心（temperature=0 等价取 argmax）
#   输出确定可复现 → 适合抽取、分类、代码补全这类"答案唯一"的任务
#   代价：重复循环风险（"好的好的好的"），长文呆板

# 组 2：temperature=0.7, top_p=0.9
#   日常对话与创作的常用档：多样性够，跑飞少
#   top_p 截掉累积概率 10% 的长尾 → 低概率的胡话被挡在采样外

# 组 3：temperature=1.2, top_k=50
#   头脑风暴、起标题：高温度放大分布尾部，出新词新组合
#   代价：事实类任务错误率明显上升（每个 token 都多赌一次）

# 事实核查类任务的实录配置：temperature=0 + 结构化输出 + 引用校验
# 创作类：0.7-1.0 起步，按"重复率 vs 灵感度"微调
```

案例回流：参数错配的实录形态——客服机器人用高温度采样，同一个退款政策两次问答给出两种说法（每 token 采样引入的措辞漂移被用户当成"政策变了"），改贪心后投诉消失；代码生成用高温度，编译通过率跌三成。参数是行为控制面，不同任务档位不同——判据看任务要"唯一答案"还是"多样候选"。同一控制面思想在结构层的形态见 [[工程知识/AI 系统工程：从模型能力到生产能力/Agent与工作流/结构化输出与约束解码：schema约束形状，事实另需验证.md]]。

## 边界

- 采样参数不能修复模型能力缺陷：模型不知道的事实，怎么调温度都不会对；参数只控制"已具备的能力怎么表达"。
- temperature=0 也不等于完全可复现：浮点非结合性、批内计算顺序、硬件差异都会引入微小扰动；要严格复现需固定 seed 加确定性 kernel，代价是性能。
- 多数 API 的参数语义有细微差异（有的 top-k 与 top-p 互斥、有的 penalty 定义不同），换供应商要重新验证，照搬数值会出错。
- 评测时用采样参数要分层：能力评测（模型会不会）低温看上限，行为评测（上线表现）用生产同款参数，两者混用会让结论失真。

## 验证

最小验证：固定一组测试提示，扫 temperature {0, 0.3, 0.7, 1.0} × top-p {0.8, 0.95}，记录三类指标——事实准确率、重复率、输出长度方差；断言事实任务的准确率-温度曲线单调下降、重复率在 T=0 附近出现峰值。再测可复现性：同参数同 seed 跑三次，计算输出一致性比例，确认你的栈里温度 0 的复现边界到底在哪。
