# LLM网关把模型调用变成可治理的流量：鉴权、预算、限流与降级

要解决的问题是：模型封装成 API 后，调用方可以随意请求，但谁来管谁在调用、花了多少预算、流量超了怎么办、后端挂了怎么降级。LLM 网关（架在调用方与模型服务之间的一层代理，集中管鉴权、预算、限流与降级）就是这一层治理的集中点，读完这篇你能判断自己的场景需要网关的哪几组能力、哪些可以后补。

## 本质：网关把模型调用从点对点变成可观测、可控制、可计量的流量管道

传统 API 网关处理的是 HTTP 层面的路由、鉴权与限流（限制单位时间内放行的请求数量）。LLM 网关的额外维度来自模型调用的三个特性：

- **Token 即成本**：每次调用的开销不按请求次数算，按 token（模型处理文本的最小单位，约相当于一个词或半个词） 数算，且不同模型的 token 单价不同。限流不能只看 QPS（每秒查询数），还要看 token 消耗速率。
- **多后端异构**：同一套网关后面可能同时有 OpenAI、自部署 vLLM、Azure OpenAI、Anthropic 等多个后端，每个后端的定价、容量、延迟特征不同。
- **调用语义复杂**：流式与非流式、上下文窗口（模型一次能读入的最大文本长度）超限、token 耗尽、内容审核拒绝——这些不是 HTTP 状态码能表达的，需要网关理解模型层的语义。

LLM 网关的本质是把这些差异抽象成统一的治理接口，让调用方只关心"我要调一个模型"，不关心"调的是哪个后端的哪个版本、预算够不够、会不会被限"。

## 四组核心能力

四组能力在一条请求路径上依次生效：调用方带虚拟密钥发起调用，鉴权、预算、限流三道闸依次放行，路由策略选中后端，计量在响应后回补预算；任何一道闸不过，请求就走拒绝、排队或降级的旁路。

### 鉴权与虚拟密钥

LLM 网关的鉴权层比传统 API 网关多一个"虚拟密钥"的概念。传统网关的 API key 直接对应一个用户或一个服务，LLM 网关的虚拟密钥是一组**策略的绑定点**：

- 每个虚拟密钥关联一个预算池（月度 token 配额）、一个速率限制（每分钟/每小时/每天的最大 token 数）、一个允许的模型列表
- 同一个用户可以有多个虚拟密钥，分别用于开发、测试、生产环境
- 密钥可以临时失效（用于排查问题）或设置过期时间（用于临时授权第三方）

虚拟密钥的设计让权限管理从"谁可以调"细化到"这笔调用可以用多少、调什么模型"。密钥泄漏时只需要吊销一个虚拟密钥，不影响该用户的其他密钥。

### Token 计量与预算管理

Token 计量是 LLM 网关区别于传统网关的核心能力。网关需要实时统计每个虚拟密钥、每个用户、每个模型消耗的 token 数，并据此做预算控制。预算管理分三级阶梯：

1. **软限制（soft limit）**：达到阈值时记录告警日志，不阻断调用。用于发现异常消耗趋势。
2. **硬限制（hard limit）**：达到阈值时直接拒绝新调用，返回 429 或自定义错误码。用于防止预算超支。
3. **层级预算**：先扣项目预算，项目预算耗尽后扣部门预算，部门预算也耗尽才拒绝。层级预算避免单个项目异常消耗影响其他项目。

Token 计量有一个精度陷阱：输入 token 在请求到达时就能算出（prompt 已知），输出 token 要等流式响应结束才能知道准确值，实践中因此分成两种做法：预扣模式在请求到达时按最大输出 token 数预扣预算，响应结束后退还剩余，预扣量不准时大量预算被冻结；后扣模式在响应结束后按实际 token 数扣减，计量准确但超支已成事实。多数生产系统采用混合模式：预扣一个经验值（如最大输出的 80%），响应结束后按实际值多退少补。

### 限流与排队

- **QPS 限流**：每秒请求数，防止突发流量打爆网关本身
- **TPM（Token Per Minute）限流**：每分钟 token 消耗量，防止单个调用方耗尽后端容量
- **RPM（Request Per Minute）限流**：每分钟请求数，与 TPM 配合使用
- **并发限流**：同时进行的请求数，防止慢请求堆积占用连接

| 维度 | 适合场景 | 典型值 |
|------|----------|--------|
| QPS | 网关自身保护 | 1000 req/s |
| TPM | 后端容量保护 | 根据模型规格计算 |
| 并发 | 慢请求场景 | 单用户 5 并发 |
| RPM | 固定配额场景 | 100 req/min |

超出限流阈值时网关有三种选择：直接拒绝（返回 429，调用方自行重试，适合调用方有重试机制的场景）、排队等待（请求进入队列按 FIFO（First In First Out，先进先出）或优先级顺序处理，适合对延迟不敏感的批量场景）、降级响应（返回缓存结果或简化结果，适合对响应质量要求不严格的场景）。

### 多后端路由与降级

LLM 网关可以配置多个后端并按策略路由请求，典型策略有这些：

- **主备模式**：首选后端不可用时切换到备用后端。适合有多个同质化模型供应商的场景。
- **权重分发**：按权重将流量分配到多个后端。适合灰度（先放开给一小部分用户验证、再逐步加量的发布方式）发布新模型版本。
- **成本优先**：优先选择单价最低的后端，当前端容量不足时切换到次优后端。适合成本敏感场景。
- **延迟优先**：优先选择响应最快的后端。适合对延迟敏感的场景。

降级是路由策略的极端情况——所有后端都不可用时怎么办。降级阶梯从轻到重：

1. **语义缓存命中**：语义缓存（按问题含义而非字面匹配来命中结果的缓存，「退款流程是什么」和「怎么退钱」视为同一问题）命中时直接返回缓存结果。适合 FAQ（Frequently Asked Questions，常见问题解答）、知识问答等重复性高的场景。
2. **模型降级**：从 GPT-4 降级到 GPT-3.5，或从 70B 模型降级到 7B 模型。适合对质量要求不严格的场景。
3. **简化处理**：跳过 RAG（Retrieval-Augmented Generation，检索增强生成：先从知识库检索相关资料、拼进上下文再让模型回答的机制），只基于模型自身知识回答。适合对时效性要求高于准确性的场景。
4. **友好拒绝**：返回"当前服务繁忙，请稍后再试"的固定响应。适合所有场景的兜底。

降级在四种条件下触发：后端错误率（连续 N 个请求返回 5xx 或超时）、后端延迟（P99 超过阈值，P99 指 99% 的请求耗时不超过这个值，剩下的 1% 最慢请求不计入）、预算耗尽（月度预算用完自动降级到低成本模型）、主动降级（运维人员手动触发，用于计划内维护）。

![LLM 网关降级阶梯：请求按语义缓存、小模型、跳过 RAG、友好拒绝四级依次尝试，每级命中即返回，全部未命中落友好拒绝兜底（来源：自绘）](/static/figures/llm-gateway-degrade-ladder.svg)

每一次降级命中都要记录降级原因与所在层级，供后端恢复后评估回切。缓存命中和小模型结果要标记降级来源，调用方据此判断响应可信程度。恢复过程分四步走：第一步确认主链路后端健康；第二步把跳过 RAG 的请求接回主链路；第三步观察小模型降级的量是否降到零；第四步等错误率与延迟指标连续稳定，再放开语义缓存，让流量全部回到主链路。每完成一步就核对一次错误率与延迟指标，异常时停在当前层级不再推进。

## 效果与代价

把路径治理上线的收益有三条：
- **成本可控**：Token 计量和预算管理让模型调用成本可预测、可追溯
- **故障隔离**：单个后端故障时自动切换，不影响整体服务
- **可观测性（通过系统对外输出判断内部状态的能力）**：网关层统一记录调用日志，是模型调用行为的唯一可信数据源

这些收益要付的代价同样有三条：
- **运维复杂度**：网关本身需要高可用部署，不能成为单点（没有备份、一坏全局受影响的组件）故障
- **配置管理**：虚拟密钥、路由策略、限流参数的配置需要版本化管理
- **Token 计量误差**：预扣模式下的预算冻结、后扣模式下的超支风险，需要持续调优

## 边界与失效

LLM 网关不是万能的，以下场景需要额外处理：

- **流式响应的计量**：流式场景下输出 token 数在响应过程中不断变化，预算扣减需要逐段处理，不能等响应结束才扣
- **多模态输入**：图片、音频等非文本输入的 token 计算方式不同，网关需要理解多模态的编码规则
- **自定义模型**：自部署的 LoRA 适配器（Low-Rank Adaptation，在冻结的基座模型外挂一个低秩小矩阵做微调、不必整模训练的轻量适配方式）、微调（在预训练模型上用少量数据继续训练、让模型适配具体任务）模型需要网关支持动态加载路由表（决定数据包下一跳去向的转发表）
- **网关自身高可用**：网关挂了所有模型调用都受影响，需要多副本部署 + 健康检查

治理边界之外还有三种失效模式：

- **预算数据不一致**：网关多副本并发扣减预算时可能出现超扣或少扣，需要幂等（同一操作执行多次与执行一次效果相同）扣减或最终一致性（不承诺实时一致、但保证停止写入后副本终将一致）方案
- **降级风暴**：多个调用方同时触发降级，降级后的后端可能也被打爆，需要多级降级和熔断（circuit breaker：连续失败达到阈值后暂时断开对某后端的调用、请求直接快速失败，用探测请求判断恢复时机的模式）
- **缓存污染**：语义缓存命中错误结果后，错误会被持续返回，需要缓存失效（缓存里的数据过期或不一致、需要回源加载）机制

## 验证方法

部署 LLM 网关后，验证以下预期是否成立：

- **预算控制**：设置一个低预算阈值，验证达到阈值后请求被拒绝
- **限流生效**：用压测工具发送超过限流阈值的请求，验证 429 返回
- **降级切换**：关闭主后端，验证请求自动切换到备用后端
- **Token 计量**：对比网关记录的 token 数与模型返回的 usage 字段，误差应在 5% 以内
- **延迟影响**：对比直连模型与通过网关调用的 P99（99% 的请求耗时不超过这个值） 延迟差，应在预期范围内
