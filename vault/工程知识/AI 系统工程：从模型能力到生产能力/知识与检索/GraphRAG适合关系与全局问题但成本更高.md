# GraphRAG 适合关系与全局问题但成本更高

**有些问题要跨文档找关系、做全局聚合，普通检索答不上来，这是 GraphRAG（RAG 的图结构变体，RAG 指检索增强生成：先从资料库里找出相关片段，再让模型照着这些片段回答）要补的短板**。读完这篇你能判断什么时候值得上图结构，也知道它的成本和质量该怎么验。简言之：**跨文档关系或全局聚合的问题值得上图，局部事实和精确查值不需要**。

GraphRAG 在文档提及的人、组织、模块等实体（文档中可独立指认的对象）以及它们之间的关系上构图，并通过社区发现（先把实体聚成有联系的群组）、层次摘要或图遍历回答「全局主题、关系链和跨文档聚合」问题。它不是把所有 RAG 都换成图。

**有三类问题不该上图：精确查值类（如查某个 ID 对应的记录）、单段文字就能回答的事实性问答、需要即时读写字段的实时状态查询（如库存余量、订单状态）**。它们要的都是**精确命中单条记录**，**多一层抽取与遍历反而增加开销**，SQL 等结构化查询能直接命中。这类需求通常仍应优先 SQL、倒排（按词建立的可检索索引）、向量检索或 API（直接调用外部数据接口）。

## 为什么有些问题向量检索答不好：要解决的问题

需要跨多份文档汇总关系的问题，用向量检索只能取回零散片段，答案缺少全局视角；把图结构引入之后，构建与更新成本明显上升，收益能否覆盖成本缺少判断依据。本篇回答：哪一类问题需要跨文档关系或全局聚合、图结构在什么条件下值得承担构建与维护成本、关系与摘要怎样和原文核对，以及它与混合检索方案的对比口径是什么。

## 图结构补上了哪些短板：机制与本质

向量检索和图结构取回方式差在哪？先用一个比喻说明大致样子：向量检索像按相似度从书堆里抽页——你问"这两个部门合作过哪些项目"，它抽出 50 页各讲各的，哪页都沾边但没有一页串起关系；图结构像请人先把全书的人物关系画成图谱、按帮派写成章节摘要（实体关系抽取 + 社区摘要），你问关系与全局问题，直接翻图谱与章节，答案自带连线。代价是**画图谱这道工序本身：抽错了写进图谱**（污染会被结构化放大）、书更新了图谱要重画受影响的章节（更新成本）。这个比喻只说明取回方式的差别；至于建图和更新图要付出什么代价，下面展开构建链路时再说。

图结构到底比向量检索多做了什么？**GraphRAG 的机制层：向量检索按相似度取回片段，片段的聚合上限由 top-k（每次召回返回的最相关片段数）决定，散落在多份文档中的关系无法在一次召回里汇集**。图结构先抽取实体与关系并形成社区摘要，查询时在摘要层聚合，代价是**抽取错误会沿结构化结果放大**，且**更新一份文档需要重建受影响的社区**。

与向量检索的对照可以在邻篇看到完整流水线 [[工程知识/AI 系统工程：从模型能力到生产能力/知识与检索/检索从一次查询演进为有状态的证据获取]]，即查询向量化、ANN（Approximate Nearest Neighbor，近似最近邻搜索：牺牲精度换速度的向量检索）、相似度排序返回 top-k，本篇的重点在另一条路上——图是怎么从文档建出来的。


## 图是怎么建出来的：构建链路

```text
文档解析 -> 实体/关系抽取 -> 去重与消歧（把名称相同但指代不同的对象区分开）-> 图存储
         -> 社区/层次摘要 -> 查询分类 -> 子图/摘要检索
         -> 证据定位 -> 生成与引用
```

抽取模型的错误会成为**结构化污染：错误实体写进图后会被多份社区摘要重复引用，一处出错带动多处出错**；实体版本、来源、时间、权限和删除传播必须与文本块（chunk，文档切分后的最小检索单元）同等严格。图遍历的深度、分支和摘要层级决定 token（模型处理文本的最小单位，约相当于一个词或半个词）、延迟和证据完整性——像翻地图册，翻的层数越深、岔路越多，要读的页和等待时间就越多，这个比喻只说明层数与等待的关系，现实里各层还有算法与成本差异。**岔路对应图遍历的分支数，分支越多要访问的节点和 LLM 调用次数随之增加**。

中间的社区发现这一步值得单独看清楚：参考实现用 Leiden 算法（一种按连接密度迭代切分社区的发现算法）切社区，它的三个动作是搬节点（把连接紧密的节点移到同一社区）、细分（把过度合并的社区拆成更小的子社区）、聚合（把同一社区的节点收缩为一个超级节点），然后在新一层重复。下图第一层从杂乱连接开始，搬节点把节点归入同一颜色，细分再把聚合过头的社区拆开，聚合后每个社区变成一个节点进入第二层，第二层重复同样的三步：

![Leiden 算法的三个动作：第一层由散乱节点开始，搬节点后节点按颜色归入不同社区，细分把聚合过头的社区拆成子社区，聚合后每个社区收缩为一个节点进入第二层，第二层重复搬节点与细分](/static/figures/leiden-algorithm.png)

*图示：社区发现算法的搬节点、细分与聚合三个阶段，每一步的产物都成为下一层的输入，因此社区天然形成层次结构。图源：Traag, Waltman, van Eck《From Louvain to Leiden: guaranteeing well-connected communities》，Scientific Reports 9:5233（2019），CC BY 4.0，https://www.nature.com/articles/s41598-019-41695-z。*

「细分」这一步是**无监督地给整个语料画出结构**，它只根据节点之间的连接密度分组，不考虑文档的主题或语义是否一致，因此同一个社区里可能混入不同主题的节点，它的分辨率参数（控制社区切分的粗细程度，调大切得少而大、调小切得多而细）调得好不好要靠实测；「聚合」这一步产生的层次结构，正是**查询期逐层遍历摘要所依据的那棵树**——每收缩出一层超级节点，查询时就多一次对该层摘要的汇总，所以图上从第一层到第二层的收缩关系，就是「每跳一次 LLM（大语言模型）汇总」的跳。

## 哪些场景值得上图：适用判断

- 需要跨大量文档总结主题、组织或关系网络；
- 查询需要多跳（一个问题要沿实体关系走多步才能答完）实体关系而单次相似度召回不稳定；
- 能承受离线构图、更新、审计和额外存储成本。

前两条场景的查询期数据流，微软官方方法论文档里画得很直白：查询向量先匹配出一批实体，再沿实体-文本单元、实体-社区报告、实体-实体关系、实体-协变量四路映射取候选，各路排序过滤后合成一个回答——

![微软官方图：Local Search 数据流——用户查询经向量匹配抽取出实体，再沿实体-文本单元、实体-社区报告、实体-实体关系、实体-协变量四路映射取候选，各路排序过滤后汇合成回答](/static/figures/graphrag-local-search-dataflow.png)

*图源：Microsoft Research《GraphRAG: Unlocking LLM discovery on narrative private data》方法论文档插图（经 Zilliz 博客转载，图注注明图片来源 Microsoft Research），https://www.microsoft.com/en-us/research/blog/graphrag-unlocking-llm-discovery-on-narrative-private-data/。*

「多跳实体关系而单次相似度召回不稳定」的补法就是这张图上的四路映射：不指望一次召回命中，而是从命中的实体出发把关系邻域整体取回，再在排序过滤后汇成一份回答。

## 两代管道的成本差多少：量化锚点

向量 RAG 的检索成本是每查询一次嵌入（毫秒级、近零成本）；打个比方：向量检索只付一次查询的车费，GraphRAG 还要付建图的人工费与逐层汇总的过路费，这个比方只到「多付两笔钱」为止。**GraphRAG 在此之上多两笔钱**——**离线索引期对每个文档做实体抽取与关系抽取**（LLM 调用次数与文档数、每篇实体密度成正比，**典型语料每千字产生 3-10 次调用**），查询期做社区摘要的**逐层遍历（每跳一次 LLM 汇总）**。**公开实现（微软 GraphRAG 参考实现）的索引成本量级：1 万篇文档、平均 2000 字，抽取一遍在百万 token 级——这笔钱在向量 RAG 里是零**。语料更新频繁时，**增量索引策略（只重建受影响社区）决定这笔钱是付一次还是每天付**。

查询期那笔钱的形状，微软官方的全局搜索数据流图给了直观呈现：整图的社区报告被打乱后分成 N 批，每批各自送 LLM 打分产生一批带评分的中间响应，全部批次的响应再经排序与过滤聚合成最终回答——

![微软官方图：Global Search 数据流——用户查询与会话历史把打乱分批的社区报告逐批送给 LLM 打分，产生多份带评分的中间响应，再经排序与过滤聚合成最终回答](/static/figures/graphrag-global-search-dataflow.png)

*图源：Microsoft Research《GraphRAG: Unlocking LLM discovery on narrative private data》方法论文档插图（经 Zilliz 博客转载，图注注明图片来源 Microsoft Research），https://www.microsoft.com/en-us/research/blog/graphrag-unlocking-llm-discovery-on-narrative-private-data/。*

图上每一个 Rated Intermediate Response 都是一次 LLM 调用，批次数随社区数增长——正文说的「每跳一次 LLM 汇总」在这张图上就是从报告批次到聚合响应的整条调用链，这正是查询期成本高于向量 RAG 的来源。

## 全局问题的两种答案差在哪：案例回流

"这个代码库的架构演进主线是什么"是 GraphRAG 的典型主场：向量检索按相似度召回片段，"主线"散布在全部提交记录里，任何 top-k 都只捞到碎片（存储空间里零散不连续的小块）；GraphRAG 先建实体（模块、作者、决策）与关系图，查询时在社区摘要层聚合，一次回答覆盖全局。本库 [[工程知识/AI 系统工程：从模型能力到生产能力/知识与检索/GraphRAG适合关系与全局问题但成本更高]] 讲的取舍在缺陷分析域有同构经验：[[工程知识/缺陷分析：从个案到体系/缺陷分析：从个案到体系——导读与开源地图]] 的个案定位靠局部相似检索就够，跨个案的体系性结论（哪类缺陷反复出现）靠的是人工建的图谱——两件事都是局部检索解决个案、跨个案结论靠人工建图谱，处理路径完全一致，所以是同一类取舍（同构，指结构一致、可用同一套取舍来处理）。

## 怎么自己验一遍效果：验证

图检索收益要与查询分桶（按查询类型分组）对账（逐一检验）：预先设定的**关系型与全局型查询上，证据覆盖率相比混合检索有提升；局部事实类不低于混合检索**。如果实测结果与这个预期对不上，而构图成本照付，**就不值得上**。

按关系型、全局型、局部事实、无答案和更新/撤权查询分桶，与普通 hybrid RAG 比较证据覆盖、引用精度、召回、延迟、构图成本和更新滞后。图上的边和摘要必须能对应到原文出处，因为模型抽取的关系若在原文中找不到依据，就可能是编造的，用这样的图做判断会出错；只凭模型生成、在原文中找不到依据的关系不算数。

## 收益和成本分别从哪来：效果与代价

引入图结构的收益出现在跨文档与全局问题：关系链与主题聚合能一次回答覆盖较多材料，引用可以逐条回到原文。代价是**离线抽取与摘要带来的额外调用**，以及实体消歧、增量更新与删除传播的持续维护；单跳事实查询与精确查值在这套结构下面临的延迟与滞后都比直接检索更高。

哪些场景不该用：单跳事实查询（"某个函数在哪定义"）直接向量检索或关键词检索更快更准，上图是付了构建与维护成本换不来收益；实体与关系频繁变化、删除传播成本高于查询收益的高更新率语料不适合；语料规模小到全文检索就能覆盖时，图结构的聚合优势没有施展空间。**边界一句话判据：问题需要跨文档聚合关系才能回答时上图，局部相似度就能回答时留在混合检索**。
