# GraphRAG 适合关系与全局问题但成本更高

它的边界是：只有当问题需要跨文档关系、社区或全局聚合时，图结构才值得承担构建和更新成本；局部事实、精确查值和高频实时状态不应强行图化。验证时要把关系边、摘要和原文逐条对齐，并与 hybrid RAG 比较质量、延迟、更新滞后和运维成本。

GraphRAG 在文档实体和关系上构图，并通过社区发现、层次摘要或图遍历回答“全局主题、关系链和跨文档聚合”问题。它不是把所有 RAG 都换成图：精确查值、简单语义问答和实时状态通常仍应优先 SQL、倒排、向量或 API。

## 构建链路

```text
文档解析 -> 实体/关系抽取 -> 去重与消歧 -> 图存储
         -> 社区/层次摘要 -> 查询分类 -> 子图/摘要检索
         -> 证据定位 -> 生成与引用
```

抽取模型的错误会成为结构化污染，并在社区摘要中放大；实体版本、来源、时间、权限和删除传播必须与文本 chunk 同等严格。图遍历的深度、分支和摘要层级决定 token、延迟和证据完整性。

## 何时值得用

- 需要跨大量文档总结主题、组织或关系网络；
- 查询需要多跳实体关系而单次相似度召回不稳定；
- 能承受离线构图、更新、审计和额外存储成本。

## 验证

按关系型、全局型、局部事实、无答案和更新/撤权查询分桶，与普通 hybrid RAG 比较证据覆盖、引用精度、召回、延迟、构图成本和更新滞后。图上的边和摘要必须能回指原文，不接受只有模型解释的关系。
