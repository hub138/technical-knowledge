# GraphRAG 适合关系与全局问题但成本更高

它的边界是：问题需要跨文档关系、社区或全局聚合时，图结构值得承担构建和更新成本；局部事实、精确查值和高频实时状态不应强行图化。验证时要把关系边、摘要和原文逐条核对，并与 hybrid RAG 比较质量、延迟、更新滞后和运维成本。

GraphRAG 在文档实体和关系上构图，并通过社区发现、层次摘要或图遍历回答“全局主题、关系链和跨文档聚合”问题。它不是把所有 RAG 都换成图：精确查值、简单语义问答和实时状态通常仍应优先 SQL、倒排、向量或 API。

## 构建链路

```text
文档解析 -> 实体/关系抽取 -> 去重与消歧 -> 图存储
         -> 社区/层次摘要 -> 查询分类 -> 子图/摘要检索
         -> 证据定位 -> 生成与引用
```

抽取模型的错误会成为结构化污染，并在社区摘要中放大；实体版本、来源、时间、权限和删除传播必须与文本 chunk 同等严格。图遍历的深度、分支和摘要层级决定 token、延迟和证据完整性。

## 何时值得用

- 需要跨大量文档总结主题、组织或关系网络；
- 查询需要多跳实体关系而单次相似度召回不稳定；
- 能承受离线构图、更新、审计和额外存储成本。

## 量化锚点：两代管道的价格差

向量 RAG 的检索成本是每查询一次嵌入（毫秒级、近零成本）；GraphRAG 在此之上多两笔钱——离线索引期对每个文档做实体抽取与关系抽取（LLM 调用次数与文档数、每篇实体密度成正比，典型语料每千字产生 3-10 次调用），查询期做社区摘要的逐层遍历（每跳一次 LLM 汇总）。公开实现（微软 GraphRAG 参考实现）的索引成本量级：1 万篇文档、平均 2000 字，抽取一遍在百万 token 级——这笔钱在向量 RAG 里是零。语料更新频繁时，增量索引策略（只重建受影响社区）决定这笔钱是付一次还是每天付。

## 案例回流：全局问题的对照

"这个代码库的架构演进主线是什么"是 GraphRAG 的典型主场：向量检索按相似度召回片段，"主线"散布在全部提交记录里，任何 top-k 都只捞到碎片；GraphRAG 先建实体（模块、作者、决策）与关系图，查询时在社区摘要层聚合，一次回答覆盖全局。本库 [[工程知识/AI 系统工程：从模型能力到生产能力/知识与检索/GraphRAG适合关系与全局问题但成本更高]] 讲的取舍在缺陷分析域有同构经验：[[工程知识/缺陷分析：从个案到体系/缺陷分析：从个案到体系——导读与开源地图]] 的个案定位靠局部相似检索就够，跨个案的体系性结论（哪类缺陷反复出现）靠的是人工建的图谱——两件事在检索路径上同构。

## 验证

验证的锚点：图检索收益要与查询分桶对账——预写关系型与全局型查询上证据覆盖提升、局部事实类不低于混合检索，实测与预期对不上而构图成本照付，就不值得上。

按关系型、全局型、局部事实、无答案和更新/撤权查询分桶，与普通 hybrid RAG 比较证据覆盖、引用精度、召回、延迟、构图成本和更新滞后。图上的边和摘要必须能回指原文，不接受只有模型解释的关系。

## 效果与代价

引入图结构的收益出现在跨文档与全局问题：关系链与主题聚合能一次回答覆盖较多材料，引用可以逐条回到原文。代价是离线抽取与摘要带来的额外调用，以及实体消歧、增量更新与删除传播的持续维护；单跳事实查询与精确查值在这套结构下面临的延迟与滞后都比直接检索更高。

## 机制与本质

GraphRAG 的机制层：向量检索按相似度取回片段，片段的聚合上限由 top-k 决定，散落在多份文档中的关系无法在一次召回里汇集。图结构先抽取实体与关系并形成社区摘要，查询时在摘要层聚合，代价是抽取错误会沿结构化结果放大，且更新一份文档需要重建受影响的社区。

## 要解决的问题

需要跨多份文档汇总关系的问题，用向量检索只能取回零散片段，答案缺少全局视角；把图结构引入之后，构建与更新成本明显上升，收益能否覆盖成本缺少判断依据。本篇回答：哪一类问题需要跨文档关系或全局聚合、图结构在什么条件下值得承担构建与维护成本、关系与摘要怎样和原文核对，以及它与混合检索方案的对比口径是什么。
