# 多模态RAG：图表、PDF与音频的证据不能只靠文本化

**把带图表的 PDF 转成纯文本入库，图表里的数字就全丢了——检索能命中报告，却答不出图里的问题**。**读完这篇你能按模态选解析策略，让视觉、表格和音频里的证据可被检索定位**。 这里的检索底座是 RAG（检索增强生成：先从资料库里找出相关片段，再让模型照着这些片段回答），只是被检索的对象从纯文本扩展到了图表、表格与音频，因此解析和索引要按模态分别处理。

用户问"第三季度各区域销售额的趋势"，库里是带图表的 PDF（Portable Document Format，便携文档格式）报告；**系统把 PDF 转纯文本入库，图表里的数字全部丢失，检索命中了报告但答非所问——把多模态文档硬压成文本再检索，会系统性丢掉只存在于图表、表格结构和音频里的证据**。**要解决的问题：按模态选择解析与索引策略，让视觉、表格、音频里的证据可被检索、可被定位、可被引用，而不是退化为"检索到文档但答不出图里的问题"**。

**本质是模态保真（保留每种模态原始信息的程度）与检索粒度（检索能定位到多细）之间的权衡**。**文本化即 OCR（Optical Character Recognition，光学字符识别：从图片里认出文字）转写——OCR 是 Optical Character Recognition、光学字符识别——把一切拉回文本管道，所有模态都塞进已有的纯文本 RAG 管道、不用新建检索设施，所以基建复用最大，但丢视觉证据**；**多模态 embedding 把图、文映射进同一个向量空间**，可以想成把图和文都翻译成同一本字典里的页码，页码靠近的就语义相近——这个比方只用于理解「不同模态进了同一个可比较空间」，相似度怎么标定要看正文。

跨模态检索更方便，但匹配精度和存储计算成本更高；混合方案（文本 + 图像描述 + 结构化表格抽取是当前工程主流，三路证据并存、按问题路由）。

## 多模态文档怎么按模态解析、怎么建三路索引

**RAG 的整体结构可以拆成两段：离线把文档处理成可检索的索引，在线按查询检索后把结果连同问题交给模型**。**分模态解析改变的是前一段——图表、表格不再被压成残缺文本**。

![RAG 的高层架构：文档经处理后进入索引，查询时先检索再把结果连同问题一起交给模型生成答案](/static/figures/ms-rag-high-level-architecture.svg)

*图源：Microsoft Learn 中文文档，CC BY 4.0，https://learn.microsoft.com/zh-cn/azure/architecture/ai-ml/guide/rag/rag-solution-design-and-evaluation-guide。*


| 模态 | 解析方式 | 索引形态 | 保真要点 |
| --- | --- | --- | --- |
| 图表/图像 | OCR + 布局分析 + 视觉模型描述 | 图像描述文本 + 原图位置引用 | 图中数值与标签须进描述，不只说"有张图" |
| 表格 | 表格结构抽取（行列关系） | 序列化表格（把二维表转成一行行可存储的文本）+ Markdown/HTML 结构 | 行列语义保留，跨页表格合并 |
| 音频/视频 | ASR（Automatic Speech Recognition，自动语音识别）转写 + 时间戳匹配 | 转写文本 + 时间轴索引 | 说话人与时间窗可定位 |
| 扫描件 | OCR + 置信度过滤 + 人工抽检 | 文本 + OCR 置信度标记 | 低置信区降权或送人工 |

**四路模态各走各的解析与索引链，汇入同一个索引库，即检索时按证据类型路由的向量与结构化索引集合；证据定位粒度按模态落到页加区域、行列坐标、起止秒三种引用形态，扫描件经 OCR 并入文本路、按页定位**。

**文本化丢的不是一种东西：表格丢的是结构，剩下的一串数字还能靠表头猜回行列；图表丢的是整块证据，图没了就是没了，生成模型再强也补不回来**。**先分清丢在哪一档，才谈得上按模态补索引**。

```mermaid
flowchart TB
    a["表格丢结构"] --> a1["列名与数值脱钩<br>还能部分恢复"]
    a1 --> b["图表丢整块证据"]
    b --> b1["图形内容不在库里<br>无法恢复"]
    b1 --> c["音频丢语气与说话人"]
    c --> c1["归属错乱<br>谁说的对不上"]
```

**三档里只有第一档能靠下游补救，后两档的补救只能发生在入库之前**。

**关键设计：证据定位粒度到"页 + 区域"。多模态文档的引用要能回到原图/原时间点，生成端引用"报告第 7 页左上图表"而不是只引用文档名，否则用户无法核验**。

## 只靠文本化会丢掉哪些证据：失效形态

| 失效 | 机制 | 信号 |
| --- | --- | --- |
| 图表证据丢失 | PDF 文本化时图表被跳过 | 问图中数据时检索不到或答错 |
| OCR 幻觉 | OCR 把模糊字符猜成真实值 | 引用文字与原页不符 |
| 模态错配假支持 | 图像描述与图内容脱节，检索命中但答案无据 | 引用了"描述"而非图本身 |
| 表格语义断裂 | 序列化丢行列关系，"行3列2"变碎片 | 聚合类问题（趋势/对比）答错 |
| 时间轴丢失 | 音频转写不保时间戳 | "第10分钟说了什么"无法回答 |

## 这套说法在哪儿会失效

- **多模态 embedding（把文字、图片等内容转成一串数字向量，机器靠向量距离算相似度）仍处于快速演进期：跨模态检索质量对不同模型的差异大，选型要拿自己的语料实测——公开 benchmark（标准评测数据集）是在别的模型、别的语料上测出的，你的语料分布不同，结论不能直接外推**。
- **"描述生成"是一把双刃剑：视觉模型生成的描述可能幻觉（图中没有的数字被描述出来），描述必须带原图引用并抽样人审**。
- **三路索引的维护成本明显高于文本管道：解析、索引、更新、权限都要按模态各做一遍，小规模场景先确认收益再上**。
- **模态缺失降级（主动牺牲部分功能或精度，保住核心链路）要显式设计：查询带图但索引只有描述、或 ASR 失败的音频段，检索层要能报告"证据不完整"，静默忽略会让残缺证据当成完整证据使用**。

## 动手跑一遍会看到什么：同一页 PDF 的两种索引


**路由发生在检索侧：问题先按证据类型分到图表块、结构化表格、时间轴索引三条支路（这里的「支路」只是检索路由的比喻，指同一检索系统按证据类型走不同索引，并非三套独立系统），再各自过一遍「该模态是否已入库」，缺了就走「检索层报告证据不完整」而不是静默退回正文**：

```mermaid
flowchart TB
    G["引用粒度"] -->|"图表块"| G1["页加区域"]
    G -->|"结构化表格"| G2["行列坐标"]
    G -->|"时间轴索引"| G3["起止秒"]
```

**路由与降级决定了同一页 PDF 能不能答出图里的问题：四类证据各自入库检查，缺失或 ASR 失败时检索层报告证据不完整，静默退回正文会把残缺证据当成完整证据使用**。

一页含柱状图与表格的财报 PDF，纯文本化与分模态索引的证据差异：

```python
# 方案 A：纯文本化（常见默认路径）
text = pdf_page.extract_text()
#   柱状图 → 一个字都提不出来（图形内容整块丢失）
#   表格   → "Q1 320 Q2 410 Q3 295 ..." 列名与数值脱钩，单元格关系全断
#   后果：查询"哪个季度环比下滑最大"→ 检索命中该页 → 模型看着残缺文本瞎算

# 方案 B：分模态解析 + 三路索引
images = extract_figures(pdf_page)          # 图表按块提出，保留原图
table  = extract_table(pdf_page)            # 表格按结构化行提出
capt   = pdf_page.text                      # 正文文本
index.upsert([
    ("fig-3",  embed(caption_of(images[0])), {"type": "figure", "data": images[0]}),
    ("tab-1",  embed(serialize(table)),      {"type": "table",  "rows": table}),
    ("txt-1",  embed(capt),                  {"type": "text"}),
])
#   查询"哪个季度环比下滑最大" → 表格行被召回（含列名与数值的对应关系）
#   → 生成时把原始行数据放进上下文 → 答案：Q3
```

跑一遍的收获：文本化丢的重量分级——表格丢结构（还能部分恢复），图表丢整块证据（无法恢复），音频转写丢语气与说话人（归属错乱）。分模态索引让每种模态用自己无损的表示进库，检索时按证据类型路由。

## 量化锚点怎么取、案例怎么回流

**图像链路与文本链路是同一套工程结构：采集、标注、训练、部署**。**多模态 RAG 的索引侧可以参照这条链路来建**。

![计算机视觉的 MLOps架构：图像数据从采集、标注、训练到部署的完整链路](/static/figures/ms-computer-vision-architecture.png)

*图源：同上（Microsoft Learn 中文文档），CC BY 4.0。*


**从丢失率看：图表密集型文档（财报、论文、运维报告）里图表承载的信息占比按语料实测，纯文本化等于整块证据进不了库——这类查询的失败在检索层就注定，与生成模型能力无关**。**从成本看：分模态解析的入库成本高于纯文本化（版面分析 + 多模态编码两道工序叠加），高出的倍数以自家语料的图表密度实测为准，但这份多出的成本只在入库时付一次——检索时用的是已经建好的索引，不再重新解析，所以检索侧成本不变**。**案例回流：跨模态归属错乱的实录形态见 [[工程知识/缺陷分析：从个案到体系/正确性/案例三十九：身份在改写中丢失——RLS 子查询与视图 DEFAULT 的静默失真]]**。**中间表示（视图、转写文本这类系统内部用来衔接上下游的数据形式）在格式转换时会把说话人、归属等字段丢弃，且转换后无法还原；下游只能拿到失真证据继续算，静默错值**；[[工程知识/AI 系统工程：从模型能力到生产能力/Agent与工作流/结构化输出与约束解码：schema约束形状，事实另需验证.md]]（schema 指数据结构定义）的分工在多模态域同样成立——**表格行进上下文是"形状可解析"，数值对不对要靠原始行数据而非模型记忆**。

## 怎么自己动手验证

**多模态管道要与问题类型对照检验——预写「答案只在图里」的问题，图表、表格、时间轴三路索引的召回显著更高、纯文本类两者持平，实测与预期对不上就说明该批图表不值得单建索引**。

**最小验证：构造一个含 10 张图表、5 张表、2 段音频的测试语料，准备两类问题——"图中数据类"（答案只在图里）与"文本类"，分别测文本化管道与三路索引管道；断言图中数据类问题的召回率（该找出的证据被成功检索出来的比例）三路方案显著更高、文本类问题两者持平**。**再做 OCR 抽检：随机抽 20 个 OCR 结果与原页对照，统计字符错误率与幻觉率，幻觉（编造数字）零容忍、字符错误率 >2% 时该批次降权**。
