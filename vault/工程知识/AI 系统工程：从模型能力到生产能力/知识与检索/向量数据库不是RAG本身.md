# 向量数据库不是 RAG 本身

**向量数据库负责保存向量、近似最近邻索引、过滤和部分数据服务能力；RAG（Retrieval-Augmented Generation，检索增强生成：先检索资料再让模型基于资料回答） 还包括文档解析、权限、版本、召回策略、证据组装、生成和评测。一个高性能向量库不能修复错误切分、错误 embedding（把文本转成向量的表示）、缺失 ACL（访问控制列表：一条条写明"谁对什么能做什么"的权限表）或无法引用原文的问题。**
读完这篇你能判断检索效果不好该换库还是改切分与召回，也知道向量库解决不了哪几类问题。

## 要解决的问题：向量库在检索链路中实际负责哪一段

把向量数据库当作 RAG 的整体，上线后发现引用出错、撤回的数据仍能被搜到、返回条目数少于预期。本篇回答：向量库在检索链路中实际负责哪一段、索引选型与分块和嵌入（把文字或对象映射成向量、语义越近向量距离越近）模型相比谁的影响更大、权限与撤回应放在链路的哪个位置，以及索引选择要在什么条件下才有意义。

一个可用的比方是：向量库像图书馆里按内容相似把书归到邻近书架的那道工序，它不管书怎么拆页、谁有权借、最后怎么写读书报告——向量库负责的是「按距离找近邻」这一段，把整座图书馆当成这道工序就错了。这个比方只对应检索这一段，馆舍怎么盖、借阅权限系统怎么运转是另外几道工序；检索链路其余几段各有各的机制，逐节看。

## 索引靠什么在召回、延迟、内存之间做权衡？

精确最近邻在规模增大时成本高，ANN（Approximate Nearest Neighbor，近似最近邻，用近似换速度）通过图（如 HNSW：分层可导航小世界图，向量近似最近邻索引的主流算法）、倒排聚类（如 IVF：倒排文件索引，向量检索的聚类分桶方法）或乘积量化减少搜索范围和内存。**参数改变的是召回率（被找回来的相关样本占全部相关样本的比例）、延迟、内存和构建时间的权衡**：调大 HNSW 的 ef 或 IVF 的 nprobe 会多探测候选，召回率升高但延迟和 CPU 随之上升。**不同索引、不同参数算出的相似度分数口径不同，不能拿 0.8 分在两套配置间直接比较谁更相关。**

## 选型时要先回答哪些问题

- 数据规模、向量维度、更新/删除频率和重建窗口是什么？
- 过滤条件是租户/ACL 硬约束，还是可接受近似的业务属性？过滤发生在召回前、后还是索引内部？
- 需要单机库、关系数据库扩展、搜索引擎，还是多租户分布式服务？
- 持久化、备份、复制、分片（把数据按规则切开、分散到多个节点存储）、冷热数据、压缩和升级如何验证？
- 结果如何回到原文、版本和证据位置？

## 为什么把向量库当成 RAG 全部会出错？

把向量库当成 RAG 的全部，等于把传输层当成整条链路——传输层这个比方和上面的图书馆工序说的是同一件事，只是换了强调的侧面：传输层只管两点间把包送达、不管内容对错，正如向量库只管「相似的东西找出来」、不管切分与权限；上面还有检索编排与生成，下面还有元数据过滤与权限检查。但 RAG 链路不等于网络栈，不能把重试、拥塞这类网络机制类推过来。


- 只看 benchmark 的 QPS（每秒查询数：一秒钟处理了多少个请求），不固定维度、硬件、过滤、更新和 Recall@k。
- 把向量距离阈值**当作「相关/不相关」的通用标准**。
- 新旧 embedding 混在同一个索引，却没有模型版本和迁移策略。
- 让向量检索绕过数据库 ACL，再在生成阶段「提醒模型注意权限」。

## 最小实验能看清索引选择的哪一段影响？

用真实查询和人工相关性标注，比较精确基线（正常状态下的指标水平、用来对比异常）与 ANN 的 Recall@k、p95 延迟、内存、构建/更新时间和过滤正确率；加入删除、撤权、热点（访问集中在少数键或节点上的现象）、空查询和重启恢复。只有在 RAG 端到端质量、引用和成本同时满足门槛时，索引选择才有意义。

## 这些量在什么数量级：检索质量的分账本

**端到端答案质量是全链路的乘积**——这里是比喻各环节相互制约，任一环节差到零，整体就失效——向量库只占其中一段：**分块策略（块大小与重叠）对召回质量的影响常大于索引选型**（同一问题，512 字与 128 字分块的召回率差可达 15-30%），**嵌入模型的影响又大于分块**（不同模型的召回差距 10-40%）。索引层的账（HNSW 的 ef 参数、IVF 的 nprobe）决定的是"给定向量，近似检索的召回率-延迟曲线"——**把它调到 99% 召回也救不回坏的分块。调优顺序按影响面从大到小依次为：嵌入模型、分块、检索后处理（rerank）、索引参数，成本递增、收益递减。**

## 真实案例里发生了什么：新鲜度与权限的衔接

向量库在 RAG 里管不了的两件事有专文：[[工程知识/AI 系统工程：从模型能力到生产能力/知识与检索/RAG的新鲜度与权限传播：撤回的数据不能再被检索到]] 讲撤回传播与权限过滤的位置（过滤放检索后会被清空 top-k），[[工程知识/AI 系统工程：从模型能力到生产能力/知识与检索/GraphRAG适合关系与全局问题但成本更高]] 讲向量检索够不着全局问题。三篇合起来的判据：先问问题是局部的还是全局的、有没有权限边界、撤回要求多快，再决定向量库在链路里的位置。

**向量库只覆盖检索一段，若问题本就是全局的或有权限边界，先选库才发现不顶用，返工与迁移成本更高，所以先选数据库后问问题的顺序是反的。**

## 动手跑一遍会看到什么：RAG 全链路的账

可运行示例：同一个"查不到正确答案"的症状，三层各自的可能性：

```python
query = "q3 的退货率环比变化"
# 症状：向量库返回了 top-5，答案还是错的

# 第 1 层 数据入库（在向量库之前，最常见的断点）
doc = load("q3_report.pdf")
chunks = naive_split(doc, 500)      # 表格被从中间切断
#   "环比 -28%" 在表格右半页 → 切走的碎片里没有数值 → 检索必失败
#   修复：结构感知切分（按版面元素切），表格整块入库

# 第 2 层 检索（向量库所在的层）
results = vector_db.search(embed(query), top_k=5)
#   向量库只做"按相似度找 chunk"这一件事
#   词汇精确匹配弱（"退货率"在文档里叫"refunded ratio"）→ 混合检索补

# 第 3 层 生成（拿到证据之后的层）
answer = llm(query, context=results)
#   证据在 context 里但模型没用上 → 输出约束与引用校验补
```

把 RAG 失败全归因向量库的实录——换向量库指标纹丝不动，真正病灶在入库切分把表格切碎（第 1 层）；换库的采购与迁移成本以周计，改切分逻辑的成本以天计——诊断分层省下的就是这种绕路。分层职责的姊妹篇：[[工程知识/AI 系统工程：从模型能力到生产能力/知识与检索/混合检索、重排与查询改写各自解决什么问题.md]]（第 2 层内部四件套）、[[工程知识/AI 系统工程：从模型能力到生产能力/知识与检索/RAG的核心是选择可引用证据.md]]（证据标准），三篇合起来是"选型只是全链路一环"的完整论证。

## 这套说法在哪儿会失效

- 索引层只决定给定向量下的召回与延迟曲线：分块策略与嵌入模型对召回的影响面大于索引选型，把索引参数调到高召回也补不回分块造成的损失。
- 近似检索的召回率与延迟互为代价：提高探测范围能提升召回，同时抬高每次查询的延迟与 CPU 占用，参数要按实际查询分布定。
- 权限过滤的位置决定结果：过滤放在检索之后时，先被过滤掉的条目会掏空 top-k（返回最相似的前 k 条），返回的条目数少于预期。
- 撤回与更新沿索引传播存在延迟：条目从向量索引中删除和对文本库的删除是两个动作，不同步时仍能被检索到。
- 向量库不承担全文检索的职责：标识符、报错码、专有名词这类精确匹配需要关键词检索配合。
