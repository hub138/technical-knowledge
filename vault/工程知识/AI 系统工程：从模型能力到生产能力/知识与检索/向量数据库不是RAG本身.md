# 向量数据库不是 RAG 本身

向量数据库负责保存向量、近似最近邻索引、过滤和部分数据服务能力；RAG 还包括文档解析、权限、版本、召回策略、证据组装、生成和评测。一个高性能向量库不能修复错误切分、错误 embedding、缺失 ACL 或无法引用原文的问题。

## 索引的本质

精确最近邻在规模增大时成本高，ANN 通过图（如 HNSW）、倒排聚类（如 IVF）或乘积量化减少搜索范围和内存。参数改变的是召回率、延迟、内存和构建时间的权衡；索引分数不是跨配置的统一概率。

HNSW 的图结构在图上分三层看，查询路径逐层下降：

来源：Wikimedia Commons「Hierarchical Navigable Small World (HNSW)」条目图。三层从上到下点密度递增，红色查询箭头逐层 descend——这就是「用图结构减少搜索范围」的具体形态：顶层图长、跳得远，用来快速接近目标区域，下层图密、跳得近，用来精确定位；「提高探测范围能提升召回」对应的是放大每层的候选队列，代价就是图上箭头要走更多分叉。

## 选型要回答的问题

- 数据规模、向量维度、更新/删除频率和重建窗口是什么？
- 过滤条件是租户/ACL 硬约束，还是可接受近似的业务属性？过滤发生在召回前、后还是索引内部？
- 需要单机库、关系数据库扩展、搜索引擎，还是多租户分布式服务？
- 持久化、备份、复制、分片、冷热数据、压缩和升级如何验证？
- 结果如何回到原文、版本和证据位置？

## 常见误区

- 只看 benchmark 的 QPS，不固定维度、硬件、过滤、更新和 Recall@k。
- 把向量距离阈值当作“相关/不相关”的通用标准。
- 新旧 embedding 混在同一个索引，却没有模型版本和迁移策略。
- 让向量检索绕过数据库 ACL，再在生成阶段“提醒模型注意权限”。

## 最小实验

用真实查询和人工相关性标注，比较精确基线与 ANN 的 Recall@k、p95 延迟、内存、构建/更新时间和过滤正确率；加入删除、撤权、热点、空查询和重启恢复。只有在 RAG 端到端质量、引用和成本同时满足门槛时，索引选择才有意义。

## 量化锚点：检索质量的分账本

端到端答案质量是全链路的乘积，向量库只占其中一段：分块策略（块大小与重叠）对召回质量的影响常大于索引选型（同一问题，512 字与 128 字分块的召回率差可达 15-30%），嵌入模型的影响又大于分块（不同模型的召回差距 10-40%）。索引层的账（HNSW 的 ef 参数、IVF 的 nprobe）决定的是"给定向量，近似检索的召回率-延迟曲线"——把它调到 99% 召回也救不回坏的分块。调优顺序按影响面排：嵌入模型 > 分块 > 检索后处理（rerank）> 索引参数，成本递增、收益递减。

## 案例回流：新鲜度与权限的衔接

向量库在 RAG 里管不了的两件事有专文：[[工程知识/AI 系统工程：从模型能力到生产能力/知识与检索/RAG的新鲜度与权限传播：撤回的数据不能再被检索到]] 讲撤回传播与权限过滤的位置（过滤放检索后会被清空 top-k），[[工程知识/AI 系统工程：从模型能力到生产能力/知识与检索/GraphRAG适合关系与全局问题但成本更高]] 讲向量检索够不着全局问题。三篇合起来的判据：先问问题是局部的还是全局的、有没有权限边界、撤回要求多快，再决定向量库在链路里的位置——先选数据库后问问题的顺序是反的。

## 可运行示例与案例回流：RAG 全链路的账

可运行示例：同一个"查不到正确答案"的症状，三层各自的可能性：

```python
query = "q3 的退货率环比变化"
# 症状：向量库返回了 top-5，答案还是错的

# 第 1 层 数据入库（在向量库之前，最常见的断点）
doc = load("q3_report.pdf")
chunks = naive_split(doc, 500)      # 表格被从中间切断
#   "环比 -28%" 在表格右半页 → 切走的碎片里没有数值 → 检索必失败
#   修复：结构感知切分（按版面元素切），表格整块入库

# 第 2 层 检索（向量库所在的层）
results = vector_db.search(embed(query), top_k=5)
#   向量库只做"按相似度找 chunk"这一件事
#   词汇精确匹配弱（"退货率"在文档里叫"refunded ratio"）→ 混合检索补

# 第 3 层 生成（拿到证据之后的层）
answer = llm(query, context=results)
#   证据在 context 里但模型没用上 → 输出约束与引用校验补
```

案例回流：把 RAG 失败全归因向量库的实录——换向量库（Milvus 换 Qdrant 再换 pgvector）指标纹丝不动，真正病灶在入库切分把表格切碎（第 1 层）；换库的采购与迁移成本以周计，改切分逻辑的成本以天计——诊断分层省下的就是这种绕路。分层职责的姊妹篇：[[工程知识/AI 系统工程：从模型能力到生产能力/知识与检索/混合检索、重排与查询改写各自解决什么问题.md]]（第 2 层内部四件套）、[[工程知识/AI 系统工程：从模型能力到生产能力/知识与检索/RAG的核心是选择可引用证据.md]]（证据标准），三篇合起来是"选型只是全链路一环"的完整论证。

## 边界

- 索引层只决定给定向量下的召回与延迟曲线：分块策略与嵌入模型对召回的影响面大于索引选型，把索引参数调到高召回也补不回分块造成的损失。
- 近似检索的召回率与延迟互为代价：提高探测范围能提升召回，同时抬高每次查询的延迟与 CPU 占用，参数要按实际查询分布定。
- 权限过滤的位置决定结果：过滤放在检索之后时，先被过滤掉的条目会掏空 top-k，返回的条目数少于预期。
- 撤回与更新沿索引传播存在延迟：条目从向量索引中删除和对文本库的删除是两个动作，不同步时仍能被检索到。
- 向量库不承担全文检索的职责：标识符、报错码、专有名词这类精确匹配需要关键词检索配合。

## 要解决的问题

把向量数据库当作 RAG 的整体，上线后发现引用出错、撤回的数据仍能被搜到、返回条目数少于预期。本篇回答：向量库在检索链路中实际负责哪一段、索引选型与分块和嵌入模型相比谁的影响更大、权限与撤回应放在链路的哪个位置，以及索引选择要在什么条件下才有意义。
