# RAG的新鲜度与权限传播：撤回的数据不能再被检索到

RAG 系统上线后最常见的失效不是检索不准，而是"检索到了不该检索的东西"：文档已更新但索引里还是旧版，作者已撤回但向量库里还能召回，用户没有权限但摘要层把内容漏了出去。要解决的问题：把新鲜度、权限和删除当作检索链路的一等公民，而不是索引之外的事后过滤。

本质是三个缓存一致性问题叠加。索引、摘要、向量、图结构都是源文档的派生物；源变了派生物必须跟着变，权限判断必须在召回前生效，删除必须传播到所有派生层。任何一层漏掉，用户看到的都是过期、越权或已删除的内容。

## 三类失效形态

| 失效 | 机制 | 信号 |
| --- | --- | --- |
| 新鲜度失效 | 源文档更新后索引未重建，召回旧版本 | 引用时间戳早于源 updated；同一问题新旧答案不一致 |
| 权限失效 | 召回时只看语义相似度，ACL 在生成后才检查或不检查 | 低权限用户引用中出现高权限内容 |
| 删除失效 | 源已删除但向量、摘要、缓存、图节点残留 | 已撤回文档仍被引用；删除后命中率未降 |

## 机制：版本、过滤位置与传播路径

权限过滤的正确位置在召回之前或之中：向量库支持带 filter 的检索时把 ACL 作为过滤条件传入，不支持时在候选集生成后、context 组装前过滤。生成后再检查已经晚了，因为越权内容可能已进入 prompt 或被模型转述。

新鲜度用版本对齐保证：源文档带 revision 与 valid time，索引记录同 revision；召回时带出版本，生成引用时展示版本与时间。检测新旧分叉最简单的办法是定期对账源与索引的 hash。

删除传播是三者的老大难。一次"删除文档"实际要清理：向量库条目、摘要、父子文档树中的子块、图索引的节点与边、检索缓存、已生成的历史回答（后者通常不追溯，但要在证据链上标记失效）。漏掉任何一层，删除就只是"入口不可见"。

## 边界

- 先过滤权限会缩小召回池，可能让低权限用户得到"拒答"而非"部分回答"，这是产品决策不是技术缺陷，需要明确选一个。
- 向量库的 filter 性能有限：ACL 维度多、规模大时，先粗召回后细过滤可能比全量带 filter 更快，两种顺序都要测。
- 版本对齐有窗口期：源更新到索引重建之间必然存在旧版可召回的间隙，重要的场景要在引用上标注时间戳让用户可判断。
- 图索引（GraphRAG 类）的删除传播成本远高于平面向量：节点被多份摘要引用时，删除需重建受影响的摘要层。

## 验证

最小验证三件套：一是删除传播测试，删一篇文档后遍历所有派生层断言零命中，记录传播时间；二是越权零容忍测试，用不同权限身份跑同一问题集，断言低权限回答不含高权限内容的 hash；三是新鲜度对账，抽样比较源与索引的 revision，统计分叉率。
