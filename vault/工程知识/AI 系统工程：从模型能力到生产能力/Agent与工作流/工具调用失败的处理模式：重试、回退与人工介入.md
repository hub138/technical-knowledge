# 工具调用失败的处理模式：重试、回退与人工介入

Agent 调用工具时，**失败是常态**。网络抖动、服务过载、模型输出格式错误、工具本身返回异常——**每个环节都可能出错**。读完这篇，你能判断当前场景该用哪种失败处理模式、重试与回退的边界在哪、以及什么情况下必须交给人工。

本篇要解决的问题是：工具调用失败后，Agent 该自动恢复还是交给人工，自动恢复的边界在哪，为什么这道边界定错会让小故障放大成事故。**失败模式的选择决定了 Agent 的可用性**——重试太激进会放大负载，回退太保守会降低任务完成率。处理模式的本质是：在不确定的环境中，用确定的策略管理失败——**把不可预测的失败转化为可预测的恢复路径**。

## 失败类型与处理模式

工具调用失败按原因分四类，每类对应不同的处理模式：

| 失败类型 | 典型原因 | 处理模式 | 重试安全 |
|---------|---------|---------|---------|
| 网络/超时 | 连接断开、服务端超时 | 重试（带退避） | 安全（幂等） |
| 工具返回异常 | 工具内部错误、数据不存在 | 回退（降级/替代） | 不安全（重试可能重复） |
| 模型输出格式错误 | JSON 格式错误、参数缺失 | 重新解析/重生成 | 安全 |
| 安全/权限错误 | 鉴权失败、越权调用 | 人工介入 | 不安全 |

**网络/超时类失败**是最常见的失败类型。这类失败通常可以通过重试解决，但**重试策略决定了恢复效率**。指数退避（exponential backoff）是标准做法：第一次重试等待 1 秒，第二次 2 秒，第三次 4 秒，以此类推，最大等待时间不超过 30 秒。**退避的数学原理是让负载自然扩散，避免所有重试在同一时刻冲击后端**——如果所有客户端都在 1 秒后重试，退避等于没退。加入随机抖动（jitter）可以进一步打散重试时间点，把重试风暴（重试流量层层放大、让故障雪上加霜）的概率降到最低。

**工具返回异常类失败**需要区分"工具本身不可用"和"工具返回了业务异常"。工具本身不可用时（如数据库连接失败），回退到替代工具或降级方案；工具返回了业务异常时（如查询无结果），需要判断是重试还是返回给 Agent 重新决策。**判据是"重试能否改变结果"**——查询无结果重试 10 次也不会变，但超时重试可能成功。

**模型输出格式错误**是 Agent 框架特有的失败类型。模型可能输出不合法 JSON、参数类型错误、或调用了不存在的工具。处理模式是让模型重新生成输出，但需要限制重试次数（通常 2-3 次），超过后回退到人工。**重试时把错误信息作为反馈传给模型，让模型知道哪里错了**。

**安全/权限错误**必须交给人工。**自动重试安全错误等于绕过安全策略，这是不可接受的**。安全错误的典型场景包括：越权（访问了权限范围之外的资源）调用工具、访问未授权数据、触发速率限制。

## 重试策略的工程实现

重试不是简单的"失败了再试一次"。**一个完整的重试策略包含四个参数**：

- **最大重试次数**：通常 2-3 次，超过后进入回退。3 次的原因：第一次重试解决瞬时故障，第二次解决短暂恢复，第三次是兜底——超过 3 次还失败，大概率不是瞬时问题。
- **初始退避时间**：1 秒的初始退避对大多数场景足够。对于长耗时工具（>10 秒），初始退避可以设为 5 秒。
- **最大退避时间**：30 秒是常见上限。超过这个时间，用户已经感知到延迟，不如直接回退。
- **退避策略**：指数退避是最常用的策略。退避公式为 `min(初始退避 × 2^(重试次数), 最大退避时间)`。加入随机抖动后，实际等待时间在 `[退避时间 × 0.5, 退避时间 × 1.5]` 之间随机。

重试的前置条件是**幂等（同一操作执行多次与执行一次效果相同）性**。如果工具调用不是幂等的（如创建订单、发送消息），重试可能导致重复操作。**幂等性判断是选择重试还是回退的分水岭**：非幂等操作的重试必须带幂等键（idempotency key），或者直接回退到人工。

幂等键的实现：客户端生成唯一请求 ID，服务端按 ID 去重。如果重试时服务端已经处理过该请求，返回已处理的结果而不是重复执行。幂等键的生成规则要保证全局唯一，通常用 UUID 或"用户 ID + 时间戳 + 随机数"组合。

## 回退策略：降级与替代

当重试失败或重试不安全时，**回退是第二道防线**。回退有三种模式：

**降级回退**：用简化版本替代原工具。例如，搜索工具不可用时，用本地缓存结果替代；精确计算不可用时，用近似估算替代。**降级的代价是精度或覆盖范围下降，但任务可以继续**。

**替代回退**：用功能相似的不同工具替代。例如，A 模型不可用时切换到 B 模型，主数据库不可用时切换到只读副本。**替代回退的前提是系统中有冗余能力**。

**跳过回退**：跳过当前工具调用，让 Agent 调整计划。**这是最保守的回退**，适用于工具不可用且没有替代方案的情况。Agent 需要重新规划，用其他方式完成任务。

回退策略的选择顺序：替代回退优于降级（压力过大时关闭次要功能，保住主流程）回退，降级回退优于跳过回退。**替代回退保持功能完整，降级回退牺牲精度但保持流程，跳过回退打乱任务计划**。

## 人工介入的触发条件

人工介入是系统设计的一部分。以下情况必须交给人工：

- **安全/权限错误**：自动处理安全错误可能绕过安全策略。
- **重试与回退都失败**：所有自动恢复手段用尽后，交给人工是最稳妥的选择。
- **不确定性超过阈值**：模型对工具返回结果的置信度低于阈值时，交给人工判断。
- **成本超过收益**：自动恢复的成本（重试消耗的 token、回退导致的质量下降）超过人工介入的成本时，应该交给人工。

人工介入的实现方式：将失败上下文（失败类型、重试历史、回退结果、当前状态）打包成工单，推送到人工处理队列。人工处理后，结果回写到 Agent 上下文，Agent 继续执行。工单的最小字段：

```json
{
  "task_id": "task-xxx",
  "failed_tool": "search_documents",
  "failure_type": "tool_exception",
  "retry_count": 3,
  "fallback_result": "降级到本地缓存，返回了 3 条结果",
  "context": "用户查询：2024年Q3财报数据",
  "decision_needed": "是否接受降级结果，或重新执行查询"
}
```

## 这些模式在哪些场景不适用

重试策略的前提是**失败可重试**。以下场景重试无效或有害：

- **业务逻辑错误**：工具返回"用户不存在"，重试 100 次也不会变。
- **数据一致性错误**：写操作重试可能导致数据重复。
- **速率限制**：重试会加剧速率限制，**应该退避等待而不是重试**。
- **工具已废弃**：工具返回 410 Gone，重试没有意义。

回退策略的前提是**有替代方案**。对于唯一依赖的工具（如核心数据库），回退可能不可行。这种情况下，**系统设计时就要考虑冗余，而不是在失败时才找替代**。

人工介入的前提是**有人可介入**。无人值守的自动化系统（如夜间批处理任务）需要预设默认行为——通常是"跳过并记录，次日人工审查"。

## 验证方法

验证失败处理模式是否有效，测试要覆盖以下场景：

1. **重试有效性验证**：模拟网络故障，验证重试次数、退避时间和最终恢复是否符合预期。
2. **幂等性验证**：对非幂等操作模拟重试，验证幂等键是否有效防止重复。
3. **回退验证**：模拟工具不可用，验证回退策略是否按预期执行。
4. **人工介入验证**：验证失败上下文是否完整传递到人工工单。
5. **边界条件验证**：重试次数超限、所有回退失败、安全错误等边界情况。

最小验证方案：用测试工具模拟三种失败类型（超时、异常、格式错误），各跑 10 次，验证处理模式是否符合预期。验证结果记录到测试报告。
