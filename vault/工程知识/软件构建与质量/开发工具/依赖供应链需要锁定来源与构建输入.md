# 依赖供应链需要锁定来源与构建输入

## 核心拆解

| 维度 | 回答 |
| --- | --- |
| 要解决的问题 | 构建结果会受传递依赖、镜像、脚本、工具链和仓库状态影响；仅记录“安装成功”无法复现、审计或安全回滚。 |
| 本质 | 把源码之外的每一个可影响产物的输入固定成可追溯身份，并在隔离环境中验证其行为和来源。 |
| 做法 | 使用 lockfile、版本/哈希/签名、可信 registry、工具链清单、SBOM 和构建证明；升级先评估许可证、漏洞、兼容和回滚。 |
| 效果与代价 | 产物可重建、风险可定位、升级可回退；代价是锁文件维护、存储证明、扫描和供应商治理成本。 |
| 边界 | 锁版本不能证明依赖无漏洞或行为适合业务；缓存命中、扫描绿色和包能安装都不是完整安全结论。 |
| 验证 | 在干净环境构建两次，比较产物与输入；注入恶意脚本、缓存污染、源不可用和升级回滚，检查门禁证据。 |

依赖管理解决的不只是“把包下载下来”，还包括版本解析、传递依赖、许可证、漏洞、构建脚本、镜像、缓存和可重现性。一个短暂的网络成功不能成为产物身份。

一个 lockfile 相同的构建仍可能因 registry、平台 wheel、编译器、环境变量或安装脚本不同而产生不同产物；供应链治理的目标是知道每个输入是谁、从哪里来、做过什么，而不只是让命令今天跑通。

## 构建输入

```text
源码 revision + lockfile + registry/mirror
      + toolchain + compiler flags + generated files + environment
```

锁文件固定解析结果，但仍需校验仓库来源、完整性、签名/证明和平台差异。依赖升级要区分安全补丁、行为变化和破坏性版本，记录直接/传递依赖和回滚组合。

## 风险与门禁

- 安装/构建脚本可能执行代码；在隔离环境和最小权限下运行。
- 依赖混淆、恶意接管、typosquatting 和缓存污染需要私有源策略和名称保护。
- 漏洞扫描有误报/漏报，不能替代版本、调用路径和可利用性分析。
- 生成代码、基础镜像、模型权重和插件也属于供应链输入。

## 验证

新依赖通过许可证、来源、哈希、维护状态、漏洞和最小行为测试；构建两次比较产物或记录不可避免差异。升级后跑 API、性能、安全、兼容和回滚测试，保留上一份可部署 lockfile/镜像。
