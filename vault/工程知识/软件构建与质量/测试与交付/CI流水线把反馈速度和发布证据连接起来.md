# CI 流水线把反馈速度和发布证据连接起来

它解决的是变更在开发机“看起来没问题”，却无法在干净环境重现、审计或安全发布的问题。核心做法是按风险编排静态、单元、集成、性能和发布检查，并保存 revision、环境、命令、退出码和产物；收益是反馈和发布证据连续，代价是运行时间、维护矩阵和 flaky 治理。通过缓存污染、runner 崩溃、依赖不可用和部分发布实验验证。

CI/CD 不是把命令排成 YAML，而是把一次变更从源码身份带到可验证产物、环境和回滚。快反馈检查发现明显错误，慢反馈检查证明集成、性能、安全和发布行为；两者需要按风险分层。

## 一条可信流水线

```text
变更 -> 静态/格式 -> 单元 -> 构建产物
     -> 集成/契约 -> 安全/性能 -> 发布候选
     -> 灰度观测 -> 扩大或回滚
```

每一步保存 revision、环境、依赖、命令、退出码、日志和产物。缓存只加速可重建结果，不能隐藏输入变化；并行任务要避免共享可变目录和相互清理。

## 质量门禁

门禁要对应风险：schema 兼容、迁移、并发、权限、依赖漏洞、性能回归和 AI 模型/索引质量不能被一个绿色单测代替。失败分类要区分代码、测试、环境、网络、权限和数据问题，重试预算不能覆盖失败事实。

## 验证

故意制造 flaky、依赖不可用、缓存污染、取消、超时、runner 崩溃和部分发布；检查重跑是否可解释、产物是否绑定正确 revision、报告是否能支撑发布结论。周期性在干净环境重建，验证流水线不是依赖开发机状态。
