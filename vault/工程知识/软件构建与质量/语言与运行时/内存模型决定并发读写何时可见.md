# 内存模型决定并发读写何时可见

## 核心拆解

| 维度 | 回答 |
| --- | --- |
| 要解决的问题 | 多线程读写可能因重排、缓存可见性、非原子更新和错误同步产生未定义或业务错误，即使单次测试看似通过。 |
| 本质 | 语言内存模型规定哪些读写有定义，以及锁、原子变量、channel 等同步如何建立 happens-before 关系。 |
| 做法 | 为共享状态写出不变量和线性化点，选择合适同步原语，缩小共享范围，并让取消、资源释放和跨进程/网络边界显式化。 |
| 效果与代价 | 行为在允许的执行重排下仍可推理；代价是同步开销、争用、复杂度，以及不同架构和运行时的验证成本。 |
| 边界 | 原子性不自动保护多字段不变量；语言锁不能跨越数据库事务、进程隔离或网络消息的可见性边界。 |
| 验证 | 使用 race detector、并发压力、随机调度、弱内存架构和故障注入，检查正确性、饥饿、ABA、取消与释放。 |

多线程程序不仅面临“两个线程同时写”的数据竞争，还面临编译器/CPU 重排、缓存可见性、原子性和同步顺序。语言内存模型定义哪些读写组合有定义、哪些同步建立 happens-before；锁、原子变量、channel 和消息传递是建立关系的工具。

单次测试读到“正确值”不能证明并发程序正确：未同步的读写可能在另一架构、优化级别或时序下重排，多个原子字段也可能共同违反业务不变量。先写线性化点和可见性要求，再选择同步原语。

最小并发实验：让一个线程发布多字段状态，另一个线程在不同同步策略下读取；在高并发、随机调度和弱内存架构上检查是否观察到半更新、旧值和 ABA。再用 race detector/TSAN 与业务断言交叉验证。

## 常见误区

- volatile/atomic 可能提供可见性或单次原子性，不自动保护多个字段组成的不变量。
- 无数据竞争不等于业务顺序正确；检查与使用之间仍可能被插入。
- 只在 x86 测过不等于在弱内存序架构、编译优化或不同运行时成立。
- 数据库事务、进程隔离和网络消息有自己的可见性边界，不能用语言锁跨越。

## 验证

用 race detector、并发压力、随机调度、弱内存架构/模拟和故障注入验证；为共享状态写出不变量和线性化点。性能优化减少锁或使用无锁结构后，同时检查正确性、饥饿、ABA、取消和资源释放。
