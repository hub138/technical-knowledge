# MoE 用稀疏激活换取参数容量和通信复杂度

MoE（Mixture-of-Experts，混合专家）解决的是：**在每 token 的计算预算不变的前提下，把模型参数做得更大。**

它是 DeepSeek、Qwen3、Mixtral 等现代大模型的共同选择。理解它，才能看懂"671B 参数但只激活 37B"这种参数是什么意思，以及为什么这类模型**推理成本不低**。

## 背景：为什么需要 MoE

### Dense 模型的困境

传统（Dense）模型：**每个 token 都要用到全部参数**。

```
100B 参数的模型，处理 1 个 token：
  → 需要读取 100B 个权重
  → 计算量 ∝ 参数量
```

**想让模型更强 → 加参数 → 每个 token 更贵。** 这条曲线很快就撞上成本墙。

### MoE 的思路

**参数还是那么多，但每个 token 只用其中一小部分。**

```
假设：32 个专家，每个 8B 参数 → 总参数 256B
处理 1 个 token：router 选 2 个专家 → 只用 16B 参数

结果：
  总参数 256B（容量大，能装更多知识）
  每 token 激活 16B（计算量和 16B 的 dense 模型差不多）
```

**这就是"稀疏激活"**：参数总量大，但每次前向传播只激活一小部分。

**关键数字**：

| 模型 | 总参数 | 每 token 激活 | 激活比例 |
| --- | --- | --- | --- |
| DeepSeek-V3 | 671B | **37B** | 5.5% |
| Mixtral 8x7B | 47B | 13B | 27% |
| Qwen3-235B | 235B | 22B | 9.4% |

## 从 0 开始：MoE 长什么样

### 结构：把 FFN 换成"多个专家 + 路由器"

Transformer 每一层有两个主要部分：**Attention** 和 **FFN**（前馈网络）。

**MoE 只替换 FFN 部分**：

```
标准层：                          MoE 层：

  Attention                         Attention
     ↓                                 ↓
   FFN（1 个大网络）                Router（选 top-k）
     ↓                                 ↓
   输出                          ┌──────┼──────┐
                              专家1  专家2 ... 专家N
                                 └──────┼──────┘
                                    加权合并
                                        ↓
                                      输出
```

**Attention 通常保持 dense**——因为它是全局相关的，难以稀疏化。

### Router：怎么选专家

```
输入 token 的向量 x
   ↓
router 计算每个专家的分数：logits = W · x
   ↓
取 top-k（通常 k=1 或 2）
   ↓
token 只送给这 k 个专家
```

**Router 本身很小**（就是一个线性层），它是训练出来的——**模型自己学会"什么 token 该给什么专家"**。

### 专家学到了什么

**通常是"模式"而不是"领域"**，这点常被误解：

| 常见期待 | 实际情况 |
| --- | --- |
| 专家 1 = 数学，专家 2 = 代码 | ❌ 通常不是这样 |
| 专家按**语法/token 类型**分化 | ✅ 更常见 |
| 专家是**可解释**的 | ❌ 多数情况下不可解释 |

有研究发现专家会按"标点符号"、"专有名词"、"数字"这类**表层模式**分化，而不是按学科。**不要指望用专家做领域隔离或可解释性。**

## 代价：三个新问题

MoE 不是免费的午餐。**它把计算问题换成了工程问题。**

### 代价 1：显存并没有省

**这是最常见的误解**：

```
"只激活 37B，所以只需要 37B 的显存"  ← 错

实际：所有 671B 的权重都要在显存里
      （因为不知道下一个 token 会用哪个专家）
```

| | Dense 7B | MoE 47B（激活 13B） |
| --- | --- | --- |
| 显存 | ~14 GB | ~94 GB |
| 每 token 计算 | 7B 的量 | 13B 的量 |

**MoE 省的是计算（FLOPs），不是显存。**

**后果**：MoE 模型对显存要求高，部署门槛更高。

### 代价 2：负载均衡（训练时的核心难题）

**问题：router 可能把所有 token 都送给同一个专家。**

```
现象：
  专家 3 收到了 80% 的 token（过载，其余 token 被丢弃）
  专家 17 只收到 0.1%（几乎没训练到）

后果：
  - 过载的专家成为瓶颈，其余 token 被 drop（质量下降）
  - 未使用的专家浪费显存
```

**解法：负载均衡损失（load-balancing loss）**

训练目标里加一项，惩罚"分配不均"，鼓励 token 均匀分散到各专家。

**以及容量因子（capacity factor）**：

```
每个专家最多能接收的 token 数 = capacity_factor × (总token数 / 专家数)

capacity_factor = 1.0  → 严格平均，超出的 token 被丢弃（质量损失）
capacity_factor = 2.0  → 允许 2 倍余量，但通信和显存开销更大
```

**这是质量和效率的权衡。**

### 代价 3：All-to-All 通信（推理时的核心难题）

**问题：专家分布在不同 GPU 上，token 要被送过去再送回来。**

```
GPU 0 的 token 需要专家 5（在 GPU 3 上）
GPU 1 的 token 需要专家 2（在 GPU 0 上）
...

→ 所有 GPU 之间要交换 token（all-to-all 通信）
```

**这个通信开销可能吃掉稀疏计算省下的收益。**

| 部署形态 | 通信开销 | MoE 收益 |
| --- | --- | --- |
| 单卡（所有专家在一张卡） | 无 | ✅ 最大（但受显存限制） |
| 同机多卡（NVLink） | 中 | ✅ 较好 |
| **跨节点（网络）** | **高** | ❌ 可能被吃光 |

**结论**：MoE 在**单卡或同机多卡**上收益明显，**跨节点部署要非常小心**。

## 工程要点

### 训练和推理的差异

| 阶段 | 特点 |
| --- | --- |
| **训练** | batch 大，负载均衡是主要问题，可以用多种并行策略 |
| **推理** | batch 小（尤其是单用户），**通信延迟占比更高**，专家可能空闲 |

**推理时的小 batch 问题**：

```
batch = 1 时，一个 token 只用 2 个专家
  → 其余 254 个专家完全空闲
  → 但它们的权重仍占显存
  → GPU 利用率很低
```

**这是为什么 MoE 模型在**大 batch**下吞吐优势明显，而单请求延迟不一定更好。**

### 优化方向

| 优化 | 做法 |
| --- | --- |
| **专家并行** | 专家分布到不同设备 |
| **共享专家** | 设 1-2 个"总是激活"的专家处理通用模式（DeepSeek 的做法） |
| **分层路由** | 先粗分再细分，减少通信 |
| **量化** | 专家权重量化，降低显存和带宽 |
| **预取** | 提前把可能用到的专家权重加载 |

### 什么时候选 MoE

| 场景 | 建议 |
| --- | --- |
| 显存充足、追求大容量 | ✅ MoE 合适 |
| 显存紧张 | ❌ Dense 更实际 |
| 大 batch 高吞吐服务 | ✅ MoE 优势明显 |
| 单请求低延迟 | ⚠️ 不一定更好 |
| 跨节点部署 | ⚠️ 要仔细评估通信 |

## 常见错误

**错误 1：认为"激活 37B"等于"显存只要 37B"**

**错。** 所有权重都要在显存里。**MoE 省计算，不省显存。**

**错误 2：认为激活参数少 = 延迟低**

FLOPs 少 ≠ 延迟低。**all-to-all 通信、小 batch、负载倾斜都会吞掉收益。**

**错误 3：以为专家是按领域分的**

多数情况下按**表层模式**分化，不可解释。**不要用它做领域隔离。**

**错误 4：忽略负载均衡**

router 坍缩到少数专家 → 过载 + 其余闲置。**必须加均衡损失并监控 expert load。**

**错误 5：跨节点直接上 MoE**

通信开销可能让 MoE 比 Dense 还慢。**先测同机多卡。**

**错误 6：只看总参数判断能力**

"671B"听起来很强，但**实际计算量只有 37B 的水平**。要和同等激活量的 Dense 模型比，而不是和同等总参数的比。

## 验证清单

- 按 token 统计**每个专家的负载**（是否均衡）
- 统计 **overflow/drop 的 token 比例**（影响质量）
- 测量 **all-to-all 通信量**和占比
- 对比 **dense 基线**（固定质量和 batch）
- 在不同 **batch size** 下测吞吐和延迟
- 在小 batch 和大 batch 下的表现**差异很大**，都要测
