# AI 系统工程：把模型能力变成生产能力

AI 系统工程不是把模型接到界面上。它要把概率性的生成能力，放进有数据边界、执行语义、容量约束和质量反馈的软件系统。模型决定能力上限，系统决定这项能力能否稳定地服务真实用户。

## 一套完整的分层

~~~mermaid
flowchart TB
    U[用户目标与业务约束] --> A[应用与 Agent]
    A --> C[上下文、检索与记忆]
    A --> T[工具与外部系统]
    A --> M[模型接口]
    M --> S[推理服务]
    S --> R[GPU、CPU、网络与存储]
    C --> D[文档、索引与业务数据]
    A --> Q[评测、追踪与安全]
    S --> Q
    D --> Q
    Q -->|回归与发布门禁| A
~~~

| 层 | 核心问题 | 不能向下一层转嫁的责任 |
| --- | --- | --- |
| 模型 | 能理解、推理和生成什么 | 模型不能证明外部事实，也不拥有业务权限 |
| 上下文与知识 | 本次决策应该看到什么 | 长上下文不能替代筛选、来源、ACL 和更新 |
| 应用与 Agent | 何时调用模型、检索和工具 | 框架不能替代业务状态、幂等和完成条件 |
| 推理服务 | 如何用有限算力交付 token | GPU 利用率不能替代端到端延迟与质量 SLO |
| 平台 | 如何版本化、发布、回滚和治理 | 部署平台不能自动证明模型升级没有回归 |
| 质量系统 | 如何知道结果更好且风险可控 | 单一 benchmark 不能替代真实任务和线上证据 |

## AI 系统中的 Agent 在哪里

Agent 不是与 AI 系统平行的一门“技能”，而是把模型能力接入真实任务时出现的一组工程问题。按问题归位，才能在设计时同时看见它依赖的上下文、数据、权限和运营约束：

| 子类 | 回答的问题 | Agent 相关内容 |
| --- | --- | --- |
| Agent 与工作流 | 如何让一次运行有状态、边界和停止条件 | 工作流取舍、任务分解、反思、工具调用、多智能体与人工接管 |
| 模型与上下文 | 模型这一步应当看见什么 | 上下文选择、多轮状态、记忆、提示与缓存 |
| 知识与检索 | 如何取得可引用且有权限的事实 | RAG 数据管道、召回、重排、版本和 GraphRAG |
| 质量与运营 | 如何证明运行可靠且持续改进 | 评测集、轨迹、失败分类、成本、提示版本和回归门禁 |
| 安全与治理 | 模型可以提出什么、系统必须拦住什么 | 注入、授权、沙箱、审批、审计和供应链 |

例如，设计一个“读取工单并创建退款草稿”的 Agent，控制流放在“Agent 与工作流”，客户历史如何选择放在“模型与上下文”，政策证据放在“知识与检索”，草稿质量与成本放在“质量与运营”，而订单权限与提交审批必须由“安全与治理”强制执行。任何一个环节单独看起来能跑，都不能代替另一环节的责任。

## 三条不能混为一谈的链路

### 能力链路

预训练形成通用模式和世界知识，后训练塑造任务行为，推理时上下文提供当前信息，RAG 引入可更新证据，工具把输出变成外部动作。它们改变的是不同对象：

| 想改变什么 | 首选机制 |
| --- | --- |
| 临时任务条件、输出格式 | 指令、示例、结构化输出 |
| 经常变化且必须引用的事实 | RAG 或权威数据工具 |
| 稳定重复的行为和领域表达 | 微调或蒸馏，并用评测证明收益 |
| 实时状态和业务动作 | API、数据库或受控工具 |
| 多步骤动态决策 | 工作流中的局部 Agent |

完整关系见 [[工程知识/AI系统/模型与上下文/预训练、后训练、RAG与工具改变不同层次]]。

### 执行链路

模型只提出候选输出或动作。真正的执行需要 schema 校验、授权、超时、幂等、状态持久化、取消和证据采集。参见 [[工程知识/AI系统/Agent与工作流/构建可靠Agent应用]] 与 [[工程知识/AI系统/安全与治理/AI可以做语义决策，系统必须守住事实边界]]。

### 资源链路

请求先做 tokenization 和调度，再经历 prefill、逐 token decode、KV cache 读写和结果流式传输。延迟、吞吐、显存和质量互相制约，参见 [[工程知识/AI系统/推理服务与平台/推理服务的核心矛盾是延迟、吞吐、显存与质量]]。

## 从需求开始，而不是从框架开始

设计前先写清六件事：

1. **任务**：输出是答案、结构化数据、代码、决策建议，还是有副作用的动作？
2. **正确性**：哪些结果可由程序验证，哪些需要人工或语义评价？
3. **知识**：事实来自模型参数、当前上下文、企业数据还是实时系统？
4. **风险**：错误答案、越权动作、数据泄露和不可逆操作分别如何控制？
5. **服务目标**：首 token、完整响应、吞吐、可用性、成本和质量目标是什么？
6. **演进**：模型、prompt、索引、工具和代码变化后，如何比较、灰度和回滚？

没有这些约束，选模型、向量库或 Agent 框架只是把不确定性推迟到上线后。
