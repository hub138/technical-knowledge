# AI 辅助研发必须形成证据闭环

本页采用 [[工程知识/AI系统/安全与治理/执行证据必须独立于AI结论]] 的职责边界：AI 负责理解项目、选择工具、适配测试和解释失败；执行框架负责隔离、真实执行、证据采集、状态一致性和报告门禁。AI 的自然语言结论不能替代命令退出码、进程记录、日志和产物。

面对大型仓库时，代码理解还需要确定性结构/符号索引、自上而下的任务探索和增量失效机制；完整架构见 [[工程知识/AI系统/Agent与工作流/代码智能体需要结构索引、任务探索与运行证据]]。

AI 在研发中的价值不是替代验证，而是缩短“理解范围、生成假设、比较证据、整理结果”的时间。真实项目中最容易失败的方式，是让模型直接修改大量代码，却没有清晰的任务契约和可执行的验证闭环。

## 一套可复用闭环

```text
定义现象 -> 固定环境 -> 收集证据 -> 提出少量假设
       -> 定位最小改点 -> 生成最小变更 -> 编译/测试/复现
       -> 对比基线 -> 人工审查 -> 记录结论与回滚方式
```

### 定义问题

写清楚输入、期望、实际结果、版本、环境、复现概率和不可改变的约束。不要把“修一下”“看起来不对”直接当作任务规格。

### 证据优先

- 行为证据：日志、Trace、测试结果、时间线、输入数据。
- 代码证据：调用链、条件分支、生命周期、锁和错误传播。
- 环境证据：编译选项、依赖版本、配置、数据规模和机器资源。

每个假设都记录“支持证据、反证、下一步实验”。没有实验区分的多个猜测，会造成迭代振荡。

### 变更最小化

AI 输出应优先是结构化的变更计划或小 patch，而不是整文件重写。修改和执行分离：

| 阶段 | 角色 | 输出 | 是否修改磁盘 |
| --- | --- | --- | --- |
| 分析/提议 | AI 或工程师 | 假设、操作、风险、验证方案 | 否 |
| 应用 | 工具或工程师 | 经过审查的 patch | 是 |
| 验证 | 自动化环境 | 编译、测试、复现和指标 | 产生结果，不替代审查 |

### 验证闭环

至少包括：语法/编译、单元或回归测试、原始 Bug 复现、边界用例、性能影响和回滚验证。一次“测试通过”只能证明覆盖到的行为，不等于根因已被证明。

## AI 适配、框架事实门禁

### AI 负责语义决策

给 AI 完整的项目、分支、环境、目标和已有证据，让它动态完成：

- 识别语言、构建系统和版本要求；
- 探测本地工具、缓存、仓库和网络条件；
- 选择 Maven/Gradle/npm/Cargo/Go 等入口与回退方案；
- 寻找上游测试、判断是否适用于当前 revision，并改写 API 或 fixture；
- 判断目标代码是否真正被执行，区分编译、依赖、网络、权限和产品逻辑失败；
- 根据新证据决定重试、切换路径、请求人工确认或结束为环境阻断。

不要提前为每个项目写“测试适用性”规则。框架提供能力目录和受限执行接口，AI 根据真实环境动态生成构建画像、测试入口、依赖准备和回退方案。

### 框架只负责不可委托的事实

框架必须保证：

1. 每个案例使用独立 worktree、运行目录、进程树和资源租约；
2. 旧任务不能清理仍被使用的 Git 元数据、缓存或临时资源；
3. AI 声称执行的命令确实存在，且保存 argv、cwd、退出码、stdout、stderr、信号、超时和产物；
4. 结果绑定正确的项目、commit/revision、attempt、代际和环境指纹；
5. 结构化结果通过 schema 校验，报告只能读取事实投影；
6. 后一次失败不能覆盖已确认的成功事实，主进程死亡由外部 observer 兜底；
7. 重试次数、资源范围、网络出口和凭据访问有上限。

这不是让框架替 AI 判断业务语义，而是防止 AI 的文字解释冒充执行事实。典型反例和推荐事件模型见 [[工程知识/AI系统/安全与治理/执行证据必须独立于AI结论]]。
