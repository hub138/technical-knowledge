# 契约测试的适用边界：消费者驱动与提供者验证

## 要解决的问题

服务间集成（消费者调提供者的 API）的传统验证是端到端测试：拉起全部服务跑真实调用。代价高昂（环境、脆弱、慢）且发现晚（集成问题到联调才暴露）。契约测试要解决的问题是**把“接口是否兼容”从运行时验证前移到构建时验证**：消费者声明它依赖什么（期望的请求与响应），提供者验证自己满足全部消费者的期望，两边各自独立测试，不需要真实联调。这与测试策略从风险选择证据（见 [[工程知识/软件构建：让变化可以理解、验证与交付/测试与交付/测试策略从风险选择证据.md]]）中“集成点是高风险区”的判断衔接，与测试替身按依赖行为分类（见 [[工程知识/软件构建：让变化可以理解、验证与交付/测试与交付/测试替身按依赖行为而非名字分类.md]]）的“替身按契约行为实现”思想同源。

## 机制

**契约的双向结构**。
- 消费者侧：消费者测试里用 mock 提供者，测试运行时录下“消费者发了什么请求、期望什么响应”，这个记录就是契约（Pact 的 consumer-driven contract）。消费者测试通过 = 契约表达了消费者的真实依赖。
- 提供者侧：提供者拉取全部消费者的契约，回放到自己的真实实现上验证（每个期望的响应自己都能给出来）。提供者验证通过 = 兼容性有证据。

**契约与 schema 的区别**。schema（OpenAPI 类）描述接口的形状（有什么端点、什么类型），契约描述实际使用的子集与期望（消费者 A 只用这两个端点、期望这个错误码语义）。schema 是全集文档，契约是使用快照。提供者改 schema 里的未用部分不破坏契约（不影响消费者），改契约覆盖的部分立刻被验证拦住。这个“按实际使用判定破坏性变更”的粒度是契约测试对 schema 审查的精确化。

**验证的编排**。契约的流转需要中心化存储（Pact Broker 类）：消费者 CI 发布契约 → broker 校验（提供者上次验证结果对新契约的兼容矩阵）→ 提供者 CI 拉取验证 → 结果回写 broker → 消费者部署前查“我依赖的提供者版本是否已验证兼容”。这个闭环让“部署时才知道不兼容”变成“合并前就知道”。can-i-deploy 门禁是编排的关键件：部署决策时查兼容矩阵，不兼容就阻止。

**消息契约（异步接口）**。事件驱动的集成（消费者订阅提供者的事件）同样可契约化：契约描述“提供者会发布什么事件结构、消费者期望处理什么”。Pact 的消息契约、CloudEvents 的 schema 校验是同类。异步契约的验证点不同：提供者验证事件的 schema 合法，消费者验证自己能处理契约内的事件。

## 背景与代价

思想背景：消费者驱动契约（consumer-driven contracts）由 Ian Robinson 与 Martin Fowler 圈子在 2006 年前后提出（微服务前夜的 SOA 时代），洞察是“接口的兼容性由消费者的真实需求定义，不是由提供者的文档定义”。Pact（2013+）把它做成工具事实标准，微服务潮（2015+）让“N 个服务两两联调不可维护”的痛点普及化，契约测试进主流 CI。OpenAPI 的 schema 校验与契约测试的边界在 2020s 逐渐清晰：schema 是接口文档与静态校验，契约是使用证据与动态验证。

最精巧的一笔是**“契约把接口的定义权移交给消费者”**。传统集成测试里提供者定义接口、消费者被动适配（提供者改了，消费者跟着炸）。契约测试反转：消费者的真实使用被记录成契约，提供者的任何变更先过“全部消费者契约验证”这一关——破坏性变更在提供者的 CI 里就被拦住，责任从“消费者没跟上”变成“提供者破坏了契约”。这个责任反转配合 can-i-deploy 门禁，让分布式团队的集成问题从“联调现场扯皮”变成“CI 红灯的精确定位”。代价要摆明：契约测试的维护成本随消费者数量线性涨（每个消费者一份契约，提供者要验证全部），契约漂移是常态风险（消费者代码改了契约没重录，契约过期成假证据——契约与代码的同步靠 CI 自动化，手工维护必漂移）；异步契约的表达力受限（事件的时序、重试语义难以静态表达，契约只覆盖结构）；契约验证不能替代全部集成测试（契约管接口兼容，不管业务流程的正确性——跨服务的业务逻辑仍要少量端到端测试兜底，见测试策略（上文链接）的金字塔分层）。契约测试的甜点区是“接口多消费者、变更频繁、团队自治”的微服务群，单体或单消费者的场景它就是纯开销。

## 边界

- **契约覆盖接口兼容，不覆盖业务正确性**。“响应了 200 且结构对”是契约的承诺，“这个业务流程最终状态对”不是。跨服务流程的验证保留少量端到端测试（按风险挑最关键的几条），不要以为契约全绿就万事大吉。
- **契约测试的 ROI 在多消费者场景兑现**。提供者只有一两个消费者时，联调成本低于契约基建成本（broker、双端 CI 编排）。消费者数量（≥3）与变更频率（周级）是上契约测试的参考门槛。
- **契约过期是慢性风险**。消费者重构后契约未重录，broker 里躺着假证据。防漂移的机制：契约与消费者代码同仓库同 CI（改代码必触发重录）、契约的上限版本策略（过期契约自动告警）。
- **异步契约的表达力边界要承认**。事件结构可契约化，但“事件顺序”“重试语义”“恰好一次交付”这类行为契约，静态回放测不出来，要靠队列与流的解耦设计（见 [[工程知识/后端系统：在并发、失败与变化中维持服务/任务与并发/队列和流系统用时间与容量换取解耦.md]]）与生产观测兜底。

## 验证

- **破坏性变更拦截实验**：提供者故意改契约覆盖的字段（删字段、改类型），跑提供者 CI 的契约验证。预期：验证红灯且精确指出哪个消费者受影响。拦截机制的直接证据。
- **can-i-deploy 门禁演练**：模拟消费者部署时提供者尚未验证兼容（矩阵未知），门禁应阻止。预期：部署被拦、提示等待提供者验证。部署安全性的编排证据。
- **契约漂移检测**：消费者代码重构（改了请求逻辑）但故意不重录契约，检查 broker 的契约与代码的实际请求差异。预期：漂移可检测（运行时对比或过期告警）。漂移风险的实证与机制必要性。
