# 依赖升级的风险分层：CVE 补丁要快，功能升级要缓

> **一句话总结**：依赖升级按风险分三档走不同的节奏——安全补丁（CVE 有已知利用方式的）以天为单位跟进，缺陷修复版本以周为单位验证后跟进，功能大版本以季度为单位按计划升级；三档混在一个"升级策略"里，要么被 CVE 拖进被动救火，要么被激进升级引入回归。

## 要解决的问题

依赖升级的决策常被简化成"升不升"：太保守积累 CVE 与兼容债，太激进引入行为变化与回归——**问题出在把不同性质的升级混为一谈**。安全补丁（Jetty 9.4.57 修 CVE-2024-6763、ZooKeeper 3.9.3 修 CVE-2024-51504 这类）的风险是"不升被攻击"，行为变化风险低；功能大版本（Netty 4.1 主线、JDK 升级）的风险是"升了出回归"，不升的风险只是落后。**两者的节奏必须分开**。本库软件构建域"依赖升级的半衰期策略"讲过跟随与锁定的平衡；本篇把风险分层展开：**三档的判据、每档的验证深度、CVE 评分怎么用**——分层后升级从单一策略变成三条流水线，各自按自己的风险控制节奏运转。

## 机制：三档的判据与节奏

**第一档：安全补丁（天级）**。判据：修复的 CVE 有 CVSS 评分、攻击路径与本系统的暴露面匹配（公网可达的 Jetty 漏洞是紧急的，内网不直连的组件漏洞可排期）——**CVE 评分要结合暴露面用**，9.8 分的严重漏洞如果攻击路径需要本地访问，紧急度按实际可达性降档。节奏：补丁版本出来后按天验证（回归面小：版本号只差一位，功能行为基本不变）、按周灰度全量。**验证深度从简**：现有测试套通过 + 关键链路冒烟即可，补丁的性质决定了深测的边际收益低。

**第二档：缺陷修复版本（周级）**。判据：版本里的修复项与本系统踩到的缺陷相关（日志错误被吞、连接泄漏、锁竞争这类），或上游明确的行为修复——节奏：按周排期，验证深度中（相关缺陷的复现用例 + 常规回归）。**"踩过的坑修了"是这一档的主要价值**，不相关的修复项顺带获得，不作为升级的理由。

**第三档：功能升级（季度级）**。判据：主版本/次版本跨越，带新功能、行为变化、废弃 API——节奏：按季度计划，验证深度深（全量回归 + 性能基线对比 + 灰度观察），**升级窗口避开业务高峰**（回滚窗口要留足）。这一档的收益是技术债的预防性偿还（老旧版本的社区支持终止、新特性依赖），**"别人都升了"不是判据**，收益评估按自己的依赖链做。

**三档的流水线独立运转**：CVE 监控自动开单（依赖扫描工具按天对 NVD）、缺陷修复按周批量审、功能升级按季排计划——**混合运转的失败模式是两极**：全按季度等（CVE 挂三个季度）或全按天追（每个新版本都追，回归风险失控）。

## 看完能判断：验证与回滚的配套

**验证深度与档位匹配**：第一档冒烟级（测试套 + 冒烟）、第二档目标级（相关用例 + 回归）、第三档全量级（回归 + 性能基线 + 灰度）——**验证是成本，按风险配成本**：深验的收益是把回归拦在上线前，代价是升级周期拉长；给补丁配全量回归与给大版本只做冒烟是同一种错配的两个方向（前者浪费验证成本，后者把回归放进生产）。

**回滚预案按档位配**：补丁版本回滚就是退版本号（分钟级）；功能大版本回滚要考虑数据格式兼容（新版本写过的新格式旧版本读不了）——**大版本升级前先核数据与协议的向后兼容**，不可逆的升级（schema 变更、协议变更）要把迁移做成前向兼容（新旧版本可共存），回滚窗口从"版本切换"扩展到"数据迁移完成"。

**依赖链的联动核查**：升级 A 组件前核它的依赖 B 是否与当前其他组件冲突（版本对齐矩阵）——**单组件升级踩进依赖冲突是回滚的主因之一**，升级单先跑一遍依赖解析。

## 边界

三条边界防止防线走形。

**CVE 数量不等于风险**：扫描工具报 50 个 CVE，其中攻击路径可达的可能只有 2 个——**按暴露面过滤再定级**，全量 CVE 清单直接进告警会让真告警被淹没（与日志风暴同构：信号被噪声稀释）。

**锁定不等于冻结**：锁定版本（不自动跟随）与终止支持版本（必须迁离）是两个状态——**EOL 组件按第一档处理**（支持终止后新 CVE 无补丁，暴露面只增不减），"我们锁定了所以安全"在 EOL 场景不成立。

**灰度观察期与监控配套**：升级的灰度不是"部署完就结束"——**观察期按缺陷潜伏特征定**（内存泄漏看天、性能劣化看周），观察期的指标基线对比提前录好，没有基线的灰度只能看出崩溃看不出劣化。

## 验证

可复现的验证路径：

1. 分层验证：审计最近半年的升级记录，预期三档的节奏与验证深度符合分层（CVE 平均跟进天数、大版本平均验证周期）——分层策略是否在运转的直接证据；
2. CVE 过滤验证：取当前 CVE 清单按暴露面过滤，预期可达项的占比与告警量同步下降（噪声过滤生效）；
3. 回滚演练：在测试环境对最近一次升级做回滚，预期补丁级分钟内完成、大版本级数据兼容路径按预案走通；
4. 断言锚点：**依赖扫描自动开单在管、三档节奏在升级流程文档里、EOL 组件清单有迁离计划**——三件齐备，依赖升级从单一策略变成三条各按风险节奏运转的流水线。

```text
分层断言 = 三档节奏在记录中可核
过滤断言 = 可达 CVE 才进告警
回滚断言 = 各档回滚路径演练过
```

升级策略的成熟度看分层：CVE 补丁的天级响应、缺陷修复的周级验证、功能升级的季度计划——三条流水线各自运转，安全与稳定就不再互相绑架。
