# cherry-pick 的身份是补丁不是提交：落在哪个分支决定冲突面

> **一句话总结**：cherry-pick 复制的是变更内容，生成的提交与原提交只有 patch-id 相同、历史身份完全独立——冲突面由目标分支的上下文决定，重复 cherry-pick 与批量移植的乱序是两大事故源；治理靠三条纪律：移植登记（原提交与目标分支的映射）、按序移植（依赖链不倒序）、双分支验证（原侧回归 + 目标侧测试）。

## 要解决的问题：复制的到底是什么，冲突从哪来

`git cherry-pick <commit>` 把一个提交的变更应用到当前分支顶端，生成一个新提交——**新提交与原提交的关系**：变更内容（diff）相同（patch-id 一致），但 sha、父提交、所在历史完全不同。这个"身份分裂"是 cherry-pick 所有问题的根源：**两个分支各自有了"同一个修复"的不同提交**，后续的合并、追溯、重复检测都要面对"内容相同但历史无关"的事实。本库"案例十一"（发行分支的移植缺口）给过漏移植的个案；本篇展开 cherry-pick 的操作层：**冲突的来源、重复的检测、批量移植的纪律**。

## 机制：冲突、重复与批量

**冲突的来源：上下文错位**。cherry-pick 用三方合并（原提交的父为 base）应用变更——目标分支上同区域代码已偏离（改过、重构过、或原提交依赖的前置提交没过来）时产生冲突。**三类高频冲突**：前置依赖缺失（原提交依赖更早的提交，单摘它必冲突或编译不过——补齐前置提交再摘）、同区域演进分叉（两边都改了同一函数——人工决策取哪边或融合）、重命名错位（目标分支已重命名文件/符号——git 的 rename 检测失效时手工映射）。**编译检查是冲突判定的延伸**：无冲突不等于移植成功（语义冲突——接口变了调用没改——在编译与测试阶段才暴露），cherry-pick 后必须编译 + 跑目标分支测试。

**重复的检测与处理**。同一修复被摘到多个分支后，反向合并或再次移植会撞上"内容已在"——`git cherry <upstream> <branch>`（按 patch-id 对比两侧提交）、`git log --cherry-pick --left-right A...B` 列出两侧等效提交——**检测的意义**：合并发布分支回主干前核对哪些补丁已等效存在，避免再次引入与冲突放大。**patch-id 的局限**：上下文差异过大时同一逻辑变更的 patch-id 不同（等效性检测漏报），**检测辅助人工，不替代评审**。

**批量移植的纪律**。版本分支的批量移植（一次摘几十个提交）按三条执行：**按序移植**（沿原分支的提交顺序 `git cherry-pick A^..B`——依赖链不倒序，倒序必然冲突成灾）；**分段验证**（每 5-10 个提交编译 + 测试一次，错误定位在段内而不是最后一起爆）；**移植登记**（每个补丁记"原提交 sha → 目标分支 → 目标新 sha"的映射表——漏移植检查与问题回溯都查表，案例十一的移植缺口若有登记表当天就能发现）。

## 看完能判断：选择与回避

**cherry-pick 与 merge 的选择**：整条分支要过来用 merge（保历史）；个别提交要过来用 cherry-pick（轻、准）——**大量提交走 cherry-pick 是 merge 的场景被错用**（登记与冲突成本指数上升）；反过来，分支终将合并时 cherry-pick 会制造"内容重复"的合并冲突，**先定合并策略再选摘取工具**。

**重复修复的收敛**：长期并行的版本分支里，同一 bug 修两遍的风险真实存在——**纪律是"先摘后改"**：修复先在主干完成（评审 + 测试最全），版本分支一律摘取；版本分支上直接修的，必须反向摘回主干（双向登记）——单向纪律的破口就是双份修复的起点。

**冲突高峰的预防**：版本分支存在越久，与主干的分叉越大，移植冲突越多——**分叉控制**（定期把主干同步回版本分支，缩小后续移植的上下文差）与**窗口收窄**（版本分支的存活期与发布节奏对齐，长命分支是移植地狱的成因）。

## 边界

三条边界防止防线走形。

**cherry-pick 的空提交与跳过**：目标分支已含等效变更时 cherry-pick 报"空提交"——`--keep-redundant-commits` 会保留一个无 diff 的提交（污染历史），默认行为是跳过并提示——**看到空提交提示先核等效性**（patch-id 检测 + 人工确认），确认等效才跳过。

**-x 参数是低成本高收益的默认**：`git cherry-pick -x` 在新提交信息里记录原提交 sha——**追溯链的最低成本形态**（不带 -x 的移植在几个月后无法自动追溯来源），团队规范应默认要求。

**连续冲突的停止条件**：批量移植中连续 3 个以上提交冲突——**停止机械继续**（说明两侧分叉超出摘取的适用范围），改走 merge 或重新评估移植清单；硬摘的冲突解决质量随疲劳快速下降，错误修复比不修复更贵。

## 验证

可复现的验证路径：

1. 冲突复现：制造前置依赖缺失的单摘，预期冲突或编译失败，补前置提交后成功——验证"前置检查"纪律；
2. 等效检测验证：同一修复摘到两分支后跑 `git cherry`，预期 patch-id 等效被检出；人为改动上下文后预期漏报（验证检测的边界）；
3. 登记核对演练：按移植登记表抽查 10 个补丁，预期原 sha、目标 sha、分支映射全部可追溯；
4. 断言锚点：**移植登记表是流程必需件（无表不批）、-x 是团队默认、批量移植有分段验证与停止条件**——三件齐备，cherry-pick 从"随手一摘"变成有账可查的移植流程。

```text
身份断言 = 摘取生成的是独立提交
登记断言 = 每次移植有 sha 映射
顺序断言 = 依赖链按序分段验证
```

cherry-pick 的正确心智模型是"打补丁"：补丁落在哪、周围代码什么样，决定了它贴得上贴不上——前置检查、按序移植、登记映射三条纪律配齐，补丁的多分支管理才从冲突修罗场变成可追溯的日常操作。
