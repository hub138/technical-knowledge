# 设计模式解决的是变化点的隔离，不是代码复用

例如，一个订单服务最初直接调用 `WechatPay.pay()`。半年后要接支付宝，再过半年要接企业账期。每加一种支付方式，就要改 `OrderService` 里的那段 `if`，连带重跑所有订单测试。

这就是变化点没有隔离。**模式不是为了让代码"更优雅"，是为了让新增一种支付方式时，已有的订单逻辑一行都不用改。**

## 背景：变化是唯一确定的事

软件里唯一不会变的是"需求会变"。但变化不是均匀的——总有几个地方特别容易变，其他地方常年不动：

| 系统 | 高频变化点 | 常年稳定 |
| --- | --- | --- |
| 电商 | 支付方式、优惠规则、物流商 | 订单状态机、库存扣减语义 |
| 内容平台 | 推荐策略、审核规则 | 内容存储、发布流程 |
| SaaS | 计费模型、集成的第三方 | 用户身份、权限模型 |

**模式的作用就是在这两者之间划一条线**，让变化点被关在线的一侧。

判断该不该用模式，只问一句：**这个地方未来会以什么方式变？** 如果答不上来，就不要用——猜错的变化点比不用模式更糟，因为它引入了额外的抽象层却没换来任何隔离。

## 方案：先识别变化点，再选模式

不要从"我要用策略模式"开始，从"这里会怎么变"开始：

| 如果变化的是… | 用什么隔离 | 代价 |
| --- | --- | --- |
| 一个算法/规则的多种实现 | 策略 + 依赖注入 | 多一层接口，调用方要拿到正确的实现 |
| 对象怎么被创建 | 工厂 / 抽象工厂 | 构造逻辑藏起来，排查时多一跳 |
| 一个事件有哪些后续动作 | 观察者 / 发布订阅 | 执行顺序不再直观，调试要查订阅表 |
| 要给一批操作都加上同样的处理 | 装饰器 / 中间件 | 调用链的层数增加，栈变深 |
| 外部系统的模型和你的不一致 | 适配器 / 防腐层 | 多一层转换代码，要同步维护 |
| 流程骨架固定、步骤可变 | 模板方法 / 钩子 | 父类成为新的耦合点 |
| 行为随状态改变，且状态较多 | 状态机 | 需要显式建模状态和迁移 |
| 操作要支持撤销、排队、重放 | 命令 | 每个动作变成对象，类数量增加 |

## 效果与代价

**收益**

- **开闭原则落地**：新增实现不改已有代码，回归范围从"整个服务"缩到"新加的那一个类"
- **可测试性**：变化点被接口化后，测试可以注入 mock，不必依赖真实的第三方
- **团队并行**：不同人可以在各自的实现上工作，不用抢同一个文件的锁

**代价（真实存在，别忽略）**

- **间接层成本**：每个模式都至少多一层。5 个模式叠在一起，一个请求要走 8 层才能到业务逻辑，新人看代码会崩溃
- **过度设计的风险**：为"以后可能会变"提前抽象，是最大的浪费。**YAGNI 是对的模式使用纪律**——等到第二次真的要加同类变化时再抽象，因为只有到那时你才知道真正的变化轴在哪
- **调试变难**：`策略 + 装饰器 + 观察者` 组合后，一个 bug 的定位路径可能是"找到装饰器→确认策略被谁注入→查观察者回调顺序"

## 从什么地方做

**第一步：列出变化历史，而不是预测未来**

不要问"以后可能怎么变"，去翻 git log：过去一年这个模块改了几次？每次改的是什么？**过去的变化模式是未来最好的预测器。**

**第二步：给变化点命名**

找到高频改动的地方后，明确写出来："支付方式会变"、"审核规则会变"。能命名清楚才说明真的理解了变化轴。

**第三步：只在第二次重复时抽象**

第一次需求：直接写。第二次同类需求：这时候才抽象，因为你已经看到两个具体案例，知道真正的差异点在哪。**第三次：验证抽象是否正确。**

**第四步：用测试锁定边界**

抽象之后，写一组测试只针对接口（"任意支付方式都能完成支付"），另一组针对具体实现。新增实现时只加后一种测试。

## 判断抽象对没对

抽象错了的典型症状：**每次新增实现，都要改接口本身**。

比如 `PaymentStrategy` 加了支付宝后，发现需要传 `channelId`，于是给所有实现都加了参数——这说明接口抽象时漏了概念。**正确的做法是承认当初的抽象不完整，重构它**，而不是继续往里塞参数。

好的抽象应该是：**新增一种实现时，只需新增文件，不改任何已有代码**。
