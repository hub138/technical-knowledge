# 文件监视器数量失控：递归监听与上限裁剪

给一个目录树加上「文件变化就重新执行」的能力，最直接的做法是递归监听整棵树。这个做法用在含着上千个子目录的工作副本上会立刻暴露代价：进程的句柄数量与常驻内存一起上涨，涨到某一步开始出现创建失败，而失败位置在树的深处，报错信息看不出是哪一层。

## 要解决的问题

递归监听的实际成本由目录数量决定。内核提供的监听接口只登记单个路径，递归语义由用户态库模拟：遍历这棵树，为每个子目录各建一个监听，并在新目录出现时补建。监视器数量因此等于子目录数量，而非等于「监听了几个根目录」。

三个后果连着来：

- 句柄与原生内存随目录数量线性增长，工作副本越大开销越高。
- 内核侧有按用户计算的上限，越过之后创建失败并返回 `ENOSPC`，失败点取决于遍历顺序。
- 目录数量是外部输入：依赖目录、构建产物、缓存目录都会重新出现，启动时正常不代表运行中一直正常。

## 机制：递归怎么被模拟出来

```mermaid
flowchart TD
  A[请求监听根目录] --> B[遍历子树]
  B --> C{命中条目是子目录}
  C -->|是| D[为该目录登记监听]
  D --> E[监听目录创建事件]
  E --> B
  C -->|否| F[跳过]
```

内核接口每次只登记一个路径。用户态库要做递归，只能自己走一遍目录树逐个登记；为了覆盖运行期间新建的目录，还要在收到「目录创建」事件时对新目录再登记一次。这条补建链路正是数量失控的入口：依赖安装一次，目录数量可以翻几倍。

裁剪参数的价值在此处体现。一个「最多监听多少个目录」的上限参数，只有作用在每个目录各判断一次的位置才能封顶数量；若它只在遍历根目录时判断一次，对目录数量的增长毫无约束。

## 边界

- **忽略规则带来数量级下降，而非微调**。把依赖目录、构建产物、版本控制目录排除，常见的仓库能从数千个目录降到数十个。忽略掉的目录内部变化不可见，需要与定期全量扫描配合，否则会漏掉变更。
- **创建失败只在创建时刻出现一次**。之后的运行不再报错，表现为「某些目录的变化一直没有被响应」，与「本来就没有变化」无法区分，这是它难查的原因。
- **监听器创建与释放不配对会累积**。配置变更后重建监听时若不先释放旧的，数量会跨重启累加。
- **内核上限对定期扫描没有约束力**。改成扫描目录时间戳就不占用监听名额，代价是变化发现延迟与全量扫描开销。

## 验证

在公开环境造一棵含数千个空目录的树，用递归监听跑起来，再对照句柄计数：

```bash
mkdir -p "$HOME/treedemo" && for i in $(seq 1 3000); do mkdir -p "$HOME/treedemo/d$i"; done
node -e 'require("fs").watch(process.env.HOME+"/treedemo",{recursive:true},()=>{});setInterval(()=>{const c={};for(const x of process.getActiveResourcesInfo())c[x]=(c[x]||0)+1;console.log(c)},1000)'
```

**预期**是 `FSWatcher` 计数随目录数量同向上涨。加上忽略规则或改成非递归监听后重跑，计数应当回到个位数。**对不上**说明监听数量并不由目录数量决定，需要检查实现是否做了合并处理。

## 影响与代价

- 目录数量成为启动开销的隐含上限，工作副本一大就触发。
- 忽略规则换来数量级下降，代价是这些目录内的变化需要靠定期扫描补上。
- 上限参数只有放在正确的判断位置才有意义，放错位置等于没有。
- 启动自检应当核对「实际登记的监听数量」与「预期数量」，两者差距过大时立刻告警。

## 从什么地方做

1. **先数**：打印当前登记的监听数量与子目录数量，确认两者处于同一个数量级。
2. **再加忽略**：把依赖目录、构建产物、缓存目录加入忽略，重新计数。
3. **再改策略**：目录数量依然很大时改用「根目录监听加定期全量扫描」的混合策略。
4. **补上自检**：启动时核对监听数量，超出阈值就记录并告警，让下一次失控在启动阶段被看见。
