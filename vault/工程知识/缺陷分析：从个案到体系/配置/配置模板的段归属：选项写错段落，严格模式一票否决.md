# 配置模板的段归属：选项写错段落，严格模式一票否决

> **一句话总结**：带段结构的配置文件里，每个选项有它的合法归属段；官方模板把选项写进错误的段，用户启用模板即触发严格加载的"未知选项"报错——模板与解析器的世界观没对齐，启用路径从未被走过。

## 要解决的问题

成熟软件常自带配置模板：一份写满推荐参数与注释的配置文件，用户复制、去掉 `.default` 后缀即可启用。模板的价值在"开箱即优"，它的风险在**模板与解析器是两个交付物**——模板的维护者与解析器的维护者可能不是同一批人，两者的世界观（哪个选项属于哪个配置段、哪个拼写合法）一旦失配，启用模板的路径就藏着地雷。

Apache BookKeeper 的一个真实病例（上游 commit 3b06ecf9，已在本环境真实复现）：官方自带的 RocksDB 配置模板里，日志滚动时间选项被写进 `[CFOptions "default"]` 段，而它按 RocksDB 的配置规范属于 `[DBOptions]` 段。RocksDB 以严格模式加载配置——出现归属错误的未知选项直接抛错中止。用户按文档启用这个模板，bookie 启动即失败，账本读写不可用；修复除了把选项挪回正确的段，还顺带补上了模板里缺失的校验和配置项、调低了入口定位模板的后台任务并发数。

这个病例的结构值得单独成篇：**"从未被走过的路径"是模板类资产的共性风险**。模板存在仓库里，静态检查（编译、单测）不会加载它，只有"用户启用模板"这条路径会走到解析器——而维护者自己几乎不用这条路径。于是模板里的错误在仓库里安然存活，直到第一个按文档操作的用户踩中。

## 机制：模板、解析器与严格模式的三角

三个组件各有一条纪律，地雷在纪律的交点上。

**模板的纪律**：模板是可执行的配置样本，它的正确性标准与代码相同——"能被对应版本的解析器成功加载"。模板注释里"推荐参数"的语义再好，加载都过不了就是废纸。模板的问题在于它没有编译期，语法与归属错误全部潜伏到运行时。

**解析器的纪律**：严格模式（strict parsing）把未知选项、非法值一律判为错误——这是配置系统的正确取向，静默忽略未知选项正是"配置不生效"类缺陷的温床（拼写错误的参数悄悄失效，见本库配置域的多篇病例）。解析器没错，错的是模板没跟上它的世界观。

**用户的预期**：官方模板自带"官方背书"，用户按 README 启用，预期是"要么成功要么告诉我哪个参数不行"——严格模式的报错本身是好的，问题在报错的时机：**用户执行了官方推荐的操作，得到的是服务不可用**。错误预防的第一课是让推荐路径默认正确。

三角的失配点在"模板没有加载测试"。解析器有测试、功能有测试，模板作为第三个交付物游离在测试体系外——它本质是**一份从未被执行过的配置**。

## 模板类资产的防线

推广开去，一切"随代码分发的样本类资产"（配置模板、示例配置、脚手架工程、Helm values 样例、Terraform example）共享同一套防线：

**模板进加载测试**：CI 里对每个配置模板跑真实加载——用当前版本的解析器加载一遍，加载失败即构建失败。这是唯一能把"从未被走过的路径"变成"每次提交都被走过的路径"的手段。模板的加载测试不验证语义最优，只验证**可加载性**，成本极低。

**模板与解析器同源演化**：模板引用的每个选项名、段名，与解析器接受的合法集合做交叉比对（能自动化最好：解析器导出合法选项清单，模板逐项核对）。解析器新增或废弃选项时，模板的变更与代码变更在同一个提交里走——把模板纳入"改解析器必须看模板"的评审纪律。

**启用即验证**：模板启用后的首次启动，输出"从模板加载了哪些段、哪些选项"，用户核对启用是否真正生效——顺带覆盖"模板启用开关写错导致模板根本没被读"的相邻故障。

**弃用选项显式迁移**：解析器升级废弃旧选项时，提供迁移映射并在加载时报"选项 X 已迁移为 Y"，让存量模板的启用失败变成可行动的修复指引。

## 边界

三条边界防止防线走形。

**严格模式的报错要可行动**：报错信息指明"哪个段、哪个选项、合法归属是哪里"，裸抛"unknown option"让用户自己翻文档，是严格模式的体验负债。防线在建报错质量，不是放弃严格。

**模板不必覆盖所有版本**：长期维护的软件常有多版本并行的部署，模板按当前稳定版本维护、标注适用版本即可，跨版本兼容属于发布工程的范围，不要求一个模板吃遍所有解析器版本。

**宽松模式仍有其位**：允许降级到宽松模式的场景（开发环境快速试验）是合理的，纪律是**生产启用路径默认严格**，宽松是显式选择而不是默认。

## 验证

可复现的验证路径：

1. 复现失败：按官方文档启用配置模板（去掉 `.default` 后缀），启动服务——严格模式抛未知选项错误，服务不可用，捕获一次即为缺陷证据；
2. 修复后重跑：同一操作下服务正常启动，启动日志显示模板各段的加载结果，选项全部落在合法归属段；
3. 防线固化：把"全部配置模板进 CI 加载测试"加进构建流程，任何模板与解析器世界观失配的提交在 CI 即红；
4. 断言锚点：**仓库里的每个配置模板，在每次构建时被当前解析器成功加载**。

```text
操作 = 启用官方模板（按 README）
启动断言 = 服务正常启动，模板各段加载成功
CI 断言 = 模板加载失败 → 构建失败
```

"模板必须能被加载"写进 CI 之后，模板从一份静态文档升级成被持续验证的资产——这是模板类资产与代码同权的唯一途径。这笔防线的账很清楚：CI 里多几秒的加载测试，换掉的是"第一个按文档操作的用户用服务不可用来发现模板错误"的口碑代价，模板的价值承诺（开箱即优）从此有了机器背书。
