# 默认值不进账本：建库参数要写进数据目录，读库时对账

> **一句话总结**：建库时的参数决定数据文件的物理形态，参数值若只存在于启动配置里，数据目录就说不清自己是怎么建的——读方按假设解释文件，假设错了要么打不开（幸运），要么读错（静默）。

## 要解决的问题

存储引擎的数据文件是参数的函数：建库时的块大小、压缩方式、格式版本决定了文件的物理布局。这些参数有两个可能的住址——**启动配置里**（每次启动都读）与**数据目录里**（建库时写入，与数据同生命周期）。参数住错地址的后果，在"配置一直不变"时不显现，在"换环境、换版本、迁移数据"时爆发。Apache BookKeeper 的真实病例（上游 commit 697ff570，已在本环境真实复现）：bookie 建索引库时若未显式配置表格式，按引擎内置默认值建库；代码默认值长期停留在旧表格式（2），与引擎当前推荐（5）脱节——新建索引按旧格式写入，索引体积更大、读取开销更高，而数据目录里**没有任何记录说明这个库是用什么格式建的**。修复把代码与配置模板的默认值统一到 5；相邻病例（b00d2e0c，同批复现）更尖锐：格式版本没写进库属性，数据迁移到低版本引擎的环境直接打不开。

库内配置域"案例三十八：没有写下来的版本"已从迁移债的角度解剖过这对病例，本篇把方法面抽出来单独成篇：**建库参数应该写进数据目录，读库时对账**。这是存储系统的一条通用设计纪律——数据文件自带"我是怎么建的"说明书，读方不猜。

## 机制：参数的两个住址与三种失效

建库参数住启动配置还是数据目录，决定了失效形态：

**住启动配置、数据目录无记录**：参数只在启动时被读一次，之后与数据文件再无关联。失效有三种形态。**漂移**：代码默认值与推荐值脱节（本病例——表格式 2 长期不升级，新建库持续按旧格式产出更大的索引）。**迁移断裂**：数据挪到参数假设不同的环境，读方按自己的假设解释文件——假设影响"能否打开"时报错（幸运形态），影响"内容解释"时静默读错（危险形态，见本库正确性域静默失真一文）。**诊断失明**：排障时检查配置文件，看到的值可能与建库时的值无关（后来改过配置），"这个库建的时候是什么参数"无从查起。

**住数据目录（元数据随库）**：建库时把关键参数写入库属性（引擎支持的 Properties、文件头），读库时先读属性再解释文件。失效形态收敛为一种：属性与解释不匹配时报明确错误——迁移断裂从静默变成显式。

值得注意的边界：**已有库按自身格式读，不需要迁移**——RocksDB 按库内格式版本读取既有文件，本病例的修复只影响新建库。参数写进数据目录的价值在新库建立的那一刻起累积：每个库自描述，漂移与迁移问题在结构上消失。

## 为什么默认值漂移值得单独防

"默认值旧了点"听起来是小事，它的真实成本在复利：

**默认值是最大规模的配置**：显式配置只覆盖认真调优的部署，**默认部署全走默认值**——默认值落后一档，影响面是全部未调优实例。697ff570 的修复对象就是默认值：改一行代码，全部新部署受益。

**漂移不可见**：索引大 30%、读取慢 10%，在正常波动里看不出来，没有任何告警会响——性能债以复利累积，直到容量规划时被发现，而那时没人把它与三年前的默认值联系。

**修复涉及存量与增量的不对称**：默认值修复只管新建库，存量库要显式配置或重建才能吃到改进——"默认值改了但旧库没变"的混合状态会长期存在，容量评估要按两种形态分别算。

## 修复与防线

上游修复统一了默认值；防线体系让"参数与数据"的绑定成为结构性质：

**建库参数写入库属性**：格式版本、块大小、压缩方式在建库时写进引擎属性或文件头——引擎已支持（RocksDB 的 Properties）就用引擎的，不支持就在数据目录放自描述文件。关键判据：**读库所需的一切解释信息，与数据文件同生共死**。

**读库时对账**：读方按属性里的参数解释文件，参数超出支持范围时报明确错误（"库格式 7，本版本最高支持 5"）——把迁移断裂从静默读错降级为显式报错。

**默认值审计**：代码默认值与配置模板、文档三处对齐的例行审计（本库配置域静态防线的具体应用），默认值变更要在发布说明里写明影响（新建库行为变化、存量库不受影响）。

**新库验收核对**：部署验收时查询新库的实际参数（引擎 API 可查），与预期核对——把"默认值到底是什么"从猜变成读。

## 边界

三条边界防止防线走形。

**不是所有参数都值得入库**：影响物理布局的（格式、压缩、块大小）必须自描述；纯运行时参数（memtable 大小、后台线程数）每次启动可变，写进数据目录反而制造假约束。判据：这个参数改变"文件怎么解释"吗？

**自描述不能替代显式配置**：写进数据目录的是"建库时的事实"，调优意图仍要显式配置——事实记录与意图表达是两个通道，混用会让"改配置重建库"与"原样打开"的语义搅在一起。

**属性写入要原子**：建库事务里写属性，崩溃中断的半建库不能带着部分属性被当完整库打开——这是建库原子性的常规工程，参数自描述不豁免它。

## 验证

可复现的验证路径：

1. 读参数验证：新建库后查询引擎属性中的格式版本，与配置预期核对；
2. 迁移断言：把库目录复制到参数假设不同的环境（低版本引擎或显式不同配置），修复后应得到明确报错，而非打不开或读错；
3. 默认值断言：不配置任何参数建库，实际格式等于代码与模板统一的默认值；
4. 断言锚点：**数据目录的自描述信息足以让读方在不读启动配置的情况下正确解释文件**；新库建库属性与启动配置不一致时报错。

```text
建库断言 = 新库属性 == 统一默认值
迁移断言 = 假设不符 → 明确报错（无静默）
自描述断言 = 只读数据目录即可获得解释参数
```

"只读数据目录就能正确解释"是存储自描述的终局判据——迁移、扩容、跨版本运维都以它为前提。
