# 缺陷分析的本质——期望与现实的一次偏差

缺陷的本质，是期望与现实之间的一次偏差。这个定义能解释一类反直觉的现象：崩溃的缺陷吵闹但诚实，静默算错的缺陷安静但致命——后者从出现到被发现之间隔着的每一天，都是脏数据。下面两个真实病例正好代表这两种形态。

第一个：BookKeeper 的 Bookie 节点，垃圾回收线程遇到内存分配错误时**整体停止且不留日志**。已删除数据占用的磁盘空间从此不再回收，节点最终磁盘写满、写入失败（上游 commit 35b8f137，P0，稳定类）。第二个：Spark SQL 在 Union 两侧出现同名列别名时，**不报任何错，静默返回错误结果**（上游 commit d04c7884，P0，正确性类）。

把这两个放在一起看，会发现一个反直觉的事实：**更危险的是第二个**。第一个至少会把问题喊出来——服务中止了，监控响了，人被叫起来了。第二个什么都不说，答案就是错的，你的报表、你的决策、你下游的每一行数据都在悄悄跟着错。分析缺陷的第一课就在这里：崩溃的缺陷吵闹但诚实，静默的缺陷安静但致命。

## 要解决的问题

同一套排查手法，用在崩溃类缺陷上很顺手，遇上静默错算就常常扑空：前者留下现场可以看，后者什么都不说，等到被发现时数据已经错了很久。本篇要解决的问题是：给缺陷一个可以动手的判定框架，把期望、现实与触发条件三样分开，让"错在哪里"从各执一词变成可以逐项核对。

## 缺陷的本质

一个缺陷由三样东西组成，三样必须分开看：

- **期望**：这段代码被约定要做的事。垃圾回收周期应该持续运行；Union 应该逐行拼接两侧数据。
- **现实**：它在特定条件下实际做的事。GC 线程遇到内存分配错误直接终止；别名冲突时返回了拼接错误的行。
- **条件**：让期望与现实分道扬镳的那个触发点。一次内存分配失败；一个特定的列命名组合。

三者缺一不可。没有条件，缺陷只是潜在的风险；没有期望，你连"错"都无从定义。分析缺陷的全部工作，就是把这三样从一团模糊的故障现象里分离出来。

值得再追问一层：**期望从哪来**。它有三种可靠的来源——接口与配置的成文约定（API 文档、参数语义）、领域的规范定义（SQL 的 Union 语义、文件格式规范）、以及已经被测试固化的既有行为。直觉和"以前一直是这样"不算来源：没有成文的期望，偏差就无从判定，争论只会变成各说各话。这也是为什么约定意识是缺陷分析的起点——[[工程知识/后端系统：在并发、失败与变化中维持服务/服务设计/API接口约定定义输入输出和演进边界]]讲的正是这件事在服务层的形态。

这套分析方法与医生看诊是同一件事。病人说"发烧"——那是症状，不是病因；退烧药是对症治疗，不是对因治疗。工程师最容易犯的错就是把症状当病因：磁盘满了去清磁盘，查不出来为什么满，清完还满。发烧要查感染灶，磁盘写满要查为什么已删除数据不被回收——找到"垃圾回收线程已经终止"这一层，才算碰到病因。例如上面那条 Bookie 缺陷，用三分离分开就是：症状是磁盘写满，病因是回收线程终止且不留日志，治疗方案是补上异常兜底。

## 缺陷的八个家族

对 BookKeeper、Spark 两个上游项目累计 1900 余条提交的扫描中，完成分类并复现的 28 条，全部落在八个家族里：

| 家族 | 典型形态 | 条数 |
|---|---|---|
| 配置与可操作性 | 参数不生效、错误日志误导 | 7 |
| 安全 | 认证绕过、依赖带漏洞 | 5 |
| 正确性 | 静默算错、边界算漏 | 3 |
| 稳定性 | 线程终止、服务卡死 | 3 |
| 并发 | 时序竞态、共享状态失守 | 3 |
| 资源与容量 | 连接泄漏、磁盘占满 | 3 |
| 兼容与升级 | 依赖滞后、版本错配 | 3 |
| 性能 | 重复劳动、临界区过宽 | 1 |

八个家族的"发生—暴露"模式完全不同。稳定类和资源类**会喊**——崩溃、写满、超时，监控能兜住一大半。正确类**不喊**——它需要你有一个独立于被测代码的参照答案才抓得住。安全类**等别人喊**——被利用了你才知道。并发类**看运气喊**——同样的负载十次里错一次，日志里什么都没有。性能类**慢慢喊**——量级变化要跨过阈值才变成故障。配置类最隐蔽：它甚至不是代码错了，是代码的行为和读配置的人的理解不一致。

分清家族的意义在于选择武器：稳定类靠监控兜底，正确类靠对照测试，安全类靠扫描器和最小权限，配置类靠文档和启动自检。用错武器，投入再多也抓不住那一类。分类的收益也在这里：每一类的暴露方式和修复代价不同，决定了它值得哪种投入——崩溃类买监控，静默类买参照答案，这笔账在动手修任何一条缺陷之前就该算清。

把三个案例涉及的基础概念先挂上钩：后台线程为什么会被一次内存分配失败中断，见 [[工程知识/性能工程：从用户等待到资源瓶颈/操作系统与运行时/垃圾回收与内存分配决定延迟尾部]]；"静默算错"为什么只有独立参照才抓得住，见 [[工程知识/软件构建：让变化可以理解、验证与交付/架构与代码/静态分析发现结构问题但不能证明行为正确]]——结构检查证明不了行为正确，行为正确需要的是参照答案。

验证的锚点：病因层结论要与三分离对账——预写期望、现实与触发条件三样齐备才算到位，缺任一样，与预期对不上，分析还停在现象层。

## 边界与误区

- **不要把复现当根因**。复现脚本造出了故障，只说明"这个条件能触发"，不说明这就是唯一的触发路径。
- **不要认为修了就是修好了**。补丁合入只完成一半，没有回归验证的修复随时可能被下一次变更冲掉。
- **不要只盯崩溃**。上面两个案例里，静默算错的那条对业务的实际伤害更长——它从出现到被发现之间隔着的每一天，都是脏数据。
- **分类是手段不是目的**。一条缺陷同时带并发和稳定性两面时，按"暴露方式"归类——决定你用什么武器的是暴露方式。

## 验证

1. 三分离核验：对一条真实故障，分别写出期望（成文约定、领域规范或已固化的测试行为）、现实与触发条件三样，缺任何一样都说明分析还没到病因层。
2. 归属核对：按暴露方式把这条缺陷归入八个家族，核对所选武器与该类暴露方式匹配（稳定类靠监控、正确类靠独立参照答案）；归类依据写成记录。
3. 参照答案检查：对静默类缺陷，确认存在一个独立于被测代码的参照来源，用它比对结果；没有参照时先建设参照再谈修复。
4. 上游对照：到 BookKeeper 的提交 35b8f137 与 Spark 的提交 d04c7884 里核对两条病例的现象与根因，确认与正文的三分离结果一致。
5. 断言锚点：三样齐备，家族归属有依据，静默类缺陷存在独立参照，修复后回归验证通过。
