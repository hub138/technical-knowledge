# 案例三十七：锁自己变成了瓶颈——争用背后的临界区错配

> **一句话总结**：一把锁保护的东西远多于它真正需要保护的东西时，所有本可以并行的操作都会被串行化——争用不是并发度太高造成的，而是临界区画错了。

性能问题被归因为"锁争用"时，常见的反应是换更细的锁、用无锁结构、或者干脆去掉锁。这些方案都可能无效，因为争用本身通常是**症状**。Apache BookKeeper 的这组病例（已在本环境真实复现）说明了真正的病根在哪里——以及为什么它常被误诊。

## 案例背景

**项目**：Apache BookKeeper——为日志条目提供低延迟、可持久化写入的分布式日志存储服务，Apache Pulsar 的存储层。

`LedgerHandle` 是客户端写入账本的入口，它持有若干与账本状态相关的字段：当前 ensemble、最后确认的条目 ID、在途写集合。这些字段的读写被一把 `metadataLock` 保护。

`metadataLock` 的命名已经说明了它的设计意图——保护"元数据"。问题在于，随着功能叠加，实际被这把锁包起来的操作远不止元数据读写。

## 问题：一把锁保护了三种不同性质的东西

上游报告的现象（[上游 commit 84ca507b](https://github.com/apache/bookkeeper/commit/84ca507b8285)，P2）是 `metadataLock` 争用严重，影响写入吞吐。

争用的结构原因可以从这把锁实际保护的三类操作中看出来：

**第一类：真正的共享状态。** ensemble 变更、最后确认条目推进。这些必须互斥，没有争议。

**第二类：只读查询。** 获取当前状态用于判断。它们不修改任何东西，本可以并发。

**第三类：耗时操作。** 某些在锁内触发的动作会涉及等待或 I/O——它们既不修改状态，又会把锁持有一段不可预测的时间。

三类操作共享同一把锁时，实际效果是：**第三类的耗时决定了第一类的延迟**。一个需要纳秒级互斥的状态更新，要排在一个可能耗时毫秒的操作后面。而第二类操作本不该参与排队，却也在排。

这就是"临界区错配"：锁的范围（它实际圈住什么）与它需要保护的范围（真正需要互斥的东西）不一致，且前者远大于后者。

## 为什么是问题：它的表现会骗人

**表现为 CPU 不高但吞吐上不去。** 线程大部分时间在等锁，不在执行。看 CPU 会得出"资源没用满"的结论，看吞吐会得出"系统有瓶颈"，两者合起来很容易导向错误的优化方向——加资源。

**表现为延迟的长尾，而不是均匀的变慢。** 平均延迟可能正常，P99 却极差。因为是否要等待取决于运气：运气好时锁空闲，直接通过；运气差时撞上那个耗时操作，等待时间不可预测。长尾是争用的典型指纹。

**它会随并发度上升而非线性恶化。** 并发度翻倍，争用概率不止翻倍——等待队列变长，每个等待者持有锁的时间占比增加，反过来又加剧争用。这解释了为什么压测时"加到某个并发度就上不去了"。

**它会被误诊为"锁太重"。** 看到争用就换 `StampedLock`、换读写锁、换无锁队列，都是在优化"锁的实现"，而真正的改善来自缩小临界区。优化错了对象，性能不会有本质变化——甚至可能因为换用更复杂的锁而引入新的正确性风险。

## 本质：互斥的代价由临界区内最慢的操作决定

去掉 BookKeeper 的所有专有名词，骨架是：

> **一把锁的吞吐上限由"持有它的最长时间"决定，而不是由"需要互斥的操作有多快"决定；因此任何被放进临界区但本不需要互斥的操作，都会直接拉低这把锁的吞吐。**

这句话里有两个推论值得单独拎出来。

**推论一：临界区的成本是最坏情况，不是平均情况。** 即使耗时操作只占 1% 的调用，只要它存在，所有等待者都可能撞上它。长尾正来自这里——平均延迟被那 1% 拉高，而 P99 完全由它决定。

**推论二：只读操作不该与写操作互斥（在多数情况下）。** 如果锁保护的状态可以用读写锁分离，读之间不互斥，那么占绝大多数的读操作就不再参与排队。这是缩小临界区最直接的收益，也是本例这类问题的常见解法。

更深一层，这个问题是**关注点混合**的表现。一把锁在最初设计时有明确职责；随着功能迭代，新代码倾向于复用已有的锁（因为"反正要加锁，用现成的"），而不是为新的状态引入新锁。锁的职责就这样被逐步扩大，直到它保护的东西不再有共同的互斥理由。

## 比喻：一个柜台办所有业务

政务大厅开了一个窗口，最初只办"户籍证明"。后来陆续加了业务：先是"复印件盖章"（要跑去复印机，几分钟），再后来"材料初审"（要读一堆材料）。新业务都沿用同一个窗口——因为"反正排队，加进来就行"。

现在这个窗口前排着三种人：只是想拿一张证明的（十秒），需要复印盖章的（几分钟），需要初审材料的（更久）。

结果很荒谬：拿证明的人只要十秒，却要排在复印的人后面等几分钟。大厅的吞吐不是由"十秒的业务"决定的，而是由"几分钟的业务"决定的。平均等待时间被拉长，而运气差的人要等更久——这就是长尾。

正确的做法不是"让窗口办得更快"（换个熟练的公务员），也不是"多开几个一模一样的窗口"（加锁的复杂度）。而是**按业务性质分窗口**：十秒的业务走快速通道，耗时的业务走另一条。这样拿证明的人再也不用等复印。

对应到锁：**按互斥理由拆分，而不是按"要不要加锁"聚合**。

## 机制：锁的职责是如何被扩大的

从上游提交改动的文件位置能定位到案发地：

```
bookkeeper-server/src/main/java/org/apache/bookkeeper/client/LedgerHandle.java
```

`metadataLock` 在 `LedgerHandle` 里保护账本元数据。随着 ensemble 变更、写入推进、错误恢复等逻辑的加入，越来越多方法进入了这个锁的保护范围。

这类演化有个典型模式：新功能的作者看到某个字段"需要保护"，于是找到保护它的那把锁，把自己的方法也包进去。每一步单独看都合理——这个字段确实要保护，这把锁确实保护着它。**累积起来，锁保护的范围就超出了任何单一步骤的意图**。

相关的另一条上游修复（[commit 3b06ecf9](https://github.com/apache/bookkeeper/commit/3b06ecf938f1)）处理的是 RocksDB 的 `CFOptions` 默认配置错误。它与本例看似无关，实际共享一个主题：**默认值在演化中被继承了，而继承它的人并不知道它当初为什么是这个值**。锁的范围是代码演化的默认值，配置项的取值也是。两者都是"沿用时没有重新审视前提"的产物。

上游修复的方向是缩小临界区：把不需要互斥的操作移出锁外，把只读路径与写路径分离，让真正需要互斥的部分尽可能短。

## 怎么发现：测量等待，而不是测量锁

**测量锁的等待时间与持有时间分布。** 重点不看平均值，看 P99 与最大值。持有时间的最大值直接决定了最坏等待时间。如果最大持有时间远超中位数，说明临界区里有"少数慢路径"。

**记录等待者的堆栈。** 谁在等、等在哪个锁上、等多久。这能直接定位到"哪个锁是瓶颈"，而不是"系统慢"。

**按调用路径拆分统计。** 同一个锁被十条路径获取，各自的持有时间差别很大。不做拆分就只能看到"这把锁慢"，看不到"是其中一条路径拖垮了它"。

**在压测中观察吞吐随并发度的曲线。** 如果并发度上升到某点后吞吐不再增长甚至下降，而 CPU 未打满，基本可以判定争用。这是最廉价的初筛。

**审查时检查锁的"互斥理由一致性"。** 把锁保护的所有操作列出来，逐个问：这个操作与那个操作为什么必须互斥？答不出共同理由的，就不该在同一把锁里。

## 上游怎么修

修复落在临界区的重新划分：把只读操作从互斥路径上摘出，把耗时操作移出锁外，让锁内只保留真正需要互斥的状态变更。

值得注意的是，修复没有更换锁的实现。`metadataLock` 仍然是一把普通锁——因为在临界区正确划定之后，它不再被频繁争用。**换锁是最后手段，划对范围是第一步**。顺序颠倒会得到一个更复杂、更难维护、性能却没有改善的系统。

## 边界与教训

- **争用是症状，临界区错配才是病。** 优化锁的实现前先确认锁的范围是对的。
- **锁的吞吐由最慢的持有者决定。** 临界区里的少数慢路径决定整体表现。
- **长尾是争用的指纹。** 平均延迟正常而 P99 很差时，优先怀疑锁。
- **CPU 没打满而吞吐上不去**，说明线程在等待，不是在计算。
- **新功能复用已有锁是锁膨胀的主要途径。** 加锁前问：这把锁的互斥理由是什么，我的操作符合吗？
- **考虑读写分离。** 占绝大多数的只读操作不该参与互斥排队。
- **默认值会被继承，前提却不会。** 锁的范围如此，配置项如此——沿用时重新审视它当初为什么是这个值。
