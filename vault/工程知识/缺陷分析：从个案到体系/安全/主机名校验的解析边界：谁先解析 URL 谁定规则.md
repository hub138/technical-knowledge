# 主机名校验的解析边界：谁先解析 URL 谁定规则

> **一句话总结**：校验逻辑拿"解析器给出的主机名"与白名单比对，而解析器对畸形 URL 的宽容解析会给出与浏览器不同的主机名——校验器认定合法的地址，浏览器访问到别处；白名单防住的是解析器的世界观，不是攻击者的。

## 要解决的问题

Web 服务里有一类安全校验长得都一样：外部提交一个 URL（跳转地址、回调地址、资源引用），服务端解析出主机名，与拦截名单或白名单比对，合法才放行。校验逻辑写对了吗？比对逻辑本身几乎总是对的——问题出在更早的一步：**主机名是哪个组件解析出来的，它对畸形输入怎么解释**。

Apache BookKeeper 的两个真实病例（上游 commit add68082 与 cda3c6b6，均已在本环境真实复现）把这条边界演示了两遍：内嵌的 Jetty 版本里，`HttpURI` 对 authority 部分含 userinfo、空格、井号、非法百分号等字符的 URL 采取宽容解析，解析出的"主机名"与浏览器实际请求的主机名可以不一致；指标端点用这个解析结果做主机校验时，非法 authority 地址绕过校验。上游两处修复的动作一致——升级 Jetty，让解析行为与规范及浏览器对齐。

修复改的是依赖版本，教训却属于每一个写校验逻辑的人：**校验器的输入不是"URL 的语义"，是"某个解析器对这段字节的解释"。两者不等价的时候，白名单防住的是解析器，防不住攻击者。**

## 机制：三个解析者，三种世界观

同一个 URL 字符串，在链路上要被至少三个组件各自解析一遍，三者对畸形输入的解释规则并不相同。

**服务端解析器**（Jetty 的 HttpURI、各语言的标准 URL 库）：为容错与兼容而生，对不规范输入倾向"尽量解释出一个结果"——userinfo 里的 @、稀奇位置出现的 #、非法编码的百分号，各有各的取舍规则。它输出的"主机名"是对输入的**一种解释**。

**浏览器**：URL 的最终裁判。用户实际访问哪个主机由浏览器决定，它的解析最贴近 RFC 3986 的规范语义，对畸形输入的处理（拒绝、忽略、规范化）与库实现常有出入。

**攻击者**：主动寻找三个解析者解释不一致的输入。服务端解释成"合法主机 A"、浏览器访问"主机 B"的输入，就是绕过校验的钥匙。历史上大量 SSRF 与开放重定向漏洞的根子都是这个不一致。

校验逻辑处在链条中间：它信任服务端解析器的输出当事实。**解析器与浏览器的世界观差多少，校验的漏洞就有多大。**这就是"谁先解析 URL 谁定规则"的含义——白名单比对的是解析器的世界观，而真正访问资源的是浏览器的世界观。

## 为什么这类缺陷反复出现

三个工程惯性叠出了反复出现的土壤。

**"解析是成熟库的事"的信任惯性**：URL 解析被当成已解决的基础设施问题，校验代码直接取 `uri.getHost()` 不再追问语义。库没有错——它如实执行自己的解析规则；错在**校验器没有声明自己依赖哪套规则**。

**测试输入的善意惯性**：测试用例里的 URL 都是规范的（`https://example.com/path`），畸形输入（userinfo、混合编码、井号错位）几乎不出现在校验逻辑的测试集里。缺陷只在攻击者构造的输入上暴露——而安全缺陷的暴露等的是主动寻找它的人。

**升级滞后的传导惯性**：解析器对畸形输入的解释规则本身在演进（Jetty 对 HttpURI 的多次收紧就是例子）。应用锁死旧版本，校验逻辑继承旧规则，上游已经修好的解析缺陷在发行包里继续活着。依赖升级在这里不只是功能问题，是**校验语义的正确性来源**。

## 修复与防线

上游修复用升级对齐了解析行为；落到防线体系，按纵深排四层。

**解析器先对齐**：校验所依赖的解析库保持更新，让服务端解析与规范语义的偏差最小化。这是地基——后面每层防线都建立在"解析结果可信"的前提上。

**拒绝优于修复（fail-closed）**：对解析结果存疑的输入（authority 含 userinfo、非常规字符、编码混乱）直接拒绝，不尝试"清洗后再校验"。清洗逻辑是新的攻击面——每一条"把脏输入洗成合法输入"的规则，都是攻击者研究的对象。安全校验的第一原则：解释不了的输入不进入系统。

**白名单比对规范化形态**：比对前把主机名做规范处理（小写、去端口歧义、IDNA 处理），比对对象是规范化后的值；对跳转类校验，优先比对完整 URL 前缀而非主机名单独比对，缩小解释空间。

**端到端验证**：校验有效性用真实浏览器（或与浏览器行为一致的客户端）验证——服务端说放行到 A，实际到达的必须是 A。这条防线覆盖所有未知的解析分歧，代价是要有端到端测试设施。

## 边界

三条边界防止防线变形。

**fail-closed 与可用性的权衡要显式做**：拒绝一切畸形输入可能误伤真实用户（某些客户端会生成带 userinfo 的合法地址）。拒绝名单的宽度是业务决策，要按实际流量画像定，并监控拒绝率——突然升高的拒绝率要么是攻击要么是误伤，两种都需要人知道。

**主机名校验防不住全部跳转风险**：开放重定向的完整防御还包括跳转确认页、域名的允许列表按业务最小化。主机校验是一层，没有哪一层单独充分。

**内部服务间调用不豁免**：服务间调用的 URL 同样经过解析器，内网环境不是解析分歧的豁免区——内部跳转被利用做横向移动的案例不少。防线按"所有外部输入"口径部署，不按"外部用户"口径。

## 验证

可复现的验证路径：

1. 构造畸形集：按 RFC 3986 的语法边界造一批畸形 URL（userinfo 混入、井号错位、百分号非法编码、混合大小写主机、端口歧义），每条标注"预期解释"；
2. 双解析对照：同一批输入分别过服务端解析器与参照实现（浏览器或规范测试集），不一致的条目就是校验漏洞候选；
3. 端到端断言：对每条被放行的 URL，实际请求到达的主机必须与白名单一致；
4. 回归固化：畸形集与端到端断言进持续集成，升级依赖时重跑——解析行为的变化当场暴露。

```text
畸形集 = RFC 3986 语法边界输入
断言   = 放行 URL 的实际到达主机 ∈ 白名单
回归   = 依赖升级后重跑双解析对照
```

"双解析对照"是这类校验的通用体检：不需要懂每个库的内部规则，只需要找不一致——不一致的地方就是漏洞。
