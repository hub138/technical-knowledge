# 缺陷分析五步法——从个案到通用模型

判断影响、真实复现、合入回归，三段方法各自成立；只有把它们与前端的收集、后端的归档串成一条完整流水线，才能持续运转，而不是一次性动作。这条流水线就是五步法：收集、判断、复现、修复、回归。它从对 BookKeeper、Spark 两个上游项目 267 条提交的实际处理过程中提炼而来。

整套流程像急诊室的分诊台：病人源源不断地进来（上游提交），分诊护士快速分流（影响判断），重病号进抢救室做检查（真实复现），手术（合入修复），术后复查（回归）。分诊台的价值在于：**资源永远花在需要的人身上，且每个人都被记录、被追踪、有结论**。

## 五步

**第一步：收集。** 盯住上游的提交流，按范围批量拉取。做：按分支和时间窗批量扫，给每条提交建档。不做：凭记忆记"哪些上游最近有问题"——记忆是最先过期的存储。

**第二步：判断。** 对每条提交回答"要不要跟"。做：四种结论（需要合入 / 不涉及生产代码 / 目标已有修复 / 未使用相关功能）逐条落档，结论带证据和置信度。不做：所有提交一视同仁地细看——67 条里通常只有 32 条值得往下走。

**第三步：复现。** 给值得跟的缺陷造证据。做：确定输入、可判定输出、修复前后的对照。不做：用"应该会好"代替"跑过确认"。

**第四步：修复。** 合入补丁。做：读 diff、比对本地差异、标记冲突位置。不做：跳过差异比对直接原样合——编译通过不代表语义成立。

**第五步：回归。** 闭环收口。做：复现脚本复跑通过 + 共享路径测试全绿，两个都写进记录。不做：合入即宣告完成。

## 示例：用五步法重走两个案例

**Bookie 垃圾回收卡死**（P0，稳定类）：收集扫到上游补丁；判断为目标分支受影响、需合入；复现在本环境跑通——GC 线程终止、磁盘不再回收；合入时发现与目标分支的本地修改冲突，走人工改造；回归确认回收恢复、日志补齐。五个环节，一个不少。

**Spark SQL 静默错算**（P0，正确类）：收集扫到补丁；判断为正确性缺陷、需合入；复现构造同名列别名用例——错误结果稳定重现；合入无冲突；回归确认原用例通过。静默缺陷的每一步都依赖"有一个独立参照答案"，这正是它比崩溃类更依赖流程的原因。

## 你会遇到什么

对两个上游项目（BookKeeper、Spark）已扫描的提交做分类，分布是：配置与可操作性 8、安全 6、正确性 4、兼容与升级 4、稳定 3、资源与容量 3、并发 3、性能 1（以最先完成全量处理的 67 条项目为例，其中 32 条需合入、24 条不涉及生产代码、8 条目标已有修复、3 条功能未启用）。两类洞察：

- **配置类最多**。它不是代码写错，是行为和读配置的人的理解不一致——这类缺陷靠文档和启动自检压降，不靠重构。
- **正确类最少但最贵**。它靠对照测试抓，而对照测试要先有一个独立参照——建设参照的成本，就是正确类缺陷的预防成本。

## 边界与误区

- **五步的入口是"一条有据可查的线索"**。案例里的线索来自上游提交；日常开发中，测试失败、评审意见、线上告警、故障复盘同样是合格线索。换掉收集步的来源，后面四步不需要改动。
- **不要把五步做成五张表格**。每一步的价值在证据，不在表单；只有表单没有证据的流程会退化为仪式。
- **不要让任何一步"口头通过"**。每步产出都落档，是这套方法可以审计、可以改进的前提。

让五步真正咬合的是**交接物**：每一步的产出就是下一步的输入——判断步交出"影响结论 + 证据等级"，复现步交出"可运行的脚本 + 前后对照"，合入步交出"diff + 冲突标记"，回归步交出"两绿记录"。交接物缺失的地方就是流程断裂的地方。度量同样有据可依：每一步的积压量、通过率、平均耗时，是这条流水线的健康指标——哪一步积压最深，哪一步就是瓶颈。
