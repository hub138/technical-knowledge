# 案例四十一：确认了却没确认——Pulsar 消息语义的三种失真

> **一句话总结**：消息系统的核心承诺是"确认过的消息不重投、没确认的消息必重投"——Pulsar 的三个病例让这条承诺以三种方式失真：确认被丢弃、负确认只重投半个消息、处理失败还继续写入。三种失真的共同点：**记账与实际发生了偏离，而偏离是静默的。**

## 案例背景

**项目**：Apache Pulsar——分布式消息系统，"确认语义"是它的立身承诺：消费者 ack 一条消息，服务端就把它标记为已处理，不再重投；消费者 negative ack 一条消息，服务端就重投它。这条承诺支撑着"至少一次"的投递保证。 这条承诺一旦失真，消费者面对的难题是双重的：该收的收不到（积压不清零），不该收的反复来（已处理的消息重投）——两边都需要业务侧自己兜底。

三个病例（[上游 commit 9883d92e](https://github.com/apache/pulsar/commit/9883d92ed0edec4bac4556467d55240662a0fd47)、[上游 commit 7ecc31d8](https://github.com/apache/pulsar/commit/7ecc31d818277be333fe0d9b317f6bb98e26520d)、[上游 commit 4f156b56](https://github.com/apache/pulsar/commit/4f156b5661b842c1ff025a9ec6c555a426dd4ec5)，P1，均已真实复现）各破一条规则。

## 三种失真

**失真一：确认被丢弃**。事务场景下逐条确认整批消息时，确认记录被游标**丢弃**——消费者明明 ack 了，服务端却认为没处理，消息反复重投，订阅积压长期不清零。重投的消息再被 ack、再被丢弃——死循环。

确认在账本两侧的失真：

```text
消费侧：ack 已发送，本地记"已处理"
服务侧：游标确认记录被丢弃，账本仍记"未处理"
结果：两侧账本永久不一致 → 反复重投 → 积压不清零
```


**失真二：负确认只重投半个消息**。分块消息（一条大消息拆成多个 chunk 发送）被 negative ack 时，追踪器用整型键映射记录——分块消息的键冲突，**只有最后一个 chunk 被重投**。应用收到一个永远拼不完整的消息，无法重组处理。

**失真三：处理失败还继续写入**。消息负载处理器失败后，broker 仍继续该主题的写入——消息**静默丢失或顺序错乱**，生产端收不到任何失败反馈。

## 案例关联

三种失真并排放着看，不变量浮出来：**记账系统（确认位点、重投记录、失败反馈）与实际状态（消息是否被处理）之间，任何一次静默的偏离都会破坏投递承诺。** 失真一记错了"已处理"，失真二记错了"要重投哪部分"，失真三是"该记账的时候没记"。消息系统的全部复杂性都在这条记账链上——[案例八](./../稳定性/案例八：承诺没有兑现——Pulsar 里六个永不返回的请求.md)的六个病例（回调悬空）发生在请求侧，这三条发生在确认侧，**同一个项目的两端**：请求要有着落，确认也要有着落。

## 上游怎么修

三个修复各自回归承诺：事务确认正常记录并推进删除位点；分块负确认改用完整消息标识追踪、重投完整消息；负载处理器失败后按序立即失败写入，让生产端拿到反馈重试。三条修法共享一个原则：**记账的每一步都要有对应的实际效果，记了就必须发生，没记就必须有人知道。**

## 边界与教训

- **分块/聚合类特性是确认语义的放大器**：一条消息拆成五个 chunk 或五条合成一批，确认的最小单位就从"一条"变成了"一批"——键的设计（整型 vs 完整标识）直接决定会不会张冠李戴。
- **积压不清零不是性能问题，是正确性问题的症状**：看到"确认了还在重投"，第一反应应该查确认记录是否真的落了账，而不是加大消费并行度。
- **静默丢失最晚暴露**：生产端以为发成功了，消费端永远收不到——两端都对得上自己的日志，错的是中间。关键链路上"失败必须有反馈"和"成功必须有落账"同等重要。
