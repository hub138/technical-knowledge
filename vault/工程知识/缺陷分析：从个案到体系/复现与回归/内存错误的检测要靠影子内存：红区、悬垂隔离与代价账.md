# 内存错误的检测要靠影子内存：红区、悬垂隔离与代价账

**C/C++ 程序里的内存错误是沉默的破坏者：越界读一个字节，程序继续跑，值悄悄错了；释放后再访问，多数时候返回的还是旧数据，直到某天堆结构被改坏才当场崩溃**。**等崩溃时因果链早被后来的写入冲掉**。**AddressSanitizer（ASan，编译器插桩的内存错误检查器）这一族工具要解决的问题：让"已经写坏的内存"在写坏的那一行当场报警，检测依据是一张影子内存地图，外加红区与悬垂隔离两道护栏**。

> **要点**：ASan 的检测不靠运气也不靠崩溃，靠一张把每 8 字节真实内存映射成 1 字节影子字节的地图。凡是"不该碰的内存"，要么在地图上标成红区，要么被隔离区扣住不放——访问它就是踩进雷区，当场报警。四种 sanitizer 各管一族错误，射程与代价都写在本篇的账上。

## 它是怎么做到的

**先打个比方：图书馆给每本书办一张借阅卡，卡上写清这 8 字节内存"可借"还是"只读"还是"根本不外借"（每 8 字节真实内存对应 1 字节影子字节，卡上能记"8 字节全部可借"或"头 2 字节可借、其余 6 字节禁区"）**。**程序每次访问内存前，运行时先查卡：卡上写着可借就放行，写着禁区就当场报警**。**这个比喻到「查卡放行、越权（访问了权限范围之外的资源）报警」为止，影子字节的真实编码与隔离区机制以下文为准**。

**1 比 8 的对应关系长什么样，Trail of Bits 博客的这张图画得最直白——上排是进程内存（process memory，低地址往高地址排），下排是影子内存（shadow memory），下排每一个格子描述上排的 8 个字节（granule，粒度组）**：

![进程内存与影子内存的映射：上方每个色块是一个字节的应用内存，下方一行是影子内存，每个影子字节描述应用内存的 8 字节粒度组，四组颜色一一对应](/static/figures/asan-shadow-memory-mapping-trailofbits.png)

*图源：Trail of Bits 博客《Understanding AddressSanitizer》（Dominik Czarnota 与 Dominik Klemba，2024），Figure 6「Logical division of process memory and corresponding shadow memory bytes」，https://blog.trailofbits.com/2024/05/16/understanding-addresssanitizer-better-memory-safety-for-your-code/。*

检测机制分三层，各堵一类漏：

| 层 | 做什么 | 拦下什么 |
| --- | --- | --- |
| 影子内存 | 每 8 字节真实内存映射 1 字节影子字节，标记"这 8 字节里前几个可访问" | 编译期无法定位、运行时才发生的越界访问 |
| 红区（redzone） | 在每块分配的堆内存四周、全局变量之间、栈帧里各变量之间填入带毒标记的内存 | 溢出 1 字节的写、差一位的越界读 |
| 隔离区（quarantine） | free 掉的内存扣在隔离区里不立刻归还系统，影子字节保持"已释放"标记 | use-after-free（悬垂指针读写）、双重释放 |

**影子字节里到底写了什么值，微软 MSVC（微软 Visual C++ 编译器）官方文档给出完整图例（shadow byte legend，一个影子字节代表 8 个应用字节）：00 表示 8 字节全部可访问，fa 是堆红区，fd 是已释放的堆内存，f1/f2/f3 是栈变量的左/中/右红区——报警信息里附带这份图例，读懂它就能直接判出踩的是哪类禁区**：

![AddressSanitizer 影子字节图例：00 可寻址、fa 堆左侧红区、fd 已释放堆区域、f1/f2/f3 栈左中右红区、f5 返回后栈、f8 作用域外栈、f9 全局红区等全部编码值](/static/figures/asan-shadow-byte-legend-mslearn.png)

*图源：Microsoft Learn 官方文档《AddressSanitizer 影子字节》，CC BY 4.0，https://learn.microsoft.com/zh-cn/cpp/sanitizers/asan-shadow-bytes。*

**UAF（Use-After-Free，内存释放后继续使用的错误）为什么能被抓：free 之后内存进隔离区，影子标记保持"已释放"，此后任何通过悬垂指针的读写都会查到这张带毒的卡**。**双重释放同理，第二次 free 会发现内存已在隔离区**。**MSan 比这更进一步，把所有未初始化内存的影子标成"未定义"，读到未定义值就报警——代价是 MSan 必须给全部内存访问插桩（没有 ASan 那样的按需查卡优化空间），通常要重编所有依赖**。

**ASan 论文（USENIX ATC 2012）给出的账单：平均约 2 倍减速、内存占用约 3 倍——换来的是溢出、UAF、双重释放这类"平时沉默、崩溃时才暴露"的错误全部变成带调用栈的即时报警**。

## 为什么这些错误值得专门建一套检测体系

**因为它们是 C/C++ 代码库里占比最高的一族安全缺陷**。**微软安全响应中心对 2006 到 2018 年间修复的安全缺陷统计，约 70% 的 CVE（Common Vulnerabilities and Exposures，公开披露的安全漏洞编号）是内存安全错误**（来源：微软 BlueHat IL 2019 演讲《Proving that software is free of vulnerabilities》）。

**Chromium 项目统计同期 912 个高危安全缺陷里约 70% 属内存安全错误，其中约一半是 use-after-free**。**两份独立统计指向同一结论：堆溢出、悬垂指针、未初始化读正是这两个大型 C/C++ 代码库安全工作的主战场，值得为它们建立一套专门的运行时检测体系**。

## 每种 sanitizer 的射程与代价账

**四种工具，射程各管一族，代价各不相同**：

| 工具 | 管什么 | 代价 |
| --- | --- | --- |
| ASan（AddressSanitizer） | 越界、UAF、双重释放、栈/全局溢出 | 约 2 倍减速、内存约 3 倍 |
| MSan（MemorySanitizer） | 读未初始化内存 | 更重，需重编全部依赖 |
| UBSan（UndefinedBehaviorSanitizer） | 整数溢出、除零、空指针解引用等未定义行为 | 最轻：clang 官方文档将其定位为 fast，并提供适合生产环境的 minimal runtime |
| TSan（ThreadSanitizer） | 数据竞争（happens-before 追踪） | 官方手册：执行时间约 2 到 20 倍、内存约 5 到 10 倍 |

**表里 TSan 的 happens-before（判断一个操作的结果对另一操作可见的先后关系） 追踪需要一句解释：运行时为线程间的每次读写记录先后次序，两次冲突访问之间若不存在先行发生的同步关系，就判定为数据竞争**（开销数字来自 ThreadSanitizerCppManual 官方手册）。

**这四个名字在库里的位置：TSan 在并发缺陷的复现策略里有完整展开**（[[工程知识/缺陷分析：从个案到体系/并发/并发缺陷的复现策略：压力放大与确定性调度.md]]）**，UBSan 作为"运行即证"的分析层在门禁证据分层的表格里出现**（[[工程知识/软件构建：让变化可以理解、验证与交付/开发工具/静态分析在门禁里定位为证据生成器.md]]）。

**代价账决定用法：ASan 的 2 倍减速在测试环境可承受，进不了高并发生产；UBSan 足够轻，适合常开在开发构建里；MSan 因为要重编全部依赖，通常只在专门排查未初始化读时按需启用；TSan 独占线程交错观察，与 ASan 互斥使用（两者都要插桩内存访问，同开互相干扰）**。

## 边界：它证到哪一步为止

- **报警是"错误存在"的证据，不是"线上会发作"的证据**：**ASan 报警只说明这条路径碰了不该碰的内存，发作概率取决于线上数据分布与执行频率，严重性评估要另行完成**。
- **只测执行过的路径**：**没跑到的代码 ASan 不说话，覆盖率不足时"没报警"不构成安全结论，判定要回到覆盖率的证据强度去看**。
- **插桩改变时序**：**2 倍减速让竞态窗口变形，竞态缺陷的排查不要与 ASan 同跑，各自单独跑**。
- **射程错配**：**ASan 抓内存边界，抓不住数据竞争（那是 TSan 的射程）与逻辑竞态（TSan 也抓不住，见复现策略篇的射程对照）**。**选错工具等于用错尺子量错东西**。

## 怎么自己动手验证

拿一段越界代码，在两种构建下对照：

```bash
# 安装：Debian/Ubuntu 下安装 clang 工具链
apt install clang

# 写一个越界访问的 C 程序（保存为 overflow.c）：
# int main(void) { int a[8]; volatile int x = a[8]; return x; }

# 普通构建：无任何输出，exit 0——错误沉默
gcc -O0 -g overflow.c -o overflow_plain && ./overflow_plain; echo "exit=$?"
# 预期：exit=0，程序正常返回，错误没有暴露

# ASan 构建：clang 开启 address sanitizer，栈越界当场报警
clang -O0 -g -fsanitize=address overflow.c -o overflow_asan && ./overflow_asan
# 预期：报告 stack-buffer-overflow，附变量名与分配栈，exit 非 0
```

**把数组改成 malloc 后故意 free 再读，重跑 ASan 构建，报告变成 heap-use-after-free——同一份影子地图，换一类错误照样抓**。**若换成 `-fsanitize=thread` 跑一个含数据竞争的程序，对照预期：TSan 报数据竞争、对越界沉默——射程错配的一手确认**。

## 演进与选型

**影子内存方案在 2012 年的 ASan 论文里定型（Serebryany 等人，USENIX ATC），此后 LLVM（编译器基础设施，模块化编译与优化） 与 GCC（GNU Compiler Collection，GNU 编译器套件） 都内置了 `-fsanitize` 家族**；**论文版本之前工业界靠 Valgrind 的二进制翻译实现类似检测（官方手册：Memcheck 让程序比原生执行慢 10 到 50 倍，如今只在无源码重编场景保留价值）**。**与 Rust 的所有权模型是互补关系：所有权在编译期（代码编译成可执行文件时发生的阶段）静态拒绝悬垂指针，sanitizer 在运行时兜住既有 C/C++ 代码的错误——存量代码重写不动的那部分，运行时检测是现实可用的防线**。
