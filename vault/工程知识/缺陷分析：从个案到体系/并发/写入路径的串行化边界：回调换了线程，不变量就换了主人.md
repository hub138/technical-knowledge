# 写入路径的串行化边界：回调换了线程，不变量就换了主人

> **要点**：一条写入路径的线程安全，依赖"所有会碰到共享状态的动作都在同一个串行域里执行"；完成回调一旦换到别的线程上执行，串行域出现两个主人，集合、计数这些不变量就开始说谎。

## 要解决的问题

异步写入有一个固定结构：调用方把请求交给写入路径，写入路径维护一个"已发出未完成"的集合，等结果回来后把这一项移走。集合非空表示还有在途的写，限流、关闭、统计全靠这个判断。这个结构隐含一个前提：**登记与移除这两件事，永远发生在同一个串行域里**——同一个单线程事件循环、同一把锁、或者同一个按 key 分派的执行器。前提满足时，不需要任何同步原语，集合天然一致。

前提什么时候被打破？答案藏在一条真实缺陷里。Apache BookKeeper 客户端曾出现这样的病例（上游 commit 804b2b61，已在本环境真实复现）：客户端到存储节点的连接反复中断时，同一账本上的并发写入有一部分收不到完成通知，账本写入停滞。上游修复只有一个动作——把错误分支的回调从网络 I/O 线程投递回账本绑定的工作线程再执行。本文把这个修复动作背后的通用机制讲清楚：**回调换了线程，不变量就换了主人。**

## 机制：串行域与它的两个主人

先定义串行域：一组动作如果在执行上保证互不交错（单线程事件循环、互斥锁保护的临界区、按 key 哈希到同一线程的 ordered executor），就说它们在同一个串行域里。写入路径的集合不变量——"每个已登记的请求恰好被移除一次"——只在串行域内部成立。

正常完成路径是这样走的：网络线程收到确认报文，把"这次写完成了"这条消息投递给账本的工作线程，工作线程在串行域内把集合项移走、更新计数、触发上层回调。全程一个主人。

异常完成路径在出问题的版本里是这样走的：连接失败被网络 I/O 线程感知，错误分支**直接在网络线程上调用**完成回调。于是移除集合项的动作第一次发生在串行域之外。两个线程同时进出同一个集合：

- 网络线程移除 A 项时，工作线程正在遍历或修改同一批项，顺序错乱；
- 两个线程各自认为"这次完成由我处理"，通知被吃掉或重复触发；
- 集合计数与实际在途数对不上，限流判断、关闭等待全部失真。

注意这里没有数据竞争意义上的"脏读"——集合操作本身可能是线程安全的——坏掉的是**上层不变量**：恰移除一次、计数一致、完成通知恰好一次。线程安全的容器加非串行化的使用方式，得到的是一致性被撕裂的结果。

## 上游怎么修

修复把错误分支也送回串行域：网络线程不再自己执行完成逻辑，而是通过按账本分派的有序执行器投递，让账本工作线程统一处理成功与失败。修复之后，完成路径不管成功失败，都在同一个串行域里排队执行，集合不变量的主人重新只剩一个。

这个修复模式有个名字可以记：**回到属主线程**（re-ownership）。网络线程只负责感知事件，凡是要碰账本状态的动作，一律投递回账本属主的执行器。代价是多一次线程切换与一层队列；收益是整个写入路径的并发推理退化为单线程推理。

## 代价与边界

回到属主线程不是免费的，三笔代价要心里有数。

**延迟与吞吐**：每次回调多一次投递。高频小写入的场景下，这笔开销在压测里看得见。上游选择全量投递而保留"个别路径直调"的优化，正是因为局部优化重新打开串行域缺口——只要有一条路径在网络线程上碰共享状态，整个不变量作废。串行域纪律是全有或全无的。

**顺序性**：按 key 分派的 ordered executor 保证同一 key 的动作有序，不同 key 之间并行。如果回调处理依赖跨 key 的全局顺序，这个模型不提供，要另行设计。

**投递失败**：执行器关闭或队列拒绝时，投递的回调本身也要有出路（记录、降级、或同步执行），否则错误处理路径自己变成新的丢回调路径。异常路径上再埋一个异常路径，是这类修复最常见的返工原因。

边界也很明确：如果回调不碰任何写入路径共享状态（纯通知、无状态转发），直调没有一致性问题。判据是**回调是否触碰串行域内的状态**，碰就回属主，不碰才允许直调。这条判据让"哪些回调必须投递"变成可审查的规则，靠约定记忆迟早漏。

## 验证

复现这类缺陷不需要构造复杂的分布式场景，压力方向就是触发条件：让连接反复中断并伴随并发写入。可复现的检查路径：

1. 并发写入同一账本（或同一 key 的资源），同时用故障注入让底层连接周期性中断；
2. 统计"提交数"与"收到完成通知数"（无论成功失败），两者相等是底线；
3. 监控在途集合的长度：正常波动后归零；只增不减或长期非零即命中；
4. 修复后重跑同一压力，提交数等于完成数、在途集合最终清空，为回归基准。

```text
提交写入 N 次 → 完成回调必须恰好 N 次（成功或失败都算）
在途集合长度 → 请求结束后必须归零
```

对不上这两个等式中的任何一个，先查完成回调在哪个线程上执行——那是不变量最容易被换主人的地方。代价与收益在这里同时显形：直调省下的一次投递是微秒级的收益，撕裂一次不变量是小时级的事故，权衡不需要犹豫。
