# 只读旁观者不能改变被观察对象的状态

为了自动放行一次审批、为了看一眼会话跑到哪、为了给界面补一个进度条，工程上经常需要「接进去」一个额外的参与者。接入方的意图是只看不做，可一旦这次接入写入了一个共享槽位、订阅了一个消费位置、占用了一个名额，它就从旁观者变成了参与者。

信息系统里的观测者效应就体现在这里：**观测动作本身消耗被观察对象的资源，或者修改它的共享状态**，于是被观测的行为发生了变化。后果比「观测不准」更重一层，是被观察对象本身开始出错。

## 要解决的问题

三类最常见的接入方式，代价差异极大：

| 接入方式 | 是否改变被观察对象 | 典型后果 |
| --- | --- | --- |
| 读日志、读追踪、读指标端点 | 只消耗少量资源 | 抓取频率过高会抬高负载 |
| 加入一个消费者组 | 改变消费位置分配 | 触发重新分配，原消费者停止消费 |
| 写入会话的应答槽位 | 改变请求的收件人 | 原本的应答者收不到请求 |

第二、三类问题的共同结构是：**被观察对象里有一个共享的、只有一个位置的资源**。消费位置分配、会话应答槽位、独占写权限都属于这一类。接入方一次写入，原持有者就失去了它，而写入方往往只打算看几眼。

## 机制：从旁观到参与只需要一次写入

以会话应答槽位为例。

一个会话要处理审批、选项题、文件读写委托，这些请求都要送到明确的收件人手里。实现上通常维护一个「当前应答者」引用，连接完成握手时写入。于是：

- 接入方完成握手 → 写入引用 → 接管了应答权；
- 原客户端的界面从此收不到请求，用户看到的界面不再弹出审批；
- 接入方若只打算旁观、没有应答实现，请求就停在原地；
- 接入方若中途断开，引用还指着它 → 后续所有请求投给一个已经关闭的连接。

观察者不仅改变了被观察对象，还把双方一起拖住。这与 [[工程知识/缺陷分析：从个案到体系/并发/案例十四：一方取消，旁观者陪葬——RocksDB 状态加载的并发陷阱]] 是同一个家族：共享可变状态被第二个参与者写入，代价由原来的持有者承担。

另一类更隐蔽的形式是「观测压垮被观测者」：指标轮询在组件关闭后继续读统计接口，读到的已经是释放后的资源，一次只读的调用把整个服务带下来，见 [[工程知识/缺陷分析：从个案到体系/并发/关闭与观测的并发错位：生命周期边界要算上读它的人]]。那里错的是生命周期，这里错的是共享槽位的归属。

对照一组安全与不安全的设计：

- **广播（安全）**：事件推给所有订阅者，新增订阅者不影响已有订阅者，采集侧的代价只在存储与采样频率，见 [[工程知识/性能工程：从用户等待到资源瓶颈/观测与诊断/指标、日志、Trace与剖析各答一问，合起来才构成证据]]。
- **可归还的槽位（有条件安全）**：写入者在退出时归还槽位，且归还动作绑定在连接的关闭事件上，不能依赖定期探测。
- **写入即覆盖的槽位（不安全）**：没有认证、没有归还、没有回退到上一任的路径。

## 边界

- **完全隔离的旁路代价最低**。读日志与追踪不改变执行路径，只带来存储与采集开销；采集频率是唯一需要约束的变量。
- **只读副本要接受延迟**。从副本读观测数据不会干扰主体，代价是数据滞后，不能用于判断「此刻是否卡住」。
- **可归还的槽位需要确定性事件**。靠定期探测判断持有者是否还活着存在时间盲区，绑定连接关闭事件才干净，理由见 [[工程知识/后端系统：在并发、失败与变化中维持服务/分布式可靠性/健康检查只能提供有时效的失败证据]]。
- **广播也非零成本**。订阅者数量增长会放大推送开销，需要在订阅侧做上限。

## 验证

在公开环境复现「一个额外加入者打断原有消费者」：起一个单分区主题，两个消费者先后加入同一个消费者组。

```bash
docker run -d --name kafka -p 9092:9092 apache/kafka:latest
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --topic demo --partitions 1 --replication-factor 1
```

先用一个消费者持续消费并打印，再启动第二个消费者加入同一分组。**预期**是第二个消费者加入的瞬间触发重新分配，第一个消费者停止拿到消息。用不同的 `group.id` 各起一个消费者后重跑，两个消费者都会持续收到消息 —— 这组对照说明：决定行为变化的是「加入了同一个共享分配」，多一个消费者本身不构成原因。

验证旁观接入是否改变了路由，用连接标识核对：

```bash
grep -o 'connectionId=[^ ]*' "$CLIENT_LOG" | sort | uniq -c
```

**预期**是会话期间只有一个连接标识承接请求。**对不上**说明存在中途接管，回到槽位归属上查写入点。

## 影响与代价

- 选广播式旁路：观测方零影响，代价是订阅侧需要去重与限流。
- 选可归还的槽位：功能上够用，代价是必须保证归还动作在所有退出路径上都执行。
- 不区分这三类而随手接入，代价由用户承担：界面不再弹审批，工具调用永久等待。
- 上线前应把「接入方是否写入共享状态」列为评审项，这是唯一能在故障前拦住的检查点。

## 从什么地方做

1. **先分类**：把每一处接入按上表归到三类之一，标出写入共享状态的那些。
2. **再改优先级**：能改广播的改广播，必须写槽位的补上归还与认证。
3. **再补清理**：槽位清理绑定在连接关闭事件上，不依赖定期探测。
4. **最后加观测**：记录槽位的写入者与时间，接入异常时能立刻看出是谁写进去的。
