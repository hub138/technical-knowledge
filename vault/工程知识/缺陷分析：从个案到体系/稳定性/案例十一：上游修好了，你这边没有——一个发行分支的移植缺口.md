# 案例十一：上游修好了，你这边没有——一个发行分支的移植缺口

> **一句话总结**：有一类缺陷不在代码里，在代码的历史里——上游已经修好，下游分支因为fork、改写或漏合而没有这段修复。它的可怕之处在于：上游的 issue 已关闭，你的漏洞仍然开着，而 CVE 数据库不会告诉你。

前面十个案例有一个共同前提：缺陷存在于代码里，等着被人发现。一个 PostgreSQL 发行分支的这批病例推翻了这个前提——**缺陷是已知的，修复是存在的，只是不在你的分支上**。上游的提交记录里躺着修复，目标分支上同样的代码仍是修复前的样子。执行一条 SQL 就能让后端崩溃。

## 五条可达的崩溃路径

**病例 A · 一条 SQL 打崩后端**（[上游 commit 85f0d470](https://github.com/postgres/postgres/commit/85f0d470380902c8c62d0165c349c82d81c3e056)，P1）。`lo_manage` 在非触发器调用时对无效的触发器上下文解引用，后端崩溃。触发方式简单到不需要任何前置条件：

```sql
SELECT lo_manage();
```

同一个提交还修了 `unique_key_recheck` 在 assert 构建下先于协议校验触发节点断言的问题。两处的共同点是**缺少入口校验**：函数假设自己被调用在某种上下文里，而没有验证这个假设。

**病例 B · 临时表的并发索引**（[上游 commit 9055344b](https://github.com/postgres/postgres/commit/9055344b495f7015205658741734be9d67cf4f4a)，P1）。`DefineIndex`、`RemoveRelations`、`index_drop` 三处入口没有为临时表做强制非并发降级。临时表是会话局部的，多事务并发构建会产生事务可见性冲突，进而崩溃。

这一例在下游分支上更复杂：这个 PostgreSQL 发行分支上的 `REINDEX CONCURRENTLY` **也没有排除临时表**，意味着即使移植了上游的三处保护，这条分支特有路径上的崩溃仍然可达。这是移植工作的典型陷阱——上游只修它有的代码，分支上多出来的部分它管不到。

**病例 C · 触发器里动态建分区**（[上游 commit 8aad248f](https://github.com/postgres/postgres/commit/8aad248f7c67f1225027414530ce2809c1fcd104)，P1）。`CREATE TABLE PARTITION OF` 路径缺少 `CheckTableNotInUse`。执行器仍持有父分区表引用时动态建分区，引用失效，后端崩溃。

这例展示了保护覆盖不全的典型形状：`CheckTableNotInUse` 在代码里是存在的，但只覆盖了 TRUNCATE 和 ALTER TABLE（含 ATTACH PARTITION）两条路径。新增的第三条路径没有接上同一个保护。

**病例 D · Perl 值的强转**（[上游 commit 7594b7a5](https://github.com/postgres/postgres/commit/7594b7a53366f6c262103acd161e6fee0a30e5c2)，P1）。`plperl_to_hstore` 对非哈希的 Perl 值直接强转成 `HV*`，缺少 `SvTYPE` 校验，后端崩溃。触发路径可达——hstore transform 的生产入口仍指向这个函数。

**病例 E · LATERAL 下推的断言**（[上游 commit 6443cd2e](https://github.com/postgres/postgres/commit/6443cd2e2421f0a69d1e0b93a4d1e6a30e5b2f0c1)，P1）。子查询限制子句下推的安全检查没有拦截 LATERAL 引用。debug 构建下断言失败，非 debug 构建下生成非法计划，执行器段错误。

这一例的后果分裂值得单独注意：**同一个缺陷，在不同构建下表现完全不同**。断言把问题拦在构建期，但生产构建没有断言，于是问题以段错误的形式出现在运行时。

## 机制：缺口是怎么产生的

把这五例的产生原因分类，得到下游分支缺修复的三种典型途径：

- **fork 时间点早于修复**。分支从上游切出之后，上游才修的问题，自然不在分支上。这是最容易被理解的一种，也最容易通过定期同步解决。
- **代码被改写，修复无法自动应用**。上游的修复是对着上游的代码写的，下游同名函数可能已经在这个分支上被改写过，cherry-pick 会冲突，自动合并失败，于是被跳过或推迟。病例 E 的备注里明确写着"需手工移植到改写后的同名函数"。
- **保护被复制到新路径时漏掉**。上游为路径 A 加了保护，分支上新增了路径 B，没有接上同一个保护。病例 C 属于此类，病例 B 的 `REINDEX CONCURRENTLY` 也是。

第三类最危险，因为它**在这个分支上是新引入的缺陷**，上游永远不会有对应的修复提交。等着上游来修，等不到。

## 为什么这一类危险

**修复已经存在，所以没人再找它**。上游 issue 关闭、提交已合入、CVE 已分配并标注"已在版本 X 修复"。安全扫描器比对版本号，看到你的基线版本高于 X，就认为你是安全的。它不知道你的分支从来没有这段代码。

**可达性极高**。病例 A 只需一条无参数 SQL。不需要认证绕过、不需要构造畸形报文、不需要特定时序——一个能执行 SQL 的账号就够了。这类缺陷的利用成本接近于零。

**它会随时间累积**。fork 之后每过一天，上游就多修一些问题，缺口就大一分。不定期同步的分支，缺口是单调递增的。

**分支上多出来的部分永远不在上游的视野里**。上游的修复只覆盖上游的代码。病例 B 里这个发行分支的 `REINDEX CONCURRENTLY`，上游不可能为它提交修复——这段代码的正确性责任，完全在维护这个分支的一方。

## 怎么发现这一类

这一类的发现方法和前面十个案例完全不同。不是靠复现，是靠**比对**：

- **按文件比对，不按版本号比对**。对同一个源文件，列出上游在 fork 之后的全部提交，逐条检查是否已存在于目标分支。版本号落后不代表有缺口，版本号领先也不代表没有。
- **对分支上多出来的代码单独做一次保护审计**。列出上游在各个入口加的通用保护（`CheckTableNotInUse`、并发降级、上下文校验），检查这些路径是否每一条都接上了。
- **优先看"一条语句就能触发"的缺陷**。崩溃类、注入类、越权类，触发成本最低，优先级最高。
- **关注构建相关的分支**。病例 E 在 debug 和非 debug 下表现不同，说明只测一种构建会漏掉一半。

## 边界与教训

- **版本号不等于代码状态。** 安全基线和版本比对只能覆盖"上游修了什么"，覆盖不了"你的分支上有没有"。真正的依据是代码本身。
- **保护是成体系的，新增路径要接上同一套保护。** 加了第三条访问路径，就检查前两条路径上的保护是不是也该加。
- **分支特有代码的正确性责任在维护方。** 上游不会为你的分支提交修复，也不会为你分支上多出来的功能提交修复。
- **cherry-pick 冲突是信号，不是障碍。** 冲突说明这段代码被改过，改过的代码更可能有移植缺口——把它标记出来人工处理，而不是跳过。
- **回归用例要跟着修复一起移植。** 病例 C 的备注里专门提到要同步移植 `create_table.sql` 和 `alter_table.sql` 的用例。没有用例的移植，无法验证是否真的修好了。
