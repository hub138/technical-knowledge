# 案例四十三：升级把前提带走了——依赖行为变更引发的下游失效

> **一句话总结**：升级依赖不总是为了用新东西，很多时候是被动跟着走——安全补丁、EOL、发行版打包。危险在于：依赖内部行为悄悄变了，你在它旧前提上写的代码随之失效，而这类变化不进 changelog 头条、不报错，静默地改变返回值语义。

## 背景：一次无害的升级，一轮无声的失效

升级依赖在多数团队的流程里是"低风险操作"：版本号 bump、CI 绿了就合入。本案例的病灶恰好长在这个流程盲区——版本升级不改变任何调用点代码，改变的是依赖内部的行为前提。

### 病例一：默认值悄悄变了（P2）

一个数据管道框架（如 Spark Structured Streaming 类）的连接器，老版本里 `failOnDataLoss` 默认是 `true`——数据丢失时任务失败，值班人员收到告警。升级后新版本把默认值改成了 `false`：数据丢失静默跳过，任务继续跑，绿色面板背后数据已经缺了一块。失败转静默，失败语义从"值班可见"变成"事后再现"。

默认值变更是最隐蔽的一类行为变更：签名不变、返回类型不变、不抛新异常，只有"没传参时的那个值"变了。而恰是最依赖默认值的人，最不会去读这条 changelog。

### 风险不止于默认值

同一模式的其他变体：

- **迭代顺序变了**：老版本遍历配置键按插入序，新版本按字典序；依赖这个顺序做 diff 的代码产出的差异报告错了方向。
- **异常类型变了**：老版本抛 `IOException`，新版本改抛自定义运行时异常；catch 块从"兜住处理"变成"放过穿透"，异常处理路径整体失效。
- **单位变了**：库内部从秒改毫秒，常量名不带单位，`timeout = 30` 从"半分钟"变成"30 毫秒"超时，任何带单位的注释在升级中一并过时。

### 病例二：隐藏依赖的连锁（P1）

升级主依赖 A 时，传递依赖 B 也被连带升级。A 从未承诺 B 的版本（它只在文档里说"需要 3.x 以上"），你的代码从未直接调用 B，但 B 的 `getKeyOrder()` 在 4.0 改了实现。你的代码依赖 A 的一个方法，A 的这个方法内部用了 B 的迭代序——**你没有任何一行代码直接碰 B，B 的行为变更却穿透到你的返回值**。

这个病例演示了"传递依赖的隐藏前提"：你在 A 的 API 上写代码，实际依赖的是 A 与它全部依赖在当前版本组合下的联合行为。升级 A 时，你验证的是 A 的调用点，没验证 B 在 A 内部路径上的行为变化。

### 病例三：EOL 驱动的被动升级（P1）

不是所有升级都是主动的。运行时平台宣布 EOL（如 JDK 8 → 17、Python 3.8 → 3.12），CI 基础镜像随之外推，不升级的分支连构建都过不去。被动升级的病灶与主动升级同构：你被迫在时间窗口内完成一次你并未计划的行为验证，而窗口压力下最容易省略的就是"验证依赖内部行为没变"这一步。

## 机制：为什么这类缺陷绕过了所有防线

为什么这类失效绕过了编译期、单测、以及常规 CI？

1. **编译不查行为**：签名兼容时编译零告警。默认值、迭代序、异常类型都属签名兼容的行为变更，编译器管不到。
2. **单测测调用点**：你的单测断言"我调用 X 得到 Y"，当 Y 依赖依赖的内部行为时，Y 的变化要靠"依赖的测试"发现，但那是别人的测试，不在你的 CI 里。
3. **changelog 只列"改了什么"，不列"什么没变但此前不是这样"**：默认值变更常被写进 changelog 但读者忽略；迭代序这种实现细节根本不进 changelog。
4. **语义化版本不能承诺行为**：SemVer 只承诺 API 兼容，不承诺行为兼容。从 3.9 到 3.10 是 patch 级，但默认值翻面完全合法。SemVer 的兼容是"不会编译错"级别的承诺，与"运行起来结果一样"差着一层。

## 防线：行为兼容性验证清单

升级前（针对每个直接依赖，传递依赖按调用面排查）：

- **diff 配置面**：老新版本的配置项默认值逐项 diff，产出的差异表进升级 PR 描述。默认值变更是头号风险源。
- **diff 异常面**：检查依赖新版本的异常声明与抛出行为，比对 catch 块是否仍匹配。
- **关键路径行为快照**：升级前对关键路径的输入输出做快照，升级后同样输入重放，断言输出一致。快照内容：返回值、迭代序、异常类型、时间语义。
- **传递依赖清单冻结**：传递依赖解析出的版本树在升级前后 diff，任何漂移都当行为变更处理。

升级后（黄金 24 小时）：

- **静默指标盯梢**：任务成功率、数据完整性指标、异常分类计数——找"从有到无"的静默转变（如异常计数归零）。异常计数归零比异常飙升更危险，它可能是 catch 变穿透，也可能是失败变静默。
- **对比验证**：同一输入双跑老新版本，diff 输出。这是默认值变更与迭代序变更的唯一可靠防线。

## 失效形态

| 失效 | 机制 | 信号 |
| --- | --- | --- |
| 默认值翻面 | 新版本未传参路径行为改变 | 配置面 diff 出现差异行 |
| 迭代顺序改变 | 内部数据结构换实现 | diff 报告方向错误 |
| 突破类型替换 | catch 块失配 | 异常计数归零 |
| 传递依赖穿透 | A 内部路径用了 B 的新行为 | 无直接调用关系的行为漂移 |
| EOL 被动升级 | 时间窗内省略行为验证 | 基础镜像外推日历 |

## 边界

- 本案例与案例七互为反面：案例七是"不升级的风险"（滞后依赖里藏着已修复的缺陷），本案例是"升级的风险"（新版本带走旧前提）；两个方向都要防，不存在"安全的一侧"。
- 与案例十一正交：案例十一是分支漏合（修复存在但不在你的分支），这里是依赖内部变更（不涉及修复的传播）。
- 与案例三十四机制不同：案例三十四的改动在你自己的代码里（优化改变前提），这里改动在依赖内部，你的代码一行未动。
- 软件构建域的理论篇（见 [[工程知识/软件构建：让变化可以理解、验证与交付/开发工具/依赖升级按风险分层，兼容性验证跟着层走]]）已给出升级的分层策略；本案例是该分层中"行为兼容验证"一环的失败实例与操作化清单。
- 行为兼容快照有成本：仅对关键路径做，不追求全量。关键路径的定义：其输出直接进产品语义或数据语义的调用面。

## 验证

最小验证：选一个真实依赖的两次版本，对同一配置集与输入集做双跑对比——配置面 diff 无未审差异行、关键路径快照 diff 为空、异常分类计数无"归零"项；任一条件不满足则升级 PR 打回。传递依赖版本树 diff 为空（或漂移已审）。黄金 24 小时的静默指标盯梢中，"异常计数归零"为最高优先级告警。
