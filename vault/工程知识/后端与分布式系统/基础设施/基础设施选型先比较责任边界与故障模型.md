# 基础设施选型先比较责任边界与故障模型

基础设施选型不是比较“谁的 QPS 更高”，而是把业务约束映射到组件提供的保证：数据是否为事实源、是否需要事务、能否丢失、是否需要重放、延迟和尾延迟目标、谁负责运维，以及故障时如何恢复。

例如“把数据库换成缓存”可能让演示环境延迟下降，却同时丢失事务约束、审计和恢复语义；“换成事件流”也不能自动得到可查询的当前状态。选型结论应写成责任矩阵和可验证假设，而不是组件排行榜。

## 先问六个问题

1. **事实源是什么？** 订单、账务和配置通常需要可审计的持久化事实源；缓存、索引和派生视图不应反过来成为唯一事实源。
2. **一致性边界在哪里？** 明确哪些读必须线性一致，哪些读允许最终一致，并写出过期、补偿或人工校正路径。
3. **消息能否丢失或重复？** 选择投递语义、幂等键、去重记录和重放策略，而不是只看“有没有队列”。
4. **流量形态是什么？** 区分请求响应、持续推送、批处理、事件流和大文件传输；不同形态的连接、背压和成本模型不同。
5. **故障如何被发现和恢复？** 需要健康检查、超时、限流、隔离、降级、告警、回滚和演练证据。
6. **变更由谁承担？** 托管服务降低底层运维，但会带来供应商边界、配额、网络和迁移约束；自管软件则需要自己承担升级和高可用。

## 能力域与适用边界

| 能力域 | 典型选择 | 适合解决 | 不应默认承担 |
| --- | --- | --- | --- |
| 事务事实源 | 关系型数据库 | 约束、事务、查询、审计 | 极低延迟的所有读请求 |
| 热点和短期状态 | KV/缓存 | 缓存、计数、限时状态、分布式协调 | 需要完整审计的唯一事实 |
| 搜索与检索 | 倒排/向量/混合检索系统 | 文本、向量、过滤和相关性排序 | 事务提交和权限最终裁决 |
| 异步解耦 | 队列 | 任务削峰、重试、消费者隔离 | 需要长期查询和复杂事务的主存储 |
| 可重放事件流 | 日志型流平台 | 多消费者、顺序、回放、流式处理 | 低流量同步 RPC 的替代品 |
| 大对象 | 对象存储 | 文件、模型、备份、数据集 | 小事务记录和低延迟随机更新 |
| 流量入口 | CLB/反向代理/API 网关 | L4/L7 转发、TLS、健康检查、路由 | 业务幂等和数据一致性 |
| 任务调度 | 容器编排/作业系统 | 调度、扩缩容、滚动发布、资源隔离 | 跨服务业务事务 |

## 常见组合，而不是单点替代

```text
客户端 -> 托管负载均衡 -> 网关/反向代理 -> 无状态服务
                                      |-> 关系型数据库（事实源）
                                      |-> 缓存（可重建的派生状态）
                                      |-> 队列/事件流（异步与重放）
                                      |-> 搜索/向量索引（可重建的查询视图）
                                      |-> 对象存储（大对象与归档）
```

组合时分别写清：写入顺序、失败补偿、幂等键、数据重建方式和观测指标。不要用“WebSocket + Redis”或“缓存 + 数据库”这样的产品名组合代替一致性设计。

## 选型检查表

- [ ] 为每类数据标注事实源、派生源、保留期限和删除策略。
- [ ] 为同步调用定义超时、取消、有限重试和幂等行为。
- [ ] 为队列或事件流定义顺序键、重复处理、积压告警和重放流程。
- [ ] 为缓存定义失效、穿透、击穿、雪崩和冷启动策略。
- [ ] 为入口层定义健康检查语义、连接耗尽、TLS 终止、路由和灰度策略。
- [ ] 为每个关键组件记录容量模型、配额、备份、恢复目标（RPO/RTO）和迁移路径。
- [ ] 用接近生产的负载验证 p50/p95/p99、错误率、资源成本和故障恢复时间；不要引用脱离环境的固定 QPS 或延迟数字。
