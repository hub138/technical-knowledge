# 服务发现与负载均衡决定请求落到哪里

## 核心拆解

| 维度 | 回答 |
| --- | --- |
| 要解决的问题 | 调用方只知道逻辑服务名，却需要把请求送到当前可达、就绪且有容量的实例。 |
| 本质 | 发现系统维护候选集合，负载均衡依据健康、负载、拓扑和会话语义选择目标；缓存传播决定信息有多新。 |
| 做法 | 明确注册/注销、健康与就绪、DNS/代理 TTL、连接池、路由权重、重试代际和模型服务的 token/KV 负载。 |
| 效果与代价 | 提高可用性、扩展性和故障转移速度；代价是陈旧端点、路由倾斜、粘性、观测和重试风暴风险。 |
| 边界 | 能解析或探针返回成功不代表业务可处理；重试前必须知道操作是否幂等以及 deadline 是否仍有效。 |
| 验证 | 注入半故障实例、陈旧注册、连接耗尽、DNS 延迟和节点丢失，检查目标选择、重复副作用和端到端失败时间。 |

服务发现把逻辑名称解析为当前可用实例；负载均衡在候选实例中选择目标。DNS、注册表、Kubernetes Service、客户端库和代理各自拥有不同的缓存、健康和故障语义，不能只看“能解析到 IP”。

## 决策维度

- **可达性**：实例是否监听、端口是否开放、网络策略是否允许。
- **就绪性**：是否加载模型/缓存、是否有容量接收新请求。
- **负载**：连接数、请求数、token、队列、权重、拓扑和租户，而非只做轮询。
- **一致性**：注册信息多久传播，旧端点何时淘汰，DNS/代理缓存多久失效。
- **会话**：是否需要粘性、分区键、连接迁移或请求重放。

健康检查失败只能说明探针观察到的问题；它不证明所有请求都安全重试。连接池、DNS TTL、代理超时和服务端 deadline 必须配套设计，否则会出现黑洞、重试风暴和流量倾斜。

## AI 服务的特殊性

LLM 请求的长度、KV cache 和优先级差异很大，按 HTTP 请求数均衡会把长请求集中到单个副本。路由还可能需要考虑模型版本、GPU 型号、LoRA、区域、租户和上下文缓存命中。

## 验证

注入实例半故障、陈旧端点、连接耗尽、DNS 延迟、单节点丢失和拓扑变化；观察请求是否落到健康容量、是否重复副作用、是否在 deadline 内失败。记录路由决策、端点版本和重试代际。

最小实验：让一个实例继续响应 TCP 连接但停止加载模型或耗尽连接池，比较只做端口探活、做 readiness、按队列/token 负载路由三种配置。检查请求是否仍被送入无容量实例、摘除传播时间和重试次数，验证“可达”与“可服务”不是同一个信号。
