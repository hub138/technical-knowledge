# 认证授权决定请求能看什么和做什么

## 核心拆解

| 维度 | 回答 |
| --- | --- |
| 要解决的问题 | 系统需要确认请求代表谁，并限制该主体能读取哪些资源、执行哪些动作和影响多大范围。 |
| 本质 | 认证建立主体身份，授权把主体、租户、资源、动作和环境映射成一次服务端可解释的允许/拒绝决策。 |
| 做法 | 校验 issuer、audience、签名、过期和 scope；服务端每次执行资源级策略，并为高风险动作设置最小权限、审批、幂等和审计。 |
| 效果与代价 | 降低越权、数据泄露和副作用风险；代价是策略维护、身份传播、缓存撤销和跨服务一致性成本。 |
| 边界 | 登录成功不等于拥有业务权限；UI、Prompt、token 解码和一次中间层校验都不能替代资源侧判定。 |
| 验证 | 测跨租户 ID 替换、过期/撤销 token、scope 缩小、缓存命中、RAG 检索和 Agent 工具组合，断言真实数据和副作用。 |

认证回答“请求代表谁”，授权回答“这个主体对哪个资源执行什么动作”。把身份 token 验证通过当成拥有全部权限，是最常见的后端和 Agent 安全错误。权限必须在服务端根据资源、租户、动作和上下文重新判定。

一个带合法 token 的请求仍可能越权：把 `/users/alice` 改成 `/users/bob`、把租户 ID 换掉，或让 Agent 组合“搜索 + 导出”工具，都要求资源侧重新检查关系和动作。身份是输入，不是授权结论。

## 权限链路

```text
凭据 -> 认证 -> 主体/租户 -> 资源策略 -> 动作约束
     -> 数据过滤/工具参数 -> 审计与撤销
```

OAuth 授权主要解决委托访问和 token 生命周期，不规定业务资源模型。RBAC 适合稳定角色；ABAC/关系型授权表达资源归属、环境、时间和条件，但需要可解释策略、默认拒绝和变更传播。

## 关键边界

- 身份 token 的 audience、issuer、过期、签名和 scope 必须校验；不能只解码 payload。
- 服务间调用需要明确代表用户还是服务自身，不能无意扩大权限。
- 多租户数据过滤是每次查询的约束，不是 UI 或 prompt 的提示。
- 高风险动作需要二次确认、幂等键、最小范围和审计；撤权要传播到缓存、索引和任务。
- 日志不能泄露 token、个人数据或完整敏感请求。

## 验证

测试跨租户 ID 替换、资源枚举、过期/撤销 token、scope 缩小、服务间 confused deputy、缓存命中、RAG 检索和 Agent 工具组合。断言实际数据和副作用，而不是返回“authorized”。
