# API 契约定义输入输出和演进边界

它解决的是调用方只能猜测接口行为，导致重试重复副作用、升级互相破坏和错误无法恢复的问题。契约把输入、状态、错误、时间、权限和兼容性变成可测试的边界；收益是跨团队演进可预测，代价是需要契约测试、迁移和版本治理。用旧客户端读新服务、新客户端读旧服务、未知字段和超时重试验证兼容性。

API 是跨进程、跨团队或跨版本的行为契约，不是 URL 加几个字段。契约需要表达输入约束、成功结果、错误类别、超时/取消、幂等、分页、授权和兼容策略；否则调用方只能从偶然实现推测语义。

## 先定义行为

| 契约部分 | 要回答的问题 |
| --- | --- |
| 输入 | 哪些字段必需？空值、范围、未知字段和大小上限是什么？ |
| 成功 | 是否已提交、已完成，还是只接受异步任务？结果是否稳定？ |
| 错误 | 客户端、权限、冲突、限流、依赖和服务端错误如何区分？能否重试？ |
| 时间 | deadline、取消、分页快照和数据新鲜度如何表达？ |
| 兼容 | 新旧客户端如何共存？字段删除和枚举新增如何处理？ |
| 观测 | request/trace id、版本、租户和审计字段如何传播？ |

## 让接口难以被误用

契约不只是字段齐全，还要尽量让非法状态无法表示。`Transfer(from string, to string, amount int64)` 很容易把两个账户传反，也没有说明金额单位；更清晰的输入使用 `SourceAccountID`、`DestinationAccountID` 和带 currency/最小单位的 `Money`。更新接口还要区分“字段未提供”和“明确设置为零”，不能依赖语言零值猜测调用意图。

写操作把幂等身份放进契约；分页定义稳定排序、游标和快照边界；错误按输入、权限、冲突、限流、依赖和未知提交分类。返回 `200 {"error": ...}` 会破坏监控和重试语义，裸 `map[string, any]` 则把 schema 推回文档和猜测。

## 兼容演进

默认 additive-first：先增加可选字段和新读路径，迁移消费者后再删除旧字段。未知字段应按协议约定忽略或拒绝；枚举、错误码和默认值要有向前/向后兼容测试。schema 通过不等于业务兼容，仍需验证状态、权限和副作用。

同步 API 只在调用者需要立即结果且能在 deadline 内完成时使用；长任务应返回稳定 task id 和状态查询/取消语义。分页必须定义排序、游标有效期和快照一致性，否则翻页会重复或遗漏。

最小对照：保留一个旧客户端，用新服务依次增加可选字段、改变枚举、删除字段和调整错误码；再让新客户端请求旧服务。记录解析结果、副作用、重试行为和监控告警，把“schema 能解析”与“业务仍正确”分开验收。

## 验证

用契约测试覆盖旧客户端读取新服务、新客户端读取旧服务、未知字段、重复请求、超时后不确定提交、权限拒绝和错误重试。每次 schema 变更绑定代码、数据库/消息迁移、文档和回滚路径。
