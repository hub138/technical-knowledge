# 队列和流系统用时间与容量换取解耦

## 核心拆解

| 维度 | 回答 |
| --- | --- |
| 要解决的问题 | 生产者和消费者速度、可用性或部署节奏不同，直接同步调用会把峰值和依赖故障传递到请求链路。 |
| 本质 | 用持久化消息和时间缓冲把提交、处理、重试与重放拆开，同时把完成语义从调用栈变成状态机。 |
| 做法 | 定义确认点、分区键、顺序范围、幂等键、重试预算、死信、TTL、堆积上限和业务提交边界。 |
| 效果与代价 | 获得削峰、异步、隔离和重放能力；代价是延迟、重复、乱序、积压、运维和一致性协调。 |
| 边界 | offset 前进或消息被确认都不能证明业务事实已经提交；跨分区顺序和 exactly-once 不能凭产品名假设。 |
| 验证 | 注入崩溃、确认丢失、重复/乱序、堆积、分区变化和 schema 升级，检查业务不变量、处理次数和最终状态。 |

队列把生产和消费拆开，让系统削峰、异步、重试或隔离故障；流系统还保留有序日志，使消费者可以按 offset 重放。它们引入的不是“可靠性自动提升”，而是延迟、重复、乱序、堆积和状态恢复的新边界。

## 先区分语义

| 语义 | 典型行为 | 不能假设 |
| --- | --- | --- |
| at-most-once | 先确认再处理，可能丢消息 | 业务一定完成 |
| at-least-once | 处理后确认，可能重复 | 全局 exactly-once |
| ordered partition | 分区/key 内有序 | 跨分区全局有序 |
| replayable log | 按 offset 重放 | 重放不会重复副作用 |

生产者确认、消费者确认、提交 offset 和业务提交是不同事件。要把消息状态写进数据库，通常需要 outbox、幂等键、事务性消费或补偿；“队列显示已处理”不能证明事实数据已提交。

## 容量和背压

队列长度是时间单位的库存。根据到达率、服务率和处理时间估计可接受堆积，并设置最大长度、TTL、优先级、死信、消费者并发和限流。无限重试会让坏消息占满健康任务；重试要有退避、预算和可观测原因。

最小对照：让消费者在“处理成功后确认”和“收到消息立即确认”两种模式下，在业务写入前注入进程退出；前者应允许重投但要求幂等，后者会产生可观测丢失。再让消费者在确认后、提交后分别崩溃，记录消息次数、业务状态和死信数量，才能把投递语义与业务完成语义分开。

## 验证

测试生产者重试、消费者崩溃、确认丢失、重复/乱序、分区扩展、死信重放、堆积、下游超时和 schema 变更。断言业务不变量、最终状态、处理次数、延迟和资源，而不是只看 offset 前进。
