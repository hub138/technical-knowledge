# 队列和流系统用时间与容量换取解耦

订单接口在高峰期不能等通知、积分和搜索索引全部完成，但“把消息发进队列”也不等于订单已经完成。生产上最常见的事故是：订单事务提交后进程在发布事件前退出，通知永远不会发生；消费者写入成功后确认丢失，重投又发了一次优惠券；或者消费者先确认再写库，进程退出后业务事实直接丢失。队列把时间换成解耦，也把完成条件从一次函数调用变成一条可恢复的状态机。

## 先看一个事故

| 时间点 | 代码做了什么 | 故障 | 最终结果 |
| --- | --- | --- | --- |
| T1 | 写入订单数据库 | 事务提交成功 | 订单存在 |
| T2 | 发布 `OrderCreated` | 进程在发布前崩溃 | 通知、积分都不知道订单存在 |
| T3 | 消费者扣库存并返回成功 | ack 在网络中丢失 | 同一订单被再次扣库存 |
| T4 | 消费者收到消息立即 ack | ack 后进程退出 | 业务写入从未发生 |

这四个时间点对应四个不同的确认：数据库提交、生产者确认、消费者确认、业务事实提交。把它们混成一个“已处理”状态，系统就无法解释丢失、重复和补偿。

## 队列和流系统各自解决什么

| 选择 | 适合的问题 | 主要语义 | 代价 |
| --- | --- | --- | --- |
| **任务队列** | 一项工作只需要一个消费者完成 | ack 后消息可删除，失败可重投 | 重放和多组独立消费通常较弱 |
| **持久化日志/流** | 多个消费者各自读取、审计或重建状态 | 消费者保存 offset，可回放 | 分区、重平衡、保留周期和存储成本 |
| **同步调用** | 需要立即返回确定结果 | 调用链内完成 | 峰值和依赖故障直接传递 |

队列适合“生成一张缩略图”这类一次性工作；流适合“订单事件同时供库存、风控、分析读取”。Kafka 的 offset、RabbitMQ 的 publisher confirm 和 consumer acknowledgement 都只描述各自协议边界，不能自动替代业务事务。产品名称里写着 durable 或 exactly-once，也不代表你的数据库副作用天然只执行一次。

## 从 0 开始：先写清完成条件

### 1. 定义业务事实和幂等键

先写不变量，再选 broker：

```text
同一个 order_id 的库存扣减最多成功一次
同一个 payment_id 的退款最多成功一次
同一个 event_id 可以被重复投递，但重复处理不能重复副作用
```

幂等键必须进入业务存储的唯一约束或去重表，不能只放在进程内存里。进程重启、消费者扩容和重放都会让内存状态消失。

### 2. 用 outbox 连接数据库和消息

不要在一个函数里“先写库，再直接 publish”：

```text
同一数据库事务：订单状态 + outbox(event_id, payload, status=pending)
事务提交后：outbox worker 发布事件
收到 publisher confirm：标记 sent
发布失败：按退避重试，超过预算进入人工可见的死信
```

这样允许事件重复发布，但不会因为进程在两个动作之间退出而静默丢失。消费者仍然必须幂等，因为 worker 可能在收到确认前崩溃，重启后会再次发布同一个 `event_id`。

### 3. 把消费者顺序固定下来

推荐顺序是：

1. 解析和校验 schema、版本和租户边界。
2. 用 `event_id` 或业务幂等键抢占去重记录。
3. 在同一事务里写业务事实和处理状态。
4. 事务提交成功后再 ack 或提交 offset。
5. 失败时区分可重试错误、不可重试错误和毒消息。

“先 ack 再写库”换来的只是短暂吞吐，代价是不可恢复的丢失；“写库后 ack”换来的是可能重复，因此必须配唯一键、幂等更新或状态机条件更新。

## 投递语义不是业务语义

| 语义 | 怎么得到 | 允许发生什么 | 仍需自己保证 |
| --- | --- | --- | --- |
| **at-most-once** | 处理前确认 | 丢消息，不重复 | 不能用于不可丢的事实 |
| **at-least-once** | 处理成功后确认 | 重复投递 | 幂等副作用、去重和重试预算 |
| **分区内有序** | 相同 key 固定到同一分区 | 分区间乱序 | key 设计、热点和重平衡 |
| **可回放** | 保留日志和 offset | 重放会再次触发消费者 | 重放模式、幂等和副作用隔离 |

“exactly-once”最多是某个 broker、生产者、消费者和事务边界内的协议保证；跨数据库、邮件、支付和外部 API 仍需要幂等键、对账或补偿。RabbitMQ 的 publisher confirms 与 consumer acknowledgements 彼此独立，收到 broker confirm 不代表消费者完成业务，收到 consumer ack 也不代表生产者知道下游事实。

## 分区、顺序和扩容

同一个订单、账户或设备的事件需要有序时，把业务 key 作为分区键；不要把随机 UUID 当分区键后再要求同一实体有序。分区数限制同一消费组的最大并行度，热点 key 会让一个分区成为瓶颈，即使集群总 CPU 还有余量。

扩容前要先回答三个问题：

- 新增分区后，旧 key 是否会迁移并改变顺序？
- 消费者重平衡时，未提交 offset 会不会重复处理？
- schema 是否能让旧消费者读取新事件、让新消费者读取旧事件？

事件必须带 `event_type`、`event_version`、`event_id`、发生时间、租户或聚合 key。字段只增不删并不能自动保证兼容，真正上线前要用旧消费者读取新样本做回归。

## 容量和背压：把堆积换算成时间

队列长度不是“还有多少条”这么简单，而是库存时间。若积压 100,000 条、消费者稳定处理 500 条/秒，理论清空时间至少是 **200 秒**，还没算新流量、重试和下游抖动。应同时限制：

- broker 队列长度、消息 TTL、单条消息大小；
- consumer 并发、连接数、prefetch/in-flight 数；
- 重试次数、退避上限、死信容量；
- 下游写入 QPS 和单租户配额。

优先监控**最老消息年龄**、有效处理速率、处理 p99、重试率、死信数、发布确认延迟和 in-flight 数。只看 queue length 可能漏掉“长度没变但处理时间翻倍”的故障。

背压顺序应是：入队前 admission control → 有界队列 → 超限快速失败或降级 → 可观测重试。无界内存队列只是把 broker 的容量问题改成进程 OOM。

## 死信和重放要有操作边界

毒消息不能无限重试：达到次数或时间预算后进入死信，记录最后错误、schema 版本、消费者版本和原始 `event_id`。重放前先修复根因、选择隔离队列，并保证已成功的业务状态不会被再次推进；不要把死信一键倒回主队列，否则会重新制造同一波故障。

## 验证：用故障注入证明语义

| 注入点 | 应观察什么 | 通过条件 |
| --- | --- | --- |
| 数据库提交后、发布前崩溃 | outbox 是否留下待发布事件 | 事件最终可发布，订单不丢 |
| publish 后、confirm 前崩溃 | 同一 event 是否重发 | 消费者副作用只成功一次 |
| 业务提交后、ack 前崩溃 | 消费次数和唯一约束 | 重投不重复扣款/扣库存 |
| ack 后、业务提交前崩溃 | 是否出现事实缺失 | 该模式应被测试禁止 |
| 单分区消费者变慢 | 最老消息年龄、热点分区 | 背压和告警先于 OOM |
| schema 升级、旧消费者在线 | 解析错误和回滚 | 新事件可被旧消费者安全忽略或处理 |
