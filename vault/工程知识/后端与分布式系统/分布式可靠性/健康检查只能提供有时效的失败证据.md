# 健康检查只能提供有时效的失败证据

三者都在“观察状态”，但目的不同：轮询获取业务结果，心跳检测连接或成员是否仍在，健康检查决定实例是否接收流量。不要用一个接口同时承担三种语义。

例如一个实例可能仍能返回 `/healthz`，但模型尚未加载、数据库连接池已耗尽或租户配额已满；反过来，短暂的下游抖动也不应让所有实例同时被摘除。检查结果必须带上观察时间、作用范围和过期语义，调用方不能把一次成功当成未来一段时间的保证。

## 语义对比

| 机制 | 发起方 | 问题 | 设计重点 |
| --- | --- | --- | --- |
| 轮询 | 客户端/消费者 | 任务是否完成、资源是否更新 | 间隔、退避、截止时间、游标和重复读取 |
| 心跳 | 连接两端/集群成员 | 对端是否仍可通信、租约是否续期 | TTL、丢包容忍、时钟偏差、脑裂和误判 |
| 健康检查 | 入口/编排系统 | 实例现在能否安全接流量 | 存活与就绪分离、依赖范围、摘除与恢复 |

## 轮询设计

- 有事件推送、Webhook、消息队列或长连接时优先使用它们；没有可靠事件通道时才轮询。
- 使用指数退避和抖动，避免所有客户端在同一时刻打满服务；服务端返回 `Retry-After` 时遵守它。
- 每次轮询都带总截止时间、取消信号和最大次数；超时后返回“未知/待处理”，不要无限等待。
- 用任务 ID、版本号或 cursor 增量读取，保证重复响应不会重复执行副作用。
- 监控轮询 QPS、空响应率、任务完成延迟和取消率；任务状态接口应限流并可缓存。

## 心跳与租约

心跳只能证明“最近一次通信仍成功”，不能证明业务依赖健康。实现时明确：

- 发送周期、失效 TTL、允许丢失次数和重连策略，并考虑网络抖动和暂停造成的误判。
- 租约续期必须幂等；过期后的旧持有者不能继续写入，必要时使用 fencing token。
- 成员发现和领导选举要处理网络分区，不能把“收不到心跳”直接等同于“节点已宕机”。
- TCP keepalive、WebSocket Ping/Pong 和应用层心跳的检测范围、配置和故障语义不同，按协议文档验证。

## 健康检查

- **liveness**：进程是否需要重启；不应依赖易抖动的下游服务。
- **readiness**：实例是否具备接收业务流量的条件，可检查关键本地状态和必要依赖。
- **startup**：启动慢的服务先通过启动检查，再进入存活/就绪判断。
- 检查接口应轻量、鉴权、限频且不产生业务副作用；返回状态要能区分“不可用”“降级”和“未知”。
- 摘除、恢复、滚动发布和依赖故障都要在压测或故障演练中验证，防止检查风暴和级联摘除。

## 参考伪代码

```python
deadline = monotonic() + timeout
delay = initial_delay
while monotonic() < deadline and attempts < max_attempts:
    result = get_status(task_id, timeout=request_timeout)
    if result.done:
        return result
    sleep(with_jitter(delay))
    delay = min(delay * 2, max_delay)
    attempts += 1
raise TimeoutError("task status unknown")
```

伪代码只表达边界，不代表某个 SDK 的默认值。生产实现还要处理取消、服务端限流、时钟单调性、认证和错误分类。
