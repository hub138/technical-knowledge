# 消息投递与业务提交需要显式的一致性边界

业务数据写入数据库、事件发布到消息系统是两个独立动作。先写库再发消息可能漏发，先发消息再写库可能让消费者看到并不存在的事实。可靠系统要明确哪个状态是事实源，以及两个系统如何最终收敛。

## Transactional Outbox

应用在同一个本地事务中写业务事实和 outbox 记录；独立 relay 再把 outbox 发布到 broker。这样数据库提交后事件不会永久丢失，但 relay 崩溃会重复发布，所以消费者仍需幂等。

```text
数据库事务: business row + outbox event
                         ↓
                 relay 反复读取/发布
                         ↓
               broker 至少一次投递
                         ↓
          consumer inbox 去重 + 业务事务
```

事件 ID、聚合 ID、业务版本和 schema 版本必须稳定。把数据库行直接序列化成事件，会泄漏内部结构并使 schema 演进失控。

## 投递语义的真实边界

- **At-most-once** 可能丢，但不会由传输层重投；不代表下游没有重复业务请求。
- **At-least-once** 不丢已确认消息的目标下允许重复，消费者必须去重。
- **Exactly-once** 通常只在特定 broker、事务和消费者状态边界内成立。跨数据库、外部 API 和人工动作后，仍需幂等与对账。

消息顺序也只在明确分区或 key 内成立。扩分区、重试、并行消费和死信重放都可能改变观察顺序，业务状态要用版本或状态机拒绝旧事件。

## 积压、背压与重放

积压不是单个“队列长度”：要看最老消息年龄、生产/消费速率、分区倾斜、处理延迟、失败/重试和剩余保留期。扩消费者前先判断瓶颈是 CPU、数据库、外部依赖还是单 key 顺序。

重放历史消息前要确认消费者版本、schema 兼容、外部副作用和去重记录是否仍在。把死信直接批量塞回主队列，可能重复触发已完成操作或再次压垮依赖。

## 事件与命令

事件表达已经发生的事实，名称使用过去式且可被多个消费者观察；命令请求某个接收者执行动作，可能被拒绝。把命令伪装成事件会模糊所有权，把可变数据库快照称为事件则无法审计历史。

## 验证

- 在业务提交、outbox 发布、broker 确认和消费者提交的每个间隙注入崩溃。
- 重复、乱序和延迟投递同一事件，验证最终状态。
- 用旧/新 schema 双向兼容测试部署顺序。
- 在真实下游容量下制造积压，验证 admission、恢复时间和告警。
