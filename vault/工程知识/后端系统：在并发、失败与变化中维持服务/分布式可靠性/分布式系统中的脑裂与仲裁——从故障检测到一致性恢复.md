# 分布式系统中的脑裂与仲裁——从故障检测到一致性恢复

脑裂（split-brain）指集群中多个节点同时自认是主，各自接受写入，数据因此分叉。仲裁（quorum）是防止脑裂的核心机制：只有凑齐多数派同意的决定才生效，少数派一侧即使自选主（多节点中选出一个负责决策的主节点的过程）也无法提交写入。读完这篇你能说清脑裂难在哪：为什么发生、仲裁如何阻断它、以及仲裁之后一致性怎么恢复。

可以把它想成两个船长同时掌舵一艘船：一个说左满舵，一个说右满舵，船身同时往两个方向扭——船不会裂开，但航向记录从此对不上。这个比喻到「两个指令同时生效」为止。真实集群里脑裂的后果比航向分歧严重：数据分叉之后，无论以哪一侧为准都会丢失另一侧的写入，不可恢复的损失已经发生。

## 脑裂的三种典型成因

脑裂是故障检测不精确与仲裁机制缺失共同导致的结果，三类成因背后往往有多个因素叠加。以下三种场景各自独立，实际事故往往是它们的组合。

### 成因一：**心跳超时误判**

节点 A 是主，节点 B 和 C 是跟随者。网络抖动（性能指标不稳定的起伏）叠加心跳（节点定期互发的存活信号，超时收不到就判定故障）丢失，导致 B 和 C 在超时窗口内没收到 A 的心跳，B 发起选举，C 投票给 B，B 当选新主。此时 A 并不知道自己已被取代，继续接受写入。集群中出现两个主：

```text
时刻 1：A(主) ←→ B(从) ←→ C(从)  正常
时刻 2：A(主) ←✗→ B(从) ←→ C(从)  网络抖动，A 与 B、C 断开
时刻 3：A(主)          B(主) ←→ C(从)  B 当选新主，A 仍自认是主
```

心跳超时的时间窗口是脑裂的惯常成因。超时设得太短会因网络抖动频繁误判，设得太长则故障恢复慢。Raft（一种以易于理解著称的共识算法：靠领导者与日志复制达成多数派一致） 的随机超时机制（每个节点在 [T, 2T] 之间随机取超时值）降低了同时选举的概率，但没有消除误判本身——误判是心跳检测的固有属性，不是参数能完全解决的。

### 成因二：**网络分区下的双主**

网络设备故障把集群切成两个分区，每个分区内部都能通信，但分区之间完全隔离。如果两个分区都能凑齐多数派（例如 5 节点集群切成 3+2，3 节点一侧凑齐多数派），3 节点一侧选出新主，2 节点一侧的旧主虽然凑不齐多数派，但如果仲裁机制缺失或配置错误，它可能继续接受写入。

更危险的情况是偶数节点集群：4 节点切成 2+2，两侧都凑不齐多数派（都需要 3 票），但某些实现中如果配置了"允许单节点自选主"或仲裁机制被绕过，两侧可能同时自认主。

### 成因三：**时钟偏差与租约失效**

基于租约（lease）的主节点持有者依赖时钟同步。如果主节点的时钟比实际时间慢，它认为租约还有效时租约实际上已经过期，其他节点已经选举了新主。两个主同时存在，各自接受写入。

时钟偏差导致的脑裂比前两种更难排查，因为问题不在网络而在时间——监控系统看到的是网络正常、节点正常，只有对比各节点的时钟才能发现偏差。

## 仲裁如何阻断脑裂

仲裁是脑裂的阻断机制，不是一个可选的配置项。它的核心原理是：**任何两个多数派必然有交集**。

### 多数派交集的数学保证

N 节点集群，多数派大小为 floor(N/2) + 1。任意两个多数派的交集大小至少为 1：

```text
3 节点：多数派 = 2，任意两个 2 节点集合必有 1 个重叠
5 节点：多数派 = 3，任意两个 3 节点集合必有至少 1 个重叠
```

这个交集是共识安全性的数学基础：一个值被多数派持久化之后，后续任何多数派必然包含至少一个持有该值的节点，因此新选出的主不可能缺少已提交的数据。

### 仲裁在选举中的作用

选举本身也依赖仲裁：候选人必须获得多数票才能当选。这意味着：

- 3 节点集群中，候选人至少需要 2 票
- 5 节点集群中，候选人至少需要 3 票

分区时，只有包含多数节点的分区才能选出主。少数派分区即使自选主，也拿不到多数票，无法提交写入。这就是仲裁阻断脑裂的机制——少数派可以自认主，但提交任何写入都会被多数票拦下，数据分叉不会发生。

### 仲裁在写入中的作用

写入同样需要多数派确认。主节点把日志复制给所有跟随者，收到多数派确认后才提交。这意味着：

- 少数派分区内的主即使自认是主，也收不到多数派确认，写入无法提交
- 分区恢复后，少数派分区内未提交的写入被丢弃，已提交的写入由日志复制补齐

## 常见仲裁配置及其风险

### 奇数节点 vs 偶数节点

**奇数节点集群（3、5、7）是标准做法**。偶数节点集群（2、4、6）有对称分区风险：4 节点切成 2+2 时，两侧都凑不齐 3 票的多数派，集群整体不可写。偶数节点不增加安全性，只增加成本。

### 仲裁与可用性的权衡

节点数越多，容错能力越强，但写入延迟也越大（需要等更多节点确认）：

| 节点数 | 多数派大小 | 容忍故障数 | 写入延迟（等多数派确认） |
|--------|-----------|-----------|----------------------|
| 1      | 1         | 0         | 最低                 |
| 3      | 2         | 1         | 低                   |
| 5      | 3         | 2         | 中                   |
| 7      | 4         | 3         | 高                   |

5 节点集群容忍 2 个故障，但每次写入要等 3 个节点确认。如果写入延迟是关键约束，3 节点可能更合适。

### 仲裁绕过的危险

某些系统允许配置"允许单节点自选主"或"多数派可配置为 1"，这实际上**绕过了仲裁机制**。这种配置在开发测试环境中可以接受，但在生产环境中直接打开了脑裂的大门——网络分区时两侧都能自选主并接受写入，分区恢复后数据冲突无法自动解决。

## 一致性恢复：分区愈合后发生了什么

脑裂阻断之后，分区愈合时集群需要恢复一致性。恢复路径取决于仲裁机制是否完整执行。

### 场景一：仲裁完整执行，少数派无写入

多数派分区正常服务，少数派分区因凑不齐多数派而无法提交写入。分区愈合后：

1. 少数派分区中的节点发现更高 term 的 leader，自动降级为跟随者
2. 跟随者从 leader 同步日志，补齐分区期间错过的写入
3. 少数派分区中未提交的写入（如果有）被丢弃
4. 集群恢复正常，数据一致

这是最理想的恢复路径，数据不丢、不冲突。

### 场景二：仲裁被绕过，少数派有写入

少数派分区在分区期间接受了写入（例如配置了"允许单节点自选主"）。分区愈合后：

1. 两个分区都有已提交的写入，且写入互不兼容
2. 集群无法自动决定以哪一侧为准
3. 需要人工介入：选择一侧作为权威数据源，丢弃另一侧的写入
4. 被丢弃一侧的写入永久丢失

这是脑裂事故的典型后果。恢复路径取决于业务影响评估，业务决策先于技术选型——选择保留哪一侧的写入取决于业务影响评估。

### 场景三：仲裁完整执行，但少数派有未提交写入

少数派分区在分区期间接受了写入但未提交（因为凑不齐多数派）。分区愈合后：

1. 少数派节点发现更高 term 的 leader
2. 未提交的写入被回滚（日志被覆盖）
3. 节点从 leader 同步最新日志
4. 数据一致，未提交的写入丢失

这种丢失是设计预期的——**未提交的写入本来就没有对外可见**，丢失不会造成数据不一致。

## 仲裁之外：其他脑裂防护手段

仲裁是脑裂阻断的核心机制，但不是唯一手段。以下手段作为补充，在仲裁机制被绕过或配置错误时提供额外保护。

### Fencing Token（隔离令牌）

fencing token 是一个**单调递增的令牌**，每次主节点变更时递增。旧主持有的令牌比新主小，旧主尝试写入时，存储层拒绝令牌过期的写入。

fencing token 的实现方式：

```text
1. 新主当选时，从协调服务（如 ZooKeeper）获取一个递增的 fencing token
2. 新主写入数据时，将 fencing token 附在写入请求中
3. 存储层检查写入请求的 fencing token，拒绝令牌小于当前最大令牌的写入
4. 旧主即使自认是主，也因为令牌过期而无法写入
```

![fencing token 机制图：协调服务向新主发放 token 34、曾向旧主发放 token 33，新主携 34 写入被存储层接受，旧主携 33 写入因令牌小于最大令牌被拒绝（来源：自绘）](/static/figures/fencing-token-reject.svg)

fencing token 的防护范围仅限于写入被存储层拒绝，旧主仍然可以接受客户端请求并返回过时数据。因此 fencing token 必须与客户端感知的主节点变更配合使用。

### 隔离（Quarantine）

隔离是把疑似故障的节点从集群中移除，阻止它接受请求。隔离手段包括：

- 从负载均衡器中摘除节点
- 关闭节点的网络端口
- 重启节点进程

隔离的问题是它本身也依赖故障检测——如果故障检测误判，隔离会把健康节点移出集群，降低可用性。

### 预投票（Pre-Vote）

Raft 的预投票机制在正式选举之前先探询能否拿到多数票。如果候选人发现自己的日志落后于多数节点，或者集群中已经有活跃的主节点，它不会发起正式选举。预投票减少了不必要的 leader 变更，从而降低了脑裂的概率。

预投票不消除脑裂，但减少了因短暂网络抖动导致的 leader 频繁切换——这种切换是脑裂的前奏，因为每一次选举都打开了误判的窗口。

## 脑裂检测：事后发现

脑裂阻断是事前防护，脑裂检测是事后发现。即使仲裁机制完整，配置错误或实现 bug 仍可能导致脑裂。检测手段包括：

- **term 监控**：term 短时间内连续飘升是网络分区的迹象——分区使多个节点各自超时发起选举、term 各自递增
- **双主检测**：监控系统同时查询所有节点的主节点状态，如果发现多个节点自认是主，触发告警
- **数据一致性校验**：对比不同节点的数据校验和（对数据算出的指纹，用来发现传输或存储中的损坏），检测数据分叉

检测到脑裂之后，恢复路径取决于数据分叉的程度。轻度的分叉（少数未提交写入）可以自动恢复，严重的数据分叉需要人工介入。

## 脑裂与仲裁的工程实践

### 实践一：始终使用奇数节点

3 节点集群容忍 1 个故障，5 节点容忍 2 个；4 节点、6 节点买不来额外容错，还引入 2+2 对称分区的风险。

### 实践二：不要绕过仲裁

生产环境中不要配置"允许单节点自选主"或"多数派大小为 1"。这些配置在开发测试中方便，在生产中直接打开脑裂的大门。

### 实践三：监控 term 和主节点状态

term 频繁变化是网络不稳定的信号，双主告警是脑裂的最后防线。两者都应该配置告警。

### 实践四：使用 fencing token

在存储层实现 fencing token 检查，防止旧主在脑裂期间写入数据。这是仲裁机制被绕过时的最后一道防线。

### 实践五：验证分区行为

在故障演练中注入网络分区，验证集群在分区期间和分区愈合后的行为是否符合预期。验证要点：

- 分区期间少数派是否拒绝写入
- 分区愈合后数据是否一致
- 是否有数据丢失或冲突

## 自己动手验证

最小实验：用 etcd（分布式键值存储，Kubernetes 用它存集群状态）或 Raft 实现搭建 3 节点集群，注入网络分区，观察脑裂是否发生。

```bash
# 1. 启动 3 节点 etcd 集群
etcd --name node1 --initial-cluster node1=http://localhost:2380,node2=http://localhost:2381,node3=http://localhost:2382
etcd --name node2 --initial-cluster ...
etcd --name node3 --initial-cluster ...

# 2. 在 node1 上写入一个值
etcdctl put key1 value1

# 3. 注入网络分区：隔离 node1
iptables -A INPUT -s <node2-ip> -j DROP
iptables -A INPUT -s <node3-ip> -j DROP

# 4. 在 node1 上尝试写入（预期：被拒绝，因为凑不齐多数派）
etcdctl put key2 value2  # 请求超时（etcd 默认 5s），etcdctl 返回非零退出码

# 5. 在 node2 上写入（预期：成功，因为 node2+node3 是多数派）
etcdctl put key3 value3

# 6. 恢复网络分区
iptables -F

# 7. 检查 node1 是否同步了 key3（预期：已同步）
etcdctl get key3 --endpoints=http://localhost:2379
```

预期结果：分区期间少数派写入被拒绝，分区愈合后数据一致。如果少数派写入成功，说明仲裁机制被绕过或配置错误。

## 这套说法在哪儿会失效

- 本篇讲的是共识协议中的脑裂与仲裁。非共识系统（如 Gossip 协议、最终一致数据库）中的脑裂判定不同——它们允许临时不一致，最终通过冲突解决机制收敛，不需要严格的仲裁阻断。
- 仲裁阻断脑裂的前提是**多数派定义明确且所有节点遵守同一套仲裁规则**。混合版本集群或配置不一致时，仲裁规则可能被违反。
- 本篇假设网络分区是双向的。单向分区（A 能收到 B 的消息但 B 收不到 A 的消息）的脑裂风险更高，因为少数派节点可能误以为多数派仍然可达。
- fencing token 依赖存储层配合实现。如果存储层不支持 fencing token 检查，fencing token 无法阻止旧主写入。
