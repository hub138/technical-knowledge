# 凭据的生命周期决定泄露半径：签发、注入、轮换、吊销的闭环

**凭据（credential，访问某个系统所需的密钥、令牌或口令）一旦存在，泄露只是时间问题——工程能控制的是泄露半径：多少凭据会被一起带走、多久能被发现、多久能换掉**。 读完你能回答：**为什么凭据不能进环境变量之外的地方、轮换为什么必须是零停机操作、吊销链路缺失的凭据为什么等于永久授权**。

## 要解决的问题

数据库密码、API key、签名密钥、云厂商 access token——每一项凭据都经历同一生命周期：**签发 → 注入 → 使用 → 轮换 → 吊销**。**生命周期任何一环缺失，泄露半径就从「一把钥匙」放大成「一个系统」**：

- **签发不做有效期：凭据永久有效，泄露后无法靠时间自愈**；
- **注入进代码仓库或镜像：一次 push，全世界可见，Git 历史里永久残留**；
- **轮换不能在线做：换一次密码要停机，于是永远不换**；
- **吊销没有执行路径：知道泄露了也换不掉**。

**安全设计的单位因此不是「凭据是否安全」，是泄露半径 × 发现时长 × 修复时长**。**三项都小的凭据体系才成立**。

## 机制：四环各自的最小标准

### 签发：短有效期是默认

**长期凭据是给人的，服务间调用一律短时效令牌（几分钟到几小时），到期自动重取**。**有效期短意味着泄露的影响窗口与 TTL 同长**——**令牌体系里 access token 短 TTL + refresh token 可撤销的组合在这里通用**。

### 注入：运行时获取，不落任何静态处

**凭据只允许在运行时从密钥管理系统（KMS/Secret Manager/Vault）取进内存，禁止出现在三类地方：代码与配置文件（进 Git 就进历史）、容器镜像（镜像分发给所有人）、CI 日志（构建输出常被完整保存）**。**环境变量是通行做法但仍有残留面——进程崩溃转储、子进程继承**；**更严格的边界是凭据代理模式：进程不拿原始凭据，调用本地代理代签**。

### 轮换：新旧并存的双密钥过渡

零停机轮换的标准结构：**新凭据签发后，验证方同时接受新旧两把（密钥带 kid 标识），消费方逐步切换，全量切换后撤销旧凭据**。**JWT 的 kid 字段、数据库的双账号过渡、云密钥的版本化都是这条结构的实例**。**轮换不能在线执行等于没有轮换——验收标准是演练：触发一次真实轮换，服务全程无感知**。

### 吊销：知道泄露到失效的时长要可测

吊销链路的最小闭环：**泄露检测（扫描与告警）→ 一步执行的撤销命令 → 验证撤销生效**。**缺任何一环，「撤销」只是文档里的名词**。**数据库密码的吊销要连着连接池（已建立的连接不自动断），令牌吊销要连着黑名单或 TTL——每类凭据的吊销机制不同，写进运维手册才有执行价值**。

## 怎么测

- **仓库扫描：gitleaks/trufflehog 全历史扫描清零，CI 挂钩防新增**。
- **轮换演练：每季度对核心凭据执行一次真实轮换，服务无感知为通过标准**。
- **吊销计时：从「模拟泄露」到「凭据失效」的全程计时，超过预设阈值（如 15 分钟）即整改**。
- **镜像与日志审计：抽查镜像层与 CI 日志，确认无凭据残留**。

## 哪些认识一看就错

- **「环境变量足够安全」——它防的是进仓库，防不了崩溃转储与子进程继承；按威胁等级选注入方式**。
- **「轮换有计划文档就行」——不能在线执行的轮换计划等于没有，演练是唯一验收**。
- **「内部系统凭据不用管」——横向移动首选内部弱凭据，泄露半径按攻击者视角算，不按网络边界算**。
- **「密钥泄露了改掉就行」——改掉的密钥签发的令牌仍在有效期内，吊销要覆盖签发物而不只是签发源**。

## 效果从哪来、要付什么代价

**短 TTL 把影响窗口压到分钟级，运行时注入消灭静态残留，双密钥过渡让轮换变成常态动作，可测的吊销链路把「知道泄露」与「损失终止」之间的时长变成可核算指标**。**代价是基础设施与流程：密钥管理系统、每季度的轮换演练、CI 扫描门禁——都是一次搭建、长期摊销的成本**。**泄露半径小的系统被拖库后是「换一批凭据」，泄露半径大的是「重置整个信任域」，差价就是这套体系的采购价**。
