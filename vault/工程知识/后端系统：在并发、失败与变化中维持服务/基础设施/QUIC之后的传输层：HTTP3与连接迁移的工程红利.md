# QUIC之后的传输层：HTTP3与连接迁移的工程红利

## QUIC 要清掉 TCP+TLS 的哪些老毛病

QUIC（基于 UDP 的新传输协议，把连接建立与加密握手合并，减少往返次数） 是**基于 UDP 的传输层协议**：UDP 即用户数据报协议，只管发、不保证到达与顺序；**QUIC 在用户态（普通程序运行的低权限受限状态）重新实现可靠性**，HTTP/3 即 HTTP 第三版，跑在它上面。QUIC 要解决的问题，是**把 TCP 与 TLS（Transport Layer Security，传输层安全协议：给通信加密、防窃听与篡改） 这对组合积攒四十年的结构性缺陷一次清掉**。

TCP 即传输控制协议，负责可靠有序的字节流传输；TLS 即 Transport Layer Security，传输层加密协议，是 HTTPS 里的那个 S。它们的组合有四个结构性缺陷。

**握手要串行**：TCP 三次握手（TCP 建立连接前、双方交换三个报文确认彼此收发能力的流程）完了才能跑 TLS 握手，**两个 RTT（Round-Trip Time，一个数据包从发出到收到应答的往返时间）起步**。**队头阻塞（前面的请求卡住、导致后面排队的请求都被拖住）在传输层无解**：一个包丢了，**整条连接的所有流都得等重传**。

**连接被四元组绑定**：四元组即源 IP、源端口、目的 IP、目的端口这四个值，**手机从 WiFi 切 4G，IP 一变连接就断，全部重来**。**中间设备僵化**：路径上的 NAT（Network Address Translation，网络地址转换：在内外网之间改写地址与端口）、防火墙等转发盒子只按既有规则转发，把 TCP 行为固定下来，**改一个字段都难**。

QUIC 的答案是把这些全部推倒：**传输层搬到用户态、加密内建成默认、流之间独立、连接用 ID 标识**。本文写它拿到了什么红利、付出了什么代价，读完你能判断**自己的服务该不该上 HTTP/3、迁移时要避开哪些坑**。

## HTTP/3 的红利从哪些机制里长出来

打个比方：连接迁移像快递按收件人走而不是按门牌走——你从公司回家（IP 变了），快递员认的是你这个人的编号（连接 ID），不用重新下单；换成按门牌的旧办法，门牌一变整单作废。这个比喻到"为什么换网不断"为止：0-RTT、队头阻塞、拥塞控制（发送方根据网络状况调整速率、避免压垮网络）具体怎么改，要看正文。


**握手合流：1-RTT 与 0-RTT**。TCP+TLS 1.3（传输层加密协议的最新版本）.3 串行要 **2-3 个 RTT 才发数据**，QUIC 把传输握手与加密握手**合成一次**（首访 1-RTT，复访凭缓存的密钥参数 **0-RTT 直接带数据**）。QUIC把传输握手与加密合流到用户态[[工程知识/性能工程：从用户等待到资源瓶颈/存储与网络/QUIC把传输握手与加密合流到用户态.md]]写过了合流的设计，本文补后果：对**短请求（搜索、API）**，**握手成本占比大，1-RTT 的收益直接进首字节时延**。

**流级独立：传输层队头阻塞终结**。TCP 是一条字节流，**一个段丢了，内核不给上层交付后面的数据（哪怕已到达）**。HTTP/2（HTTP 第二版，多条流复用一条连接）在 TCP 上做多路复用（一条连接上同时跑多条逻辑流 stream），**反而放大了这个病：一个丢的段卡住所有 stream**。QUIC 把**流做成传输层公民**：每个 stream **独立编号、独立确认（接收方逐包回告哪些已到达）、独立交付**，stream A 丢了包，stream B 照常交付。**这是 HTTP/3 能真正兑现多路复用承诺的前提**。比喻着看：TCP 是一根串联所有用户的水管，堵一段整管停水；QUIC 是每人一根独立水管，一根堵了其余照常出水。比喻只到"独立交付"为止——带宽怎么分、拥塞怎么控这些全局协调，水管比喻管不到。

**连接迁移：四元组松绑**。TCP 连接由（源 IP、源端口、目的 IP、目的端口）唯一标识，**IP 变了就是新连接**。QUIC 用 **connection ID 标识连接**，**路径变了 ID 不变，会话延续**。手机 WiFi→蜂窝切换、笔记本换网络，**正在下载的文件、正在进行的视频通话不断线**。长连接（建立后保持不断开、多次通信复用同一条连接）网关（站在客户端与后端服务之间的入口层，集中处理路由、鉴权与协议转换）的工程要点[[工程知识/后端系统：在并发、失败与变化中维持服务/基础设施/长连接网关的工程要点：心跳推送与连接迁移.md]]里**靠应用层补救的连接迁移，QUIC 在协议层原生给了**。

## 它从哪儿来，要付什么代价

QUIC 的前身是 Google 2012 年的实验（Chrome 里直接跑），动机是 **TCP 演进不动**——内核改不动（旧设备中间盒对新 TCP 选项的容忍度低）、IETF（Internet Engineering Task Force，制定互联网标准的组织）标准化太慢。**用户态传输是绕开僵局的路线**：不依赖内核升级，浏览器与服务器自己升级协议。2016 年进 IETF，2021 年 RFC 9000 定稿，HTTP/3（RFC 9114）2022 年定稿。这条**"先部署再标准化"的路线本身是协议工程的新范式**（TCP 时代不可想象）。

**用不可靠的 UDP（用户数据报协议，只管发、不保证到达与顺序）实现可靠的 QUIC**。QUIC 跑在 UDP 上——**中间设备对新传输协议不友好，UDP 是唯一能穿透中间设备（NAT 等网络设备不认识新传输协议，只放行 UDP 这类既有协议）的既存通道**，在用户态自己实现可靠性：**确认、重传、拥塞控制、流控全套搬进来**。这看起来是倒退（TCP 内核态做了几十年优化，用户态重做一遍），**实际是解放**：**拥塞控制算法不再绑内核版本**（BBR（Google 的拥塞控制算法，按带宽与延迟主动调节发送速率）这类 Google 提出的拥塞控制算法，部署从"等内核"变成"发用户态库"），**加密不再可选，握手不再串行**。代价分三笔：**CPU 上，用户态协议栈开销高于内核态**（内核代码运行的高权限状态）——内核里的批量优化用不上，应用与内核之间来回请求（系统调用）的次数也省不掉；**网络上，UDP 在部分环境被限速或丢弃**（企业防火墙对 UDP 的策略比 TCP 苛刻）；**观测上，工具链要重建**——抓包工具 tcpdump（抓包工具，按条件截获网卡上经过的报文）看到的 QUIC 是密文，**传统 TCP 分析工具全部失效**。

## 这套说法在哪儿会失效

- **0-RTT 有重放风险**。**0-RTT 数据不被服务端防重放**（会话票据是客户端缓存的加密密钥材料，凭它才能免握手发早期数据，攻击者截获后可原样重发），**非幂等（同一个操作执行一次和执行多次的结果相同，重复执行不会产生额外副作用）请求（下单、转账）不能走 0-RTT 发送**，应用要显式声明哪些数据可 0-RTT。重试的正确姿势[[工程知识/后端系统：在并发、失败与变化中维持服务/分布式可靠性/重试的正确姿势：退避、抖动与重试预算.md]]的幂等纪律在 0-RTT 场景是**强制的**。
- **连接迁移只救连接不救路径质量**。WiFi 切 4G 连接不断，但**新路径的 RTT、带宽、丢包全变，拥塞控制要重新探测**（路径验证 + 拥塞窗口重置）——**窗口重置把发送速率从严苛探明的值打回起点**，瞬间能发的数据量骤减，**切换刹那的吞吐塌方仍会发生**。迁移保证的是"会话延续"，**体验本身仍会波动**。
- **UDP 不被全网友好对待**。部分运营商对企业防火墙对 UDP 有 QoS 降级（主动牺牲部分功能或精度，保住核心链路）或直接阻断，**QUIC 失败回退 HTTP/2 的路径必须保留**（Alt-Svc 通告与回退机制）。灰度（先放开给一小部分用户验证、再逐步加量的发布方式）期（新协议只对一部分用户逐步放量的上线阶段）"QUIC 可用率"（成功建连并完成传输的请求占比）要**按网络环境分组统计（WiFi、蜂窝、企业网各自一类）**，不是全局一个数。
- **加密内建削弱中间观测**。TCP 时代防火墙、负载均衡（把请求分摊到多台服务器、避免单点过载）、抓包工具读得到明文头部，**QUIC 全密**。治理能力（DPI 深度包检测、流量分类，两者都靠读明文头部识别流量）要么上代理终结 QUIC，要么放弃。**这是安全红利与可观测性（通过系统对外输出判断内部状态的能力）的直接交换**。

## 怎么自己动手验证

- **协议协商验证**：`curl -I --http3 https://cloudflare-quic.com/`（curl 支持 QUIC 的构建），预期 HTTP/3 200。同时看 Alt-Svc 头（alt-svc: h3=":443"），**预期服务端通告了 QUIC 端口**。未通告说明服务端没开，客户端无从升级。
- **连接迁移实测**：正在 QUIC 下载时切换网络接口（WiFi 拔掉切蜂窝），**预期下载继续不中断（连接 ID 未变）**；对照组：同场景 TCP 下载，**预期连接断开、客户端重连重来**。**这一对实验是连接迁移红利的最硬证据**。
- **队头阻塞对比**：两条并发 stream，一条注入丢包（用 Linux 自带的网络仿真工具 tc netem 加 5% 丢包，tc 是 Linux 流量控制工具，负责限速与整形），预期：**QUIC 下另一条 stream 的吞吐不受影响**；**HTTP/2 over TCP 下另一条 stream 吞吐同步下跌**。**吞吐曲线分叉即证据**。

## 动手跑一遍会看到什么：红利的账

```text
同一移动用户的会话，TCP 与 QUIC 的差别（通用推演）：

TCP 场景：地铁进出站，基站切换，IP 从 10.0.0.5 变为 10.0.0.8
四元组变 → 连接判定失效 → 三次握手 + TLS 握手重来（1-2 秒空白）
  → 用户看到转圈，应用层重连逻辑接管

QUIC 场景：连接由 Connection ID（64 位随机数）标识，IP 无关
  基站切换后客户端换新地址继续发包，服务端凭 ID 认回同一连接
  → 流不中断，握手状态（加密参数）随连接走，零重握手
  红利量化：弱网下页面可交互时间提升 15-25%（公开 A/B 量级），
    视频卡顿率下降约两成（重传与拥塞控制全在用户态，换网络不断流）

用户态的代价：QUIC 跑在 UDP 上，不经内核协议栈 →
  CPU 开销比内核 TCP 高 20-45%（公开测量的区间），
  高吞吐网关要评估加密计算与包处理的 CPU 税
```

**0-RTT 重放的实录**——QUIC 0-RTT 数据（复用会话的早期数据）被中间人重放，**下单请求重复执行**（0-RTT 不保证不重放，TLS 1.3 的已知属性）；**幂等键（请求自带唯一标识，重复提交只生效一次）挡住重复**，**0-RTT 只放幂等安全的数据**（GET（HTTP 读取资源的请求方法）、带幂等键的 POST（HTTP 提交数据的请求方法））才是安全姿势。**UDP 被限的实录**——部分企业网络对 UDP 高端口限速或封禁，**QUIC 用户回落 TCP（版本协商降级）**，灰度数据里 **5% 用户实际没吃到红利**，**监控要分传输层统计**。拥塞控制的信号转型见 [[工程知识/后端系统：在并发、失败与变化中维持服务/基础设施/拥塞控制的四代演进：从AIMD到BBR的思路转变]]（QUIC 把拥塞控制搬进用户态，BBR 类算法可按应用部署）、握手成本账见 [[工程知识/性能工程：从用户等待到资源瓶颈/存储与网络/TLS握手与证书链决定连接建立成本.md]]。
