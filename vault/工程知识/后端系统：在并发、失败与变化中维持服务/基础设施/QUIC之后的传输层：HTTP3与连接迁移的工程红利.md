# QUIC之后的传输层：HTTP3与连接迁移的工程红利

## 要解决的问题

QUIC 要解决的问题，是把 TCP+TLS 这对组合积攒四十年的结构性缺陷一次清掉：握手要串行（TCP 三次握手完了才能跑 TLS 握手，两个 RTT 起步）、队头阻塞在传输层无解（一个包丢了，整条连接的所有流都得等重传）、连接被四元组绑架（手机从 WiFi 切 4G，IP 一变连接就断，全重来）、中间设备僵化（NAT 与防火墙把 TCP 行为焊死，改一个字段都难）。QUIC 的答案是把这些全部推倒：传输层搬到用户态、加密内建成默认、流之间独立、连接用 ID 标识。本文写它拿到了什么红利、付出了什么代价。

## 红利的机制来源

**握手合流：1-RTT 与 0-RTT**。TCP+TLS1.3 串行要 2-3 个 RTT 才发数据，QUIC 把传输握手与加密握手合成一次（首访 1-RTT，复访凭缓存的密钥参数 0-RTT 直接带数据）。QUIC把传输握手与加密合流到用户态（见 [[工程知识/性能工程：从用户等待到资源瓶颈/存储与网络/QUIC把传输握手与加密合流到用户态.md]]）写过了合流的设计，本文补后果：对短请求（搜索、API），握手成本占比大，1-RTT 的收益直接进首字节时延。

**流级独立：传输层队头阻塞终结**。TCP 是一条字节流，一个段丢了，内核不给上层交付后面的数据（哪怕已到达）。HTTP/2 在 TCP 上做多路复用，反而放大了这个病：一个丢的段卡住所有 stream。QUIC 把流做成传输层公民：每个 stream 独立编号、独立确认、独立交付，stream A 丢了包，stream B 照常交付。这是 HTTP/3 能真正兑现多路复用承诺的前提。

**连接迁移：四元组松绑**。TCP 连接由（源 IP、源端口、目的 IP、目的端口）唯一标识，IP 变了就是新连接。QUIC 用 connection ID 标识连接，路径变了 ID 不变，会话延续。手机 WiFi→蜂窝切换、笔记本换网络，正在下载的文件、正在进行的视频通话不断线。长连接网关的工程要点（见 [[工程知识/后端系统：在并发、失败与变化中维持服务/基础设施/长连接网关的工程要点：心跳推送与连接迁移.md]]）里靠应用层补救的连接迁移，QUIC 在协议层原生给了。

## 背景与代价

思想背景：QUIC 的前身是 Google 2012 年的实验（Chrome 里直接跑），动机是 TCP 演进不动——内核改不动（旧设备中间盒对新 TCP 选项的容忍度低）、IETF 标准化太慢。用户态传输是绕开僵局的路线：不依赖内核升级，浏览器与服务器自己升级协议。2016 年进 IETF，2021 年 RFC 9000 定稿，HTTP/3（RFC 9114）2022 年定稿。这条"先部署再标准化"的路线本身是协议工程的新范式（TCP 时代不可想象）。

最精巧的一笔是**用不可靠的 UDP 实现可靠的 QUIC**。QUIC 跑在 UDP 上（因为中间设备对新传输协议不友好，UDP 是唯一能穿透的既存通道），在用户态自己实现可靠性：确认、重传、拥塞控制、流控全套搬进来。这看起来是倒退（TCP 内核态做了几十年优化，用户态重做一遍），实际是解放：拥塞控制算法不再绑内核版本（BBR 部署从"等内核"变成"发用户态库"），加密不再可选，握手不再串行。代价要摆明：用户态协议栈的 CPU 开销高于内核态（系统调用省了但失去了内核的批量优化），UDP 在部分网络环境被限速或丢弃（企业防火墙对 UDP 的策略比 TCP 苛刻），运维观测工具链要重建（tcpdump 看到的 QUIC 是密文，传统 TCP 分析工具全部失效）。

## 边界

- **0-RTT 有重放风险**。0-RTT 数据不被服务端防重放（拿到的会话票据可重放早期数据），非幂等请求（下单、转账）不能走 0-RTT 发送，应用要显式声明哪些数据可 0-RTT。重试的正确姿势（见 [[工程知识/后端系统：在并发、失败与变化中维持服务/分布式可靠性/重试的正确姿势：退避、抖动与重试预算.md]]）的幂等纪律在 0-RTT 场景是强制的。
- **连接迁移只救连接不救路径质量**。WiFi 切 4G 连接不断，但新路径的 RTT、带宽、丢包全变，拥塞控制要重新探测（路径验证 + 拥塞窗口重置），切换瞬间的吞吐塌方仍会发生。迁移保证的是"会话不死"，不是"体验不变"。
- **UDP 不被全网友好对待**。部分运营商对企业防火墙对 UDP 有 QoS 降级或直接阻断，QUIC 失败回退 HTTP/2 的路径必须保留（Alt-Svc 通告与回退机制）。灰度期"QUIC 可用率"要按网络环境分桶监控，不是全局一个数。
- **加密内建削弱中间观测**。TCP 时代防火墙、负载均衡、抓包工具读得到明文头部，QUIC 全密。治理能力（DPI、流量分类）要么上代理终结 QUIC，要么放弃。这是安全红利与可观测性的直接交换。

## 验证

- **协议协商验证**：`curl -I --http3 https://cloudflare-quic.com/`（curl 支持 QUIC 的构建），预期 HTTP/3 200。同时看 Alt-Svc 头（alt-svc: h3=":443"），预期服务端通告了 QUIC 端口。未通告说明服务端没开，客户端无从升级。
- **连接迁移实测**：正在 QUIC 下载时切换网络接口（WiFi 拔掉切蜂窝），预期下载继续不中断（连接 ID 未变）；对照组：同场景 TCP 下载，预期连接断开、客户端重连重来。这一对实验是连接迁移红利的最硬证据。
- **队头阻塞对比**：两条并发 stream，一条注入丢包（tc netem 5% loss），预期：QUIC 下另一条 stream 的吞吐不受影响；HTTP/2 over TCP 下另一条 stream 吞吐同步下跌。吞吐曲线分叉即证据。
