# 代理后的真实IP要靠协议传递：X-Forwarded-For的信任边界与PROXY protocol

**反向代理终结了 TCP 连接，应用看到的来源地址永远是代理的 IP；真实客户端 IP 必须由协议字段传递，而任何可伪造的传递字段都必须在受信任的代理链内逐跳重写**。 读完你能回答：**XFF 头为什么逐个追加而不是覆盖、信任哪一跳由什么决定、PROXY protocol 解决什么 XFF 解决不了的问题**。

## 要解决的问题

应用在 Nginx/负载均衡后面，`socket.remote_addr` 是代理的地址。**限流、审计、风控、地理定位全都需要真实客户端 IP，于是代理把原始地址写进 HTTP 头传给应用**。**问题从「怎么传」变成「怎么传才可信」：头是请求的一部分，客户端可以自己带上一个假的 `X-Forwarded-For`——代理的处理方式决定了这个假值会不会一路骗到底**。

## 机制：XFF 的追加语义与信任链

### 逐跳追加与信任右端

XFF 头的规范语义是**每经过一代理，把自己的上游地址追加到列表右端**：

```text
客户端 1.2.3.4 → 代理A → 代理B → 应用
X-Forwarded-For: 1.2.3.4          （代理A写）
X-Forwarded-For: 1.2.3.4, 10.0.0.5（代理B追加）
```

攻击者首发请求自带 `X-Forwarded-For: 9.9.9.9` 时，列表变成 `9.9.9.9, 1.2.3.4, 10.0.0.5`——**伪造值永远在左端，真实链路在右端**。**取哪个值由「信任多少跳代理」决定**：应用前面有两层可信代理，就取右数第三个（第一层代理的入方向地址）。**Nginx 的 `real_ip` 模块把这个规则实现为 `set_real_ip_from`（可信代理列表）+ `real_ip_header` + `real_ip_recursive on`，逐跳向左回溯、跳过可信段、在第一个不可信地址停住**。**默认取最左是错的——那是攻击者可自由填写的位置**。

### PROXY protocol：在 HTTP 之下传，伪造面更小

XFF 只覆盖 HTTP，且头与应用逻辑混在同一层。PROXY protocol（HAProxy 定义）在 TCP 层发一个固定格式头：**连接建立瞬间，代理先发 `PROXY TCP4 <源IP> <目的IP> <源端口> <目的端口>` 再转应用数据**。**好处两条：对后端协议透明（HTTP、gRPC、Redis 都能带），头在连接建立时由可信代理写入、客户端无法预先注入**。**代价是后端必须显式支持解析**，且**只允许在可信链路启用——对公网直连的端口启用它，任何人都能发个假头**。**v2 版本还带 TLS 信息与命名空间扩展**。

### 判定句

**来源 IP 是凭据，凭据的可信度等于传递链上最弱一环。** **HTTP 头字段默认不可信，信任必须显式配置在「网络位置」（哪些地址是可信代理）上，而非「字段名」上**。

## 案例：CVE-2024-51504 的信任错位

[[工程知识/缺陷分析：从个案到体系/安全/案例五：安全两例——认证绕过与带漏洞依赖]] 里 ZooKeeper 的认证绕过，根子是**把 XFF 头当成了认证输入：信任了攻击者可控的 header，鉴权形同虚设**。**这是 XFF 信任边界错位的最严重形态——来源 IP 不该参与认证判定（认证该由密码学凭据完成），IP 的合法用途是限流与审计这类「尽力而为」的场景**。**头部信任与凭据信任的分界，正是那道被跨过的线**。

## 怎么测

- **伪造测试：自带假 XFF 头的请求经全链路到达应用，日志里记录的 IP 必须仍是真实客户端地址（证明逐跳重写生效）**。
- **递归校验：双层代理场景下逐个 IP 段验证 `set_real_ip_from` 配置，确认只信任了实际代理网段**。
- **协议层验证：PROXY protocol 后端直连（绕过代理）发送连接必须被拒或按默认策略处理，证明启用范围受控**。
- **审计回放：用真实攻击样本（扫描器流量）回放，确认风控与限流记录的 IP 归属正确**。

## 哪些认识一看就错

- **「取 XFF 第一段就是真实 IP」——第一段在客户端手里，取右端并按信任跳数回溯才是规范读法**。
- **「上 HTTPS 请求头就可信」——TLS 保护的是传输，不改变「头可被客户端填写」的事实；信任边界在代理配置，不在加密**。
- **「内网代理不用配」——内网被攻破后伪造头横向利用是常见路径，可信列表按网段配置，与内外无关**。
- **「PROXY protocol 更高级所以全开」——后端不解析时它是语法错误；对不可信来源启用等于把伪造面从 HTTP 头挪到 TCP 层**。

## 效果从哪来、要付什么代价

**逐跳重写让伪造值只能在链路左端自说自话，显式的可信代理列表把「信谁」变成配置事实，PROXY protocol 把传递下沉到协议无关的连接层**。**代价是每一层代理都要参与维护**（少配一层，链路就断），**后端要显式支持 PROXY protocol 解析**，**CDN/云负载均衡的场景还要对齐各自的自定义头**（如 `X-Real-IP`、`CloudFront-Viewer-Address`）——**多一跳服务商，就多一个头要配置映射**。
