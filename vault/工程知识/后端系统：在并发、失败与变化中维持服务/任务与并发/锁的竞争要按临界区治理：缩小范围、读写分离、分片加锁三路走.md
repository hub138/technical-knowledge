# 锁的竞争要按临界区治理：缩小范围、读写分离、分片加锁三路走

> **要点**：锁竞争像多人抢一间只剩一把钥匙的房间，**排队等人越多越堵**——**性能悬崖不在锁本身，在临界区**（一段必须串行互斥执行的代码）——治理三路：**缩小临界区**（只护真正共享的写操作，慢调用移出锁外）、**读写分离**（读多写少用读锁并行）、**分片加锁**（按 key 分片把全局锁变局部锁）；每路的前提是**先定位竞争点**（哪个锁、哪段代码、竞争度多少），三路可叠加。

## 锁竞争到底卡在哪、为什么非得按临界区治理？

三路走对应三种不同的成因：



服务在低并发下正常、并发上来后**吞吐不升反降**（线程堆栈全在等同一把锁）——**锁竞争（多个执行流争抢同一把锁造成的等待开销）把多核机器退化成单核**。这题到底在解决什么：性能瓶颈为何常在临界区而非锁本身，以及定位竞争点后怎么在三路治理里选型。本库任务与并发域"案例三十七"给过一个争用案例；本篇展开成完整的治理方法：**竞争的度量（怎么确认瓶颈是锁）、三路治理各自的适用前提与交换、常见反模式**——锁竞争的诊断意义在于它伪装成容量问题**（"加机器"救不了它：瓶颈是单进程内那一把锁，**加机器不增加进程内的并行度，跨进程场景也常常无效）。

## 怎么先定位竞争点、再用哪三路治理？

打个比方：锁像只有一把钥匙的洗手间——队伍排得长，因为每个人占用它的时间太长，而不是因为洗手间不够。缩小临界区是让每个人少待一会儿，读写分离是让只是看一眼的人不用排队，分片加锁是多开几间。这个比喻到"三种办法各解决什么"为止：具体哪段代码该放进临界区、读写锁（允许多读并发、写时独占的锁）的饥饿（参与者长期抢不到资源、一直被推迟）问题、分片怎么选键，要看正文。


**定位与度量**：竞争的确认靠三类证据——线程转储的锁等待分布（大量线程 BLOCKED，这是 Java 线程状态，表示正在等锁，集中在同一把锁上）、性能分析的锁竞争热点（profiler 的 lock contention 视图）、竞争度指标（锁的等待队列长度、等待时间占比）。**先确认竞争存在与位置，再谈治理**——"感觉有锁就优化锁"是**过早优化的变体**。

线程转储里 BLOCKED 线程长什么样，真实面板给一个样例（BLOCKED 即正在等锁的线程状态）：

![perfmatrix：BLOCKED 线程的锁持有调用栈与依赖图](/static/figures/thread-dump-blocked-thread-stack-trace.png)

上图取自 [perfmatrix 的线程转储分析页](https://perfmatrix.com/thread-dump-analysis/)：其中标 `- locked` 的是持锁线程的调用栈快照（锁地址就写在旁边），另一张是依赖图把阻塞关系连成一串——定位锁竞争时看到的就是这两样。

**第一路：缩小临界区**。锁内的代码只留**"必须互斥的共享状态读写"**，其余全部移出——**锁内出现 IO、网络调用、长计算是竞争的头号放大器**（一把锁的持有时间从微秒变毫秒，竞争度放大千倍）。缩小后的收益：持锁时间缩短 → 等待队列变短 → 吞吐回升；交换：代码结构变复杂（锁内外分段），正确性要求不变。上游 BookKeeper 的一个复现修复是缩小 LedgerHandle 的 metadataLock 持有范围（把元数据锁内的非必要操作移出）——同一手法的上游实践。

**第二路：读写分离**。读多写少的共享状态用读写锁（读锁共享、写锁独占）——**适用前提是读远多于写**（写占比超过两三成时读写锁的管理开销反超收益），且读操作只需共享读锁、读临界区内无写穿插，就能拿到一致性快照（读到的数据像某一时刻拍下的照片，不会读到写了一半的中间状态——前提是写路径也遵守同一把锁）。JDK（Java Development Kit，Java 开发工具包）的StampedLock 提供乐观读（无锁读 + 版本验证），读占比极高的场景收益更大，代价是 API 更复杂、误用面更大。

**第三路：分片加锁**。全局一把锁按 key 分片成 N 把（按 hash 取模选锁）——竞争从全局降到分片内，**可同时进行的分片数约等于分片数**，**吞吐近似随分片数上升**。适用前提：**操作只涉及单个 key 的状态**（跨 key 操作要么用全局锁、要么设计多锁获取顺序防死锁）；交换：跨 key 操作的复杂度、分片数的选择（太少竞争降不够、太多内存与上下文开销）——**分片数按竞争度目标反推**（如"单分片竞争度 < 10%"）。

**三路叠加的顺序**：先缩小（所有场景的第一步）、再分片（把竞争分散）、读写分离（对读多场景）——**缩小是前提**：临界区不缩，分片只把大临界区复制 N 份。

同一把锁，临界区里藏没藏长动作，结局分岔见下面这张图：

## 读完这一段你能判断什么：常见反模式与边界

**三个反模式**：锁内调用外部服务（持锁做 RPC——Remote Procedure Call，远程过程调用：像调本地函数一样调远端服务——**持锁时间不受自己控制**）；锁的粒度漂移（起初护一行，后来顺手护了整个方法，没人收窄）；双检锁的失效实现（无 volatile/内存屏障的懒加载，检查通过但对象可能还没初始化完）——**反模式的共同点是一把锁承担了两种职责**（互斥 + 可见性/时序），职责分开后方案自然清晰。

**竞争与死锁（多个执行流互相等待对方释放资源）的分界**：竞争是性能问题**（等得久但会来），死锁是**正确性问题（永远不来）——分片加锁引入多锁获取时，**固定获取顺序**（按 key 全序）防死锁，这条纪律写进代码评审清单。

**跨进程的锁**：单进程内的锁治理三路不直接适用于跨进程（分布式锁、数据库行锁）——分布式锁的持锁成本更高（**网络往返**），**跨进程场景优先用无锁的原子机制**（CAS：一条原子指令完成读取、判断、写入；队列串行化让单个消费端天然串行），锁是最后手段。

## 怎么自己动手验证三路治理真的有用？

可复现的验证路径：

1. 竞争复现：并发压测临界区含 IO 的服务，预期吞吐在并发超过核数后不升反降、线程转储显示 BLOCKED 聚集——竞争形态复现；
2. 治理验证：按三路逐一改造后重压，预期吞吐按治理路数放大（缩小的收益看持锁时间下降、分片的收益看分片数比例）；
3. 正确性验证：分片 + 并发写同一 key 的竞态（多个执行流争抢资源、结果取决于时序）测试（多线程对同一 key 并发操作，断言结果一致）——分片不引入正确性回退；
4. 断言锚点：**锁的持锁时间有性能分析基线（正常状态下的指标水平、用来对比异常）、竞争度指标（等待队列/等待占比）进监控、多锁获取的顺序纪律在评审清单**——三项齐备，锁竞争从"并发一高就悬"变成按度量治理的常规项。

```text
度量断言 = 持锁时间与等待占比有基线
治理断言 = 三路改造后吞吐可量化
纪律断言 = 多锁顺序进评审清单
```

锁竞争的治理顺序是度量先行、缩小打底、分片与读写分离按场景叠加**——三路走完，**多核的吞吐才真正兑现成服务的容量。
