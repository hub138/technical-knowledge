# 长任务把请求与结果拆成两个资源：202、状态端点与终态迁移

视频转码、批量导入、模型微调（在预训练模型上用小数据继续训练以适配具体任务）这类操作跑几分钟到几小时，**一次 HTTP 请求装不下它们：连接会被网关（站在客户端与后端服务之间的入口层，集中处理路由、鉴权与协议转换）掐断、线程被占住、客户端重启后结果无处可取**。**要解决的问题是：操作时长超过一次请求的存活时间时，提交与结果怎么各自表达。**

**长任务 API 的答案是把「请求-响应」拆成两个资源——提交时立刻创建一个任务资源，结果事后由它的终态给出**。读完这篇你能判断哪些操作该走任务资源、状态端点要返回什么字段、终态迁移有哪些不可绕过的纪律，也能看出**「拿同步接口硬扛长操作」会在哪一刻先崩**。

## 先记住哪几句

| 维度 | 回答 |
| --- | --- |
| 要解决的问题 | 操作时长超过一次请求的存活窗口，同步等待会把超时、线程占用与重启丢结果叠加成一次故障 |
| 本质机制 | 提交与查询拆成两个资源：POST（HTTP 提交数据的请求方法） 返回 202 与任务资源位置，GET 状态端点轮询或 Webhook 通知，终态只有成功、失败、取消三种 |
| 核心做法 | 状态机显式建模（queued/running/succeeded/failed/canceled），提交接口带幂等（同一操作执行多次与执行一次效果相同）键，状态响应带 Retry-After，结果与状态分离存储 |
| 效果与代价 | 换来连接即释放、进度可见、可取消可重试；代价是状态存储、轮询流量、终态清理与更多的接口面 |
| 边界 | 亚秒级操作用它是自找复杂；僵尸任务、终态结果无限留存、提交不幂等是三个常见失效点 |
| 验证 | 提交两次同幂等键应返回同一任务；终态后状态端点必须稳定可查；轮询响应遵守 Retry-After 可用 curl（命令行 HTTP 客户端） 核对 |

## 为什么同步接口扛不住长操作：要解决的问题

同步请求-响应的前提是**「处理在连接存活期内完成」**。长操作要连撞**三层叠加的边界**：反向代理（替后端服务器接收请求、再转发的中间层）与网关有自己的读超时（常见 30 到 60 秒），到了就返回 504，**任务还在跑，调用方却拿到了失败**；服务端为等待的请求占着连接、线程或协程（用户态调度的轻量执行单元、切换不进内核），**吞吐随并发长请求线性塌陷**；客户端进程重启或页面刷新，已经发起的请求彻底丢失，**任务算完也没有人来取**——这正是「已接受但无回执」在 HTTP 层的形态，**超时只表示调用方在期限内没得到响应，服务端是否执行完全不可知**，见 [[工程知识/后端系统：在并发、失败与变化中维持服务/分布式可靠性/超时、重试与幂等共同定义调用语义.md|超时、重试与幂等共同定义调用语义]]。

把超时调大治标不治本：网关超时放宽到十分钟，**这十分钟里连接随时可能被中间任何一跳——负载均衡、NAT 网关（Network Address Translation，网络地址转换：在内外网之间改写地址与端口）、浏览器——掐断**；就算连接活着，客户端崩溃后结果照样丢失。问题不在超时数值，在**「单次请求同时承担了提交与结果交付两个职责」**——**职责拆开，每个职责才有各自的可靠性手段**。

## 提交与查询拆成两个资源：它是怎么做到的

先打个比方：长任务 API 像医院挂号取号——窗口不会让你站在原地等报告，先给你一张回执单（任务资源），报告出来之前你随时凭单子问「好了没有」（状态查询），也可以打电话通知你来取（Webhook 回调）。这个比喻到「凭单查询」为止——现实里单号由谁生成、报告保留多久、电话打不通怎么办，都是 API 设计决策，医院流程里没有对应物，下面逐个展开。

### 提交：POST 返回 202 与任务资源

```
POST /api/reports
Content-Type: application/json
Idempotency-Key: 7f3a-2024-submit-001

{"type": "monthly_summary", "month": "2024-09"}
```

```
HTTP/1.1 202 Accepted
Location: /api/operations/op_9x2m
Retry-After: 2
Content-Type: application/json

{"operationId": "op_9x2m", "status": "queued", "statusUrl": "/api/operations/op_9x2m"}
```

三个要素各司其职：`202 Accepted` 表示「已受理，尚未完成」，与 `201 Created`（资源已建成）划清界限——**用 201 回长任务等于向调用方谎报完成**；`Location` 指向任务资源，**调用方后续的所有交互都围绕它**；`Idempotency-Key`（幂等键：同一请求重复发送结果不变，标识一次业务意图）**保证客户端重试提交时不产生第二个任务，重复请求应返回同一个 operationId**。幂等键的生成、存储与事务边界在 [[工程知识/后端系统：在并发、失败与变化中维持服务/任务与并发/幂等性的完整谱系：从操作语义到删除接口的天然陷阱.md|幂等性的完整谱系]] 展开。

### 查询：状态端点返回机器可读的状态

```
GET /api/operations/op_9x2m

HTTP/1.1 200 OK
Retry-After: 5
Content-Type: application/json

{"operationId": "op_9x2m", "status": "running", "progress": 45,
 "createdAt": "2026-10-01T08:00:00Z", "retryCount": 0}
```

状态端点每次返回 `200` 加状态体，**不靠状态码区分「进行中」与「完成」**——这是 Azure 架构中心的 Async Request-Reply 模式与 Google API 设计规范 AIP-151（Long-running Operations 一节）的共同选择。另一种实现是完成时返回 `303 See Other` 重定向到结果资源，客户端跟随重定向取结果；**两种都成立，混用会让调用方无所适从，选一种写进接口约定**。`Retry-After` 告诉调用方多久后再来，**遵守它是客户端的义务：忽略它按固定间隔硬轮询，服务端的查询流量会随任务数线性膨胀**。

### 通知：Webhook 把「来问」变成「来告」

轮询之外，提交时可带回调地址，任务终态时服务端 POST 通知：

```
POST https://client.example/webhooks/operations
X-Signature: sha256=8a1f...
Content-Type: application/json

{"operationId": "op_9x2m", "status": "succeeded", "resultUrl": "/api/reports/rpt_31"}
```

**Webhook 与轮询不是二选一：Webhook 快但不可靠（客户端地址可能不可达、消息可能丢失），轮询慢但必然可用**。公开 API 的成熟做法是**两者都提供、轮询作兜底**——GitHub 的 Checks API、Stripe 的事件通知、AWS 的 S3（Simple Storage Service，AWS 的对象存储服务）事件全走「Webhook 优先 + 资源可查」的双通道。**通知必须带签名**（防止伪造）**与去重标识**（同一事件可能投递多次），**客户端收到通知后仍应回查一次状态端点确认，通知只是「该去查了」的信号，状态端点才是事实源**。

### 状态机：五个状态与三条不可逆终态

提交、执行、查询三个环节怎么连起来：

![长任务把提交与结果拆成两个资源：202 立即返回、连接释放，结果由任务资源终态给出（来源：自绘）](/static/figures/long-task-two-resources.svg)

五个状态怎么走、三个终态为什么只进不出：

![长任务状态机：五个状态三条不可逆终态，终态改回 running 会让调用方的补偿动作全部作废（来源：自绘）](/static/figures/long-task-state-machine.svg)

状态机的纪律有三条。**终态不可逆**：**任务一旦进入 succeeded、failed、canceled 之一，任何后续请求都不能把它改回运行中**——「失败后自动重跑」必须创建新任务，**原地复活会让「查询到 failed」这个事实失去意义，调用方基于它做的补偿动作全部作废**。**失败要带错误分类**：failed 响应里给稳定的错误码（如 `UPSTREAM_TIMEOUT`、`INPUT_INVALID`）与可重试标记，**调用方据此决定重提还是报警**，错误分类的通用做法见 [[工程知识/软件构建：让变化可以理解、验证与交付/架构与代码/错误处理的分类学：错误类型与恢复策略的映射.md|错误处理的分类学]]。**取消是显式操作**：暴露 `POST /api/operations/op_9x2m/cancel`，**执行者在检查点（定期保存进度、故障后从最近一次保存处恢复）查询取消标志后进入 canceled**——**不允许取消的长任务会把调用方的错误提交变成必须干等的惩罚**。

这三条纪律合起来回答了同一个问题：**调用方拿到状态后能采取什么动作**。**终态稳定，失败可分类，取消有通道——调用方才能把「任务在跑」变成可管理的业务过程**。这正是后端域导读把异步任务与 HTTP 服务归到同一组问题的原因：**换形态不换问题，换的是每项设计动作的载体**（见 [[工程知识/后端系统：在并发、失败与变化中维持服务/后端系统：在并发、失败与变化中维持服务.md|后端系统导读]]）。


## 什么时候该用、什么时候不该用：看完能判断

任务资源服务于特定操作形态，「更高级」的说法会带偏选型。判断顺序从操作时长开始：

| 判断项 | 走同步接口 | 走任务资源 |
| --- | --- | --- |
| 典型时长 | 亚秒到数秒，deadline 内稳定完成 | 超过网关超时（常见 30-60 秒）或时长不可预测 |
| 调用方要什么 | 立即拿结果，慢一步就不可用 | 可以接受稍后取结果，更在意「不丢、可查、可取消」 |
| 副作用形态 | 无副作用或天然幂等 | 不可逆副作用（扣款、发消息），需要幂等键与状态留痕 |
| 客户端形态 | 服务间调用、健康探测 | 浏览器、移动端、跨重启的批处理 |

两栏都在同一负载假设下成立：**时长栏按 P99（99 分位延迟）估，不是按均值——均值 2 秒 P99 40 秒的操作，按均值判断会选错形态**。**偶发慢但通常快的操作，该修慢的原因（索引、缓存、下游超时），转成任务资源会把「该修的病」藏进异步通道里，故障定位反而更难**。

批量与任务的分界有现成判据：超过同步上限的批量走任务接口，任务是「一把」操作的大号形态，取舍边界见 [[工程知识/后端系统：在并发、失败与变化中维持服务/服务设计/批量与单条接口的取舍分界：按调用方节律与平台职责定边界.md|批量与单条接口的取舍分界]]。

## 轮询流量怎么算：这些量在什么数量级

**轮询不是免费的，动手前先算账**。假设任务平均跑 30 秒、客户端每 2 秒轮询一次，每个任务在存活期内产生约 15 次状态查询；每小时 10000 个任务，就是 15 万次查询，折合约每秒 41.7 次——**如果状态端点的容量预算是每秒 60 次，光轮询就吃掉七成，新任务一进来就过载**。能把这个数字压下来的是三项具体措施（下表的「旋钮」即指它们：退避间隔、完成通知、响应缓存）：

| 旋钮 | 机制 | 数量级效果 |
| --- | --- | --- |
| Retry-After 与指数退避 | 服务端指定间隔，客户端按 2s→4s→8s 递增并设上限 | 15 次查询压到 5-6 次 |
| 完成通知（Webhook） | 终态主动推送，轮询只作兜底 | 轮询降一个数量级 |
| 状态响应缓存 | 状态端点响应可短时缓存（1-5 秒） | 同一客户端的重复查询不再落库 |

算完的收获在第一行：**退避与 Retry-After 是流量杠杆**，写进客户端 SDK 的默认行为，比写进文档等人自觉靠谱得多。

## 僵尸任务与结果清理：这套说法在哪儿会失效

**「running 永远不落终态」是最常见的失效形态**。worker 崩溃、队列丢消息、取消标志没人读，**任务状态会卡在 running，调用方按 Retry-After 轮询到天荒地老**。治理手段与后台任务一致：任务带租约（带过期时间的临时授权，过期即失效）与心跳（执行者按固定间隔发出的续期信号，接收方超时未收到即判定执行者已失联），**执行者定期续期，到期未续的任务由看门狗接管改判 failed**。守护与托管机制见 [[工程知识/后端系统：在并发、失败与变化中维持服务/任务与并发/后台任务的守护链：进程托管与会话脱离是可靠性的底线配置.md|后台任务的守护链]]。状态端点还要暴露 `retryCount` 与 `lastError`，**调用方连续 N 次看到同一状态且 retryCount 不动，就应放弃轮询转人工**。

**终态结果无限留存是慢性失效**。每个任务都存结果，**存储随任务量线性增长**；TTL（存活时间）到期后查询应返回 `410 Gone`（资源已永久消失）而不是 **404**，**让调用方分清「任务还没建」与「结果已清理」**。TTL 的取值跟着业务走：报表类保留 24 小时，审计类按合规要求保留数年。

**提交不幂等是隐形失效**。客户端超时重试，**服务端建了两个任务、扣了两次费——提交接口必须校验幂等键，重复键返回原任务而不是新任务**。这一条与同步接口的幂等纪律完全同构，见 [[工程知识/后端系统：在并发、失败与变化中维持服务/分布式可靠性/超时、重试与幂等共同定义调用语义.md|超时、重试与幂等共同定义调用语义]]，**长任务把它的后果放大了：重复执行的是一次跑几十分钟的作业**。

**AI 场景的边界**：LLM（大语言模型）推理走流式输出时不需要任务资源——**流式把首字节时间（time to first byte，从发出请求到收到第一个数据块的耗时；流式场景下模型边生成边交付，这个时刻就是用户看到回答开始的时刻）变成交付语义，边生成边交付**；**只有整段生成完才有意义的操作（批量评估、微调、长文档批处理）才转任务**。Agent 的多步任务比单次长操作更复杂：**中间步骤的状态外置与断点续跑是任务资源的延伸形态**，见 [[工程知识/AI 系统工程：从模型能力到生产能力/Agent与工作流/Agent状态机与任务恢复：进度是状态不是聊天记录.md|Agent状态机与任务恢复]]。

## 怎么自己动手验证

验证一条任务 API 是否守纪律，用 curl 走四步（命令在公开环境可复现，`example.com` 换成目标服务）：

```bash
# 1. 提交两次同幂等键，应返回同一 operationId
curl -s -X POST https://example.com/api/reports \
  -H "Idempotency-Key: test-001" -H "Content-Type: application/json" \
  -d '{"type":"demo"}' -D - | grep -Ei "HTTP|location|operationId"
curl -s -X POST https://example.com/api/reports \
  -H "Idempotency-Key: test-001" -H "Content-Type: application/json" \
  -d '{"type":"demo"}' -D - | grep -Ei "HTTP|location|operationId"

# 2. 查询进行中任务，核对 Retry-After 与状态字段
curl -s https://example.com/api/operations/op_9x2m -D - \
  | grep -Ei "HTTP|retry-after|status|progress"

# 3. 终态后重复查询，状态必须稳定
curl -s https://example.com/api/operations/op_9x2m | grep -oE '"status":"[a-z]+"'

# 4. 取消已终态任务，应报错而非复活
curl -s -X POST https://example.com/api/operations/op_9x2m/cancel -D - | head -1
```

预期与判定：第 1 步两次输出同一 operationId，若不同则提交不幂等，重复提交会产生重复副作用；第 2 步响应携带 `Retry-After` 且状态属于 {queued, running}，缺字段说明调用方只能盲等；第 3 步连续两次查询状态一致且属于终态集合，出现状态回退说明终态可被改写；第 4 步对终态任务发起取消应返回 4xx 错误，任务状态变回 running 就已经构成终态不可逆被破坏，返回 200 是附加证据。对不上就查提交接口的幂等键校验路径与状态机的迁移条件。

## 案例回流：任务生命周期断在半路的两个实录

[[工程知识/缺陷分析：从个案到体系/稳定性/案例二十一：异常路径上没有完成——永不兑现的 future]] 是任务终态丢失的直接形态：**异常路径上的任务没有走到完成回调，future 永不兑现，调用方等一个永远不会来的结果**。它对应本篇「僵尸任务与结果清理」一节——**状态机必须覆盖异常路径，每个状态都要有「谁负责推进到终态」的答案**。轮询误判的形态见 [[工程知识/缺陷分析：从个案到体系/正确性/案例十八：空集合被当成了"全部已确认"——游标跳过的位置.md]]：**查询任务列表时空集合被当成全部完成，与状态端点把「查不到」当成「已完成」是同一类错误**。两案共同判据：**任务资源的每个查询与迁移都要区分「没发生」「进行中」「已完成」三种语义，把其中两种合并成一种的实现都会在异常路径上出事**。
