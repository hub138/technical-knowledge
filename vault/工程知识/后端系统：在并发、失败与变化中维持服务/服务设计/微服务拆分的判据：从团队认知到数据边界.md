## 要解决的问题

一个跑得好好的单体，要不要拆、在哪拆、拆多细？拍脑袋拆的结局两边都见过：拆晚了——团队在同一个代码库里互相踩脚（改一处冲突、发布互相等待），迭代速度被协调成本吃掉；拆早了——一堆服务共享一个数据库，分布式事务、联调成本、运维复杂度全来了，收益没见着，事故翻了几番。问题的本质：**拆分是组织结构与系统结构的对齐决策（康威定律的工程化），判据不是技术时髦度，是团队认知边界与数据所有权这两个硬约束**。判据摆出来之前，"要不要拆"没有答案。

## 机制

**判据一：认知边界（团队的心智负载）**。单体到某个规模后，无人能理解全貌，每个开发者只敢动自己那块（改别人的代码要读三天上下文）。信号：新功能开发的上下文加载时间（读代码时间超过写代码时间）、跨模块改动的冲突率（git 冲突频率是耦合度的可测量代理）、发布协调成本（一次发布要 N 个团队对齐窗口）。**拆分的认知判据：一块业务能被一个团队完整持有（理解、修改、运维都在团队认知半径内）**，边界就画在认知过载的地方——两个团队改同一段代码常驻冲突，是拆分的第一信号。

**判据二：数据边界（所有权的完整性）**。服务拆分的第一原则是数据随之拆：每个服务独占自己的数据存储（Database per Service），跨服务不直连对方的库。**数据边界的判据是"不变量的归属"**：一组必须一起保持一致的业务规则（订单与订单明细、账户与余额）该归一个服务；数据被两个业务域高频读写（同一张表被订单团队和库存团队都改 schema），说明边界划错了地方（数据是共享的就必然耦合，拆服务不拆数据是假拆分）。判据的实操：先画数据模型的关系簇（外键、事务、一致性依赖成簇），簇与簇之间靠事件（而非共享表）同步，簇即服务边界的候选。

**判据三：变更节奏（发布的独立性）**。两块业务的变化频率差一个量级（秒杀活动周周改、账户规则一年不动），捆在一个发布单元里，快的被慢的拖住（等窗口、等回归）。变更节奏判据：**发布频率差异显著 + 各自回滚独立**，拆开后快的块提速。反例：两块业务总是一起变（一次需求两边都改），拆成两个服务只增加一次联调——**耦合度看变更历史，不看代码长相**（git log 里两个模块的同变更率是耦合的真实度量）。

**拆分的顺序与颗粒度**。顺序：先模块后服务（单体内部先按边界分模块、模块间强制单向依赖——验证边界画得对不对的最便宜方式），边界稳定后再拆物理服务（分布式化的运维成本一次性付清）。颗粒度：从"能独立发布的最小单元"往上收，每个服务至少一个完整持有它的团队（低于团队粒度的服务是孤儿服务，无人负责的拆分碎片）。**"微"指的是团队认知半径，不是代码行数**。

## 背景与代价

思想背景：微服务潮（2014 前后，Fowler 与 Lewis 的定义文章、Netflix/Amazon 的实践输出）把拆分推成主流；反思潮（2018-2022，"分布式单体"的批评、Monolith First 的倡导——Fowler 2015 就写了先单体后拆的文章、Shopify/StackOverflow 的大单体反例、Basecamp 的 Modular Monolith 路线）把判据拉回冷静。康威定律（1968）的逆推（组织决定架构）与 Team Topologies（2021，Skelton 与 Pais）给拆分提供了组织侧的操作系统。

最精巧的一笔是**把拆分判据锚在"变更与数据的真实流"而非架构图的美感上**：git 同变更率、数据一致性簇、发布窗口冲突——三个可测量的信号替代了"高内聚低耦合"的口号。判据可测量，拆分决策就可以复盘（拆之前预测的解耦收益，拆之后用同变更率、故障隔离性对账），架构决策从信仰变成工程。代价要摆明：**拆分的真实成本在拆后**——分布式调试（一个请求穿三个服务，排障要跨服务 trace 基建）、最终一致性（原来一个事务的拆成事件驱动的补偿链）、运维矩阵（每个服务一套部署监控告警，平台基建先于拆分存在才付得起）；**判据是必要条件不是充分条件**——认知、数据、节奏三条全中，还要组织能力兜底（服务治理、平台工程、on-call 轮值），能力缺位的拆分是把复杂度从代码转移到组织，总量不减反增。适用判定：单体协调成本已实测可见（冲突率、联调时间）且平台基建就绪，拆；两者缺一，先补弱的那个。

## 边界

- **共享库与共享数据的两个假拆分形态**：服务 A、B 共享一个公共业务库（版本地狱：改库要同时发两个服务）或共享一个数据库（表结构是隐式契约，改表炸别人）。真拆分的检验：每个服务能独立重构自己的数据模型而不通知别人。
- **"为了性能拆"多半是错的方向**：单机的进程内调用（ns 级）拆成跨服务网络调用（ms 级），性能方向是变差的。性能问题的正解通常是拆数据（分库分表、读写分离）或拆进程（同机多进程），不是拆服务。性能诉求的拆分只在一类场景成立：资源隔离（某模块的流量洪峰不吃掉别人的资源——但那是部署隔离，模块化单体加独立部署也能做到）。
- **先拆后补基建的顺序陷阱**：服务发现、集中日志、分布式 trace、统一发布管道——这些平台件在单体时代可以后补，拆分后是空气。拆分计划里平台基建的前置项要打勾，否则拆分即事故季。
- **拆分可以回头吗**：可以但贵（服务合回单体是数据与发布的双重回迁）。判据拿不准时用"绞杀者模式"渐进（新功能在外围新服务长，旧单体逐步抽干），保留回退余地——一次性的大爆炸拆分（big bang rewrite）是最高风险形态。

## 验证

- **同变更率测量**：对候选拆分的两个模块，统计 git 历史里两者的同 commit 变更率（近 6 个月）。预期：边界清晰的模块对同变更率低（<10%，各自独立演进），纠缠的对高（>50%，拆开只会增加联调）。判据一的数据化实测。
- **数据簇划分演练**：对数据模型做一致性依赖分析（事务边界、外键、同事务更新的表集），输出关系簇。预期：簇的数量与形态跟业务域对得上（订单簇、库存簇、账务簇），簇间靠事件同步可行；出现"桥接表"跨两个簇的，即边界争议点，需要人工决策。判据二的方法验证。
- **拆分收益对账**：找一次已完成的拆分，对比拆分前后的发布频率、变更冲突率、故障隔离案例（A 服务的故障是否不再拖垮 B）。预期：判据选对的拆分，三项全改善或两项改善一项持平；对不上的拆分（拆了更慢、事故更多），复盘判据哪条漏了。决策方法的闭环校验。
