# 容量估算的通用骨架：从峰值QPS到机器数的推导演练

## 容量估算到底在解决什么问题

**容量估算要解决的问题，是把"业务说要有多少人用"翻译成"系统需要多少台机器"。**读完这篇，你能照着六步把业务口中的人数推成机器数与成本，并和老板对上账。**没有这层翻译，扩容就是拍脑袋：高峰前临时加机器、事后回收，要么浪费要么不足。**容量规划与压测要用同一个负载模型说话[[工程知识/后端系统：在并发、失败与变化中维持服务/基础设施/容量规划与压测要用同一个负载模型说话.md]]，估算正是这套语言的起点：先有可推导的数字，压测才有靶子，扩缩容才有依据。

## 这条结论是怎么一步步推出来的

打个比方：容量估算像算一场演唱会要开几个检票口——先看峰值一分钟来多少人（峰值 QPS），再看一个人过闸要几秒（单机处理时延），两个一乘就知道至少要开几个口，再留出有人临时上厕所的余量。这个比喻到"估算的形状"为止：检票口比喻只说明乘法关系怎么摆（峰值人数 × 单人耗时 ÷ 单口吞吐），单机的并发上限怎么压测出来、冗余系数取多少、读写比例怎么影响机器数，这些正文的六步推导里展开，比喻不负责这些细节。

从峰值 QPS 推到机器数，中间要靠队列吸收峰值：请求突发时不直接压到后端，而是先缓冲，后端按自己的节奏消费。队列像医院候诊区，病人先取号排队，诊室按自己节奏叫号，门口再挤也不会冲垮医生。

*图源：Microsoft Learn 中文文档，CC BY 4.0，https://learn.microsoft.com/zh-cn/azure/architecture/patterns/queue-based-load-leveling。*

从业务量到机器数，整条链六步，每步的误差来源单独可控，见下图：

1. **日活 → 日请求总量**。DAU（Daily Active Users，日活跃用户数：一天里打开过产品的去重人数）× 人均请求次数。

**人均次数拿真实日志统计，不拍：一个用户一次会话刷新列表 5 次、点开详情 3 次，人均 20 次与人均 5 次意味着四倍机器。这个参数是整条链里最常被拍的，也是事后最好校准的。**

2. **日请求总量 → 平均 QPS**。总量 ÷ 86400。

**平均数只用于规划阶段做粗校，机器数按峰值推。**
3. **平均 → 峰值 QPS**。

**有历史数据直接取历史峰均比；没有历史时用集中度粗估：80% 流量集中在 20% 时间，80%÷20%=4，即最忙时段强度约为日均的 4 倍，故峰值系数粗取 4。促销秒杀类场景不适用——那类瞬时洪峰要单独建模型，后文「这套说法在哪儿会失效」一节专门讨论。**

4. **峰值 QPS → 机器数**。峰值 QPS ÷ 单机安全容量，再乘冗余系数。

**单机容量来自压测："该服务在该硬件上的最大安全 QPS"（通常留 30% 余量），核数只作参考。冗余系数是可用性决策：单 AZ（可用区，机房里一个独立的故障隔离单元）用 1.2（日常波动余量），双 AZ 用 2.0（单 AZ 故障时另一半接管），异地多活 2.5 以上。**

**这一步把"可用性等级"翻译成钱——双 AZ 的代价就是机器数翻倍，这个账必须摆上桌。**
5. **机器数 → 成本**。

机器数 × 单价。**到这里第一次出现钱，才和"业务口中的 X 万人用"对上账。**

**怎么和业务对上账？把业务口中的 X 万人倒推回机器数再乘单价，才和这批人对应的成本对上账。**

**估算结果是不可接受的 500 台？说明要么技术方案——缓存、CDN（Content Delivery Network，内容分发网络：把内容提前放到离用户近的节点）、异步化即把同步操作改成后台慢慢消化的消息——要重做，要么 SLA（服务等级协议，对外承诺的可用性与响应目标）要调整。**

**估算在这里变成一个业务对话工具。**
6. **校准**。

**真实流量进来后，拿真实峰值反推误差，修正人均次数与峰值系数。估算的最终产物是"下次估得更准的模型"，服务本身就是自己的校准器。**

## 它从哪儿来，要付什么代价

这套推导替代的是两种更粗的做法：一是"CPU 高了就加机器"（滞后，且没有预算感），二是"拿 CPU 利用率公式直接算机器数"（忽略流量分布与可用性决策）。Google SRE（Site Reliability Engineering，站点可靠性工程：用软件工程方法管运维的实践）的容量规划是这条路线的代表，其核心思想是把容量当成需求与成本之间的翻译器，让"扩容"从一个指令变成一个可谈判的成本条目。

设计里最精巧的一步是**冗余系数显式化**。多数容量讨论把冗余混在"多加几台"里糊涂过去；这条链把它单列，**让"双 AZ 的代价是机器数×2"成为桌面上可谈判的条目，而不是埋在 CPU 公式里的隐形支出。代价本质要摆明：估算换来了决策依据，付出的是维护成本——人均次数、峰值系数、单机容量这三个参数每季度都要拿真实数据重新校准，不校准的估算模型比没有模型更危险（它带着错误的自信）。**

```mermaid
graph TD
    S1["① 日活 × 人均次数"] -->|"得到日请求总量"| S2["② 总量 ÷ 86400<br/>得平均 QPS"]
    S2 -->|"乘峰均比<br/>无历史时取 4"| S3["③ 峰值 QPS"]
    S3 -->|"÷ 单机安全容量<br/>× 冗余系数"| S4["④ 机器数"]
    S4 -->|"× 单价"| S5["⑤ 成本 变成业务对话"]
    S5 -->|"真实峰值反推误差"| S6["⑥ 校准三个参数"]
    S6 -.->|"下轮估得更准"| S1
```

图从天级业务量一路推到钱：人均次数拿日志统计，平均 QPS 用于粗校，机器数按峰值推；峰值除以压测压出来的单机安全容量，再乘冗余系数——单 AZ 用 1.2、双 AZ 用 2.0，可用性等级在这里被翻译成成本：承诺翻倍的可用性，机器就要接近翻倍地买。虚线是校准回路：上线后拿真实峰值反推，修正人均次数、峰值系数、单机容量三个参数，让这套模型自己变准。整条链的价值在于把「扩容」从一句指令变成一个可推导、可对账、可谈判的条目。

## 动手跑一遍会看到什么：容量推演的账

把缓冲层算进容量账之后，实际需要的机器数取决于后端能稳定维持的消费速率，而不是峰值到达速率。

![基于队列的负载调节：任务经队列缓冲后由服务按稳定速率处理](/static/figures/ms-queue-load-leveling-pattern.png)

*队列缓冲模式的稳态（系统运行指标进入平稳区间后的状态）图示来源：Microsoft Learn 中文文档《Queue-Based Load Leveling》，CC BY 4.0，https://learn.microsoft.com/zh-cn/azure/architecture/patterns/queue-based-load-leveling。*


```text
峰值 QPS 5 万的推导演练（通用骨架）：

第 1 步 列出目标：峰值 5 万 QPS（每秒查询数，系统每秒处理的请求量）、P99 200ms（P99：把所有请求响应时间从小到大排，第 99 百分位的值，99% 的请求比它快）、可用性 99.95%
第 2 步 分解路径：网关 → 业务服务 → 缓存（命中 95% 的请求在这里返回）→ 数据库（只接 5% 的回源请求）
第 3 步 算各层负载：
  业务服务：5 万 QPS × 单机 1000 QPS = 50 台 → 冗余 30% = 65 台
  数据库：5 万 × 5% = 2500 QPS 回源，主库写 5000 QPS → 一主三从（一个主库负责写，三个从库分担读）
  缓存：5 万 QPS，单节点承受 10 万 → 2 节点带主从（主缓存节点挂了，从节点顶上）
第 4 步 压对账：
  按推演配置压测 → 实测单机只有 600 QPS
  → 机器数改 84 台，容量结论以实测为准，推演值只是起点
第 5 步 留故障余量：挂 20 台还能扛峰值吗？→ 剩 64 台 < 65 台需求 → 不达标
  → 要么加机器到 84，要么确认降级预案能砍 20% 流量
```

推演算出的机器数还要过一道故障余量对账——扣掉一个可用区后剩多少，决定这条链是加机器还是砍流量：

```mermaid
flowchart TB
    A["推演给出的机器数"] --> F["扣掉一个可用区后剩余"]
    F --> C["扣掉故障机器后剩余容量够不够峰值"]
    C --> Y["余量达标<br/>预买的冗余真正起了作用"]
    C --> N["余量不足的两条出路"]
    N --> N1["加机器 把总容量抬上去"]
    N1 --> N2["启用降级预案 砍掉部分非核心流量"]
    N2 --> R["最终容量结论以压测实测为准"]
    Y --> R
```

余量不达标时的两条出路，正是把冗余系数单列出来的意义——而下面这条实录讲的是跳过对账会付出什么代价。

**跳过对账的实录——推演按"单机 1000 QPS"算好 50 台上线，真实流量一来 CPU 100%（单机实际只有 550），扩容救场；偏差来源是推演用的基准数来自别人家的压测报告（硬件、数据形态都不同）。另一实录是只算均值不算余量——容量刚好够峰值，一个可用区挂掉全站过载（故障余量那一步存在的意义）。**推演的纪律与 [[工程知识/性能工程：从用户等待到资源瓶颈/观测与诊断/基准测试必须先定义负载和测量误差.md]] 同源：**假设可对账、数字报误差、结论带边界。**

## 这套说法在哪儿会失效

- **秒杀类瞬时洪峰不适用**。**开售瞬间百倍流量不能乘峰值系数，要单独建瞬时模型（漏桶整形——一种以固定速率放行请求的限流算法）+ 队列，否则机器数虚高一个量级。**
- **自动扩缩容不替代估算**。**估算管"常态应保有的水位（队列或资源的当前占用程度）"，自动扩缩容管"临时波动"。把常态水位交给自动策略，扩容速度赶不上流量增速时，峰前就是小马拉大车。两者的关系是"估算定底盘、自动策略管波动"，共用同一个负载模型。**
- **读写比悬殊的服务要分开估算**。**读链路与写链路分别走这条链**（读侧可加缓存层折减，九成五的读请求被缓存挡下，不再打到数据库），**不能拿一个混合 QPS 一起除。**
- **依赖方容量是隐藏项**。估算自家机器数时，**同步依赖（数据库、下游 RPC（Remote Procedure Call，远程过程调用：像调本地函数一样调远端服务）的容量缺口会以超时形式表现，误判为自家容量不足。**整链路超时预算见 [[工程知识/后端系统：在并发、失败与变化中维持服务/分布式可靠性/超时、重试与幂等共同定义调用语义.md]]。

## 怎么自己动手验证

- **对账验证**：拿一个已运行服务，用这条链从 DAU 重新推机器数，**与实际机器数对不上时查三个参数——人均次数（日志值 vs 假设值）、峰值系数（历史峰均比 vs 粗估 4）、单机容量（压测值 vs 经验值）。误差全部来自这三个参数，对不上就停下查，不许硬凑。**
- **演练验证**：新服务上线 30 天后，拿真实峰值反推，**把误差从倍数级收敛到 ±20% 以内。预期一轮校准后三个参数进入该服务的容量档案，下次估算直接复用。**
