# 性能工程：从用户等待到资源瓶颈

**性能工程用模型、测量和实验回答三个问题：系统的瓶颈在哪里，优化后代价转移到了哪里，是否值得上线**。「把某个参数调大」只是这三个问题答案的落点之一。读完你能走完定位、归因、验证三步，并判断一次优化值不值得上线。

## 要解决的问题：性能问题怎样用模型与测量与实验连成完整流程

性能问题出现时，团队凭直觉调参数、加机器或换组件，改动之后无法说明瓶颈是否真的移动、改善是否值得上线。本篇回答：性能问题怎样用模型与测量与实验连成完整流程、目标从业务侧怎样反推、优化之后代价转移到哪里去查，以及什么条件下应当停止优化。

## 延迟、吞吐和并发是什么关系

**用户感知到的等待，大部分等待时间，而不是计算时间**。一次访问要经历 DNS（Domain Name System，域名系统：把域名解析成 IP 地址）、TCP（传输控制协议，负责把数据完整、有序地送达）、TLS（传输层安全协议：给网络通信加密并验证对方身份）一串往返，**每一跳都把延迟叠加进去**。

![从输入 URL 到页面可用的完整网络链路：DNS 查询、TCP 连接、TLS 握手、请求与响应依次排开](/static/figures/mdn-perf-visa-network.png)

*图源：MDN Web Docs 中文版（Mozilla 贡献者），CC BY-SA 2.5，https://developer.mozilla.org/zh-CN/docs/Web/Performance/How_browsers_work。*

**一次往返的耗时远大于服务端的计算耗时，往返次数又是按倍数放大总延迟的，所以延迟优化的第一刀通常落在"减少往返次数"上**，而不是"让每次计算更快"。

**Little's Law 在稳定系统中给出平均关系：系统内请求数 L = 到达率 lambda × 平均停留时间 W**。它不是容量保证，却能解释**为什么延迟上升会迅速堆积并发状态**。系统接近饱和后，**新增并发主要进入队列，吞吐不再线性增长，尾延迟（P99 一类的慢请求耗时指标）和超时开始放大**。

性能工程因此**先问用户等待发生在哪里，再问哪个资源造成等待**。CPU（中央处理器）使用率、GPU（图形处理器）利用率、IOPS（每秒输入输出次数，存储设备的能力指标）和带宽都是**中间证据，不是目标**。

## 证据按什么优先级采信

Profile（性能剖析：对运行中的程序取样，统计各调用路径的占用）是证据链里的第三层，它的作用是定位时间花在哪个调用路径上。火焰图的宽度代表占用比例，越宽的帧越是热点（访问集中在少数键或节点上的现象）——这让"哪个函数慢"从猜测变成可量测的结论。

![火焰图：宽度代表占用时间比例，宽帧即为热点调用路径](/static/figures/brendangregg-火焰图-宽度代表占用时间比例-宽帧即为热点调用路径.png)

*图示：真实采集的火焰图（来源：Brendan Gregg 火焰图页）。取样数据只说明占用分布，不解释原因。*

1. 用户可感知的 SLO（服务等级目标，服务对可用性或延迟作出的量化承诺）请求 trace 和错误率。
2. 资源指标与队列/锁/GC 等运行时证据。
3. Profile、系统调用（程序请求内核提供服务的入口）、内核事件和硬件计数器。
4. 基准测试和合成数据。它们用于验证假设，不能替代真实负载。

## 容量规划为什么先找瓶颈

扩容前对每种资源按 USE 方法（Utilization/Saturation/Errors，对每类资源查使用率、饱和度、错误数）过一遍。**应用实例从 4 台扩到 16 台，而数据库连接池（预先建好连接反复取用、省去反复握手建连的开销）和 CPU 已经饱和时，新增实例只会制造更多排队和连接，QPS（每秒查询数）不会线性增长**。

**容量实验要逐步增加负载，找到吞吐不再增长、p95/p99 和错误率开始陡升的拐点**。每个台阶都同时记录请求类型、并发、队列、连接池、CPU、内存、I/O 和下游限制。Little's Law `L = lambda * W` 用于解释稳定系统中并发量、到达率和停留时间的关系，但**不能替代峰值、突发和故障测试**。

容量结论必须对应到具体组件和安全余量：入口能接多少、队列能等多久、数据库能维持多少并发、降级（主动牺牲部分功能或精度，保住核心链路）后保留哪些请求。**余量的存在是为了在依赖变慢、实例损失或流量突增时仍有恢复空间，资源长年贴着 100% 跑的容量规划没有通过验证**。

## 调优的完整步骤是什么

```text
定义目标和不可退让约束
 -> 建立基线和可重复负载
 -> 只改一个变量
 -> 记录吞吐、p50/p95/p99、资源和错误
 -> 判断收益是**否转移瓶颈**
 -> 回归、灰度、设置回滚阈值
```

**优化动作改的是局部指标，而局部指标与业务结果之间隔着多层传递：CPU 空闲下来可能只是把等待挪到了别处，火焰图变窄也可能只是采样（只采集一部分数据以控制记录开销）没覆盖到真正耗时的那段**。所以**不要把「CPU 使用率下降」「火焰图变窄」直接当作成功；最终目标是业务 SLO、容量和成本改善**。

性能结论要与负载对账——**每个优化结论限定在测它的负载形态（并发、数据量、热读比例）内成立，负载变了预期要重写，实测与预期对不上的结论不进容量规划**。

性能工程的机制与本质：**性能问题是一次请求把时间花在哪的分配问题——排队、计算、传输、等待各占一份，资源是分配的约束**；
**本质方法是测量先于猜测：分层计时把等待归属到具体层，资源画像把饱和点定位到具体设备，优化就是把最贵的那份时间换掉**。


## 怎么自己动手验证

最小验证：对一个已定位的瓶颈做一次单变量改动，固定负载与测量方法，断言业务侧的 SLO 指标改善，且没有把成本、错误率或尾延迟转移到另一层。改动前后各测多轮，报告中位数与分位数（把耗时排序后取某个百分比位置的值、如 P99）。

转移检查：改动生效后复查原本正常的层级，断言该层的资源占用与延迟没有超出预先设定的范围。
