# 性能剖析与火焰图

性能分析回答的是「时间花在哪里」。读完这一页你能按「先定窗口、再缩到线程与调用路径」的顺序走一遍分析，并看出火焰图上哪一处宽度不能当作结论。**方法骨架是先用请求、队列和资源指标确定问题窗口，再用采样（只采集一部分数据以控制记录开销）或追踪缩小到线程、调用路径和等待原因。**

**火焰图只代表采样期间观察到的调用栈；它不能证明业务因果、未采样的 I/O 等待或结果正确。把图与同一窗口的请求 trace、off-CPU 证据和对照实验绑定，结论才可复核。**

## 要解决的问题

火焰图上最宽的函数被直接当成瓶颈，据此改完之后业务延迟没有变化；请求变慢时采集到的 On-CPU（线程正在 CPU 上运行的状态）数据里看不到任何热点，于是判断为"没有瓶颈"。性能分析回答的是采样期间时间花在哪里，回答不了业务因果、未采样的等待与结果正确性。本篇回答：CPU 时间、阻塞等待、跨进程路径与硬件供给分别该选哪种证据、火焰图的宽度与深度怎样读、采样频率与符号表如何影响可比性、以及一次可复现的分析流程包含哪些步骤。

## 该选哪种观测方式？

| 问题 | 首选证据 | 说明 |
| --- | --- | --- |
| CPU 在执行哪些函数 | On-CPU profile（如 perf（Linux 采样剖析工具）、async-profiler） | 采样线程正在运行的调用栈 |
| 线程为什么没有进展 | Off-CPU（线程因等待而离开 CPU 的状态）、调度情况（线程何时被分配到 CPU）、锁和 IO 等待 | 观察阻塞、睡眠、运行队列和资源等待 |
| 单次请求经过哪些服务 | Trace（分布式追踪：把一次请求在各服务间的调用串成一条时间线） | 需要跨进程关联请求 ID 和时间线 |
| 某事件是否发生以及顺序 | Tracepoint（内核埋点）、日志或 eBPF（可在内核运行的可编程观测程序） | 适合验证系统调用、调度和网络事件 |
| 硬件供给是否成为瓶颈 | PMU 计数器（CPU 内部统计硬件事件的计数器） | 结合 cycles、instructions、分支和缓存事件解释微架构现象 |

## 火焰图怎么读？

在采样之前先理解一次：浏览器拿到文档后要先构建出元素树，才会有后面的布局与绘制。这个构建过程本身就是一段可被采样的耗时——这和火焰图的采样是同一件事：哪个环节耗时，就被计进它能展开的那一层。下面回到火焰图读法。

![浏览器解析 HTML 构建 DOM：parseHTML 把字节流转成标记，按嵌套关系组装成 DOM 树，同时解析样式构建 CSSOM 树](/static/figures/dom-construction.png)

*图源：MDN Web Docs 中文版（Mozilla 贡献者），CC BY-SA 2.5，https://developer.mozilla.org/zh-CN/docs/Web/Performance/How_browsers_work。*

理解这一点之后，再看火焰图的读法：

- **横向宽度表示样本占比，不是单次调用耗时。占比按所在路径分别累加，同一函数出现在不同分支时各自占各自的宽度、不能相加成总宽度下结论，所以同一函数在不同调用路径上应分别判断。**
- **纵向是调用栈深度；从底部向上阅读调用关系，先找宽的路径，再回到业务入口验证是否重要。**
- 颜色通常只是视觉区分，没有通用的性能含义。
- **On-CPU 图宽的函数可能只是高频执行；若请求变慢但 On-CPU 不变，应检查 Off-CPU、IO、锁、GC（垃圾回收：运行时自动找出不再使用的内存并回收）和下游等待。**
- **采样频率、调用栈展开方式（采样时如何逐层还原函数调用关系）、符号表（函数地址到名字的映射）、内联（把小函数展开进调用方）和容器权限都会影响结果；比较前必须保持采集条件一致。**

横向的宽窄与纵向的层次放到一张真实的图里看，宽的路径、窄的旁支和栈的深度各自长什么样：

![中文标注的 CPU 火焰图：横轴是采样占比，一层层向上的矩形表示调用栈，最宽的块是最耗 CPU 的路径，块内标注函数名与占比](/static/figures/cpu-flamegraph-annotated.png)

来源：Brendan Gregg「Flame Graphs」官网示例（mysqld On-CPU profile）。先扫顶层最宽的矩形，再顺着它向下找调用入口——宽度是占比的直观形态，文字描述「哪个函数占多少」在图上直接变成一整行的相对长度；同一函数出现在不同分支时各自占各自的宽度，正对应上文「同一函数在不同调用路径上应分别判断」。

## 一个能复现的分析流程怎么走

1. 固定版本、配置、数据集、并发、CPU 亲和性（把进程绑到固定核，避免核间漂移）和时间窗口，记录 p50/p95/p99、吞吐、错误率和资源指标。
2. 先采集低开销的系统与请求证据，再对目标进程做短时 profile；生产采样需要明确权限、开销和回滚（把系统状态退回到改动之前的版本）。

3. 将热点或等待路径映射回请求、线程、锁、文件描述符（进程打开文件的编号句柄）、磁盘或网络依赖，排除启动和测试 harness 噪声。
4. **提出一个可证伪假设，只修改一个变量；保留原始 profile、采集命令、运行环境和采样时长与样本数。**
5. **用相同负载和相邻负载复测，观察收益是否转移到其他瓶颈**，并设置上线和回滚阈值。

## Linux 上的例子长什么样

火焰图方法的开创者 Brendan Gregg 在 MeetBSD 上讲解性能调优——perf 采样与火焰图读法的原始出处：

![Brendan Gregg 在 MeetBSD 大会讲解性能调优：perf 与火焰图方法的作者本人在白板前讲 On-CPU 与 Off-CPU 分析](/static/figures/brendan-gregg.jpg)

*图源：Wikimedia Commons，Andrew Fresh，CC BY 2.0，https://commons.wikimedia.org/wiki/File:Brendan_Gregg_on_Performance_Tuning._At_-MeetBSD_(15694477602).jpg。*

```bash
# 先看计数器和粗粒度资源，再做短时调用栈采样
perf stat -e task-clock,cycles,instructions,branches,branch-misses \
  -- ./service --scenario baseline
perf record -F 99 -g -o perf.data -- ./service --scenario baseline
perf report -i perf.data
```

`perf` 事件是否可用、调用栈方式和权限依赖内核、CPU、编译选项及容器配置。不要把某个固定采样频率、开销或 PMU（性能监控单元，CPU 内部统计硬件事件的计数器） 事件映射当成所有机器都成立的结论。

## 哪些误判最常见？

- **只看平均值，忽略尾延迟（P99 一类的慢请求耗时指标）和失败样本。**
- **把缓存 miss、CPU 使用率或火焰图宽度直接当成根因，没有结合基线（正常状态下的指标水平、用来对比异常）和对照实验。**
- 只做 On-CPU 分析，漏掉锁等待、IO、调度和下游阻塞。
- 在不同版本、不同数据规模或不同频率策略之间直接比较样本百分比。
- 只保存图片，不保存采集命令、符号文件、环境和原始数据，导致无法复盘。

性能分析回答的是时间被谁消耗，本质问题在于锁等待与 IO 阻塞这类不消耗处理器时间的场景，在只统计处理器占用的视角下会显示为没有热点。

样本占比要拿可比条件核对——预写相同条件下重复采集的同一代码位置占比应稳定，采集命令、符号文件与版本未对齐时与预期对不上。

## 哪些边界条件要对照着看

线程的时间在运行与等待之间怎么流转，哪些等待会被 On-CPU 分析漏掉：

![线程状态流转图：Running、Runnable、Sleeping、Disk、Lock、Idle 等状态与切换路径](/static/figures/brendangregg-thread-states.png)

来源：Brendan Gregg「[Off-CPU Analysis](https://www.brendangregg.com/offcpuanalysis.html)」线程状态划分图。Disk（磁盘等待）、Sleep（主动睡眠）、Lock（锁等待）、Idle（空闲）四类等待态全部挂在 off-CPU 一侧——只统计处理器占用的分析把这些场景统统显示为没有热点，正对上文「锁和 I/O 场景会显示没有热点」的边界；每条等待线标注的触发原因，就是 Off-CPU、锁与 I/O 分析要抓的证据通道。

让一个请求在 CPU 计算、锁等待、磁盘 I/O 和下游网络四种场景分别变慢；比较 On-CPU、Off-CPU、trace 和业务延迟。请求已变慢却无 CPU 热点，说明时间花在锁、I/O 这类不占 CPU 的等待上；只看 On-CPU 才会误判为没有瓶颈，这正是分析方法选择错误的证据——若只看 On-CPU，锁和 I/O 场景会显示「没有热点」。

## 怎么自己动手验证

1. 方法对照：让一个请求分别在 CPU 计算、锁等待、磁盘 I/O 与下游网络四种场景变慢，比较 On-CPU、Off-CPU、trace 与业务延迟四种证据，确认锁与 I/O 场景在只看 On-CPU 时显示为没有热点。
2. 可比性核对：把采集命令、符号文件、版本、数据规模与频率策略一起留存，在相同条件下重复采集，确认同一代码位置的样本占比波动在可接受范围内。
3. 全程复跑：按缩小范围、验证假设、改动、用相同负载复测的顺序走一遍，确认业务延迟的改善与分析结论指向的位置一致。
4. 断言锚点：方法选择与场景对应，采集条件可复现，结论经过对照实验验证，原始数据与符号文件被保留。
