# 性能剖析与火焰图

剖析回答的是“时间花在哪里”，不是“哪个函数看起来最宽”。先用请求、队列和资源指标确定问题窗口，再用采样或追踪缩小到线程、调用路径和等待原因。

火焰图只代表采样期间观察到的调用栈；它不能证明业务因果、未采样的 I/O 等待或结果正确。把图与同一窗口的请求 trace、off-CPU 证据和对照实验绑定，结论才可复核。

## 选择观测方式

| 问题 | 首选证据 | 说明 |
| --- | --- | --- |
| CPU 在执行哪些函数 | On-CPU profile（如 perf、async-profiler） | 采样线程正在运行的调用栈 |
| 线程为什么没有进展 | Off-CPU、调度、锁和 IO 等待 | 观察阻塞、睡眠、运行队列和资源等待 |
| 单次请求经过哪些服务 | Trace | 需要跨进程关联请求 ID 和时间线 |
| 某事件是否发生以及顺序 | Tracepoint、日志或 eBPF | 适合验证系统调用、调度和网络事件 |
| 硬件供给是否成为瓶颈 | PMU 计数器 | 结合 cycles、instructions、分支和缓存事件解释微架构现象 |

## 读取火焰图

- 横向宽度表示样本占比，不是单次调用耗时；同一函数在不同调用路径上应分别判断。
- 纵向是调用栈深度；从底部向上阅读调用关系，先找宽的路径，再回到业务入口验证是否重要。
- 颜色通常只是视觉区分，没有通用的性能含义。
- On-CPU 图宽的函数可能只是高频执行；若请求变慢但 On-CPU 不变，应检查 Off-CPU、IO、锁、GC 和下游等待。
- 采样频率、调用栈展开、符号表、内联和容器权限都会影响结果；比较前必须保持采集条件一致。

## 一个可复现的剖析闭环

1. 固定版本、配置、数据集、并发、CPU 亲和性和时间窗口，记录 p50/p95/p99、吞吐、错误率和资源指标。
2. 先采集低开销的系统与请求证据，再对目标进程做短时 profile；生产采样需要明确权限、开销和回滚。
3. 将热点或等待路径映射回请求、线程、锁、文件描述符、磁盘或网络依赖，排除启动和测试 harness 噪声。
4. 提出一个可证伪假设，只修改一个变量；保留原始 profile、命令、环境和样本量。
5. 用相同负载和相邻负载复测，观察收益是否转移到其他瓶颈，并设置上线和回滚阈值。

## Linux 示例

```bash
# 先看计数器和粗粒度资源，再做短时调用栈采样
perf stat -e task-clock,cycles,instructions,branches,branch-misses \
  -- ./service --scenario baseline
perf record -F 99 -g -o perf.data -- ./service --scenario baseline
perf report -i perf.data
```

`perf` 事件是否可用、调用栈方式和权限依赖内核、CPU、编译选项及容器配置。不要把某个固定采样频率、开销或 PMU 事件映射当成所有机器都成立的结论。

## 常见误判

- 只看平均值，忽略尾延迟和失败样本。
- 把缓存 miss、CPU 使用率或火焰图宽度直接当成根因，没有结合基线和对照实验。
- 只做 On-CPU 分析，漏掉锁等待、IO、调度和下游阻塞。
- 在不同版本、不同数据规模或不同频率策略之间直接比较样本百分比。
- 只保存图片，不保存采集命令、符号文件、环境和原始数据，导致无法复盘。

机制与本质：剖析回答的是时间被谁消耗，本质问题在于锁等待与 IO 阻塞这类不消耗处理器时间的场景，在只统计处理器占用的视角下会显示为没有热点。

验证的锚点：样本占比要与可比条件对账——预写相同条件下重复采集的同一代码位置占比应稳定，采集命令、符号文件与版本未对齐时与预期对不上。

## 边界对照

线程的时间在运行与等待之间怎么流转，哪些等待会被 On-CPU 剖析漏掉：

![Brendan Gregg 线程状态图：User 与 Kernel 的运行态在顶部，经 schedule 进入 Runnable，再分出 Disk、Sleep、Lock、Idle 四类等待态与 Swapping，左侧标注 off-CPU，每条等待线旁标注磁盘 I/O、网络 I/O、锁阻塞、等活等触发原因](/static/figures/thread-states.png)

来源：Brendan Gregg「Off-CPU Analysis」。Disk、Sleep、Lock、Idle 四类等待态全部挂在 off-CPU 一侧——只统计处理器占用的剖析把这些场景统统显示为没有热点，正对上文「锁和 I/O 场景会显示没有热点」的边界；每条等待线标注的触发原因，就是 Off-CPU、锁与 I/O 剖析要抓的证据通道。

让一个请求在 CPU 计算、锁等待、磁盘 I/O 和下游网络四种场景分别变慢；比较 On-CPU、Off-CPU、trace 和业务延迟。若只看 On-CPU，锁和 I/O 场景会显示“没有热点”，这正是剖析方法选择错误的证据。

## 验证

1. 方法对照：让一个请求分别在 CPU 计算、锁等待、磁盘 I/O 与下游网络四种场景变慢，比较 On-CPU、Off-CPU、trace 与业务延迟四种证据，确认锁与 I/O 场景在只看 On-CPU 时显示为没有热点。
2. 可比性核对：把采集命令、符号文件、版本、数据规模与频率策略一起留存，在相同条件下重复采集，确认同一代码位置的样本占比波动在可接受范围内。
3. 闭环复跑：按缩小范围、验证假设、改动、用相同负载复测的顺序走一遍，确认业务延迟的改善与剖析结论指向的位置一致。
4. 断言锚点：方法选择与场景对应，采集条件可复现，结论经过对照实验验证，原始数据与符号文件被保留。

## 要解决的问题

火焰图上最宽的函数被直接当成瓶颈，据此改完之后业务延迟没有变化；请求变慢时采集到的 On-CPU 剖析里看不到任何热点，于是判断为"没有瓶颈"。剖析回答的是采样期间时间花在哪里，回答不了业务因果、未采样的等待与结果正确性。本篇回答：CPU 时间、阻塞等待、跨进程路径与硬件供给分别该选哪种证据、火焰图的宽度与深度怎样读、采样频率与符号表如何影响可比性、以及一次可复现的剖析闭环包含哪些步骤。
