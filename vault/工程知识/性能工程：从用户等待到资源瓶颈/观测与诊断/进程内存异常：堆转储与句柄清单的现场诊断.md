# 进程内存异常：堆转储与句柄清单的现场诊断

一个长跑的进程内存持续上涨，日志干净、业务正常，很容易被当成「缓存在长大，先不管」。等到内存告警真的来了，RSS 已经涨到几个 GB，而堆快照里翻不出任何可疑对象。此时继续在堆里翻，方向就错了。

## 要解决的问题

进程占用的内存由几块互不相干的部分叠起来：托管堆里的对象、原生句柄、映射进来的文件、以及通信缓冲。堆转储只能看见第一块。把这几块混在一起看，会得到一个错误结论 —— 「堆里没异常，所以内存没异常」。

分开看的意义在于处置动作完全不同：

| 增长载体 | 典型来源 | 处置动作 |
| --- | --- | --- |
| 托管堆对象 | 引用被长期持有、缓存没有上限 | 修引用关系、给缓存加上限 |
| 原生句柄 | 监听器、连接、定时器只创建不释放 | 修创建与释放的配对 |
| 映射文件 | 大文件按需映射后一直保留 | 改访问方式、显式解除映射 |
| 通信缓冲 | 未被消费的队列、积压的响应 | 补背压、限流 |

句柄型增长在堆快照里永远找不到证据，因为句柄由运行时之外的库分配，不进入托管堆。

## 机制：三类内存各走各的账

**托管堆**由运行时的垃圾回收器管理，堆快照记录的就是这一层。对象只要有引用链可达就不会被回收，快照按类型与保留大小排序，能直接指出是谁持有它。

拿到现场快照的办法按运行时各不相同，共同点是都需要进程还活着：

```bash
node --heapsnapshot-signal=SIGUSR2 app.js
kill -USR2 <pid>
```

这条命令让运行中的进程在收到信号时写出一个 `.heapsnapshot` 文件，生成的时刻可控制，不需要重启进程。Java 用 `jcmd <pid> GC.heap_dump /path/dump.hprof`，Go 用 `pprof` 的 heap profile。只有一份快照看不出去向，采两份间隔若干分钟的样本做差分，按增长量排序，才能把「谁在持续持有」与「本来就有的常驻对象」区分开：

```text
快照 A（T0） → 快照 B（T0+10min） → 差集按增长量降序 → 嫌疑类型
```

快照采集会让进程短暂暂停，堆越大停顿越久，生产环境放在低峰期做。

**原生句柄**由运行时之外的库分配，每个句柄背后是一份原生内存：文件系统监听、网络连接、管道、定时器都属于这一类。以 Node 为例，`process.getActiveResourcesInfo()` 返回当前活跃资源类型的列表，按类型计数就能看出哪一类在涨：

```bash
node -e 'const c={};for(const x of process.getActiveResourcesInfo())c[x]=(c[x]||0)+1;console.log(c)'
```

间隔一段时间再看一次，某一类计数只增不减，它就是增长的主体。

**文件描述符**是另一本账。文件系统监听、网络连接、管道各占一个描述符，定时器与部分内部对象不占。所以描述符数量只能算出一部分增长，单独依赖它会漏：

```bash
ls /proc/<pid>/fd | wc -l
grep -E 'VmRSS|VmSize' /proc/<pid>/status
```

三样对照着看，判据很清楚：RSS 上涨、句柄计数上涨、描述符也上涨，增长计入占用描述符的句柄类型；RSS 上涨、句柄与描述符都平稳，回到堆快照；RSS 上涨而堆与句柄都平稳，查映射文件与通信缓冲。

## 边界与内核上限

文件系统监听走内核的 inotify 接口，而这个接口有按用户计算的监听数量上限。到达上限后继续创建会失败并返回 `ENOSPC`，失败发生在哪一次创建上取决于当时的计数，报错位置难以推断：

```bash
cat /proc/sys/fs/inotify/max_user_watches
```

这条上限约束内核侧的监听对象，对应用自己维护的定期扫描任务没有约束力。另外几条边界：定时器与部分内部句柄不占描述符，只看 `fd` 数量会漏掉它们；堆快照在生成时会让进程短暂暂停，堆越大耗时越长，生产环境要在低峰期做；上限报错只在创建时刻出现一次，之后运行不再提示。

## 验证

在公开环境复现一次句柄型增长：写一个循环创建文件监听且不释放的小程序，观察句柄计数与 RSS 是否同步上涨。

```bash
node -e 'setInterval(()=>{const fs=require("fs");fs.watch(__dirname,()=>{})},10);setInterval(()=>{const c={};for(const x of process.getActiveResourcesInfo())c[x]=(c[x]||0)+1;console.log(process.memoryUsage().rss,c)},2000)'
```

**预期**是 `FSWatcher` 计数与 RSS 一起单调上涨；把创建改成「先关闭再创建」之后重跑，两项应当都稳定下来。**对不上**说明增长另有来源，回到三样对照的判据重新分账。

## 影响与代价

- 句柄型增长只修堆修不好，必须核对创建点与释放点是否配对。
- 分账需要三种工具各跑一次，换来的是定位方向正确，避免在堆里空转。
- 把句柄数量纳入阈值告警，代价是告警项变多，收益是下一次增长能在早期被看见。
- 上限报错只在创建时刻出现，需要在启动自检里核对实际创建数量与预期数量。

## 从什么地方做

1. **先确认增长**：采两次 RSS 与句柄计数，间隔足够长，确认增长单调而非波动。
2. **再分账**：句柄计数、描述符数量、堆快照三样各取一次，判定增长计入哪一本账。
3. **定位创建点**：句柄型增长把句柄类型映射回代码里的创建调用，检查释放是否在同一条路径上。
4. **补上限与告警**：给句柄数量设阈值，并核对创建失败的返回值是否被检查。
