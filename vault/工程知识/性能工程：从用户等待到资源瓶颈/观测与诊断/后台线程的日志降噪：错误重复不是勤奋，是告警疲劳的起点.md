# 后台线程的日志降噪：错误重复不是勤奋，是故障时的自我放大

> **要点**：后台周期线程（GC、恢复探测、心跳）在故障期的日志量与故障本身成正比——一次 bookie 掉线，探测线程每秒打一条"连接失败"，日志膨胀把真正的诊断信息淹没；降噪的三板斧是状态变化才记（transition log）、失败计数进指标不进日志、首个错误带完整上下文后续降级为计数——上游"Improve auto-recovery noise log when some bookie down"与"log all the error in GC thread"正是一体两面：既要安静，又不能把唯一的错误信号静音。

## 要解决的问题：周期线程的日志经济学

周期线程的日志困境在于它的失败是"持续状态"：前台请求失败打一条日志对应一次事件，后台探测失败打一条日志对应一个**还在持续的状态**——bookie 掉线十分钟，探测线程按秒级周期产生六百条等价日志。**等价日志的三重代价**：告警系统按日志模式触发时误判为独立事件（风暴式告警）、日志存储与采集管道被灌满（本库"日志是诊断的证物也是故障源"的故障源面）、人眼检索诊断信息时被等价行淹没（定位变慢）。上游"Improve auto-recovery noise log"改的就是这个形态——"some bookie down"从每条连接失败一记，改为状态级汇总一记。

## 机制：三板斧与例外

**第一板斧：状态变化才记（transition logging）**。后台线程维护上一个周期的状态（正常/异常），本周期状态与上周期不同才写日志——进入异常记一条（带完整上下文：目标、错误类型、重试计划），恢复时记一条（带异常持续时长）——**两条日志完整讲述一次故障**，中间的持续期安静。**实现要点**：状态判定要幂等（探测超时与连接拒绝映射为同一"异常态"，细节进指标），避免在两个错误类型间抖动造成 transition 刷屏（抖动场景加最短状态持续时间）。

**第二板斧：失败计数进指标，不进日志**。持续异常期的每次探测失败记进指标（失败次数、最近错误码），仪表盘看趋势——**指标承担"还在坏"的表达，日志只承担"开始坏/恢复好"的表达**。指标的告警配置接故障告警（失败计数率超阈值），替代按日志模式告警——日志告警对重复行的天然脆弱（去重、聚合逻辑复杂且易错）被绕开。

**第三板斧：首个错误全上下文，后续摘要**。进入异常态的首条日志带全部诊断字段（目标标识、错误调用栈、重试策略、相关配置），持续期的日志（如果保留）降级为摘要行（每 N 次失败一记，含累计计数）——**摘要行的作用**：长故障时留时间线（哪几段在坏），频率降到不淹没检索（每分钟一记与每秒一记的检索体验差一个量级）。**上游"log all the error in GC thread"的反向教训**：GC 线程曾经吞错（异常不打），修复时全打又回到刷屏——**正确形态就是第三板斧**：每类错误首次全记 + 后续计数摘要，吞错与刷屏之外第三条路。

**例外：不可重复的失败不受降噪约束**。数据损坏、校验失败、写入丢失类错误**每次都全量记**——这类错误事件本身就是稀缺证据（本库证据四件套），降噪丢掉一条等于丢一份孤证；降噪只对"等价的重复失败"生效，判定标准是"错误是否携带新信息"（同一目标、同一错误码、无新上下文 = 等价）。

## 看完能判断：降噪配置的核对清单

**四个配置点**：状态机的状态集合与映射规则（哪些错误归并为一态）；transition 日志的字段清单（进异常与出异常各记什么）；摘要行的频率与累计字段；指标的面板与告警阈值。**验收动作**：故障演练（摘掉一个 bookie/依赖）观察日志量——预期从 O(故障时长 × 周期) 降为 O(1) + 摘要行，且首条日志的字段足够定位（不用翻多页拼上下文）；恢复时的"持续时长"字段可查。**反模式自查**：探测日志里出现同一秒多条等价行（状态机没生效）；故障恢复后无"恢复"日志（transition 漏了恢复侧）；指标与日志双轨都在告警（重复告警源，收敛到指标）。

## 边界

三条边界防止防线走形。

**降噪不改变重试行为**：日志安静了，重试与退避按原策略继续——降噪是可观测性治理，别顺手改重试参数（那是另一件事，有另一套纪律）。

**transition 状态机要覆盖线程生命周期**：线程启动（初始态）、停止（终态）也是 transition——**启动日志缺失**让人不知道探测根本没跑起来（比探测失败更隐蔽的故障），终态日志缺失让线程悄无声息地终止，没人知道（本库"异常处理器覆盖面"的同类边界）。

**日志量治理有整体预算**：单线程降噪了，多线程同故障（十几个 GC/探测线程对同一掉线目标各自记一轮）还是风暴——**同目标跨线程的聚合**（按目标标识聚合 transition，全局每目标每状态一记）是降噪的下一层，层数按日志总量预算倒推。

## 验证

可复现的验证路径：

1. 降噪复现：摘依赖演练，对比降噪前后的日志行数与告警条数，预期行数降两个量级、告警从风暴变单条；
2. 首条质量验证：随机抽故障的首条日志，人工判定字段能否独立定位（不需要后续日志补充）；
3. 指标验证：故障期失败计数率曲线与恢复归零，告警按指标触发且不重复；
4. 断言锚点：**周期线程有状态机与 transition 日志、失败指标有面板与告警、演练验收过日志量**——三件齐备，后台线程从"故障时的日志噪声源"变成"故障时间线的记录员"。

```text
安静断言 = 故障期日志量与时长无关
表达断言 = 指标管持续日志管变化
例外断言 = 稀缺错误不参与降噪
```

后台线程的日志纪律是一笔经济学：把"持续状态的重复表达"从日志迁到指标，日志只承担状态变化的首尾记录——故障期日志从淹没检索的洪水变成几行干净的时间线，告警从风暴变成一次精准的触发。
