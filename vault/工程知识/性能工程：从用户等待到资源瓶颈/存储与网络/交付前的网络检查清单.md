# 交付前的网络检查清单

服务上线后第一次事故往往出在网络：DNS 切换没等 TTL、健康检查打的是本机回环、连接池上限配错。要解决的问题：网络层的"日常怎么做、守什么规矩"是知识库当前真空格，本篇给出服务交付前逐项过的网络检查清单，把这类事故在上线前拦截。

## 机制：四段检查清单

清单按交付流程分段，每项都是可执行的命令或可核对的配置，不是提醒。

| 段 | 检查项 | 命令/核对 | 拦截的事故 |
| --- | --- | --- | --- |
| 依赖 | 出向依赖全部列出且连通 | `dig +short`、`nc -zv` 逐项 | 上线即解析失败 |
| 入口 | DNS TTL 与切换预案匹配 | `dig +noall +answer` 看 TTL | 切流量后部分用户还在旧 IP |
| 超时 | 每个出向调用都有显式超时 | 代码审查 + `curl --max-time` 验证 | 无超时调用拖垮线程池 |
| 兜底 | 健康检查路径真实穿过依赖 | `curl` 从 LB 侧打，而非 localhost | LB 健康但用户不通 |

清单纪律：收益是把网络事故从"上线后现场救火"变成"上线前清单拦截"，代价是每次交付多出 15-30 分钟核对时间与清单本身的维护成本——这项代价是值得的：清单项全部来自真实事故模式，每拦截一次就回本。清单不是一次性的，事故复盘后要把新根因补进对应段。

## 验证

```bash
# 依赖连通：把所有出向依赖跑一遍
while read host port; do nc -zv -w 3 $host $port; done < deps.txt
# TTL 核对：确认 DNS 记录的 TTL 小于回滚窗口
dig +noall +answer api.example.com
# 健康检查真实性：从 LB 视角打，确认路径穿过依赖
curl -s -o /dev/null -w '%{http_code}\n' http://lb-internal/healthz
# 超时验证：故意拔掉一个依赖，确认调用在超时时间内失败
curl --max-time 3 http://service/api?dep=down
```
预期：清单全部绿后，"依赖不可用"类故障的恢复时间由超时配置决定（秒级），而非线程池耗尽的级联（分钟级）。验证记录归档到交付单。SRE 书的发布工程章节是这份清单的方法论出处，HTTP 语义（超时返回码）以 RFC 9110 为准。
