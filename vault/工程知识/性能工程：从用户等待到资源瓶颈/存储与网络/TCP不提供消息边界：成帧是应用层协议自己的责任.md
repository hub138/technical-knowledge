# TCP不提供消息边界：成帧是应用层协议自己的责任

这篇讲一个独立开发网络服务最常见的缺陷源头：把「一次 write 对应一次 read」当成理所当然。读完你能解释为什么发送端写三次、接收端可能一次读到三条消息拼起来的字节，也能在出现「半条消息」「多出来的尾巴」这类症状时，直接判定为成帧缺失，并按长度前缀、定界符、定长三条路线补上边界。核心机制是 TCP 的字节流语义与消息单元之间的错位由应用层协议自带成帧规则来弥合；收益是**消息边界明确、半包与粘连都有确定处理路径**，代价是**每条应用协议都要先设计编码规则并处理边界异常**。

TCP（传输控制协议）只承诺一件事：字节按序、完整地到达，一段接一段，没有别的。它在协议里没有「消息」这个概念，发送端三次 `write` 各写 100 字节，接收端完全可能一次 `read` 拿到 250 字节，也可能拿到 50 字节。这两件事都是 TCP 的正常行为；把「读到的字节不等于一条完整消息」当成故障去调网络参数，方向就错了。这是 [[工程知识/性能工程：从用户等待到资源瓶颈/存储与网络/Socket与TCP把连接可靠性分成多层.md]] 里分层责任的延续：那篇讲 TCP 保证到哪一层为止，这篇讲应用层怎么把 TCP 不管的消息边界补齐。

## 要解决的问题：字节流里怎么认出一条消息

## 字节流为什么会错位：机制拆解

错位的两个来源，一个起于发送侧、一个显形于接收侧的缓冲区里，最终都落在接收端一次 `read` 的返回上。第一个来源是 TCP 的发送优化：发送端的三次 `write` 进入发送缓冲区后，Nagle 算法（把小包攒大再发的优化）与拥塞窗口可能把它们合并成一段发出；接收端内核把到达的段放进接收缓冲区，应用一次 `read` 就把缓冲区里现有的字节全部取走——三次写的 300 字节可能以一段到达，一次读走。第二个来源是分段：单条消息的字节数超过最大段大小 MSS（Maximum Segment Size：TCP 单段数据上限，约为 MTU——最大传输单元，一次能载货的上限——减头部长度）时，一条 `write` 会被切成多段各自到达，接收端先读到的就是半条消息。一句话：发送端的「写几次」与接收端的「读到什么粒度」之间没有任何对应关系，中间只有一条连续的字节河。

「粘包（多条消息在 TCP 字节流里连成一块、接收方分不清边界）」这个词在国内文章里常用，它描述的就是第一种来源——多条消息的字节粘连在同一个 `read` 里；但这个词容易误导，问题不在 TCP 把包「粘」住了，包在 TCP 内部从来没有粘过，每一段都有清晰边界，错位发生在应用把「一次 read 的返回」当成「一条消息」的那一刻。理解机制比记术语重要：边界是**应用层没定义**，才让字节流显得「粘」。

## 三条成帧路线与真实协议的选择

应用层协议定义消息边界，公开成熟协议已经给出三条主路线：

| 路线 | 机制 | 谁在用 | 该路线特有的边界异常 |
|---|---|---|---|
| 长度前缀 | 消息头带长度字段，读满 N 字节才算一条 | HTTP/2 帧头 9 字节、gRPC、Redis（内存键值数据库，常当缓存与排行榜用） RESP 数组、Thrift | 长度字段本身不完整（读到 7 字节只有 6 个）；长度值超出预设上限需拒绝，防按 2GB 去读 |
| 定界符 | 约定特殊字节序列表示结束 | Redis RESP 行协议（行尾 CRLF）、HTTP/1.1 头部（空行）、文本协议 | 定界符出现在消息体内需转义；恶意构造无界消息耗尽内存 |
| 定长 | 每条消息固定字节数 | 定长心跳包、简单二进制协议 | 变长需求出现时僵化，只适合消息天然等长的场景 |

三路线共有的边界异常是半包（单条消息分多次到达）与粘连（多条消息并作一次到达），任何路线都要靠装配缓冲区兜住，见下一节。三路线不是三选一的对立选项，成熟协议常混用：HTTP/1.1 用空行定界头部，再按头部里的 Content-Length（长度前缀的特例）或 chunked 编码（每个 chunk 自己带长度，结尾一个零长度 chunk）读正文；Redis 的 RESP 用行定界声明类型与长度，再按长度读二进制安全的值。选型的第一问题：消息体里会不会出现定界符字节？会，就转义（要定义转义规则）或直接选长度前缀；不会，定界符简单直接。选型的第二问题：单条消息有没有长度上限？有上限才能在长度前缀里做校验拒绝，防住「长度字段被写坏后按 2GB 去读」的内存耗尽。

UDP（用户数据报协议）是现成的对照组：它的首部自带 16 位长度字段，每个数据报天然有边界，应用一次收到的就是完整一条。代价是**它不保证到达、不保证顺序**。TCP 不带长度字段换来了流控、拥塞控制（发送方根据网络状况调整速率、避免压垮网络）与可靠性；消息边界这笔账就从协议转移给了应用。成帧与序列化的分工也在这里划清：序列化（把内存对象转成可存储或传输的字节格式的过程）只解决对象怎么变字节（见 [[工程知识/后端系统：在并发、失败与变化中维持服务/服务设计/RPC框架的通用骨架：序列化连接管理与超时传递]]），成帧解决字节怎么组成消息，两者拼起来才是一条完整的线路。

## 缓冲区装配是成帧的另一半

定好编码规则只是设计的一半，实现时还要面对「读到的字节不够一条消息」与「读到的字节多过一条消息」两种常态。标准做法是接收侧维护一个装配缓冲区（accumulate buffer）：每次 `read` 把字节追加进去，按成帧规则从头扫描，能切出几条完整消息就处理几条，剩余不足一条的尾巴留在缓冲区里等下一次 `read`；缓冲区该有上限，超限即判定对端违约，断开连接，否则一个只发长度字段不发正文的恶意连接能把内存拖垮。

漏掉装配环节的典型形态，正是 [[工程知识/缺陷分析：从个案到体系/正确性/复用缓冲区的残留字节：清零是复用的入场费.md]] 讲的残留问题：上一条消息没消费完的尾巴留在缓冲区，被下一条消息的解析当成开头，从第一个字节就错位。调试这类问题有个可靠手段：把「一次 read 的返回」与「一条消息的边界」分开记录，错位发生时对比两者，立刻能看出是粘连（一条 read 含多条消息）还是半包（一条 read 不足一条消息）。

粘连与残留是两种不同的病，症状都带「多出来的字节」：粘连的尾巴属于下一条消息，是收发节奏错位，成帧规则本身没有错；残留的尾巴属于上一条消息，是装配缓冲区没消费干净，实现有 bug。区分方法看尾巴的归属——解析得动的是粘连，解析报格式错误的是残留。

## 三条成帧路线与真实协议的选择

- **UDP 与带边界的传输不用成帧**。每个数据报自带边界，应用层再设计长度前缀是重复劳动。
- **HTTP 服务由框架包办**。HTTP/1.1 自己就是成帧规则的一个应用：Content-Length 与 chunked 就是它的长度前缀，Web 容器（如 Nginx、应用服务器的 HTTP 解析层）在应用层替业务代码完成了成帧解析，业务层拿到的是完整请求体；成帧知识主要用在独立开发的 TCP 服务、长连接（建立后保持不断开、多次通信复用同一条连接）推送、以及读框架源码时。
- **消息中间件的消费语义在另一层**。Kafka、Pulsar 的消息边界由客户端协议保证，业务侧的消费错位（重复消费、位移跳过）是另一类问题，与 TCP 成帧无关，别混着排查。

## 怎么自己动手验证

- **复现粘连与半包**：写一个最小回显服务，客户端连续 `write` 三条 100 字节消息后立即 `flush`，服务端循环 `read` 每次把返回字节数打日志。预期：三次读之间出现 250/50 这类非 100 的数值（粘连），或单条消息分两次到达（半包）。加大消息到 100KB 再跑，超过常见 MSS（约 1460 字节）后大概率分段出现半包；若网络启用了巨型帧（jumbo frame，MTU 达 9000 字节的以太网帧）等特殊配置，仍可能整段到达——复现实验按「大概率」预期，不按必然。若每次都恰好读到整数条，把服务端读循环加上 `sleep` 制造接收缓冲区积压再观察。
- **验证装配逻辑**：在装配缓冲区实现里故意只处理「刚好一条」的情况（不循环切分、不留尾巴），用上一条消息的尾巴加下一条消息的头部拼出一次错位请求，预期：解析直接报格式错误——这就是缺装配环节的失败形态。补上循环切分与尾巴保留后再跑，错位消失。
- **对照现成协议**：用 `redis-cli` 发 `SET key value`，同时 `tcpdump`（命令行抓包工具：把网卡上的数据包按条件过滤打印出来） 抓包看 RESP 的 `*3\r\n$3\r\nSET\r\n...`——长度前缀与行定界混用在真实协议里长什么样，抓包一目了然。

## 核心要点

| 要点 | 判定与做法 |
|---|---|
| TCP 不提供消息边界 | `read` 返回的字节数与消息条数无对应关系，这是正常行为 |
| 粘包不是 TCP 故障 | 错位发生在应用把「一次 read」当「一条消息」，调网络参数救不了 |
| 成帧三路线 | 长度前缀（要设上限）、定界符（要处理转义）、定长（适合天然等长） |
| 装配缓冲区必备 | 循环切分完整消息、保留不足一条的尾巴、设上限防恶意长度 |
| 排查先分型 | 半条消息判半包，多出尾巴判粘连，残留错位查装配缓冲区，无规律错乱查成帧规则 |
