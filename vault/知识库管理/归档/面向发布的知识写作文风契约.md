# 面向发布的知识写作文风契约

本仓库的知识会作为公开站点发布，读者是外部工程师。内容正确只是及格线；文风必须让读者感觉"这是一份成熟的技术材料"，而不是"某次 AI 生成的草稿"。

这份契约只管**表达层**——怎么说话。知识结构、证据分层、去重规则由 [[知识库管理/归档/知识点写作与教学输出契约]] 负责。

## 为什么单列这一份

已发生过的问题全部属于表达层，而结构契约一条都没拦住：

- 正文里混入未翻译的英文单词（"性能类会 metamorphosis"）。
- 声称方法的适用边界时写成自我辩护（"你自己代码里独有的缺陷不经过这条流水线"）。
- 反复强调"没人报告""很少有人当缺陷报"来证明价值。
- 在正文里写"专文暂缺""待补""下一步"这类对自己状态的说明。
- 开头用"先看两个案例""前几篇讲了"制造阅读顺序依赖。
- 语法漏字（"有一最阴险的形态"）。

这些句子单独看都不算错，但堆在一起就暴露了生成来源，并且会消耗读者对内容的信任。

## 三条判断标准

写任何一句之前，问自己三个问题。任一答案为"是"，重写。

1. **这句话是在给读者信息，还是在说明这份材料自身的状态？** 说明材料自身的句子（进度、缺口、计划、写作顺序、来源合法性）一律移到专门的元信息区块或删除。
2. **抽掉这一句，读者会损失什么？** 如果答案是"什么都没损失"或"只会少一点作者的自我解释"，删掉。
3. **这句话像不像一个怕被质疑的人在提前辩解？** 免责声明式、自嘲式、反复保证式的表达全部重写为陈述。

## 硬禁令

以下表达在 `vault/工程知识/` 的任何正文中都不允许出现，检查器会直接拦截。

### 自曝与自我指涉

| 禁止 | 原因 | 改成 |
| --- | --- | --- |
| 缺口、待补、暂缺、后续补、尚无专文、留待以后 | 暴露材料不完整 | 删除，或改写为指向已有的相邻主题 |
| 下一步、下一期、后续计划、TODO | 这是路线图，不是知识 | 移到项目页，正文只留已成立的内容 |
| 不是编出来的、不是纸面设计、真实做过 | 自我保证无效，证据才有效 | 直接给出来源、commit、命令输出 |
| 很少有人、没人会、大多数人不会 | 用"没人做"来抬高自己 | 陈述事实本身，不做人群比较 |
| 本书记为、本书认为、本材料 | 拟人化自我指涉 | 直接陈述结论 |

### 边界声明不能写成免责

说明适用边界是必要的，但必须写成**能力的前提**，而不是**方法的无能**。

- 禁止："你自己代码里独有的缺陷不经过这条流水线，靠自己的测试与评审。"
- 正确："方法建立在一个前提上：缺陷的期望有据可查。案例的期望来自上游已合入的修复提交；在自有项目里，测试失败、评审意见、线上告警、故障复盘同样是合格线索。换掉收集步的来源，后面四步原样适用。"

区别在于：前者说"这条做不到"，后者说"这条的输入可以换"。

### 开篇不能依赖阅读顺序

概览页会把正文首段自动截取为摘要，读者可能从任何一篇进入。首段必须**自包含**——能独立回答"这篇讲什么、对我有什么用"。

- 禁止："先看两个真实缺陷……""前几篇讲了三段各自的方法……""如上所述""在上一篇里"
- 正确：首段直接给出结论或问题，需要上下文时在句中补一个短语，而不是引用序号。

### 语言

中文正文中是否保留英文术语，取决于语境，不做机器硬检查——正则判不准，误报远多于收益。判断原则：

- 技术专有名词、API 名、命令、代码标识符保留英文（如 `commit`、`MVCC`、`SetMaxOpenConns`）。
- 已有通顺中文译名的，用中文（"垃圾回收"而非 "garbage collection"）。
- 真正要避免的是一个普通英文单词孤立地混在中文句子里充当谓语或名词，例如"性能类会变形"写成"性能类会 metamorphosis"。这类属于生成痕迹，靠人工通读发现。

标点不混用导致断句歧义；语法必须完整，特别注意量词（"一种形态"不是"一形态"）。

### 语气

- 不命令读者（"先看""请注意""记住"）。用陈述句，让结构本身引导阅读。
- 不自我贬低、不过度谦虚、不反复致谢。
- 比喻可以用，但要用得准（"崩溃留下 core dump"比"崩溃有尸体"专业）。

## 展开不足：篇幅是展开充分后的结果

知识点不是被"提到"就算讲完。一句话结论加两条例子，读者拿到的是"知道有这么回事"，不是"会用、能判断、能迁移"。判据是读者读完能不能自己拿去分析一个新问题。

篇幅本身不是指标，不设门槛，也不做机器检查。本仓库案例文实测多数在两千字出头，其中相当一部分偏短，原因是展开漏了层，而不是案例简单。字数可以作为自查信号：觉得"讲完了"但全文明显短时，回头查是不是漏了下面某一层。不要为了拉长而重复结论、堆同义句——那同样违反三条判断标准。

## 揉碎：一篇文章要展开的层次

写案例或模型时逐层自查，缺任何一层读者都会在某个地方掉队。

1. **问题**：长什么样，用户实际遇到的是什么。具体到能认出来——报错原文、现象、触发条件。
2. **为什么是问题**：不修会怎样，代价的量级是什么（崩溃、静默错算、资源耗尽、重跑整轮训练）。
3. **本质**：去掉项目专有名词后剩下的骨架那句话。写不出来说明还没看懂。
4. **比喻**：一个日常场景的对照，让没接触过这个系统的人建立直觉。宁可不打，不要打歪。
5. **机制**：代码层面到底发生了什么——哪一行、哪个分支、哪个时序，带 commit、函数名、路径。
6. **怎么修与怎么发现**：上游怎么修的，思路和代价是什么；同类问题靠什么手段能发现。

偏短的文章多数是第 2、4、6 层被压掉了：直接给结论、不打比喻、不写发现方法。这三层正是从"知道"到"会用"的桥。

## 跨页关联是正文的一节，不是脚注

知识点的价值在于它和别的知识点之间的关系。同一族的现象互相指认，读者看到的才是模子而不是散例。

- 案例文正文要有独立一节做**案例关联**，把本篇和相邻篇并排放，指出共享的不变量，并说清差别在哪。
- 关联要写**为什么是同一族**（共享哪条骨架）。"和案例三类似"这类句子没有信息量。
- 同项目的多篇要显式串起来。例如同一个数值边界根因下的几例，每一篇里要点明这是同族的哪一种，读者从任何一篇进入都能看到全貌。
- 文末 `相关：` 链接区只是导航，不能替代正文那一节。入链存在不等于关联讲清楚了。

## 事实归属一律指向上游

素材常来自对某个发行分支的扫描比对，但成文时一切事实归属上游：上游 commit、上游 issue、上游修复、上游版本。扫描与复现可以作为**发现手段**写进"怎么发现"那一层，缺陷本身的归属只能是上游。

- 禁止把缺陷归属到任何下游分支：行业里指"自行研发"的那个常用复合词（zì yán，两字，第二个字是"研"）及其派生说法（某某代码、某某方、某某实现）全部禁用。**包括否定与解释语境**——"这不是某某的"同样违规，辩解会把词带进正文，风险更大。本条不写出该词字面，因为这份文件本身要进版本库。
- 分支特有代码写成"这个发行分支上的 X""该分支特有的路径"，责任方写成"维护这个分支的一方""下游维护方"。
- "你的分支""目标分支"这类通用第二人称用来指读者手上的发行分支，属于允许表述。
- 不确定某个表述是否越界时，换成"上游"开头重写一遍：能说清就用那句。

## 概览摘要的特殊要求

站点从正文**第一段**自动提取摘要。因此：

- 第一段必须是完整的价值主张或结论，不能是素材来源说明、写作过程说明或过渡句。
- 第一段不得包含"本书""本篇""这一篇"等指代词——脱离上下文后它们无法解析。
- 第一段不得出现序号引用（"案例一""第二步"）作为主干。

## 发布前检查

```bash
python3 scripts/audit-writing-style.py
```

检查器扫描 `vault/工程知识/` 全部 Markdown，报出违规的文件、行号和规则名。它同时检查：

- 禁止词表命中（自曝、路线图、自我保证、自我指涉、命令读者、归属错误）。
- 首段是否以指代词或顺序依赖词开头。
- 常见语法漏字模式。

**它是回归网，不是及格线。** 通过只说明没有命中已知的坏短语，不说明文章合格。已经滑进去过的表达会再滑进去，机器能在上百页里一次性发现它们，这是它唯一的价值。契约里的原则——展开到哪一层、跨页关联有没有讲清共享骨架、某个英文术语该不该留——全部不进检查器：它们靠判断执行，写进正则就会退化成凑指标。

不做机器检查的部分：英文术语是否该保留、比喻是否恰当、语气是否自然。这些依赖语境判断，靠写作时的三条判断标准和人工通读。

检查器只是门禁，不替代人工判断。检查通过但读起来仍像草稿的，仍需重写。契约新增字面禁用短语时，同步加入检查器词表；新增原则时不加。

## 选材与去重

这一节管**动笔之前**的判断：这条值不值得写、会不会和已有内容重复。素材从哪个平台来、怎么取数、有哪些项目，属于操作，记在流程笔记里，这里不重复。

### 选材：按根因机制，不按缺陷家族

按缺陷家族（正确性、稳定性、并发、安全、性能、资源容量、配置可操作、兼容升级）分类是错的：几个家族一轮就全覆盖，之后每篇都是同一个模子的换皮。真正的增量在**根因机制**——这条揭示了哪个别人没讲过的断裂方式。

判据：**能不能抽出一句去掉项目名之后仍然成立的话**。抽不出来就是孤立 bug，没有迁移价值。一簇多条共用同一机制时，写成一篇并展开机制的不同断点，而不是每例一篇。

### 去重：先查库里有什么

动笔前扫一遍已有案例的骨架句，看机制是否被讲过。撞车有两种处理：合并进已有那篇当变体（正文加一节同类现场），或者换条目。不要写第二篇讲同一机制的文章。

同一项目的多篇反过来做——主动互相指认，每篇点明自己是同族的哪一种，让读者从任何一篇进入都能看到全貌。

**只有真实复现过的条目可以写**——它有复现步骤和实际观察结果，机制才站得住。仅靠推断的条目没有复现，写出来的机制是编的。
