# 全库新鲜度审计

> 审计日期：**2026-09-03**。范围是 `工程知识/` 下的 127 篇 Markdown；`Clippings/` 未读取、未修改。目的不是给笔记打分，而是区分“多年有效的机制”和“必须重新核验的实现事实”，避免稳定知识被版本细节污染，也避免过期事实继续指导工程选择。

## 结论

全库的核心问题不是所有页面都过期，而是**稳定原理、中速演进和高频变化混在同一页面中，复查门槛不一致**：

- `AI系统/生态与选型/AI技术动态.md` 以及 MCP/A2A、Agent 框架、推理引擎表格是最高风险，版本、弃用、规范和能力矩阵可能在一个发布周期内改变；
- AI 模型基础、RAG 原理、分布式一致性、数据库原理、CPU/内存抽象、算法复杂度大多可以保留，但需要把实现数字、产品行为和实验结论单独隔离；本轮新增的 RAG 前沿页专门覆盖重排、AutoRAG、倒排/混合索引和开放表格式边界。
- MySQL 8.4、Python 3.13/3.14、Go 1.27、Kubernetes GPU、OpenTelemetry GenAI 等页面或引用已有时效性，应以官方发布页重验；
- 首次审计发现约 65 篇页面没有 `review_after`；本轮已为全库工程页补齐复查日期、变化速率和置信度。当前新鲜度扫描不再有缺失属性，但到期页面仍需按窗口复查。

审计等级：

| 等级 | 含义 | 处理 |
| --- | --- | --- |
| P0 立即复查 | 版本、协议、弃用、默认值或安全状态可能已改变，错误会直接导致选型/迁移事故 | 逐项对照一手来源；事实放动态页，核心页只保留边界 |
| P1 本周期复查 | 实现和生态中速变化，原理仍有效但例子或能力矩阵可能漂移 | 3 个月内复查；锁定版本和实验环境 |
| P2 维护时复查 | 稳定机制或抽象，短期不太可能失效 | 6–12 个月或来源发生变化时复查 |
| 元数据风险 | 内容未必过期，但缺少复查日期、来源或置信度 | 补 Properties 和一手来源，不重写正文 |

## 当前可确认的一手事实

以下事实在审计日由官方资料核验，仍应放在高频动态层，不能当成永久原理：

- OpenAI 文档当前将 Responses API、工具、Agents SDK、检索、评测、模型目录和弃用分开维护；弃用页仍同时列出 Agent Builder、Evals 和 Assistants 等迁移入口，具体下线日期必须按该页复查。[OpenAI API deprecations](https://developers.openai.com/api/docs/deprecations)
- MCP 使用带日期的规范路径，A2A 使用 1.0 规范和版本头；协议页的字段、能力协商、授权和弃用说明应按规范发布复查，而不应只引用博客摘要。[MCP specification](https://modelcontextprotocol.io/specification/2026-07-28) · [A2A specification](https://a2a-protocol.org/v1.0.0/specification/)
- vLLM、NVIDIA Dynamo、Ray Serve LLM、PyTorch FSDP 和 Kubernetes GPU device plugin 分处推理内核、分布式服务、服务编排、训练分片和资源暴露层；它们的组合关系是架构边界，具体参数与支持矩阵是快速变化事实。[vLLM](https://docs.vllm.ai/en/latest/) · [Dynamo disaggregated serving](https://docs.nvidia.com/dynamo/dev/knowledge-base/concepts/system-architecture/disaggregated-serving) · [Ray Serve LLM](https://docs.ray.io/en/latest/serve/llm/) · [PyTorch FSDP](https://docs.pytorch.org/docs/stable/fsdp.html) · [Kubernetes GPU scheduling](https://kubernetes.io/docs/tasks/manage-gpus/scheduling-gpus/)
- MySQL 8.4 手册明确区分新增、弃用和移除的行为，并列出默认值变化、认证插件变化和升级陷阱；涉及具体默认值或语法的页面必须绑定 8.4/目标版本，不能只写“MySQL 通用行为”。[MySQL 8.4 changes](https://dev.mysql.com/doc/refman/8.4/en/mysql-nutshell.html)
- Python 和 Go 的 release cadence、解释器并发能力、标准库和工具链会持续变化；运行时页应引用官方 release history，不把某个版本的新特性写成语言永久语义。[Python downloads](https://www.python.org/downloads/) · [Go release history](https://go.dev/doc/devel/release)
- lm-evaluation-harness、HELM、NIST AI RMF 和 OWASP LLM Top 10 都会迭代；评测和安全页需记录采用的版本/快照以及自身任务映射。[lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness) · [HELM](https://crfm.stanford.edu/helm/) · [NIST AI RMF](https://www.nist.gov/itl/ai-risk-management-framework) · [OWASP LLM Top 10](https://genai.owasp.org/llm-top-10/)

### 后端可保留的稳定主轴

部分失败、网络分区、时间不可靠、消息投递与业务提交不同、TTL 不能阻止旧持有者写入、缓存会改变一致性和读取路径，这些是长期有效的机制。页面应避免把某个库的默认超时、重试次数或部署参数写成通用答案。

### 需要统一补齐的 Properties

本次不直接修改知识页，但下一轮维护应为缺少字段的页面补齐：

```yaml
status: active
updated: YYYY-MM-DD
review_after: YYYY-MM-DD
change_rate: stable | medium | fast
confidence: high | medium | low
sources:
  - https://一手来源
```

规则：

- 稳定原理：`review_after` 设为 6–12 个月；只有语义反例或来源变化才提前复查；
- 中速演进：3 个月复查，绑定目标版本、实验环境或规范版本；
- 高频变化：每周/每月复查，事实只放技术动态或来源核验页；
- 没有一手来源的经验可以保留为“实践证据”，但必须标明适用环境，不能冒充通用结论；
- 正文出现版本、价格、默认值、弃用、下线、能力矩阵或性能数字时，必须在同一页或来源注册表中有可点击的一手链接；
- 论文只证明论文中的模型、数据、硬件和实验设置；不能把 benchmark 提升直接写成生产保证；
- 来源失效不等于结论立即错误，但必须把页面标为待核验，并暂时降低置信度。
