# 知识体系缺口审计

## 结论

当前知识库已经有一批关于 Agent、事实门禁、分布式失败、数据库事务和性能定位的高质量判断，但覆盖曾经是不连续的：很多页面直接从“工程结论”开始，读者缺少理解结论所需的基础模型；AI 页面偏 Agent 和应用运行时，模型、数据、训练、检索、平台和安全链路没有全部展开；传统工程目录也缺少网络、操作系统、缓存、共识、数据建模、流处理、算法和供应链这些支撑层。本轮已经补上第一批地基，但仍需持续审计和扩展。

因此，当前状态不是“内容少”，而是**关键链路是否闭合**。补齐的目标不是无限增加工具介绍，而是让每个领域都覆盖：

```text
基础概念 -> 核心机制 -> 工程实现 -> 失败边界 -> 测量与验证 -> 演进与选型
```

## AI 系统应补成什么样

AI 系统不能只按“Agent 应用”理解。完整链路至少包含：

1. **模型基础与训练**：token、表示、Transformer、预训练数据、监督微调、偏好优化、蒸馏、量化和解码。
2. **模型与上下文**：上下文预算、结构化输出、记忆、工具和多模态输入如何改变模型可见信息。
3. **知识与检索**：采集、解析、切分、权限、索引、混合检索、重排、查询改写、引用、时效和评测。
4. **Agent 与工作流**：状态、工具契约、规划、执行、重试、恢复和人机协作。
5. **推理服务与平台**：prefill/decode、KV cache、批处理、并行、模型路由、GPU 资源、版本、灰度和成本。
6. **数据与 MLOps**：数据集、特征/embedding、模型和评测集的版本、注册、发布、漂移和回滚。
7. **质量与运营**：离线评测、轨迹评测、在线反馈、观测、容量、成本和事故复盘。
8. **安全与治理**：提示注入、越权工具、隐私、供应链、内容安全、审计和证据边界。

当前仍需优先扩展的是训练复现、数据/模型治理、图与多模态 RAG、AI 评测科学，以及跨地域分布式和系统软件；本轮已经建立这些主题的入口，不把入口误当成内容完成。

## 传统工程应补成什么样

后端需要从单次 HTTP 请求扩展到多节点协作：连接和协议、身份、缓存、并发控制、队列、复制、分区、共识、时间和故障恢复。数据系统需要从 MySQL 操作扩展到“数据如何建模、流动、分析、治理和恢复”。性能需要从工具清单扩展到操作系统资源、测量模型和容量边界。软件质量需要从测试门禁扩展到算法、依赖供应链、持续交付和运行时语义。

## 取舍规则

- 先补能解释多个下游主题的基础页，例如一致性、缓存、进程、数据建模、Transformer，而不是先补某个热门框架。
- 每个基础页必须连接至少两个现有主题，说明它为什么会影响 AI、后端、数据或性能。
- 快速变化内容放在专题页和动态页；稳定原理不随产品版本重写。
- 工具页只有在能改变决策、验证或排障时才保留；单纯命令抄录不进入主区。
- 目录不是课程顺序。阅读顺序由问题和依赖关系决定，目录只表达知识归属。

## 本轮补齐后的验收标准

- 每个领域至少有一个基础入口、一个机制入口、一个实践/验证入口和一个演进入口。
- AI 系统可以从 Transformer/训练一路读到 RAG、Agent、推理服务、MLOps 和治理。
- 后端可以从 HTTP/API 一路读到并发、缓存、队列、复制、一致性和容器。
- 数据可以从建模/SQL 一路读到事务、索引、CDC、流处理、分析和恢复。
- 性能可以从进程/内存/IO/网络的资源行为一路读到基准、容量和 profile。
- 软件质量可以从算法/代码结构一路读到依赖、构建、测试、CI/CD 和发布。

本页是缺口地图，不是新的知识分类。补齐后仍以五个技术领域和主题页作为日常入口。
