# 知识库管理

这是工程知识库的入口。**它只说结构和规则**，具体怎么做见「方法」两篇。

## 知识库结构

**工程知识**按知识对象分成五个领域，不按课程、时间或资料格式分类：

| 领域 | 覆盖 |
|---|---|
| **AI 系统** | 模型、上下文、Agent、检索、推理服务、MLOps、安全、运营、生态 |
| **后端与分布式系统** | 服务设计、并发、分布式可靠性、基础设施 |
| **数据系统** | 数据建模、事务、索引、流处理、治理、运维 |
| **计算机系统与性能** | 操作系统、处理器、存储、网络、观测、性能工程 |
| **软件构建与质量** | 语言、算法、架构、工具、测试与交付 |

另有两个非知识分类：

- **知识库管理** —— 维护方法、工具、变更日志。**不进入知识分类**（原因见下）
- **Clippings** —— 原文摘录与待整理内容，定期迁移进工程知识

## 范围原则

**收录**：工程实践中会用到的机制与原理；需要理解权衡和设计思路的知识；跨项目可迁移的方法和模式。

**不收录**：纯操作手册（放项目文档）；一次性脚本和配置；未验证的猜测；个人日志和流水账。

判断标准是**它能不能帮人做出判断**。只是"记下来备用"的内容，不构成知识。

## 硬规则一：这个分类只保留核心文章

`知识库管理/` **根目录只放本文**。其它内容按用途归位：

| 内容 | 位置 |
|---|---|
| 长期方法、约定、规范 | `知识库管理/方法/` |
| 一次性研究、审计、进度 | `知识库管理/归档/` |
| 来源、证据、论文与项目条目 | `知识库管理/归档/来源/` |
| 尚未核验的候选 | `知识库管理/归档/更新候选/` |

**为什么**：这个分类记录的是"知识库怎么维护"，不是技术知识本身。
页数膨胀会让侧边栏计数失真、图谱被维护资料占满，把要读的工程知识淹掉
—— 那正是 2026-09-17 整合掉 28 篇的原因。

**新增长期内容时**：写入 `方法/` 或 `归档/` 下的既有页面。
不要因为"这篇比较重要"就放到根目录。

## 硬规则二：这个分类永远不进知识图谱

**规则**：`知识库管理` 下的**所有**文章，无论现在还是以后新增的，
都不出现在知识图谱里，文章页也不显示"入链"和"延伸"。

**实现**：由后端统一判定 —— `site/server.py` 的 `Vault.refresh()` 计算
`exclude_from_graph` 字段，它**按 `category` 判断**，所以新增文章自动生效，
不需要作者记得加 `exclude_from_graph: true`。前端只读这个字段，不各自判断。

**排除的是"图谱参与"，不是"可访问性"**。这些文章照常列在目录里、能被搜索、能直接打开。

## 质量检查清单

定期检查：

- [ ] 所有页面都有 frontmatter（title, updated, sources）
- [ ] 关键断言有证据支撑，未验证的明确标注
- [ ] 高变化率领域（AI）在 3 个月内更新过
- [ ] 没有孤立页面（至少有一条入链）
- [ ] 主张能回溯到缺陷案例或 P0/P1 来源（全库案例回流是主要缺口）
- [ ] 与相邻概念写明了边界，不是只给定义
- [ ] 占位页已标 `status: draft`，不伪装成成熟页

具体标准见 [[知识库管理/方法/一篇知识怎么写]]，完善度判定见 [[知识库管理/方法/知识完善度怎么判断——四象限与九个信号]]。
