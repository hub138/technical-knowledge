# 知识库管理

这是工程知识库的维护指南，记录组织结构、质量标准、更新机制和工具使用。

## 知识库结构

**工程知识**按知识对象分成五个领域，不按课程、时间或资料格式分类：

- **AI 系统** - 模型、上下文、Agent、检索、推理服务、MLOps、安全、运营、生态
- **后端与分布式系统** - 服务设计、并发、分布式可靠性、基础设施
- **数据系统** - 数据建模、事务、索引、流处理、治理、运维
- **计算机系统与性能** - 操作系统、处理器、存储、网络、观测、性能工程
- **软件构建与质量** - 语言、算法、架构、工具、测试与交付

**知识库管理**单独存放，记录维护方法、工具、变更日志，不进入知识分类。

**Clippings** 保留原文摘录和待整理内容，定期迁移到工程知识。

## 知识演化机制

### 更新触发条件

1. **主动扫描** - 每月检查领域前沿论文、技术博客、开源项目
2. **被动触发** - 遇到实际问题、工作项目、学习需求时回填
3. **质量审计** - 每季度检查过时内容、断链、证据缺失

### 更新流程

```
发现新知识 → 判断是否在范围内 → 找到对应主题 → 
更新或新建页面 → 补充证据和来源 → 更新关系链接 → 
记录变更日志
```

### 质量标准

每篇知识页面必须包含：

- **标题** - 清晰描述知识对象
- **机制解释** - 为什么这样设计，解决什么问题
- **证据** - 论文、官方文档、可复现实验
- **来源** - 标注原始出处，便于追溯
- **关联** - 链接到相关概念、上下游知识

不合格的内容：

- 只有定义没有机制
- 只有操作步骤没有原理
- 没有来源的二手转述
- 过时超过一年未更新的技术

## 学习与复习方法

**不要按时间堆积笔记**，按"问题 → 机制 → 证据 → 练习 → 迁移"组织：

1. **遇到真实问题** - 记录问题场景和背景
2. **理解核心机制** - 为什么这样设计，权衡是什么
3. **找到证据** - 论文、文档、可复现实验
4. **动手练习** - 实现 demo、跑测试、做实验
5. **迁移应用** - 在其他场景中使用，建立关联

复习时优先检查：

- 高变化率的领域（AI、工具链）
- 最近 3 个月未访问的页面
- 断链和缺少来源的内容

## 工具使用

### 本地工具

- **Obsidian** - 知识编辑、图谱可视化、双链管理
- **Codex** - AI 辅助写作、知识提取、自动补充证据
- **Git** - 版本控制、变更追踪

### 学习工具

- **Archify** - 架构图和知识关系可视化
- **OpenMAIC** - 互动课堂生成，用于建立直觉
- **DeepTutor** - 检索与学习工作区，用于追问与迁移
- **Matt Skills** - 工程协作技能（TDD、代码审查、架构改进）

调用成本：

- 图谱生成：免费
- 课堂生成：~0.1-0.5 USD/次（需访问码）
- 导师对话：~0.02-0.1 USD/轮（需登录）

### 项目集成

知识库 `projects/` 目录包含开源项目快照：

- `archify` - 架构可视化
- `OpenMAIC` - 课堂生成
- `DeepTutor` - 学习工作区
- `mattpocock-skills` - Agent 技能

更新上游时记录 commit、日期和对知识页的影响。

## 变更管理

### 变更类型

- **新增** - 新领域、新主题、新知识页
- **更新** - 修正错误、补充证据、更新版本
- **重构** - 调整结构、合并拆分、优化关系
- **废弃** - 标记过时内容，不删除但标注状态

### 变更记录

每次重要变更应在 `知识库管理/维护/变更记录.md` 中记录：

- 日期
- 变更类型
- 影响范围
- 变更原因

## 这个分类只保留一篇核心文章

**规则**：`知识库管理/` 根目录只放本文（`知识库管理.md`）。
其它内容一律放进子目录，且按用途归位：

| 内容 | 位置 |
|---|---|
| 维护方法、约定、契约 | `知识库管理/归档/` 下的对应主题页 |
| 一次性研究、审计、进度 | `知识库管理/归档/` |
| 来源、证据、论文与项目条目 | `知识库管理/归档/来源/` |
| 尚未核验的候选内容 | `知识库管理/归档/更新候选/` |

**为什么**：这个分类记录的是"知识库怎么维护"，不是技术知识本身。
页数一旦膨胀，侧边栏计数会失真，图谱也会被维护资料占满，
让真正要读的工程知识被淹掉 —— 那正是 2026-09-17 整合掉 28 篇的原因。

**新增长期内容时**：写入 `归档/` 下的既有页面，或新建归档页；
不要因为"这篇比较重要"就放到分类根目录。

## 这个分类永远不进知识图谱

**规则**：`知识库管理` 分类下的所有文章，无论现在还是以后新增的，
都不出现在知识图谱里，文章页也不显示"入链"和"延伸"。

**实现方式**：由后端统一判定，见 `site/server.py` 中
`Vault.refresh()` 的 `exclude_from_graph` 字段 —— 它按 `category` 计算，
所以**新增文章自动生效**，不需要作者记得加 `exclude_from_graph: true`。
前端只读这个字段，不再各自判断。

**注意**：排除的是"图谱参与"，不是"可访问性"。
这些文章照常列在目录里、能被搜索、能直接打开阅读。

## 质量检查清单

定期检查：

- [ ] 所有页面都有 frontmatter（title, updated, sources）
- [ ] 关键断言有证据支撑
- [ ] 高变化率领域（AI）在 3 个月内更新过
- [ ] 没有孤立页面（至少有一个双链）
- [ ] 来源链接可访问（或已归档）
- [ ] 过时内容标记 `status: deprecated`
- [ ] `知识库管理/` 根目录只有 `知识库管理.md` 一篇

## 范围原则

**收录标准**：

- 工程实践中会用到的机制和原理
- 需要理解权衡和设计思路的知识
- 跨项目可迁移的方法和模式


**不收录**：

- 纯操作手册（放项目文档）
- 一次性脚本和配置
- 未验证的猜测和假设
- 个人日志和流水账
